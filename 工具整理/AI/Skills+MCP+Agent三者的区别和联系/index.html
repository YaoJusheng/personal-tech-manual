    一、为什么要区分 Prompt、Skills、MCP、Agent¶

    在 AI 应用从"单轮问答"走向"自主执行任务"的过程中，很多概念经常被混用：有人把 Prompt 当成 Agent，有人把 Function Calling 当成 MCP，也有人把 Tool 和 Skill 视为完全同义。

    实际上，这几个概念分别处在 LLM 应用栈的不同层级，职责并不相同：

    • Prompt / Prompts：负责把 规则、上下文、任务目标 组织成 LLM 可理解的输入。
    • Skills：负责提供可复用的外部能力，是模型完成真实任务时可调用的 执行单元。
    • MCP：负责把模型应用与工具、资源、提示模板做 标准化连接。
    • Agent：负责 统筹规划、决策、执行、反馈，是整个任务闭环的 调度者。

    如果不区分它们，就很难理解一个现代 LLM 系统到底是如何从"生成一段文字"演化为"感知环境、调用工具、执行任务、持续修正"的。

    先给一个一句话总结，再细细拆解：

    • Prompt（提示词）：组装给大模型的完整“剧本”，包含系统指令、对话上下文和可用工具清单，是模型唯一的信息入口。
    • Tool（工具）：最基础的原子能力，一个函数。
    • Skill（技能）：对能力的封装与组织，可以是单个工具，也可以是一组工具的编排。
    • MCP（协议）：工具/技能暴露出来的标准插座，让任何客户端都能用同一种方式插拔使用。
    • Agent（智能体）：以 LLM 为推理引擎的自主调度程序，负责在“思考-行动-观察”循环中管理 Prompt、调用工具并驱动任务完成。

    二、四者在 LLM 系统中的整体定位¶

    2.1 一句话理解¶

    概念 一句话定义 所处层级 主要职责
    Prompt / Prompts 给模型看的任务说明书与上下文包 输入层 约束模型如何理解和回答
    Skills 可复用的专业能力或工具能力封装 能力层 让系统具备查、算、写、调、执行等外部动作
    MCP 工具与资源接入的标准协议 连接层 统一发现、描述、调用外部能力
    Agent 面向目标持续运行的调度程序 编排层 拆解任务、组装 Prompt、选择工具、控制执行闭环

    2.2 用类比理解¶

     用户输入
   ↓
 [ Agent ] ← 大脑，负责规划与决策
   │   ↑
   │   └── Prompt（组装指令，包含对话历史、系统人格、工具描述等）
   │          ↓
   │      [ LLM 大模型 ] ← 推理引擎，根据提示词生成文本或决定调用工具
   │          ↓
   │   生成的输出若是“工具调用指令”
   │          ↓
   └──→ [ MCP 客户端 ] ← 标准协议层，负责与外部工具连接
            ↓
      [ Skills/工具 ] ← 具体执行者：查天气、搜资料、发邮件...
            ↓
      返回结果给 Agent → 再次拼入 Prompt 让 LLM 理解 → 继续思考或最终回复

    可以把一个 LLM 应用理解为一个"数字员工系统"：

    • Prompt 像给员工的任务单、背景资料和操作要求。
    • Skills 像员工可以使用的专业工具箱。
    • MCP 像统一的标准接口和工位连接规范。
    • Agent 像主管或执行中枢，决定下一步做什么、什么时候调用什么工具、何时停止。

    四者不是并列替代关系，而是分层协作关系。

    三、LLM 大模型调度架构中的角色与位置¶

    3.1 架构总览¶

    flowchart LR
        U[用户输入] --> A[Agent 调度层]
        A --> P[Prompt 组装层]
        P --> L[LLM 推理层]
        L -->|自然语言回复| A
        L -->|工具调用意图| M[MCP Client / Tool Router]
        M --> S1[Skill / Tool 1]
        M --> S2[Skill / Tool 2]
        M --> R[Resource / Database / API]
        S1 --> M
        S2 --> M
        R --> M
        M --> A
        A --> Mem[Memory / History / State]
        Mem --> P
        A --> Out[最终回复 / 执行动作]

    这个架构里需要注意三点：

    • LLM 是推理引擎，不是执行引擎。它负责理解、判断、生成，不直接访问真实世界。
    • Agent 是闭环控制器。它维护状态、决定是否继续推理、是否调用工具、是否结束任务。
    • MCP 与 Skills 位于模型外部。模型只看到能力描述，不直接感知底层实现细节。
    ┌───────────────────────────────────────────────────────────┐
│                     主 Agent (Sisyphus)                   │
│                                                           │
│   ┌─────────┐    ┌─────────┐    ┌─────────────────────┐   │

│        │    │ Skill 可嵌入 MCP    │         │              │
│        │    │ 配置，通过 skill_mcp │         │              │
│        │    │ 调用外部工具         │         │              │
│        │    └────────────────────┘         │              │
│        │                                   │              │
│        └─────→ Agent 可加载 Skill ◄─────────┘              │
│                (load_skills)                              │
│                                                           │
│                Agent 也可调用 MCP                          │
│                (如果该 Agent 有权限)                        │

    3.2 调度链路总览¶

    sequenceDiagram

        participant Agent as Agent
        participant Prompt as Prompt Builder
        participant LLM as LLM
        participant MCP as MCP Client

    3.3 典型协作流程¶

    以「安全审计」为例，展示三者如何协同工作：

    步骤 1 ─ 加载知识
   skill(name="security-research")
   → 主 Agent 获得安全审计方法论

步骤 2 ─ 派发并行探索
   task(subagent_type="explore", ×3 并行)
   → 3 个 Agent 同时搜索不同模块的漏洞

步骤 3 ─ 调用外部工具
   各 Agent 通过 skill_mcp 调用扫描工具
   → 获取结构化的扫描结果

步骤 4 ─ 高阶评审
   task(subagent_type="oracle")
   → Oracle 评估漏洞严重性和可利用性

步骤 5 ─ 综合产出
   主 Agent 汇总所有结果 → 最终报告

    四、Prompt / Prompts：模型的唯一信息入口¶

    4.1 Prompt 是什么¶

    Prompt 是输入给大模型的文本上下文。严格来说，模型每次看到的并不是"一句提示词"，而是一个被组织好的上下文包，常见组成包括：

    • System Prompt：定义角色、规则、约束、输出风格。
    • Developer Prompt / Policy Prompt：定义产品或系统的能力边界。
    • Tool Descriptions：告诉模型有哪些工具、工具做什么、参数怎么传。
    • Conversation History：保留多轮对话与上下文。
    • User Prompt：当前用户给出的任务或问题。
    • Retrieved Context：RAG 检索结果、记忆、文档片段、执行反馈。

    因此，现代 AI 工程中更准确的说法往往不是单个 Prompt，而是 Prompts + Context Engineering。

    4.2 Prompt 的角色与定位¶

    维度 说明
    本质 LLM 的输入载体
    作用 指定任务、约束模型、传递上下文
    优点 灵活、成本低、改动快
    局限 只能影响模型推理，不能直接执行外部动作

    Prompt 的核心特征是：它决定模型怎么想，但不决定系统怎么做。

    4.3 Prompt 与 Agent 的关系¶

    • Prompt 是 Agent 组织出来给模型看的输入。
    • Agent 不等于 Prompt，但 Agent 的每一步决策都要借助 Prompt 与 LLM 通信。
    • 没有 Agent 时，Prompt 更多是静态问答输入。
    • 有了 Agent 后，Prompt 会随着状态、历史、工具结果动态更新。

    4.4 Prompt 的典型误区¶

    • 误区一：Prompt 就是随便写一句话。 实际上生产环境中的 Prompt 往往是多段拼装、带结构和约束的上下文包。
    • 误区二：Prompt 足够强就不需要工具。 Prompt 只能影响生成，不能替代真实查询、执行、写入、审批等动作。
    • 误区三：Prompt 等于 Agent。 Prompt 是输入材料，Agent 是执行框架与调度逻辑。

    五、Skills：系统可复用的能力单元¶

    5.1 Skills 是什么 — 领域知识注入¶

    定义¶

    Skill 是一份预制的领域专用指令集。通过 skill 工具加载后，它会将专业知识和工作流模板注入到当前对话上下文中。

    Skill 可以理解为一类可复用能力的封装。它通常不是单纯的自然语言规则，而是把以下内容打包在一起：

    • 适用任务范围
    • 输入输出规范
    • 依赖工具或外部接口
    • 执行步骤与异常处理
    • 质量要求与返回格式

    在不同框架里，Skill 的实现方式不同：

    • 在简单场景里，Skill 可能就是一个 Tool 函数。
    • 在复杂场景里，Skill 可能是一组 Prompt、工具、规则和流程的组合。

    核心特征¶

    ┌──────────────────────────────────────────┐
│              Skill 运行模型               │
│                                          │
│   skill(name="security-research")        │
│         │                                │
│         ▼                                │
│   ┌─────────────────┐                    │
│   │  知识注入到上下文  │  ← 与主 Agent 共享  │
│   │  (方法论/模板/    │    同一上下文窗口    │
│   │   checklist)     │                   │
│   └─────────────────┘                    │
│         │                                │
│         ▼                                │
│   主 Agent 按照注入的指引执行               │
└──────────────────────────────────────────┘
    特性 说明
    只读知识 不执行任何操作，只提供"怎么做"的指引
    上下文内生效 加载后相当于你多读了一份专业手册
    零隔离 和主 Agent 共享同一上下文窗口
    轻量级 加载成本 ≈ 0，但缺失代价极高

    实际示例¶

    Skill 名称 注入的知识
    omm-scan 架构扫描的完整步骤和文档模板
    security-research 安全审计的多角色协作流程和漏洞分类标准
    customize-opencode OpenCode 配置的约束规范和文件路径规则

    调用方式¶

    # 加载 Skill —— 将领域知识注入当前上下文
skill(name="security-research")
# 之后主 Agent 就"懂"安全审计了

    5.2 Tool、Skill、Workflow 的区别¶

    概念 粒度 本质 示例
    Tool 最小 一个原子操作 search_web()、run_sql()
    Skill 中等 一项可复用能力封装 "查询销售数据并汇总"
    Workflow 最大 多个 Skill 的端到端组合 "收集数据 → 分析 → 出报告 → 发送邮件"

    简单说：Tool 更像函数，Skill 更像能力模块，Workflow 更像业务流程。

    5.3 Skills 的角色与定位¶

    维度 说明
    本质 模型外部可用能力
    作用 把 LLM 的"会说"扩展为"会做"
    典型能力 搜索、查询数据库、读写文件、调用 API、生成图表、执行代码
    局限 自身不负责全局规划，需要由 Agent 或宿主程序调度

    5.4 Skills 与 Prompt 的关系¶

    • Skill 不直接等于 Prompt，但 Skill 的描述通常会被写入 Prompt。
    • 模型通过 Prompt 中的工具说明来理解某个 Skill 能不能用、什么时候用、怎么用。
    • Skill 的返回结果也会再次进入 Prompt，成为下一轮推理依据。

    5.5 Skill 的两种语义：能力封装 vs 知识注入¶

    "Skill" 在不同语境下其实指向两种并不相同的东西，初学者很容易混淆：

    语义 视角 本质 是否执行 典型代表
    广义 Skill（能力封装） 执行视角 一项可复用能力模块，可能由 Tool + Prompt + 流程组成 会执行真实动作 上文 5.1–5.4 描述的能力单元
    狭义 Skill（知识注入） 知识视角 一份注入上下文的领域知识 / 方法论模板 只读、不执行 Claude Skills、OpenCode Skills

    前面 5.1–5.4 讲的是能力封装视角：Skill 是"系统会做什么"的封装。 而在 Claude、OpenCode 等智能体框架里，Skill 还有另一层知识注入视角的含义：

    Skill 是一份预制的领域专用指令集。加载后，它把专业知识和工作流模板注入到当前对话上下文，相当于让模型临时"多读了一份专业手册"。

    这种 Skill 的运行模型有三个关键特征：

    特性 说明
    只读知识 不执行任何操作，只提供"怎么做"的指引
    上下文内生效 加载后与主体共享同一上下文窗口，零隔离
    轻量级 加载成本 ≈ 0，但在该领域缺失时代价极高

    一句话区分这两层含义：能力封装视角的 Skill 让系统"会做"，知识注入视角的 Skill 让模型"懂得怎么做"。 二者可以叠加——一个知识注入型 Skill 内部也可以携带工具通道（例如嵌入 MCP 连接配置），此时它既给方法论，又给执行能力。

    六、MCP：模型与外部能力之间的标准连接层¶

    6.1 MCP 是什么 — 外部工具通信协议¶

    定义¶

    MCP（Model Context Protocol）是一套开放协议，是一种标准化的外部工具/资源通信协议，用于标准化 LLM 应用如何连接外部能力，让 Agent 能够调用外部服务器提供的工具、读取资源、获取提示模板。

    它不直接替代 Agent，也不直接替代 Skill，而是负责把这些能力以统一方式暴露给模型应用。

    MCP 的核心价值在于三件事：

    • 标准化：不同工具可以用统一协议接入。
    • 可发现：模型应用可以动态发现有哪些工具、资源、Prompt 模板。
    • 可复用：同一个 Server 可被多个 Host 或 Agent 复用。

    核心特征¶

    ┌──────────────┐     MCP 协议       ┌──────────────────┐
│              │  ←──────────────→ │                   │
│   Agent      │   JSON-RPC 风格    │   MCP Server     │
│   (客户端)    │                   │   (外部进程)       │
│              │   ──────────────→ │                   │
└──────────────┘   调用工具/读资源    └──────────────────┘
                                         │
                                         ▼
                                    外部服务/数据源
    特性 说明
    进程隔离 MCP 服务器是独立运行的外部进程
    工具发现 通过协议动态发现可用工具
    标准化接口 统一的 JSON-RPC 风格，任何语言均可实现
    双向通信 可调用工具、可读资源、可获取提示

    三种调用模式¶

    模式 参数 用途 示例
    调用工具 tool_name 执行操作 扫描架构、生成代码、查询数据
    读取资源 resource_name 获取数据 读取文件、获取配置、查看状态
    获取提示 prompt_name 获取模板 加载预制的提示词模板

    调用方式¶

    # 通过 MCP 协议调用外部服务器工具
skill_mcp(
    mcp_name="oh-my-mermaid",       # MCP 服务器名称
    tool_name="scan_architecture",  # 要调用的工具
    arguments={...}                 # 工具参数
)
# 返回结构化结果

    6.2 MCP 的典型组成¶

    角色 作用
    Host 发起工具使用的 AI 应用，如 IDE、桌面应用、Agent 平台
    Client 协议客户端，嵌入在 Host 中，负责与 Server 建立连接
    Server 提供具体 Tools、Resources、Prompts 的服务端

    6.3 MCP 提供的不只是 Tool¶

    MCP 并不只是一个"工具调用协议"，它标准化的是三类核心能力：

    原语 作用 示例
    Tools 供模型发起操作 查询数据库、搜索网页、执行脚本
    Resources 供模型读取上下文 配置文件、日志、文档、数据库记录
    Prompts 供模型复用模板 代码审查模板、分析模板、总结模板

    这意味着 MCP 在系统中扮演的不只是"调用通道"，也是"上下文供应层"。

    6.4 MCP 与 Function Calling 的区别¶

    维度 Function Calling MCP
    绑定方式 通常绑定在单一模型 API 请求中 作为独立协议连接多个外部能力
    扩展方式 新增工具常需改业务代码 新增 Server 即可扩展
    生态范围 厂商或 SDK 内部机制 跨模型、跨平台的开放接入方式
    能力类型 主要偏工具调用 同时覆盖 Tools、Resources、Prompts

    可以把 Function Calling 看作模型接口层的一种能力，而把 MCP 看作更上层、更通用的外部连接标准。

    6.5 MCP 的角色与定位¶

    维度 说明
    本质 协议与接入标准
    作用 解耦模型应用与工具实现
    优点 统一接入、可扩展、跨平台复用
    局限 它只负责连接，不负责业务决策

    6.6 有无 MCP 的不同¶

    Skill 和 Tool 是功能本身，MCP 是连接这些功能的标准化管道。

    1. 没有 MCP 的世界（传统的直接耦合）¶

    你的 Agent 代码
    ├── 直接调用 get_weather() 函数      (写死在代码里)
    ├── 直接调用 send_email() API        (硬编码 URL 和认证)
    └── 直接操作数据库                   (内嵌 SQL 连接)
    • Skill/Tool 就是这些 get_weather() 函数本身。
    • 每次要换一个天气服务商，你得改代码。每次要让不同 Agent 复用，得拷贝代码或打包成库，库的接口还未必统一。

    2. 有了 MCP 的世界（标准化连接）¶

    你的 Agent 代码
    └── MCP 客户端 (只需实现一套协议)
          ├── 连接到 MCP 天气服务器  → 服务端封装了 get_weather
          ├── 连接到 MCP 邮件服务器  → 服务端封装了 send_email
          └── 连接到 MCP 数据库服务器 → 服务端暴露 query 操作
    • MCP 服务器背后才是具体的 Skill/Tool 实现。
    • Agent 不再关心工具的具体实现、API 格式、库版本。它只对 MCP 客户端说：“我要调用名叫 get_weather 的工具，参数是这些”。剩下的寻址、传输、格式转换全由协议处理。

    澄清：MCP 协议 vs MCP 服务器

    • MCP 协议本身：是空的规范，不提供任何工具。它只定义了 tools/list、tools/call 这些“通信模板”。所以“有了 MCP 不等于自带能力”。
    • 一个具体的、正在运行的 MCP 服务器：它内部必须已经包含了具体的 Skill/Tool 实现，才能在收到 tools/list 时返回工具列表，在 tools/call 时执行代码。所以“MCP 服务器封装了 Skill”。

    七、Agent：任务闭环的调度中心¶

    7.1 Agent 是什么 — 独立执行单元¶

    定义¶

    Agent 是拥有独立上下文、独立工具权限、独立推理能力的子进程。通过 task() 或 spawn_agent() 生成，可并行执行。

    Agent 是一个面向目标持续执行的系统，不是单次回答器。它会围绕用户目标持续进行：

    • 理解目标
    • 拆解任务
    • 组织上下文
    • 调用模型推理
    • 选择或调用工具
    • 接收反馈并修正策略
    • 判断是否完成

    因此，Agent 的核心不只是"调用了 LLM"，而是是否具备 状态管理 + 决策循环 + 外部行动能力。

    核心特征¶

    ┌─────────────────────────────────────────────────────┐
│                  主 Agent (Sisyphus)                │
│                                                     │
│   task(subagent_type="explore", ...)                │
│         │                                           │
│         ├──────→ Agent A (独立上下文, 异步执行)        │
│         │          · 有自己的对话历史                  │
│         │          · 可加载 Skill                    │
│         │          · 可调用 MCP                      │
│         │                                           │
│         ├──────→ Agent B (独立上下文, 异步执行)        │
│         │          · 与 A 互不干扰                    │
│         │          · 结果独立返回                     │
│         │                                           │
│         └──────→ Agent C (独立上下文, 异步执行)        │
│                    · 可并行执行不同任务                │
└─────────────────────────────────────────────────────┘
    特性 说明
    上下文隔离 每个 Agent 有自己的对话历史，看不到主 Agent 的上下文
    独立执行 支持异步/同步，可大规模并行
    专用能力 不同类型有不同工具集和优化模型
    结果回收 完成后通过 background_output 或同步返回结果

    Agent 类型谱系¶

    在成熟的多智能体框架（如 OpenCode）里，"Agent"并不是一个铁板一块的概念，而是按职责和成本分层的一组角色。每个子 Agent 拥有独立上下文、独立工具权限，可以被主 Agent 派发并行执行：

    层级 典型角色 特点 相对成本
    🔍 探索型 explore 代码搜索、定位实现，轻量快速，可大量并行 免费
    📚 研究型 librarian 外部文档 / 开源代码检索 低
    🧠 咨询型 oracle 高质量推理，只读，用于疑难调试与架构决策 高
    📋 规划型 metis / momus 前置需求分析 / 计划评审 高
    ⚙️ 执行型 Sisyphus-Junior 通用执行器（按 category 分配） 承接具体落地任务的通用 Agent, 通过 category 分配的通用执行器 中
    🎯 领域专家 python-pro、rust-pro 等 特定语言 / 领域的专业 Agent 中

    这个谱系反映了一个工程原则：用最便宜、最匹配的 Agent 做对应的事。探索定位用免费的 explore 大量并行；架构拿不准才动用昂贵的 oracle；具体编码交给领域专家。子 Agent 之间上下文相互隔离——A 看不到 B 的对话历史，结果各自独立返回，因此特别适合"把一个大任务拆成若干互不依赖的子任务并行推进"。

    注意区分：这里的"Agent 类型"是同一调度体系内不同职责的子 Agent，与第二章讲的"Agent 作为整个任务闭环调度者"并不矛盾——主调度 Agent 负责编排，子 Agent 负责具体执行某一类工作。

    调用方式¶

    # 同步调用 —— 等待结果返回
task(
    subagent_type="explore",
    load_skills=["security-research"],    # 给 Agent 加载领域知识
    run_in_background=False,              # 同步等待
    prompt="[CONTEXT]... [GOAL]... [REQUEST]..."
)

# 异步并行 —— 立即返回，后台执行
task(
    subagent_type="explore",
    load_skills=["security-research"],
    run_in_background=True,               # 异步执行
    prompt="Find auth middleware patterns..."
)
# → 返回 bg_... 任务 ID，稍后通过 background_output() 收集结果

    7.2 Agent 的关键组成¶

    组件 作用
    LLM 负责理解、推理、判断、生成
    Prompt Builder 组织当前轮次所需的完整上下文
    Planner 拆解任务、决定下一步策略
    Memory 管理短期状态、长期记忆、历史结果
    Tool / Skill Router 选择并调用外部能力
    Executor / Guardrails 控制执行、安全校验、权限约束

    7.3 Agent 的角色与定位¶

    维度 说明
    本质 编排与决策系统
    作用 驱动 LLM 和工具协同完成复杂目标
    优点 能处理多步任务、具备反馈修正能力
    局限 设计复杂，成本、稳定性和安全治理要求更高

    7.4 没有 Agent 和有 Agent 的差异¶

    场景 系统能力
    只有 Prompt + LLM 更适合一次性问答、摘要、改写、解释
    Prompt + Tools 可以做有限工具调用，但仍偏单步交互
    Agent + Tools / Skills 可以完成多步任务、持续决策、动态修正
    Agent + MCP + Skills 可以在标准化生态中管理复杂工具网络

    7.5 完整的简易流程示例¶

    我们追踪 get_weather 这个能力，看看它经历什么，说法如何随之变化。

    阶段 1：能力孤立存在时¶

    你写了一段 Python 代码：

    # 这是你的 Skill
def get_weather(city: str) -> str:
    # 内部调用了某个天气服务的 HTTP API
    ...
    return "苏州明天大雨"

    此时，它只是一个独立的、无任何连接协议的 Skill。

    阶段 2：动手把它“MCP化”（套上标准外壳）¶

    你写一个 MCP 服务器，把你上面的 get_weather 代码放进去，注册为一个 Tool。

    # 启动一个 MCP 服务器，它内部使用了你的 Skill
from mcp.server import Server
from my_old_code import get_weather  # <--- 你的 Skill 在这里

server = Server("weather-server")

@server.list_tools()
async def list_tools():
    return [{"name": "get_weather", ...}]  # 告诉外界：我有这个工具

@server.call_tool()
async def call_tool(name, args):
    if name == "get_weather":
        return get_weather(args["city"])  # 真正执行 Skill

    现在，这个运行起来的进程就是“MCP 天气服务器”。 我们就可以准确地说：“这个 MCP 服务器封装了 get_weather 这个 Skill”。它把原始的、调用方式五花八门的技能代码，包进了一个标准的 MCP 调用接口里。

    阶段 3：Agent 通过 MCP 客户端调用¶

    你的 Agent 只需要连接它：

    # Agent 内部，通过 MCP 客户端，用标准协议远程调用
result = await mcp_session.call_tool("get_weather", {"city": "苏州"})
# result = "苏州明天大雨"

    Agent 完全不碰原始的 get_weather Python 代码，也看不见它背后的天气 API。

    两种说法在时间轴上的统一：

    1. Skill/Tool 是“被封装的内容”（代码、业务逻辑）。
    2. MCP 服务器是“封装后的结果”（一个实现了标准协议，可以对外通信的可运行实例）。
    3. MCP 协议是“封装所用的规范”（定义封装格式和通信方式的图纸）。

    八、四者的具体区别与联系¶

    8.1 区别总表¶

    维度 Prompt / Prompts Skills MCP Agent
    核心问题 给模型看什么 系统能做什么 系统如何连上外部能力 任务如何持续完成
    关注对象 上下文与规则 具体能力 协议与连接 决策与编排
    是否直接参与推理 是 否 否 间接，通过组织推理过程
    是否直接执行动作 否 是 负责转发，不直接做业务决策 负责调度执行
    是否可独立存在 可以 可以 可以 通常依赖 LLM、Prompt、Tools
    主要产物 输入上下文 结果数据或执行动作 标准化能力接口 任务状态与最终结果

    8.2 联系总表¶

    组合关系 说明
    Prompt 和 Skills Skill 描述进入 Prompt，模型据此决定是否调用能力
    Prompt 和 Agent Agent 动态组装 Prompt，Prompt 承载 Agent 的阶段性状态
    Skills 和 MCP MCP 负责把 Skill 以标准方式暴露与调用
    Agent 和 MCP Agent 借助 MCP 统一接入多类能力，而不必逐个硬编码
    Agent 和 Skills Agent 决定何时调用哪个 Skill，Skill 负责完成具体动作

    8.3 选择决策¶

    理论分清了，落到实践还要回答一个问题——面对一个具体需求，到底该动用 Prompt、Skill、MCP 还是 Agent？ 关键是先问自己"我缺的是什么"：

    你缺的是什么？
│
├─ 缺"表达方式" → 只是想让模型按某种格式/角色回答
│   → 改 Prompt
│   例："用更专业的语气总结" "按 JSON 输出"
│
├─ 缺"领域知识 / 方法论" → 不知道某类任务该怎么做
│   → 加载 Skill（知识注入）
│   例："怎么做安全审计？" "前端组件有什么规范？"
│
├─ 缺"外部能力 / 数据" → 需要真实查询、执行、读写
│   → 接入 MCP
│   例："扫描架构生成图" "查数据库" "调用第三方 API"
│
├─ 缺"并行 / 独立执行" → 任务大、可拆分、需隔离上下文
│   → 派发 Agent
│   例："同时检索 5 个模块" "深度分析后给方案"
│
└─ 既要专业知识又要并行 → Skill + Agent 组合
    例：派发领域专家 Agent，同时为它加载领域知识 Skill

    常见场景对照：

    场景 用什么 为什么
    想换个输出风格 / 约束格式 Prompt 只影响"怎么说"，无需新能力
    不知道某类任务怎么做 Skill 需要方法论注入，不需要执行
    要调用外部工具 / 数据源 MCP 需要访问模型之外的真实能力
    要同时处理多个独立子任务 多个 Agent 需要并行 + 上下文隔离
    架构 / 疑难问题拿不准 咨询型 Agent（如 oracle） 需要高质量只读推理
    查外部库文档 / 开源用法 研究型 Agent（如 librarian） 需要检索外部资源
    专业领域 + 大量产出 Agent + Skill 专用模型承载执行 + 领域知识兜底方法论

    一个实用心法：能用 Prompt 解决就别上 Skill，能用 Skill 解决就别急着接 MCP，单线程能完成就别拆 Agent。 越往下成本和复杂度越高，按需升级而非一上来就堆全套。

    8.4 最核心的一句话¶

    Prompt 决定模型看到什么，Skills 决定系统会做什么，MCP 决定能力怎么接进来，Agent 决定整个任务怎么跑下去。

    九、在 LLM 大模型调度中的完整执行流程¶

    9.1 标准闭环¶

    flowchart TD
        A[用户目标] --> B[Agent 解析任务]
        B --> C[组装 Prompt]
        C --> D[LLM 推理]
        D --> E{是否需要外部能力}
        E -- 否 --> F[生成最终回答]
        E -- 是 --> G[选择 Skill / Tool]
        G --> H[MCP 调用对应 Server]
        H --> I[执行 Tool / 读取 Resource]
        I --> J[返回结构化结果]
        J --> K[写回状态与上下文]
        K --> C
        F --> L[回复用户或触发动作]

    9.2 用具体例子理解¶

    用户提出需求："帮我查一下苏州明天的天气，如果下雨就发邮件提醒我带伞。"

    系统内部会发生如下过程：

    1. Agent 接收目标，识别这是一个多步任务，而不是单次问答。
    2. Agent 组装 Prompt，把用户目标、可用工具、执行约束写入上下文。
    3. LLM 推理，判断第一步应先查天气。
    4. 模型返回工具调用意图，例如调用 get_weather(city, date)。
    5. Agent 通过 MCP 调用天气 Skill，获得实时天气结果。
    6. Agent 把结果写回 Prompt，再次请求 LLM 判断下一步。
    7. LLM 发现满足"下雨则发邮件"条件，于是请求调用邮件发送 Skill。
    8. Agent 再次执行工具调用，完成邮件发送。
    9. Agent 汇总执行结果，输出最终回复。

    这说明：

    • Prompt 负责传递任务和结果。
    • LLM 负责推理顺序和调用意图。
    • Skills 负责真正执行动作。
    • MCP 负责标准化接入与调用。
    • Agent 负责让这一切形成可持续的闭环。

    十、LLM 大模型的工作原理¶

    10.1 LLM 的本质¶

    LLM（Large Language Model）本质上是一个基于海量数据训练出来的概率模型，它的核心能力不是"理解世界并直接行动"，而是：

    • 根据已有上下文推断下一个最合理的 Token
    • 在足够大的参数规模和训练数据下表现出语言理解、推理、总结、编程、规划等能力

    所以从工程角度看，LLM 更接近一个 通用推理与生成引擎。

    10.2 LLM 的基本工作流程¶

    flowchart LR
        A[输入文本 Prompt] --> B[Tokenizer 分词]
        B --> C[Token 序列]
        C --> D[Transformer 多层计算]
        D --> E[上下文表示]
        E --> F[下一个 Token 概率分布]
        F --> G[采样 / 选择]
        G --> H[生成一个 Token]
        H --> I{是否结束}
        I -- 否 --> D
        I -- 是 --> J[完整输出]

    10.3 极简理解四步¶

    步骤 说明
    Tokenization 把文本切成模型可处理的 Token
    Encoding / Attention 通过 Transformer 建立上下文关系
    Probability Prediction 计算下一个 Token 的概率分布
    Decoding 选出一个 Token，持续生成直到结束

    10.4 Transformer 为什么重要¶

    Transformer 的关键在于 自注意力机制（Self-Attention）。它允许模型在处理当前 Token 时，同时参考上下文中的其他 Token，从而建立长距离依赖关系，例如：

    • 谁在修饰谁
    • 某个代词指代什么对象
    • 一段代码中的变量与函数如何对应
    • 前文提到的约束如何影响后文生成

    这也是 LLM 能处理长文本、多轮对话和复杂推理的基础。

    10.5 LLM 为什么能"调用工具"¶

    LLM 自身并不会真的调用 API、访问数据库或发送邮件。所谓"工具调用"本质上是：

    1. 系统在 Prompt 中告诉模型有哪些工具、参数如何定义。
    2. 模型在推理后输出结构化调用意图。
    3. Agent 或宿主程序识别这个意图。
    4. 外部系统代替模型去执行真正的动作。
    5. 执行结果再返回给模型，进入下一轮推理。

    因此，工具调用不是 LLM 神奇地获得了外部执行能力，而是 LLM + 外部编排系统 共同工作的结果。

    10.6 LLM 的优势与边界¶

    维度 优势 边界
    语言理解 强于模式归纳、生成和重写 不天然等于事实正确
    推理规划 可进行多步推理与任务拆解 复杂场景下可能出现幻觉和遗漏
    工具协作 能根据描述选择工具 需要外部系统真正执行
    知识能力 能吸收大量通用知识 知识可能过时，且不保证可验证

    这也是为什么现代 AI 系统必须引入 RAG、Tools、MCP、Memory、Agent 等外部机制来补足落地能力。

    十一、工程实践中的常见误解¶

    11.1 误把 Prompt 工程当成全部¶

    Prompt 很重要，但它解决的是"如何更好地表达给模型"，不是"如何让系统真正可执行、可追踪、可恢复"。一旦任务进入多步执行，必须引入状态管理、工具调用和编排逻辑。

    11.2 误把 MCP 当成 Agent 框架¶

    MCP 只是标准协议，不负责任务拆解、优先级判断、失败重试和状态推进。它是连接层，不是决策层。

    11.3 误把 Tool 等同于 Skill¶

    单个 Tool 往往只是一次操作，而 Skill 更强调围绕某类任务的能力封装。复杂 Skill 往往由多个 Tool、Prompt 模板和规则共同组成。

    11.4 误把 LLM 当成完整应用¶

    LLM 只是核心引擎之一。真正能上线的 AI 系统通常还需要：

    • 上下文工程
    • 权限与安全控制
    • 工具接入层
    • 观测与日志
    • 记忆与状态管理
    • 成本与延迟治理

    十二、总结¶

    从系统分层来看：

    • Prompt 解决的是"让模型看到什么信息"。
    • Skills 解决的是"系统具体能做什么动作"。
    • MCP 解决的是"这些能力如何被标准化接入"。
    • Agent 解决的是"围绕目标如何持续规划、执行、反馈并完成任务"。

    从调度链路来看：

    • Prompt 是 LLM 的输入载体。
    • LLM 是推理引擎。
    • Skills 是执行能力。
    • MCP 是连接标准。
    • Agent 是全局调度中枢。

    从本质上说，现代 LLM 应用并不是单纯依赖一个大模型，而是通过 Prompt、Skills、MCP、Agent 等分层协作，把"文本预测器"升级为能够理解任务、调用能力、执行动作、闭环反馈的智能系统。
