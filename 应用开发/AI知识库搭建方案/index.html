    一、目标与场景¶

    1.1 目标定义¶

    知识库系统的核心目标是把分散的文档、网页、数据库记录、代码、图片或业务资料整理成可检索、可追溯、可问答的知识服务。常见实现形态包括：

    • 企业知识问答：内部制度、产品手册、项目文档、客服知识库。
    • 个人知识管理：笔记、论文、书籍、网页收藏、代码片段。
    • 研发辅助系统：代码仓库问答、API 文档检索、故障排查手册。
    • 垂直行业知识库：医疗、法律、金融、教育等强专业领域资料检索与问答。

    1.2 核心能力¶

    能力 说明
    数据接入 支持 PDF、Word、Markdown、HTML、数据库、对象存储、Git 仓库等来源
    文档解析 提取正文、标题、表格、图片 OCR、元数据和层级结构
    分块索引 将长文档切分成适合模型理解的 Chunk，并写入向量库/全文索引
    语义检索 使用 Embedding 模型把查询和文档映射到向量空间，召回相关内容
    重排序 使用 Reranker 或规则对召回结果再次排序，提高上下文准确率
    RAG 问答 将检索结果注入大语言模型，生成有依据、可引用的回答
    权限控制 按用户、团队、租户、文档级别控制可见范围
    评估优化 对召回率、答案准确率、延迟、成本、幻觉率持续评估

    1.3 推荐技术路线¶

    数据源 -> 文档解析 -> 清洗规范化 -> 文档分块 -> Embedding -> 向量库/全文索引
                                                               |
用户问题 -> 查询改写 -> 向量召回/关键词召回 -> Rerank -> 上下文组装 -> LLM 生成 -> 引用与反馈

    建议采用 Python 负责 AI/文档处理链路，Go 负责高并发服务和工程化接口 的组合：

    • Python：生态成熟，适合文档解析、Embedding、Rerank、RAG 工作流、模型评测和离线任务。
    • Go：部署简单、并发强、资源占用低，适合 API 网关、权限服务、文件上传、任务调度和在线检索接口。
    • 纯 Python 方案：适合 MVP、中小团队、AI 功能快速迭代。
    • 纯 Go 方案：适合模型能力主要通过外部 API 调用、强调部署简单和高并发的场景。

    二、总体架构¶

    2.1 模块划分¶

    模块 主要职责 推荐语言/组件
    接入层 文件上传、网页抓取、数据库同步、Git 同步 FastAPI、MinIO、S3
    解析层 PDF/Office/HTML/Markdown 解析，OCR，表格抽取 Python、Unstructured、PyMuPDF、Tesseract/PaddleOCR
    清洗层 去噪、去重、格式规范化、敏感信息处理 Python
    索引层 分块、向量化、写入向量库和全文索引 Python、Celery/Arq、Kafka/NATS
    检索层 语义检索、关键词检索、混合召回、Rerank Go/Python、Milvus/Qdrant/pgvector、Elasticsearch
    生成层 Prompt 组装、LLM 调用、答案生成、引用输出 Python/Go、OpenAI/DeepSeek/Qwen/Ollama
    管理层 知识库、用户、权限、任务、审计、配置 Go、PostgreSQL、Redis
    评估层 测试集、召回评估、答案评估、反馈闭环 Python、RAGAS/DeepEval/自定义脚本

    2.2 部署形态¶

    小型知识库¶

    FastAPI/Gin API + PostgreSQL(pgvector) + Redis + 本地对象存储 + 外部 LLM API

    特点：部署简单、成本低、维护少，适合个人或小团队。文档规模建议在百万 Chunk 以内。

    中大型知识库¶

    Go API 网关 + Python Worker + PostgreSQL + Qdrant/Milvus + Elasticsearch + Redis + MinIO + Kafka/NATS

    特点：检索能力强、可扩展、适合多租户和多业务线。文档更新和索引任务通过队列异步处理。

    私有化知识库¶

    内网部署 + Ollama/vLLM/LMDeploy + BGE/Qwen Embedding + Qdrant/Milvus + SSO/LDAP

    特点：数据不出内网，适合企业资料、研发文档和敏感行业。需要关注 GPU 资源和模型推理延迟。

    三、数据接入与文档处理¶

    3.1 数据源规划¶

    数据源 接入方式 注意事项
    PDF/Word/PPT/Excel 文件上传、批量导入 需要处理扫描件、表格、页眉页脚、水印
    Markdown/文本 Git 同步、本地目录扫描 保留标题层级、代码块和相对链接
    网页/站点 爬虫、Sitemap、RSS 处理正文抽取、重复页面、动态渲染
    数据库 定时同步、CDC 需要字段映射、增量同步和权限映射
    代码仓库 Git Clone、Webhook 建议按文件、函数、README、注释分别建索引
    图片 OCR、图像描述模型 需要保存原图引用和识别置信度

    3.2 文档解析策略¶

    1. 保留结构：标题、章节、列表、表格和代码块比纯文本更有价值。
    2. 保留来源：每个 Chunk 记录 source_id、文件名、页码、标题路径、更新时间和权限标签。
    3. 处理噪声：去除页眉页脚、目录页、重复版权声明、空白行和乱码。
    4. 表格单独处理：小表格可转 Markdown，大表格建议保存为结构化 JSON，并提供表格摘要。
    5. 图片和扫描件：OCR 后记录图片位置；重要图表可使用多模态模型生成说明文本。

    Python 解析示例：

    from pathlib import Path
import fitz  # PyMuPDF


def parse_pdf(path: str) -> list[dict]:
    doc = fitz.open(path)
    pages = []
    for page_no, page in enumerate(doc, start=1):
        text = page.get_text("text")
        if text.strip():
            pages.append({
                "source": Path(path).name,
                "page": page_no,
                "text": text.strip(),
            })
    return pages

    四、分块策略¶

    4.1 分块原则¶

    分块质量直接决定检索质量。过小会丢失上下文，过大会引入噪声并浪费 Token。

    文档类型 推荐 Chunk 大小 Overlap 说明
    FAQ/制度条款 200-500 字 50-100 字 尽量保持一问一答或一条规则完整
    技术文档 500-1000 字 100-200 字 按标题层级和代码块边界切分
    长篇报告/论文 800-1500 字 150-300 字 保留章节摘要和页码
    代码文件 以函数/类为单位 少量 保留文件路径、依赖、注释和签名
    表格 按行组/主题切分 无或少量 避免把表头和数据行分离

    4.2 推荐实现¶

    1. 先结构化切分：优先按 Markdown 标题、HTML 节点、PDF 标题、代码 AST 切分。
    2. 再长度兜底：超过模型窗口的段落再按句子或 Token 数切分。
    3. 增加上下文标题：Chunk 文本前拼接文档标题和章节路径，例如 产品手册 > 账号管理 > 重置密码。
    4. 记录父子关系：小 Chunk 用于召回，大段落/章节用于答案上下文扩展。
    5. 为表格生成摘要：表格检索可用“表格摘要 + 原始表格 JSON/Markdown”双索引。

    Python 分块示例：

    def chunk_text(text: str, max_chars: int = 800, overlap: int = 120) -> list[str]:
    chunks = []
    start = 0
    while start < len(text):
        end = min(start + max_chars, len(text))
        chunk = text[start:end].strip()
        if chunk:
            chunks.append(chunk)
        if end == len(text):
            break
        start = max(0, end - overlap)
    return chunks

    五、模型选择¶

    5.1 Embedding 模型¶

    Embedding 模型用于生成文档和查询向量，是知识库召回质量的基础。

    模型 部署方式 特点 推荐场景
    BAAI/bge-m3 本地/API 多语言、多粒度、支持长文本，中文效果好 私有化、多语言知识库首选
    bge-large-zh-v1.5 本地 中文检索强，生态成熟 中文企业知识库
    Qwen3-Embedding 本地/API 中文、代码、多任务表现好 中文 + 代码混合知识库
    text-embedding-3-large API 质量高、维护成本低 可使用云服务且重视效果
    jina-embeddings-v3 本地/API 多语言、长上下文能力较强 多语言文档和网页知识库

    选型建议：

    • 中文私有化：优先 bge-m3 或 bge-large-zh-v1.5。
    • 中文 + 代码：优先 Qwen Embedding 或 bge-m3，并对代码文件做专门切分。
    • 快速上线：优先云端 Embedding API，减少本地推理部署成本。
    • 大规模低成本：使用本地小模型批量离线向量化，必要时做量化和批处理。

    5.2 Reranker 模型¶

    Reranker 用于对向量召回的候选结果重新排序，通常能明显提高答案相关性。

    模型 特点 推荐场景
    bge-reranker-v2-m3 多语言能力强，中文效果稳定 通用知识库首选
    bge-reranker-large 精度较高，资源开销更大 高质量问答、候选数量较少
    Qwen Reranker 中文语义理解强 中文业务知识库
    Cohere Rerank API 稳定、集成简单 海外或多语言场景

    建议先向量召回 Top 30-80，再 Rerank 到 Top 5-10。Reranker 延迟较高，不建议对过多候选直接排序。

    5.3 大语言模型¶

    LLM 负责理解问题、整合上下文和生成答案。

    模型/服务 特点 推荐场景
    DeepSeek-V3/R1 中文能力强，成本低，推理能力好 中文知识问答、分析型回答
    Qwen2.5/Qwen3 中文、代码和工具调用能力好，可私有化 企业内网、研发知识库
    GPT-4.1/GPT-5 系列 综合能力强，上下文和工具生态成熟 高质量 SaaS、复杂任务编排
    Claude 系列 长文本理解强，回答稳定 长文档分析、政策制度问答
    Llama 3.1/3.3 开源生态好，多语言可用 海外、多语言、本地部署

    模型选择原则：

    • 答案必须准确：优先强模型 + 引用来源 + 严格 Prompt。
    • 成本敏感：日常问答用低成本模型，复杂问题路由到强模型。
    • 数据敏感：使用 Qwen/Llama/DeepSeek 蒸馏模型私有化部署。
    • 长文总结：选择长上下文模型，但仍建议先检索再生成，避免全量塞入上下文。

    六、向量库与存储选型¶

    6.1 向量数据库¶

    组件 优点 缺点 推荐场景
    pgvector 与 PostgreSQL 集成简单，事务和权限好 超大规模性能有限 小中型知识库、快速上线
    Qdrant 部署简单，过滤条件强，Rust 实现性能好 生态小于 Milvus 中型知识库、多租户过滤
    Milvus 大规模向量检索能力强，生态成熟 部署和运维复杂 千万级以上 Chunk、大规模业务
    Weaviate Schema 和模块化能力好 资源占用较高 需要 GraphQL/模块化扩展
    Elasticsearch/OpenSearch 全文检索强，BM25 成熟 向量能力不是最轻量 混合检索、已有 ES 基础设施

    6.2 元数据设计¶

    建议向量库只存检索必要字段，完整文档和权限信息放在关系库/对象存储中。

    七、检索与 RAG 流程¶

    7.1 在线问答流程¶

    1. 接收问题和用户身份
2. 权限过滤：确定用户可访问的知识库和文档范围
3. 查询预处理：纠错、同义词扩展、问题改写、意图识别
4. 混合召回：向量检索 TopK + BM25 关键词检索 TopK
5. 去重合并：按文档、标题、相似度和时间过滤重复内容
6. Rerank：对候选 Chunk 做精排
7. 上下文扩展：补充相邻 Chunk、父章节摘要或表格原文
8. Prompt 组装：限制模型只能基于引用材料回答
9. LLM 生成：输出答案、引用来源和不确定性提示
10. 记录日志：问题、召回结果、答案、耗时、用户反馈

    7.2 Prompt 模板¶

    你是一个严谨的知识库问答助手。请只根据【参考资料】回答用户问题。

要求：
1. 如果参考资料中没有答案，明确说明“资料中未找到可靠依据”。
2. 不要编造不存在的政策、数字、链接或结论。
3. 答案尽量结构化，必要时使用列表或表格。
4. 每个关键结论后标注引用编号，例如 [1]、[2]。

【用户问题】
{question}

【参考资料】
{contexts}

    7.3 Python RAG 示例¶

    from openai import OpenAI

client = OpenAI(base_url="https://api.deepseek.com", api_key="YOUR_API_KEY")


def answer(question: str, contexts: list[dict]) -> str:
    refs = "\n\n".join(
        f"[{i}] {ctx['title']}\n{ctx['content']}"
        for i, ctx in enumerate(contexts, start=1)
    )
    prompt = f"""你是一个严谨的知识库问答助手。请只根据参考资料回答。

用户问题：{question}

参考资料：
{refs}
"""
    resp = client.chat.completions.create(
        model="deepseek-chat",
        messages=[{"role": "user", "content": prompt}],
        temperature=0.2,
    )
    return resp.choices[0].message.content

    7.4 Go 在线服务示例¶

    package main

import (
    "context"
    "encoding/json"
    "net/http"
    "time"
)

type AskRequest struct {
    Question        string `json:"question"`
    KnowledgeBaseID string `json:"knowledge_base_id"`
}

type AskResponse struct {
    Answer  string   `json:"answer"`
    Sources []string `json:"sources"`
}

func askHandler(w http.ResponseWriter, r *http.Request) {
    ctx, cancel := context.WithTimeout(r.Context(), 30*time.Second)
    defer cancel()

    var req AskRequest
    if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
        http.Error(w, err.Error(), http.StatusBadRequest)
        return
    }

    // 实际项目中在这里完成权限校验、检索、Rerank 和 LLM 调用。
    _ = ctx
    resp := AskResponse{
        Answer:  "根据当前知识库资料生成的回答。",
        Sources: []string{"document-a.md#section-1"},
    }

    w.Header().Set("Content-Type", "application/json")
    _ = json.NewEncoder(w).Encode(resp)
}

func main() {
    http.HandleFunc("/api/ask", askHandler)
    _ = http.ListenAndServe(":8080", nil)
}

    8.1 Python 优先方案¶

    适合快速验证和 AI 能力迭代。

    FastAPI

    • API：FastAPI + Pydantic + Uvicorn。
    • 异步任务：Celery/RQ/Arq，或 Kafka/NATS + Worker。

    • RAG 编排：LlamaIndex/LangChain 可用于原型，生产环境建议保留核心链路的自定义控制。
    • 模型服务：OpenAI SDK 兼容接口、SentenceTransformers、vLLM、Ollama。

    8.2 Go + Python 混合方案¶

    适合正式生产系统。

├── 在线问答接口、流式输出 SSE/WebSocket
└── 调用 Python RAG Worker 或模型服务

Python AI Worker
├── 文档解析和清洗
├── Chunk 生成和 Embedding
├── Rerank、评估和离线优化

    • 文件原文进入 MinIO/S3，元数据进入 PostgreSQL，检索数据进入 Qdrant/Milvus/pgvector。
    • 问答接口支持 SSE 流式输出，提升用户体验。

    九、优化细节¶

    9.1 检索质量优化¶

    问题 优化方法
    召回不到正确内容 调整 Chunk 大小，增加标题路径，使用混合检索，增加同义词和查询改写
    召回结果太杂 增加权限/知识库/时间/文档类型过滤，使用 Reranker 精排
    答案引用不准 保留页码和标题路径，Rerank 后只注入高置信内容
    多跳问题答不好 先拆解问题，多轮检索，再汇总生成
    表格问答差 表格转 Markdown + 行级 JSON + 表格摘要三种索引并存
    代码问答差 使用 AST/函数级切分，保留文件路径、导入依赖和调用关系

    9.2 模型优化¶

    1. Embedding 批处理：离线索引时批量生成向量，提高 GPU/CPU 利用率。
    2. 向量归一化：使用 Cosine 相似度时确保向量归一化，避免分数异常。
    3. Rerank 控制候选数量：TopK 过大会增加延迟，常见配置是召回 50、精排 8。
    4. LLM 温度降低：知识问答建议 temperature=0-0.3，减少发挥。
    5. 模型路由：简单事实问答用低成本模型，复杂总结/推理用强模型。
    6. 缓存：对热门问题、Embedding、Rerank 结果和模型回答做缓存。
    7. 量化部署：私有化模型可用 INT8/INT4 量化降低显存，但要用评测集验证精度损失。

    9.3 性能优化¶

    环节 优化手段
    文档导入 异步任务、批量解析、失败重试、增量更新
    Embedding 批处理、GPU 推理、按文档版本缓存向量
    向量检索 HNSW/IVF 索引调参，按租户分区，冷热数据分层
    Rerank 候选截断、并发请求、结果缓存、小模型优先
    LLM 生成 流式输出、Prompt 压缩、上下文去重、模型路由
    数据库 元数据索引、读写分离、连接池、归档旧版本

    9.4 安全与权限¶

    1. 检索前过滤：先确定用户可访问文档范围，再做向量检索。
    2. 元数据过滤：向量库中写入 tenant_id、kb_id、acl_tags 等字段。
    3. 敏感信息脱敏：身份证、手机号、密钥、合同金额等按规则脱敏或隔离。
    4. 审计日志：记录用户问题、访问文档、生成答案和下载行为。
    5. Prompt 注入防护：文档中的“忽略前面指令”等内容必须作为普通资料处理，系统提示优先级最高。
    6. 数据隔离：多租户建议库级/表级隔离，至少保证过滤条件不可绕过。

    十、评估体系¶

    10.1 检索评估指标¶

    指标 含义
    Recall@K 正确 Chunk 是否出现在 TopK 中
    MRR 正确结果排名越靠前分数越高
    NDCG 综合考虑多个相关结果的排序质量
    Context Precision 注入上下文中真正有用内容的比例
    Context Recall 答案所需信息被上下文覆盖的比例

    10.2 答案评估指标¶

    指标 含义
    Faithfulness 答案是否忠实于引用资料
    Answer Relevancy 答案是否真正回答用户问题
    Citation Accuracy 引用编号是否支持对应结论
    Hallucination Rate 无依据编造比例
    Latency/Cost 平均耗时、P95 耗时、单次问答成本

    10.3 测试集构建¶

    1. 从真实业务文档中人工整理 50-200 个高频问题。
    2. 每个问题标注标准答案、支持文档、支持 Chunk 和页码。
    3. 覆盖事实查询、流程问答、对比总结、多文档综合、无答案问题。
    4. 每次调整分块、Embedding、Rerank 或 Prompt 后跑回归评估。
    5. 将线上差评问题加入测试集，形成持续优化闭环。

    十一、实施步骤¶

    11.1 MVP 阶段¶

    1. 确定 1-2 类核心文档来源，例如 Markdown + PDF。
    2. 使用 Python 完成解析、分块、Embedding 和 pgvector/Qdrant 入库。
    3. 实现基础问答接口：向量检索 TopK + Prompt + LLM。
    4. 输出答案引用来源，支持用户查看原文位置。
    5. 构建 30-50 个问题的测试集，验证召回和答案质量。

    11.2 生产化阶段¶

    1. 引入 Go 后端管理知识库、用户、权限和任务状态。
    2. 文档索引改为异步任务，支持失败重试、版本管理和增量更新。
    3. 引入混合检索和 Reranker，提高复杂问题准确率。
    4. 增加对象存储、审计日志、监控告警和配额控制。
    5. 支持 SSE 流式问答、反馈按钮和引用跳转。

    11.3 优化阶段¶

    1. 建立自动评估流水线，跟踪 Recall@K、Faithfulness、延迟和成本。
    2. 对不同知识库配置不同 Chunk 策略、模型和召回参数。
    3. 增加查询改写、多跳检索、父子 Chunk、表格问答和代码问答能力。
    4. 对高频问题生成缓存或 FAQ 索引，降低模型调用成本。
    5. 逐步私有化 Embedding/Rerank/LLM，平衡数据安全和推理成本。

    十三、常见问题与取舍¶

    问题 建议
    是否一定要向量库 小规模可用 pgvector；规模大、过滤复杂或高并发再上 Qdrant/Milvus
    是否直接把全文塞给大模型 不建议。成本高、延迟高，且容易引入无关噪声
    LangChain/LlamaIndex 是否必须 原型可用，生产建议掌握核心检索、Prompt 和评估链路，避免过度封装
    中文知识库怎么选模型 bge-m3/bge-large-zh + bge-reranker-v2-m3 + Qwen/DeepSeek 是稳妥组合
    如何降低幻觉 强制引用、低温度、无依据拒答、Rerank、答案后校验和人工反馈
    如何处理权限 检索前过滤 + 向量库元数据过滤 + 数据库 ACL 校验，不能只在生成后过滤

    十四、结论¶

    知识库搭建不是简单的“文档向量化 + 大模型问答”，而是一套从数据治理、文档解析、分块索引、混合检索、模型生成、权限控制到质量评估的完整工程。推荐先用 Python 快速完成 AI 链路验证，再用 Go 承载高并发 API、权限和任务管理。模型上优先保证 Embedding 与 Reranker 的检索质量，再根据成本、安全和效果选择云端或私有化 LLM。生产环境必须建立评估集和反馈闭环，否则系统很难长期保持可靠。
