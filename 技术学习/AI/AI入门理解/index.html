    一、AI 背景¶

    1.1 人工智能发展历程¶

    阶段 时间 核心特征 代表性成果
    符号主义 1950s-1970s 基于规则与逻辑推理 专家系统、ELIZA
    连接主义兴起 1980s-1990s 神经网络反向传播 BP 网络、LeNet
    统计学习 2000s-2010s SVM、随机森林等机器学习方法 图片分类、推荐系统
    深度学习爆发 2012-2020 大规模神经网络 + GPU 算力 AlexNet、AlphaGo、Transformer
    大模型时代 2020-至今 超大规模预训练 + 涌现能力 GPT 系列、Claude、Gemini、DeepSeek

    1.2 大模型时代的标志性节点¶

    • 2017：Google 发表 Attention Is All You Need，提出 Transformer 架构，奠定大模型基础
    • 2018：OpenAI 发布 GPT-1，开创"预训练 + 微调"范式；Google 发布 BERT
    • 2020：GPT-3 参数量达 1750 亿，展示少样本学习与涌现能力
    • 2022：ChatGPT 上线，大模型进入大众视野；Stable Diffusion 开源推动图像生成
    • 2023：GPT-4 多模态发布；开源社区涌现 LLaMA、Mistral 等；RAG/Agent 概念成型
    • 2024：DeepSeek-V3/R1 以极低成本实现顶尖推理能力；MCP 协议发布；Claude 3.5 系列代码能力突出
    • 2025-2026：进入 Agent 与深度推理驱动的成熟期；GPT-5、Claude 4、Gemini 3 等迭代；开源模型（Qwen3、Llama 4）逼近闭源水平

    1.3 当前行业格局（2026）¶

    截至 2026 年，全球 AI 大模型市场呈现以下特征：

    • 竞争格局梯队化：闭源第一梯队（GPT-5、Claude 4、Gemini 3）与开源阵营（DeepSeek、Qwen、Llama）并行发展
    • 从模型能力转向应用落地：Agent、RAG、工具调用成为核心战场
    • 成本效率革命：MoE 架构与蒸馏技术使推理成本大幅下降（DeepSeek 仅需 1/10 成本）
    • 多模态成为标配：文本、图像、音视频的混合理解与生成已成为主流模型的基本能力
    • 协议标准化：MCP（Model Context Protocol）等工具协议推动 Agent 生态互通

    二、关键概念¶

    2.1 核心术语¶

    术语 含义
    LLM（Large Language Model） 大语言模型，通过海量文本预训练的超大规模语言模型
    Token 模型处理文本的最小单位，1 个中文约 1-2 Token，1 个英文单词约 1-1.5 Token
    上下文窗口（Context Window） 模型单次可处理的最大 Token 数，当前主流 128K-1M
    涌现能力（Emergent Ability） 模型规模达到阈值后突然出现的新能力（如推理、代码生成）
    幻觉（Hallucination） 模型生成看似合理但实际错误或虚构的内容
    Temperature 控制输出随机性的参数，越高越随机/创造性，越低越确定/一致性
    Embedding 将文本映射为高维向量，用于语义检索、相似度计算

    2.2 提示工程（Prompt Engineering）¶

    提示工程是设计和优化 LLM 输入提示的技术，目标是引导模型产生高质量、符合预期的输出。

    常用提示策略¶

    策略 说明 适用场景
    Zero-shot 不提供示例，直接给出指令 通用任务、格式转换
    Few-shot 提供少量示例，引导模型输出格式 分类、格式化输出
    Chain-of-Thought（CoT） 要求模型逐步推理 数学推理、逻辑分析
    自洽性（Self-Consistency） 多次采样取多数结果 降低随机性错误
    ReAct 推理（Reasoning）+ 行动（Acting）交替 Agent 决策循环

    最佳实践¶

    • 明确角色设定：你是一位资深的 Python 工程师...
    • 指定输出格式：请以 JSON 格式输出，包含字段：name, type, description
    • 分步骤引导：第一步...第二步...第三步...
    • 提供约束条件：不要使用第三方库、回答不超过 200 字
    • 使用分隔符区分内容：```内容``` 或 --- 分割不同部分

    趋势：2025-2026 年行业正从 Prompt Engineering 向 Context Engineering 演进——不仅优化提示文本，更关注如何系统性地管理上下文（记忆、工具、检索结果、对话历史等），使 Agent 在复杂任务中持续做出正确决策。

    2.3 微调（Fine-tuning）¶

    在预训练模型基础上，使用特定领域数据进一步训练，使模型适配特定任务。

    方式 原理 资源需求 适用场景
    全量微调 更新所有模型参数 高（需多卡 A100/H100） 数据充足、效果优先
    LoRA 冻结原权重，训练低秩适配层 低（单卡可行） 资源受限、快速迭代
    QLoRA 量化 + LoRA，4-bit 训练 极低 消费级 GPU 微调
    RLHF 人类反馈强化学习对齐 高 对齐人类偏好
    DPO 直接偏好优化，替代 RLHF 中 简化对齐流程
    蒸馏（Distillation） 大模型指导小模型学习 低 压缩部署、降低成本

    2.4 RAG（检索增强生成）¶

    RAG 通过将外部知识检索与 LLM 生成结合，解决模型知识过时和幻觉问题。

    基本流程¶

    用户提问 → 查询改写 → 向量检索/关键词检索 → 上下文拼接 → LLM 生成回答

    RAG 技术演进¶

    阶段 特征 代表技术
    Naive RAG 单次检索 + 直接拼接 基础向量检索
    Advanced RAG 查询改写、重排序、混合检索 HyDE、RRF、Cross-Encoder
    Modular RAG 模块化编排（检索、重排、压缩、生成可组合） LangChain、LlamaIndex
    Graph RAG 基于知识图谱的结构化检索 微软 GraphRAG
    Agentic RAG Agent 自主决定何时检索、检索什么 LangGraph、CrewAI

    2.5 Agent（智能体）¶

    Agent 是能够感知环境、自主决策并执行操作以完成目标的 AI 系统。

    Agent 核心闭环¶

    感知（Perception） → 决策（Planning） → 执行（Action） → 反馈（Feedback） → 记忆（Memory）

    Agent 关键组成¶

    组件 作用 代表方案
    LLM 决策大脑，负责理解、规划、判断 GPT-5、Claude、DeepSeek
    工具调用 连接外部系统（API、数据库、代码执行） MCP、Function Calling
    记忆 短期对话记忆 + 长期知识存储 向量数据库、Redis、会话历史
    规划 任务分解、步骤编排 ReAct、Plan-and-Execute、Tree-of-Thought
    执行沙箱 安全执行代码与操作 Docker 容器、权限分级

    Agent 框架对比¶

    框架 语言 特点 适用场景
    LangGraph Python 状态图编排、可恢复执行、流式输出 复杂工作流 Agent
    AutoGen Python 多 Agent 对话协作 多角色协作场景
    CrewAI Python 角色定义清晰、任务分配简单 团队协作型 Agent
    LlamaIndex Workflows Python 事件驱动、知识密集型 RAG Agent
    Dify - 低代码平台、可视化编排 快速搭建、非技术用户

    2.6 Skills（技能）¶

    Skills 是 Agent 领域中用于封装可复用能力单元的概念，指将特定领域知识、操作流程和工具组合打包成标准化的能力模块，使 Agent 能像调用函数一样调用完整的专业技能。

    Skills 与相关概念辨析¶

    概念 定位 粒度 示例
    Tool（工具） 单个原子操作 最细——一次 API 调用 search_web()、read_file()
    Skill（技能） 完成特定任务的流程组合 中等——多步操作编排 "数据库查询与可视化"、"代码审查"
    Workflow（工作流） 跨技能的业务流程 最粗——端到端自动化 "需求分析→开发→测试→部署"

    Skill 核心构成¶

    一个完整的 Skill 通常包含以下要素：

    要素 说明
    触发条件 何时激活该 Skill（意图识别、关键词、显式调用）
    知识/指令 执行该 Skill 所需的领域知识和规则（Prompt 模板、规则约束）
    工具依赖 执行过程中需要调用的外部工具列表
    执行流程 步骤定义：先后顺序、条件分支、循环、异常处理
    输入/输出规范 Skill 接收的参数格式和返回结果的结构定义
    质量约束 成功标准、超时阈值、重试策略

    主流平台的 Skills 实践¶

    平台/框架 Skills 实现方式 特点
    OpenAI GPTs / Actions 通过 Action Schema 定义工具接口，结合 System Prompt 编排 产品化程度高，面向终端用户
    Claude MCP + Skill 文件 .instructions.md / .prompt.md / .agent.md 定义技能，MCP Server 提供工具 开发者导向，可编程可扩展
    LangGraph 通过 StateGraph 节点编排 Skill 执行流程 灵活但需编码
    Dify 可视化拖拽编排 Skill 节点 低代码，上手快
    Semantic Kernel 通过 Plugin 机制注册 Skill（函数 + 描述） 企业级 .NET/Python 集成

    Skill 设计最佳实践¶

    • 单一职责：每个 Skill 聚焦一个明确的能力边界，避免"万能 Skill"
    • 声明式描述：用自然语言清晰描述 Skill 的能力、输入输出，便于 LLM 理解和调度
    • 幂等性：同一 Skill 对相同输入应产生一致结果，避免副作用不确定性
    • 可组合：Skill 之间应可串联/并联，构建更复杂的 Workflow
    • 可观测：Skill 执行过程应有日志和中间状态，便于调试和审计
    • 渐进增强：先实现最小可用版本，再逐步添加异常处理、重试、降级等能力

    2.7 MCP（Model Context Protocol）¶

    MCP 是由 Anthropic 于 2024 年底提出的开放协议，标准化了 LLM 应用与外部工具/数据源的连接方式，被称为"AI 应用的 USB-C"。

    核心目标¶

    • 统一接口：一个协议连接所有工具和数据源，避免每个工具单独适配
    • 双向通信：支持 Host 向 Server 请求，也支持 Server 主动推送（通知、进度）
    • 安全可控：权限分层、沙箱隔离、审计可追踪

    架构模型¶

    ┌───────────────┐      ┌──────────────┐      ┌──────────────┐
│   MCP Host    │      │  MCP Client  │      │  MCP Server  │
│ (AI 应用端)    │────▶│  (协议客户端)  │────▶│ (工具/数据源) │
│ Claude Desktop│      │  嵌入 Host    │      │  文件系统/API │
│  IDE 插件等    │      │  管理连接     │       │  数据库等     │
└───────────────┘      └──────────────┘      └──────────────┘
    • Host：发起连接的 AI 应用（如 Claude Desktop、Cursor、VS Code Copilot）
    • Client：协议客户端，嵌入在 Host 中，与 Server 保持 1:1 连接
    • Server：提供具体能力的轻量服务，每个 Server 独立运行

    通信方式¶

    方式 适用场景 说明
    stdio 本地进程间通信 Server 作为子进程启动，通过标准输入/输出通信，最常用
    SSE（Server-Sent Events） 远程服务 基于 HTTP 长连接，Server 可主动推送通知

    三类核心原语¶

    原语 作用 典型示例
    Tools 可被 LLM 调用的函数/操作 query_database()、search_web()、execute_code()
    Resources 可被 LLM 读取的数据/内容 文件内容、数据库记录、API 响应、日志
    Prompts 预定义的提示模板，可参数化 "代码审查模板"、"翻译提示"、"数据分析步骤"

    MCP 与 Function Calling 的关系¶

    维度 Function Calling MCP
    定义方 各模型厂商自定义 开放标准协议，跨模型通用
    连接模式 紧耦合——工具定义嵌入请求 松耦合——Server 独立部署、动态发现
    可扩展性 新增工具需修改应用代码 新增 Server 即可，Host 无需改动
    生态 各厂商生态独立 跨厂商共享 Server 生态
    适用场景 简单、少量工具调用 复杂、多工具、多数据源集成

    实践建议：简单场景可用 Function Calling 快速实现；需要集成多种工具/数据源、或希望工具可复用时，优先采用 MCP。

    MCP 开发实践¶

    快速构建 MCP Server（Python 示例）¶
    from mcp.server.fastmcp import FastMCP

mcp = FastMCP("my-tools")

@mcp.tool()
def query_user(user_id: str) -> dict:
    """查询用户信息"""
    return {"id": user_id, "name": "张三", "role": "admin"}

@mcp.resource("config://app")
def get_config() -> str:
    """获取应用配置"""
    return '{"theme": "dark", "lang": "zh-CN"}'

@mcp.prompt()
def code_review(code: str) -> str:
    """代码审查提示模板"""
    return f"请审查以下代码，关注安全性、性能和可读性：\n{code}"

mcp.run()  # 默认以 stdio 模式运行
    Host 端配置示例（Claude Desktop）¶
    {
  "mcpServers": {
    "my-tools": {
      "command": "python",
      "args": ["path/to/server.py"]
    },
    "remote-api": {
      "url": "https://mcp.example.com/sse"
    }
  }
}

    主流 MCP Server 生态¶

    类别 代表 Server
    文件与存储 filesystem、S3、Google Drive
    数据库 PostgreSQL、MySQL、SQLite、MongoDB
    开发工具 GitHub、GitLab、Jira、Linear
    通信协作 Slack、Discord、Email
    搜索与知识 Brave Search、Notion、Confluence
    云服务 AWS、GCP、Azure
    自建 企业内部 API、私有数据库、业务系统

    MCP 最佳实践¶

    • 职责单一：每个 MCP Server 聚焦一类能力（如数据库操作），避免"上帝 Server"
    • 权限最小化：Server 仅申请必要的资源访问权限，敏感操作需用户确认
    • 错误可读：工具调用失败时返回结构化错误信息，便于 LLM 理解和重试
    • 描述清晰：Tool/Resource/Prompt 的描述要准确，这是 LLM 决定是否调用的依据
    • 本地优先：能走 stdio 就不走网络，减少延迟和安全风险
    • 版本管理：Server 接口变更遵循语义化版本，避免破坏已有集成

    7. 工具调用 / Function Calling（curl 请求体）¶

    让模型按需返回结构化的工具调用请求，是 Agent 与 MCP 的底层机制。

    curl https://api.openai.com/v1/chat/completions \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-5.1",
    "messages": [{"role": "user", "content": "北京现在天气怎么样？"}],
    "tools": [{
      "type": "function",
      "function": {
        "name": "get_weather",
        "description": "查询指定城市的实时天气",
        "parameters": {
          "type": "object",
          "properties": {
            "city": {"type": "string", "description": "城市名称"}
          },
          "required": ["city"]
        }
      }
    }]
  }'

    模型会在 choices[0].message.tool_calls 中返回 get_weather({"city": "北京"})，应用据此执行真实函数，再将结果回传模型生成最终回答。

    在框架/应用中调用 API¶

    实际工程中很少直接拼 HTTP 请求，而是借助框架封装统一调用不同厂商的模型。以 LangChain 为例，框架将各家 API 抽象为统一的 Chat Model 接口，切换模型只需更换类名：

    pip install langchain langchain-openai langchain-anthropic

    from langchain_openai import ChatOpenAI
from langchain_anthropic import ChatAnthropic

# OpenAI 模型
llm_openai = ChatOpenAI(model="gpt-5.1", temperature=0.7)

# Claude 模型——接口一致，仅换类名
llm_claude = ChatAnthropic(model="claude-opus-4-6")

# 调用兼容 OpenAI 协议的模型（如 DeepSeek）：复用 ChatOpenAI + base_url
llm_deepseek = ChatOpenAI(
    model="deepseek-chat",
    base_url="https://api.deepseek.com/v1",
    api_key="<你的 DeepSeek Key>",
)

# 统一的 invoke 接口，底层 API 差异被框架屏蔽
print(llm_openai.invoke("用一句话解释什么是装饰器").content)
print(llm_claude.invoke("用一句话解释什么是装饰器").content)

    框架封装的价值：统一接口（屏蔽各家 API 差异）、可组合（与 Prompt、检索、记忆、工具串联，见 4.5）、易切换（模型路由/降级只改配置）。下一节给出基于这些 Chat Model 的最小可运行示例。

    场景 核心技术 关键要点
    智能客服 / 问答 RAG + LLM 知识库切片策略、混合检索、回答引用溯源
    代码辅助 LLM + 上下文工程 仓库级代码理解、补全、重构建议

    内容创作 LLM + Prompt 模板 风格控制、事实核查、多轮迭代优化

    4.3 RAG 系统工程实践¶

    基础架构¶

    文档入库：文档 → 分块(Chunking) → Embedding → 向量数据库(Milvus/Qdrant/Chroma)
查询流程：用户问题 → 查询改写 → 混合检索(向量+关键词) → 重排序 → 拼接上下文 → LLM 生成

    关键优化点¶

    环节 优化手段
    分块策略 按语义段落切分、重叠窗口、Markdown/代码结构感知
    检索策略 向量检索 + BM25 关键词检索（Hybrid Search）、多路召回
    查询优化 HyDE（假设文档增强）、查询改写、多查询分解
    重排序 Cross-Encoder 精排、Cohere Rerank
    上下文压缩 LLM 压缩冗余内容、仅保留相关片段
    评估 检索召回率、答案忠实度（Faithfulness）、答案相关性

    4.4 Agent 工程实践¶

    单 Agent 设计模式¶

    模式 说明
    ReAct 推理与行动交替，每步决定是否调用工具
    Plan-and-Execute 先完整规划再逐步执行，适合复杂多步任务
    反思（Reflection） 执行后自我评估并修正，提升输出质量

    Multi-Agent 协作模式¶

    模式 说明
    主管模式（Supervisor） 一个主 Agent 分配任务给子 Agent
    对话模式（Conversation） 多 Agent 平等对话协商
    流水线模式（Pipeline） 任务按顺序在 Agent 间流转

    生产级 Agent 关键要求¶

    • 可观测性：Tracing（LangSmith/Phoenix）、日志审计、调用链追踪
    • 可恢复性：状态持久化、断点续执行、事务补偿
    • 安全性：工具权限分级、输入输出过滤、敏感信息脱敏
    • 成本控制：Token 用量监控、缓存策略、模型降级路由
    • 评测体系：离线评测集、在线 A/B 测试、任务成功率指标

    4.5 框架最小可行示例¶

    下面给出 LangChain 与 LangGraph 的最小可运行示例，帮助快速建立从"调用 API"到"编排应用"的直观认知。所有示例默认已配置 OPENAI_API_KEY 环境变量。

    LangChain：LCEL 基础链¶

    LCEL（LangChain Expression Language）用 | 管道串联组件，构成 提示 → 模型 → 解析 的最小链。

    pip install langchain langchain-openai

    from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

prompt = ChatPromptTemplate.from_template("用一句话解释：{topic}")
model = ChatOpenAI(model="gpt-5.1")
parser = StrOutputParser()

# 用管道串联：输入 → 填充提示 → 调用模型 → 提取纯文本
chain = prompt | model | parser

print(chain.invoke({"topic": "什么是向量数据库"}))

    LangChain：RAG 最小链¶

    在 LCEL 基础上接入检索：文档向量化入库 → 检索相关片段 → 拼接上下文 → 生成回答。

    pip install langchain langchain-openai langchain-community faiss-cpu

    from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from langchain_community.vectorstores import FAISS
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnablePassthrough

# 1. 构建向量库（生产中应替换为真实文档分块）
docs = [
    "MCP 是 Anthropic 2024 年提出的开放协议，标准化 LLM 与工具的连接。",
    "RAG 通过检索外部知识来缓解大模型的幻觉和知识过时问题。",
]
vectorstore = FAISS.from_texts(docs, embedding=OpenAIEmbeddings())
retriever = vectorstore.as_retriever(search_kwargs={"k": 1})

# 2. 定义提示：把检索到的上下文塞进去
prompt = ChatPromptTemplate.from_template(
    "仅根据以下上下文回答问题。\n上下文：{context}\n问题：{question}"
)
model = ChatOpenAI(model="gpt-5.1")

# 3. 组装 RAG 链：检索 context，问题透传，再生成
rag_chain = (
    {"context": retriever, "question": RunnablePassthrough()}
    | prompt
    | model
    | StrOutputParser()
)

print(rag_chain.invoke("MCP 是谁提出的？"))

    LangGraph：StateGraph 基础图¶

    LangGraph 用"状态 + 节点 + 边"描述工作流。State 在节点间流转，适合带分支、循环、可恢复的复杂流程。

    pip install langgraph langchain-openai

    from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from langchain_openai import ChatOpenAI

model = ChatOpenAI(model="gpt-5.1")

# 1. 定义在节点间流转的状态
class State(TypedDict):
    topic: str
    result: str

# 2. 定义节点：接收 State，返回要更新的字段
def generate(state: State) -> dict:
    text = model.invoke(f"用一句话解释：{state['topic']}").content
    return {"result": text}

# 3. 构建图：START → generate → END
graph = StateGraph(State)
graph.add_node("generate", generate)
graph.add_edge(START, "generate")
graph.add_edge("generate", END)
app = graph.compile()

print(app.invoke({"topic": "什么是 Embedding"})["result"])

    LangGraph：最小 ReAct Agent¶

    create_react_agent 内置 ReAct 循环（推理 → 调用工具 → 观察 → 再推理），只需提供模型和工具即可。

    pip install langgraph langchain-openai

    from langgraph.prebuilt import create_react_agent
from langchain_core.tools import tool
from langchain_openai import ChatOpenAI

# 1. 定义工具：docstring 即工具描述，供模型判断何时调用
@tool
def get_weather(city: str) -> str:
    """查询指定城市的实时天气"""
    return f"{city} 今天晴，气温 22℃"

# 2. 一行创建带工具调用能力的 Agent
agent = create_react_agent(
    model=ChatOpenAI(model="gpt-5.1"),
    tools=[get_weather],
)

# 3. 运行：Agent 自主决定是否调用 get_weather
result = agent.invoke({"messages": [("user", "北京天气怎么样？")]})
print(result["messages"][-1].content)

    对比：LangChain（LCEL）适合确定性的线性链（如固定的 RAG 流程）；LangGraph 适合带分支/循环/可恢复的有状态流程（如多轮决策的 Agent）。两者可组合——在 LangGraph 节点内部调用 LCEL 链。

    4.6 模型部署方案¶

    方案 适用场景 代表工具
    API 调用 快速集成、无需 GPU OpenAI API、Claude API、DeepSeek API
    私有化推理 数据安全、合规要求 vLLM、Ollama、SGLang、TGI
    量化部署 资源受限、降低成本 GPTQ、AWQ、GGUF(llama.cpp)
    边缘部署 端侧低延迟 ONNX Runtime、MLC-LLM、Core ML
    模型路由 多模型灰度、成本优化 LiteLLM、OpenRouter、自建路由

    4.7 AI 工程化核心指标¶

    维度 指标 说明
    质量 任务成功率 完成目标且满足约束的任务占比
    质量 幻觉率 无法由证据支持或与事实冲突的内容占比
    质量 工具调用成功率 工具请求中返回成功且可解析的占比
    延迟 TTFT（首 Token 延迟） 从请求发出到首个 Token 返回的时间
    延迟 E2E 延迟 从请求到完整响应的总时间
    成本 Token 单价 输入/输出每百万 Token 价格
    成本 任务级成本 完成单次任务的平均 Token 消耗
    稳定性 可用性 服务 SLA（如 99.9%）
    稳定性 错误率 请求失败/超时的占比
