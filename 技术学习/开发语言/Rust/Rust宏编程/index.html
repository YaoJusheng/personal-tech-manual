    一、简介¶

    Rust 的宏（macro）是一套在语法树上做匹配-变换的元编程系统，分两大类：

    1. 声明宏（macro_rules!）
    2. 过程宏（Procedural Macro）
    3. 派生宏（#[derive(...)]）
    4. 属性宏（#[attr]）
    5. 函数宏（func!()）

    二、宏的本质：编译期代码生成¶

    宏是编译期代码模板，接收参数，展开成 Rust 源码，比函数更强大：

    • 函数运行时执行；宏编译期替换代码；
    • 支持可变参数、语法树匹配、自定义 DSL；
    • 分两类：声明式宏 macro_rules!、过程宏 proc-macro。

    1. 编译流程¶

    源代码
  │
  ▼
词法分析 → Token 序列
  │
  ▼
语法分析(AST)  →  遇到宏调用，介入并操作 Token/AST
                      │
                      ├─ 声明宏: 模式匹配 → 替换 Token 序列 → 递归展开
                      │
                      └─ 过程宏: 加载 proc-macro crate
                                  ↓
                             调用宏函数（编译期执行 Rust 代码）
                                  ↓
                             返回新的 TokenStream
                                  ↓
                             替换原宏调用位置
  │
  ▼
继续编译（类型检查、代码生成）
  │
  ▼
二进制

    限制：宏展开有递归深度限制（默认 128 层），macro_rules! 不支持真正的递归。

    2. 关键特征¶

    • 编译期执行，零运行时开销
    • 操作的是 TokenStream（Token 序列），而非字符串
    • hygienic（卫生宏）：宏内定义的变量不会污染外部作用域

    3. 宏的核心优势¶

    1. 消除重复样板代码

    如：SeaORM 实体、Clap 命令行、DTO 序列化、HTTP 接口等，手写 impl 极其繁琐，通过宏可以帮助调用方少写代码，自动生成；

    1. 编译期校验

    sqlx::query! 在编译阶段校验 SQL 语法，运行时无报错；

    1. 跨类型统一逻辑注入

    #[tracing::instrument] 给任意函数自动加日志埋点，不用重复写 span；

    1. 支持可变参数、动态语法

    函数参数固定，宏可接收任意多参数（format!("a{}b{}",1,2)）。

    4. Trait 与宏的区别¶

    Trait 负责定义「类型具备什么行为 / 能力」，是一套类型抽象规范；

    宏负责「编译期自动生成代码」，是代码生成工具，二者解决完全不同的问题。

    4.1 本质定位¶

    • Trait：行为抽象、类型约束（逻辑层面），是接口规范，用来描述一组方法签名，规定某类类型 “能做什么”。

    • 属于类型系统的一部分，参与类型检查、泛型约束、多态分发；

    • 运行时 / 编译时都生效，核心作用是抽象、复用行为、限制泛型。
    trait IntoResponse {
    fn into_response(self) -> Response;
}
// 任何实现该 trait 的类型，都可以转为 HTTP 响应

    • 宏：代码生成器（源码层面），是编译期文本 / 语法树模板，编译阶段直接展开成 Rust 代码，只是自动帮你手写重复代码。

    • 不属于类型系统，不定义行为，只生成代码；

    • 仅编译期执行，展开后就消失，运行时无任何痕迹。
    #[derive(Debug)]
struct User;
// 编译器自动生成 impl Debug for User { ... } 一堆代码

    4.2 作用区别¶

    • Trait 解决的问题：

    • 统一抽象行为：不同结构体共享同一套方法（如所有错误都实现 std::error::Error）；

    • 泛型约束：限定泛型必须拥有指定能力 T: Display；
    • 拓展已有类型：给外部类型新增方法（拓展 trait）；
    • 多态分发：impl Trait /dyn Trait 实现静态 / 动态分发。
    // 手动定义行为、手动实现，无代码生成
trait Greet {
    fn hello(&self);
}
struct Admin;
impl Greet for Admin {
    fn hello(&self) { println!("admin"); }
}

    • 宏解决的问题：

    • 消除样板代码：不用手动写大量重复 impl、结构体、方法；

      例：#[derive(Serialize)] 自动实现序列化 trait；

    • 自定义语法糖：vec![] format!() sqlx::query!()；

    • 注入横切逻辑：#[tracing::instrument] 自动埋日志、#[poem::handler] 包装接口；

    • 编译期校验：SQL、环境变量、命令行参数提前检查。

    // 纯语法糖，和类型抽象无关
macro_rules! print_msg {
    ($s:literal) => { println!("{}", $s); }
}
print_msg!("hello");

    三、声明宏 macro_rules!理解¶

    1. 基本结构¶

    macro_rules! macro_name {
    // 模式1 => 展开代码1
    (pattern1) => { expansion1 };

    // 模式2 => 展开代码2  
    (pattern2) => { expansion2 };

    // e.g.
    ($msg:literal) => {
        crate::error::AppError::Msg($msg.to_string())
    };
}

// 使用: macro_name!(xxx)

    匹配模式 ()/[]/{} 无区别，支持重复匹配 $(expr),*。

    2. 核心概念：Token 与匹配器¶

    匹配器 含义 示例
    $name:expr 匹配表达式 1 + 2, foo()
    $name:ty 匹配类型 i32, Vec<String>
    $name:ident 匹配标识符 foo, Bar
    $name:path 匹配路径 std::vec::Vec
    $name:block 匹配代码块 { let x = 1; x }
    $name:stmt 匹配语句 let x = 1;
    $name:pat 匹配模式 Some(x), (a, b)
    $name:literal 匹配字面量 "hello", 42
    $name:tt 匹配单个 Token Tree 任意 Token
    $name:item 匹配 item fn, struct, impl
    $name:meta 匹配属性 #[derive(Debug)] 中的内容
    $(...)* 重复 0 次或多次
    $(...)+ 重复 1 次或多次
    $(...),* 逗号分隔的重复

    3. 完整示例：自定义 vec!¶

    macro_rules! my_vec {
    // 空向量
    () => {
        Vec::new()
    };

    // 单个元素
    ($elem:expr) => {{
        let mut v = Vec::new();
        v.push($elem);
        v
    }};

    // 多个元素 [1, 2, 3]
    ($($elem:expr),+ $(,)?) => {{
        // 预分配容量优化
        let count = <[()]>::len(&[$({ stringify!($elem); }),+]);
        let mut v = Vec::with_capacity(count);
        $(v.push($elem);)+
        v
    }};

    // 带重复次数 [0; 5]
    ($elem:expr; $n:expr) => {
        std::vec::from_elem($elem, $n)
    };
}

fn main() {
    let v1 = my_vec!();           // Vec::new()
    let v2 = my_vec!(42);          // vec![42]
    let v3 = my_vec!(1, 2, 3);     // vec![1, 2, 3]
    let v4 = my_vec!(0; 5);        // vec![0, 0, 0, 0, 0]
}

    4. 重复模式的内部机制¶

    macro_rules! print_all {
    // $($x:expr),+ 展开时：
    // 输入: print_all!(1, 2, 3)
    // $x 依次绑定为: 1, 2, 3
    ($($x:expr),+) => {
        $(
            println!("{}", $x);
        )+
        // 展开为:
        // println!("{}", 1);
        // println!("{}", 2);
        // println!("{}", 3);
    };
}

    5. 卫生宏原理¶

    卫生宏（Hygienic Macro） 是指一种宏系统，在宏展开时能自动避免意料之外的标识符冲突，不会破坏调用处的变量绑定，也不会被调用处的同名变量意外影响。

    Rust 的声明宏（macro_rules!）是部分卫生的：

    • 局部变量、函数参数、标签是卫生的——它们会自动被赋予一个调用处不可见的唯一名字，绝不会与外部变量冲突。
    • 类型、函数、模块等“项”默认不卫生——它们会像正常代码一样参与到调用处的命名空间。
    macro_rules! define_var {
    ($name:ident, $value:expr) => {
        let $name = $value;  // 宏内部定义的变量
    };
}

fn main() {
    let x = 10;
    define_var!(x, 20);  // 这里不会覆盖外部的 x！
    println!("{}", x);    // 输出: 10（不是 20）
}

    卫生宏机制：编译器为宏内标识符添加上下文标记，使其与外部作用域隔离。

    四、过程宏 proc_macro 理解¶

    过程宏读取输入 Token 语法树，生成全新代码，分 3 种：

    • （1）派生宏 #[derive (XXX)]
    • （2）属性宏 #[xxx]
    • （3）函数式宏（类似 vec![]）

    1. 三种类型对比¶

    类型 属性(自定义实现) 输入 输出 使用方式 作用范围
    派生宏
    derive    		 #[proc_macro_derive(Name)] 1 TokenStream（类型定义） 新代码 #[derive(Name)] 作用在 struct / enum / union 上，自动生成 impl Trait for Type 实现代码。
    属性宏
    attribute    		 #[proc_macro_attribute] 2 TokenStreams（属性+项） 替换代码 #[attr] 作用在任意项（函数、struct、mod、async fn），接收自定义参数，包裹 / 重写整个项的代码。
    函数式宏
    function-like    		 #[proc_macro] 1 TokenStream（括号内） 任意代码 name!(...) 任何允许宏调用的位置

    2. TokenStream 的本质¶

    // TokenStream = 树状的 Token 序列
// 输入: println!("Hello, {}!", name)
// 解析为:
TokenStream([
    Ident(println),            // 标识符: foo, Bar, _unused
    Punct(!),                  // 标点: +, -, ::, =>, #
    Group([                    // 括号包裹的组: ( ... ), [ ... ], { ... }  
        Literal("Hello, {}!"),
        Comma,
        Ident(name)
    ])
])

    库 作用
    proc-macro2 proc_macro::TokenStream 的增强版，支持跨 crate 使用
    syn 将 TokenStream 解析为 AST（DeriveInput, ItemFn 等）
    quote 将 Rust 代码模板转换为 TokenStream

    // my-derive/Cargo.toml
[package]
name = "my-derive"
version = "0.1.0"
edition = "2021"

[lib]
proc-macro = true

[dependencies]
proc-macro2 = "1.0"
quote = "1.0"

// my-derive/src/lib.rs
use proc_macro::TokenStream;
use quote::quote;
use syn::{parse_macro_input, DeriveInput, Data, Fields};

// Builder：派生宏对外暴露的名称，业务代码使用时写 #[derive(Builder)]。
#[proc_macro_derive(Builder)]
pub fn derive_builder(input: TokenStream) -> TokenStream {
    let input = parse_macro_input!(input as DeriveInput);
    let name = input.ident;
    let builder_name = quote::format_ident!("{}Builder", name);

    // 解析结构体字段
    let fields = match input.data {
        Data::Struct(data) => match data.fields {
            Fields::Named(fields) => fields.named,
            _ => panic!("Builder only supports named fields"),
        },
        _ => panic!("Builder only supports structs"),
    };

    // 生成字段定义
    let builder_fields = fields.iter().map(|f| {
        let name = &f.ident;
        let ty = &f.ty;
        quote! { #name: std::option::Option<#ty> }
    });

    // 生成 setter 方法
    let setters = fields.iter().map(|f| {
        let name = &f.ident;
        let ty = &f.ty;
        quote! {
            pub fn #name(mut self, value: #ty) -> Self {
                self.#name = Some(value);
                self
            }
        }
    });

    // 生成 build 方法
    let build_fields = fields.iter().map(|f| {
        let name = &f.ident;
        quote! {
            #name: self.#name.ok_or(concat!(stringify!(#name), " is not set"))?
        }
    });

    let expanded = quote! {
        pub struct #builder_name {
            #(#builder_fields,)*
        }

        impl #builder_name {
            pub fn new() -> Self {
                Self {
                    #(#name: None,)*
                }
            }

            #(#setters)*

            pub fn build(self) -> Result<#name, Box<dyn std::error::Error>> {
                Ok(#name {
                    #(#build_fields,)*
                })
            }
        }

        impl #name {
            pub fn builder() -> #builder_name {
                #builder_name::new()
            }
        }
    };

    TokenStream::from(expanded)
}

    使用：

    age: u32,
    email: String,
}

        .age(30)

}

    // 实现 sql!() 宏，编译时检查 SQL 语法
use proc_macro::TokenStream;
use quote::quote;
use syn::{parse::Parse, parse::ParseStream, LitStr};

struct SqlQuery {
    query: LitStr,
}

impl Parse for SqlQuery {
    fn parse(input: ParseStream) -> syn::Result<Self> {
        Ok(SqlQuery {
            query: input.parse()?,
        })
    }
}

#[proc_macro]
pub fn sql(input: TokenStream) -> TokenStream {
    let SqlQuery { query } = parse_macro_input!(input as SqlQuery);
    let query_str = query.value();

    // 简单的 SQL 验证（实际可用 sqlparser 等库）
    if !query_str.to_ascii_uppercase().starts_with("SELECT")
        && !query_str.to_ascii_uppercase().starts_with("INSERT")
        && !query_str.to_ascii_uppercase().starts_with("UPDATE")
        && !query_str.to_ascii_uppercase().starts_with("DELETE") {
        panic!("sql! macro only supports SELECT/INSERT/UPDATE/DELETE");
    }

    let expanded = quote! {
        {
            const _QUERY: &str = #query;
            // 返回类型安全的查询对象
            SqlQuery { query: _QUERY }
        }
    };

    TokenStream::from(expanded)
}

struct SqlQuery {
    query: &'static str,
}

    五、TokenStream 的理解¶

    TokenStream 是过程宏的核心数据结构。可以把它理解为：编译器把宏输入源码切成一棵带括号层级的 Token 树，过程宏函数读取这棵 Token 树，再返回一棵新的 Token 树作为展开后的代码。

    它不是普通字符串，也不是已经完成类型检查的 AST，而是介于“源码文本”和“语义 AST”之间的一层结构。

    源码文本
  │
  ├─ 词法分析
  ▼
TokenStream / TokenTree      ← 过程宏主要操作这一层
  │
  ├─ syn 解析
  ▼
结构化 AST                  ← DeriveInput、ItemFn、Expr、Type 等
  │
  ├─ quote 生成
  ▼
新的 TokenStream
  │
  ├─ 编译器继续解析、展开、类型检查
  ▼
最终可执行代码

    1. TokenStream 到底是什么¶

    从过程宏 API 看，TokenStream 是一串 TokenTree：

    pub enum TokenTree {
    Group(Group),       // 被 (), [], {} 包住的一组 Token
    Ident(Ident),       // 标识符，如 User、name、println
    Punct(Punct),       // 标点，如 #、!、:、:: 中的 :、=> 中的 = 和 >
    Literal(Literal),   // 字面量，如 "hello"、123、true
}

    所以：

    • TokenStream = 多个 TokenTree 的序列；
    • TokenTree = 单个 Token，或一个括号分组 Group；
    • Group 内部又包含一个新的 TokenStream，因此整体是“树状”的；
    • 它保留了语法符号、标识符、字面量和括号层级，但不直接表达类型信息。

    例如宏输入：

    my_macro!(user.name + 1)

    传给过程宏函数的不是完整的 my_macro!(...)，而是括号里的内容，大致可理解为：

    TokenStream[
  Ident("user"),
  Punct('.'),
  Ident("name"),
  Punct('+'),
  Literal("1"),
]

    再看带括号的输入：

    my_macro!({ let x = 1; x + 2 })

    大致是：

    TokenStream[
  Group {
    delimiter: Brace,
    stream: TokenStream[
      Ident("let"), Ident("x"), Punct('='), Literal("1"), Punct(';'),
      Ident("x"), Punct('+'), Literal("2"),
    ]
  }
]

    这就是为什么过程宏常说“操作 Token”，而不是“拼字符串”。TokenStream 已经帮你处理了词法边界和括号层级，比字符串安全得多。

    2. TokenStream 不是字符串，也不是完整 AST¶

    理解 TokenStream 时最容易混淆三层概念：

    层级 示例 特点 宏编程中的作用
    字符串 "fn hello() {}" 只是文本，容易拼错、少括号、少逗号 一般不推荐直接拼接代码字符串
    TokenStream Ident(fn), Ident(hello), Group(...) 有词法结构和括号层级，但无类型语义 过程宏输入输出的标准格式
    AST syn::ItemFn, syn::DeriveInput 已按 Rust 语法解析成结构体 复杂宏开发时最常用的操作对象

    例如：

    let x = a + b;

    在 TokenStream 层，只能看到 let、x、=、a、+、b、; 这些 Token；它不知道：

    • a 和 b 是什么类型；
    • + 调用的是哪个 Add 实现；
    • x 最终推导出的类型是什么；
    • 某个函数是否存在、trait bound 是否满足。

    过程宏运行在类型检查之前，因此不能依赖类型推导结果。过程宏适合做“语法级代码生成”，不适合做“基于类型系统的运行时逻辑判断”。

    3. proc_macro 与 proc_macro2 的区别¶

    实际项目中经常同时看到两个 TokenStream：

    use proc_macro::TokenStream;
use proc_macro2::TokenStream as TokenStream2;

    它们的区别如下：

    类型 来源 使用位置 特点
    proc_macro::TokenStream Rust 标准库编译器 API 过程宏入口函数参数和返回值 只能在 proc-macro crate 的宏入口处使用
    proc_macro2::TokenStream 第三方 crate proc-macro2 普通函数、测试、syn、quote 中广泛使用 API 更稳定，能在非过程宏环境中使用

    常见写法是：

    use proc_macro::TokenStream;
use quote::quote;
use syn::{parse_macro_input, DeriveInput};

#[proc_macro_derive(Hello)]
pub fn derive_hello(input: TokenStream) -> TokenStream {
    // 入口处接收 proc_macro::TokenStream
    let ast = parse_macro_input!(input as DeriveInput);
    let name = &ast.ident;

    // quote! 生成的是 proc_macro2::TokenStream
    let expanded = quote! {
        impl Hello for #name {
            fn hello() {
                println!("hello from {}", stringify!(#name));
            }
        }
    };

    // 退出时转回 proc_macro::TokenStream
    expanded.into()
}

    记忆方式：

    • 宏入口：用 proc_macro::TokenStream；
    • 宏内部：多数时候用 syn + quote + proc_macro2；
    • 返回结果：.into() 转回 proc_macro::TokenStream。

    4. TokenStream 的输入输出规则¶

    不同过程宏收到的 TokenStream 不一样：

    宏类型 函数签名 输入 TokenStream 内容 返回 TokenStream 含义
    派生宏 fn(input: TokenStream) -> TokenStream 被 derive 的 struct / enum / union 定义 追加到原类型后面的代码，通常是 impl
    属性宏 fn(attr: TokenStream, item: TokenStream) -> TokenStream attr 是属性参数，item 是被标注的项 替换整个被标注项
    函数式宏 fn(input: TokenStream) -> TokenStream 宏调用括号里的内容 替换整个宏调用表达式 / item / pattern 等

    4.1 derive 宏：输入是类型定义，输出通常是 impl¶

    #[derive(MyDebug)]
struct User {
    name: String,
}

    宏入口收到的 input 大致对应：

    struct User {
    name: String,
}

    返回的代码会追加在原类型后面，例如：

    impl std::fmt::Debug for User {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        f.debug_struct("User").field("name", &self.name).finish()
    }
}

    注意：derive 宏不能删除原来的 struct User，只能基于它额外生成代码。

    4.2 attribute 宏：输入是属性参数和原 item，输出替换原 item¶

    #[route(GET, "/users")]
async fn list_users() {}

    属性宏收到两个 TokenStream：

    // attr
GET, "/users"

// item
async fn list_users() {}

    返回值会替换整个函数。也就是说，如果返回值里没有包含原函数定义，原函数就“消失”了。

    常见用途：

    • 包裹函数体，加日志、鉴权、耗时统计；
    • 改写函数签名；
    • 给原 item 附加额外注册代码；
    • 对结构体、模块、impl 块做统一改写。

    4.3 函数式宏：输入是括号内内容，输出替换宏调用¶

    let q = sql!("SELECT * FROM users WHERE id = ?", user_id);

    函数式宏收到：

    "SELECT * FROM users WHERE id = ?", user_id

    可以返回一个表达式：

    SqlQuery::new("SELECT * FROM users WHERE id = ?").bind(user_id)

    也可以在 item 位置返回 item：

    routes! {
    GET /users => list_users
}

    展开为：

    fn register_routes(router: Router) -> Router {
    router.get("/users", list_users)
}

    关键点：函数式宏返回的 TokenStream 必须在调用位置语法合法。表达式位置要返回表达式，item 位置要返回 item。

    5. 实际开发时如何使用 TokenStream¶

    过程宏开发一般不是手动逐个遍历 Token，而是遵循以下流程：

    TokenStream 输入
  │
  ├─ parse_macro_input! / syn::parse
  ▼
syn AST
  │
  ├─ 读取 ident、字段、属性、泛型、函数签名等
  ├─ 校验输入格式，必要时返回 compile_error
  ├─ 组织要生成的 ident、类型、语句、表达式
  ▼
quote! 生成 TokenStream
  │
  ├─ .into()
  ▼
返回给编译器

    常用 API 分工：

    工具 主要作用 典型代码
    parse_macro_input! 把入口 TokenStream 解析为指定 AST，失败时生成编译错误 parse_macro_input!(input as DeriveInput)
    parse_nested_meta! / parse_nested_meta 解析属性内部的嵌套元数据，即 #[attr(key = value, flag, nested(key = value))] 这种结构。syn 官方常用的是 Attribute::parse_nested_meta 或 syn::meta::parser，有些项目会再封装成 parse_nested_meta! 辅助宏。 attr.parse_nested_meta(|meta| { ... })
    syn::parse2 把 proc_macro2::TokenStream 解析为 AST syn::parse2::<Expr>(tokens)
    quote! 用 Rust 模板生成 TokenStream quote! { impl #trait_name for #ty {} }
    format_ident! 动态生成标识符 format_ident!("{}Builder", name)
    ToTokens 把 AST 节点重新转成 Token ty.to_token_stream()
    syn::Error 生成带位置的编译错误 syn::Error::new_spanned(field, "message")

    5.1 parse_macro_input!：解析整个宏入口 TokenStream¶

    parse_macro_input! 是过程宏入口处最常用的解析工具，它解决的问题是：把编译器传进来的完整 proc_macro::TokenStream 解析成某个 syn AST 类型；如果解析失败，自动返回 compile_error! 风格的编译错误。

    它通常出现在三类宏入口函数的第一步：

    use proc_macro::TokenStream;
use syn::{parse_macro_input, DeriveInput, ItemFn};

#[proc_macro_derive(MyDerive)]
pub fn my_derive(input: TokenStream) -> TokenStream {
    // derive 宏：整个输入应当是一段类型定义，例如 struct / enum / union
    let input = parse_macro_input!(input as DeriveInput);
    quote::quote! { /* 根据 input 生成代码 */ }.into()
}

#[proc_macro_attribute]
pub fn my_attr(_attr: TokenStream, item: TokenStream) -> TokenStream {
    // attribute 宏：item 是被属性标记的完整 item，例如 fn / struct / mod
    let item = parse_macro_input!(item as ItemFn);
    quote::quote! { #item }.into()
}

    它的基本语义可以近似理解为：

    let ast = match syn::parse::<TargetAst>(input) {
    Ok(ast) => ast,
    Err(err) => return err.to_compile_error().into(),
};

    所以它特别适合解析“整个输入必须符合某种 Rust 语法结构”的场景：

    • derive 宏输入必须是 DeriveInput；
    • 属性宏的 item 必须是 ItemFn、ItemStruct、ItemMod 等；
    • 函数式宏的输入可以自定义 Parse，例如 sql!("select ...") 解析成 SqlQuery；
    • 解析失败时直接停止宏展开，并把错误定位给调用者。

    函数式宏自定义解析示例：

    use proc_macro::TokenStream;
use syn::{parse::Parse, parse::ParseStream, parse_macro_input, Expr, LitStr, Token};

struct SqlInput {
    sql: LitStr,
    bind_args: Vec<Expr>,
}

impl Parse for SqlInput {
    fn parse(input: ParseStream) -> syn::Result<Self> {
        let sql = input.parse()?;
        let mut bind_args = Vec::new();

        while input.peek(Token![,]) {
            input.parse::<Token![,]>()?;
            bind_args.push(input.parse()?);
        }

        Ok(SqlInput { sql, bind_args })
    }
}

#[proc_macro]
pub fn sql(input: TokenStream) -> TokenStream {
    let SqlInput { sql, bind_args } = parse_macro_input!(input as SqlInput);

    quote::quote! {
        SqlQuery::new(#sql)#(.bind(#bind_args))*
    }
    .into()
}

    这里的重点是：parse_macro_input! 管的是整个 sql!(...) 括号内输入；输入格式由 SqlInput: Parse 定义。

    5.2 parse_nested_meta / parse_nested_meta!：解析属性内部的 key-value 元数据¶

    parse_nested_meta 解决的是另一个更窄的问题：解析 Rust 属性里常见的 meta 语法。

    典型输入长这样：

    #[route(method = "GET", path = "/users", auth, cache(ttl = 60))]
async fn list_users() {}

    属性参数内部包含几类常见形式：

    method = "GET"        // key = value
path = "/users"       // key = value
auth                  // flag
cache(ttl = 60)       // nested meta

    在 syn 2.x 中，常见官方用法有两种。

    第一种：解析已有 Attribute，例如 derive 宏里读取字段属性：

    #[derive(ApiModel)]
struct User {
    #[api(rename = "user_id", skip, validate(min = 1))]
    id: u64,
}

    实现示例：

    use syn::{spanned::Spanned, LitInt, LitStr};

#[derive(Default)]
struct ApiFieldOptions {
    rename: Option<String>,
    skip: bool,
    min: Option<u64>,
}

fn parse_api_attr(attr: &syn::Attribute) -> syn::Result<ApiFieldOptions> {
    let mut options = ApiFieldOptions::default();

    attr.parse_nested_meta(|meta| {
        if meta.path.is_ident("rename") {
            let value = meta.value()?;
            let lit: LitStr = value.parse()?;
            options.rename = Some(lit.value());
            return Ok(());
        }

        if meta.path.is_ident("skip") {
            options.skip = true;
            return Ok(());
        }

        if meta.path.is_ident("validate") {
            meta.parse_nested_meta(|meta| {
                if meta.path.is_ident("min") {
                    let value = meta.value()?;
                    let lit: LitInt = value.parse()?;
                    options.min = Some(lit.base10_parse()?);
                    return Ok(());
                }

                Err(meta.error("unsupported validate option"))
            })?;

            return Ok(());
        }

        Err(meta.error("unsupported api option"))
    })?;

    Ok(options)
}

    第二种：在属性宏入口中解析 attr: TokenStream，可以使用 syn::meta::parser：

    use proc_macro::TokenStream;
use syn::{parse_macro_input, LitStr};

struct RouteOptions {
    method: Option<String>,
    path: Option<String>,
    auth: bool,
}

#[proc_macro_attribute]
pub fn route(attr: TokenStream, item: TokenStream) -> TokenStream {
    let mut options = RouteOptions {
        method: None,
        path: None,
        auth: false,
    };

    let parser = syn::meta::parser(|meta| {
        if meta.path.is_ident("method") {
            let value = meta.value()?;
            let lit: LitStr = value.parse()?;
            options.method = Some(lit.value());
            return Ok(());
        }

        if meta.path.is_ident("path") {
            let value = meta.value()?;
            let lit: LitStr = value.parse()?;
            options.path = Some(lit.value());
            return Ok(());
        }

        if meta.path.is_ident("auth") {
            options.auth = true;
            return Ok(());
        }

        Err(meta.error("unsupported route option"))
    });

    parse_macro_input!(attr with parser);
    let item = parse_macro_input!(item as syn::ItemFn);

    quote::quote! {
        #item
    }
    .into()
}

    如果某个项目里出现 parse_nested_meta!(api::APIArgs, args) 这种写法，它通常不是 syn 标准入口本身，而是项目封装的辅助宏：内部大概率仍然基于 Attribute::parse_nested_meta、syn::meta::parser 或自定义 Parse，用于把属性参数映射到某个配置结构体，例如 APIArgs。

    5.3 二者核心区别¶

    对比维度 parse_macro_input! parse_nested_meta / parse_nested_meta!
    解决的问题 解析一个宏入口收到的完整 TokenStream 解析属性参数内部的 meta 项
    输入对象 proc_macro::TokenStream syn::Attribute 或属性宏的 attr: TokenStream
    典型输入 struct User { ... }、fn foo() {}、"sql", arg rename = "id", skip, validate(min = 1)
    输出结果 某个完整 AST 或自定义 Parse 类型 通常通过闭包逐项填充配置结构体
    适合语法 任意 Rust 语法或自定义 DSL Rust attribute meta 语法：path、flag、key-value、nested list
    错误处理 解析失败自动返回 compile_error! 闭包中返回 Err(meta.error("..."))，再交给外层转成编译错误
    使用位置 derive、attribute、function-like 宏入口 derive 宏读取字段 / 类型属性，或 attribute 宏读取属性参数

    一句话区分：

    • parse_macro_input!：先把宏入口的整段 TokenStream 解析成一个对象；
    • parse_nested_meta：在属性参数内部，一项一项读取 key = value、flag、nested(...)。

    5.4 什么时候用哪个¶

    优先用 parse_macro_input! 的场景：

    #[proc_macro_derive(Builder)]
pub fn derive_builder(input: TokenStream) -> TokenStream {
    let input = parse_macro_input!(input as syn::DeriveInput);
    // 解析完整 struct / enum / union
    todo!()
}

    #[proc_macro_attribute]
pub fn instrument(_attr: TokenStream, item: TokenStream) -> TokenStream {
    let func = parse_macro_input!(item as syn::ItemFn);
    // 解析完整函数
    todo!()
}

    优先用 parse_nested_meta 的场景：

    #[derive(Builder)]
struct User {
    #[builder(default, setter(into), rename = "user_name")]
    name: String,
}

    这里 #[builder(...)] 里的内容是属性 meta 配置，不是一段完整的函数、结构体或表达式。用 parse_nested_meta 可以自然处理：

    • default：flag；
    • setter(into)：嵌套配置；
    • rename = "user_name"：key-value。

    如果属性参数不是标准 meta 风格，而是自定义 DSL，例如：

    #[route(GET, "/users/:id")]
async fn get_user() {}

    这种 GET, "/users/:id" 更像自定义语法，不是 method = "GET", path = "/users/:id"，通常用自定义 Parse + parse_macro_input! 更合适：

    struct RouteArgs {
    method: syn::Ident,
    path: syn::LitStr,
}

impl syn::parse::Parse for RouteArgs {
    fn parse(input: syn::parse::ParseStream) -> syn::Result<Self> {
        let method = input.parse()?;
        input.parse::<syn::Token![,]>()?;
        let path = input.parse()?;
        Ok(RouteArgs { method, path })
    }
}

#[proc_macro_attribute]
pub fn route(attr: TokenStream, item: TokenStream) -> TokenStream {
    let args = parse_macro_input!(attr as RouteArgs);
    let item = parse_macro_input!(item as syn::ItemFn);
    quote::quote! { #item }.into()
}

    5.5 推荐的属性参数设计¶

    属性宏和 derive 字段配置通常有两种风格。

    第一种是 meta 风格：

    #[route(method = "GET", path = "/users", auth)]

    适合用 parse_nested_meta，优点是：

    • 接近 Rust 官方属性习惯；
    • flag、key-value、nested list 都好表达；
    • 错误位置容易指到具体参数；
    • 后续扩展配置项比较自然。

    第二种是 DSL 风格：

    #[route(GET, "/users")]

    适合用自定义 Parse + parse_macro_input!，优点是：

    • 调用更短；
    • 可以设计成业务领域更自然的语法；
    • 不受 meta 语法限制。

    选择建议：

    输入形式 推荐解析方式 原因
    #[attr(flag, key = "value")] parse_nested_meta 标准属性 meta 结构
    #[attr(nested(a = 1, b = 2))] parse_nested_meta 支持嵌套配置
    #[attr(GET, "/path")] 自定义 Parse + parse_macro_input! DSL，不是 key-value meta
    macro!(a + b, "text") 自定义 Parse + parse_macro_input! 函数式宏完整输入
    #[derive(X)] struct User<T> { ... } parse_macro_input!(input as DeriveInput) 完整类型定义

    实际项目中可以组合使用：先用 parse_macro_input! 解析完整 item，再用 parse_nested_meta 解析 item 上、字段上、变体上的属性配置。

    6. quote! 中的 Token 插值规则¶

    quote! 是生成 TokenStream 最常用的方式。它看起来像写 Rust 代码模板，但里面的 # 有特殊含义。

    6.1 插入变量：#var¶

    let name = &input.ident;

let tokens = quote! {
    impl Hello for #name {
        fn hello() {}
    }
};

    如果 name 是 User，生成结果就是：

    impl Hello for User {
    fn hello() {}
}

    6.2 重复生成：#(...)*¶

    如果要为每个字段生成一段代码：

    let field_names = fields.iter().map(|f| &f.ident);

let tokens = quote! {
    fn print_fields(&self) {
        #(
            println!("{}", stringify!(#field_names));
        )*
    }
};

    #(...)* 会对迭代器中的每个元素重复生成括号里的模板。

    6.3 带分隔符重复：#(...),*¶

    生成结构体初始化、数组、参数列表时，经常需要逗号：

    let field_names = fields.iter().map(|f| &f.ident);

let tokens = quote! {
    Self {
        #(#field_names: Default::default()),*
    }
};

    可能展开为：

    Self {
    name: Default::default(),
    age: Default::default(),
    email: Default::default(),
}

    6.4 生成新标识符：format_ident!¶

    字符串不能直接当作 Rust 标识符插入，必须生成 Ident：

    let struct_name = &input.ident;
let builder_name = quote::format_ident!("{}Builder", struct_name);

let tokens = quote! {
    struct #builder_name;
};

    如果 struct_name 是 User，则生成：

    struct UserBuilder;

    7. 什么时候手动处理 TokenTree¶

    大多数业务宏应优先使用 syn 解析，而不是手写 Token 遍历。但以下场景可能需要直接操作 TokenTree：

    • 设计非 Rust 标准语法的 DSL，例如 html! { <div>{name}</div> }；
    • 输入格式非常简单，只需要识别几个标识符或字面量；
    • 要保留用户输入的原始 Token，不想解析成固定 AST；
    • 做通用 Token 转发、包装、过滤；
    • 需要观察宏输入的真实 Token 结构以辅助调试。

    手动遍历示例：

    use proc_macro::{Delimiter, TokenStream, TokenTree};

#[proc_macro]
pub fn inspect(input: TokenStream) -> TokenStream {
    for token in input {
        match token {
            TokenTree::Ident(ident) => eprintln!("ident: {}", ident),
            TokenTree::Punct(punct) => eprintln!("punct: {}", punct.as_char()),
            TokenTree::Literal(lit) => eprintln!("literal: {}", lit),
            TokenTree::Group(group) => {
                match group.delimiter() {
                    Delimiter::Parenthesis => eprintln!("group: parentheses"),
                    Delimiter::Brace => eprintln!("group: braces"),
                    Delimiter::Bracket => eprintln!("group: brackets"),
                    Delimiter::None => eprintln!("group: none"),
                }
                eprintln!("inner: {}", group.stream());
            }
        }
    }

    TokenStream::new()
}

    但要注意：手动处理 Token 很容易漏掉复杂语法，例如泛型、生命周期、属性、where 子句、路径、宏调用、嵌套括号等。因此只要输入本质上还是 Rust 语法，就优先交给 syn。

    8. Span：Token 的源码位置信息¶

    每个 Token 都带有 Span，表示它来自源码中的哪个位置。Span 的主要作用：

    • 让编译错误指向更准确的位置；
    • 控制宏生成标识符的卫生性；
    • 帮助 quote_spanned! 生成带指定位置的代码。

    常用场景是给用户输入中的某个字段报错：

    use quote::quote;
use syn::{spanned::Spanned, DeriveInput};

fn expand(input: DeriveInput) -> syn::Result<proc_macro2::TokenStream> {
    let fields = match input.data {
        syn::Data::Struct(data) => data.fields,
        _ => {
            return Err(syn::Error::new_spanned(
                input.ident,
                "MyMacro only supports struct",
            ));
        }
    };

    for field in fields {
        if field.ident.is_none() {
            return Err(syn::Error::new(
                field.span(),
                "MyMacro only supports named fields",
            ));
        }
    }

    Ok(quote! {})
}

    宏入口中推荐这样把错误转为编译错误：

    #[proc_macro_derive(MyMacro)]
pub fn my_macro(input: proc_macro::TokenStream) -> proc_macro::TokenStream {
    let input = syn::parse_macro_input!(input as syn::DeriveInput);

    match expand(input) {
        Ok(tokens) => tokens.into(),
        Err(err) => err.to_compile_error().into(),
    }
}

    这样用户会看到正常的编译错误，而不是过程宏 panic。

    9. 宏卫生性与路径问题¶

    Rust 宏有卫生性，但过程宏生成代码时仍然要特别注意路径和名字冲突。

    9.1 尽量使用绝对路径¶

    如果生成代码写成：

    quote! {
    let value = Option::Some(1);
}

    用户代码中可能刚好定义了自己的 Option，导致解析到错误类型。更稳妥的写法是：

    quote! {
    let value = ::std::option::Option::Some(1);
}

    常见建议：

    • 标准库路径写 ::std::... 或 ::core::...；
    • 宏 crate 自己的运行时依赖，通常通过可配置路径或 re-export 处理；
    • 不要假设用户已经 use 了某个类型。

    9.2 生成的临时变量要降低冲突概率¶

    属性宏包裹函数体时，可能生成临时变量：

    quote! {
    let start = ::std::time::Instant::now();
    let result = { #original_block };
    result
}

    如果用户代码里也有 start、result，可能出现遮蔽或可读性问题。可以使用更不容易冲突的名字：

    quote! {
    let __my_macro_start = ::std::time::Instant::now();
    let __my_macro_result = { #original_block };
    __my_macro_result
}

    这不是绝对不会冲突，但能明显降低概率。

    10. TokenStream 中常见的解析对象¶

    syn 提供了大量 AST 类型，用来把 TokenStream 解析成结构化对象：

    输入内容 推荐解析类型 用途
    struct User { ... } syn::DeriveInput derive 宏入口，读取类型名、泛型、字段、属性
    fn foo() { ... } syn::ItemFn 属性宏包裹函数
    impl User { ... } syn::ItemImpl 修改或分析 impl 块
    name: String syn::Field 分析结构体字段
    Vec<String> syn::Type 分析类型
    a + b syn::Expr 分析表达式
    T: Clone syn::WherePredicate 分析 where 条件
    GET, "/path" 自定义 Parse 类型 解析宏属性参数或 DSL
    #[api(rename = "id")] Attribute::parse_nested_meta 解析字段、类型、变体上的属性配置

    自定义解析属性参数示例：

    use syn::{parse::Parse, parse::ParseStream, Ident, LitStr, Token};

struct RouteArgs {
    method: Ident,

impl Parse for RouteArgs {

    对应输入：

    #[route(GET, "/users")]
async fn users() {}

    然后在属性宏中解析：

pub fn route(attr: TokenStream, item: TokenStream) -> TokenStream {

    // 根据 args.method、args.path、func.sig 等生成代码

    11. 完整示例：基于 TokenStream 生成字段名数组¶

    目标：

    #[derive(FieldNames)]
struct User {
    id: u64,
    name: String,
    email: String,
}

    自动生成：

    impl User {
    pub const FIELD_NAMES: &'static [&'static str] = &["id", "name", "email"];
}

    实现：

    use proc_macro::TokenStream;
use quote::quote;
use syn::{parse_macro_input, Data, DeriveInput, Fields};

#[proc_macro_derive(FieldNames)]
pub fn derive_field_names(input: TokenStream) -> TokenStream {
    let input = parse_macro_input!(input as DeriveInput);

    match expand_field_names(input) {
        Ok(tokens) => tokens.into(),
        Err(err) => err.to_compile_error().into(),
    }
}

fn expand_field_names(input: DeriveInput) -> syn::Result<proc_macro2::TokenStream> {
    let struct_name = &input.ident;

    let named_fields = match &input.data {
        Data::Struct(data) => match &data.fields {
            Fields::Named(fields) => &fields.named,
            _ => {
                return Err(syn::Error::new_spanned(
                    &input.ident,
                    "FieldNames only supports structs with named fields",
                ));
            }
        },
        _ => {
            return Err(syn::Error::new_spanned(
                &input.ident,
                "FieldNames only supports structs",
            ));
        }
    };

    let field_names = named_fields.iter().map(|field| {
        field.ident.as_ref().unwrap().to_string()
    });

    Ok(quote! {
        impl #struct_name {
            pub const FIELD_NAMES: &'static [&'static str] = &[
                #(#field_names),*
            ];
        }
    })
}

    这个例子展示了 TokenStream 在过程宏中的完整链路：

    DeriveInput TokenStream
  → syn::DeriveInput
  → 读取 struct_name 和 fields
  → 生成字符串字面量列表
  → quote! 生成 impl 代码
  → TokenStream 返回编译器

    12. 完整示例：属性宏包裹函数并保留返回值¶

    目标：

    #[log_call]
fn add(a: i32, b: i32) -> i32 {
    a + b
}

    展开后类似：

    fn add(a: i32, b: i32) -> i32 {
    println!("enter add");
    let __log_call_result = { a + b };
    println!("exit add");
    __log_call_result
}

    实现：

    use proc_macro::TokenStream;
use quote::quote;
use syn::{parse_macro_input, ItemFn};

#[proc_macro_attribute]
pub fn log_call(_attr: TokenStream, item: TokenStream) -> TokenStream {
    let input_fn = parse_macro_input!(item as ItemFn);

    let attrs = &input_fn.attrs;
    let vis = &input_fn.vis;
    let sig = &input_fn.sig;
    let block = &input_fn.block;
    let fn_name = &sig.ident;

    let expanded = quote! {
        #(#attrs)*
        #vis #sig {
            ::std::println!("enter {}", stringify!(#fn_name));
            let __log_call_result = (|| #block)();
            ::std::println!("exit {}", stringify!(#fn_name));
            __log_call_result
        }
    };

    expanded.into()
}

    为什么用 (|| #block)() 包裹原函数体？

    • 可以把原函数体作为一个独立闭包执行；
    • return、?、借用和生命周期等场景要谨慎测试；
    • 对 async fn、含 return 的函数、发散函数 -> !，属性宏需要更细致处理。

    真实生产宏不能只看简单函数，应补充测试：

    • 无返回值函数；
    • 返回 Result 且使用 ?；
    • async fn；
    • 带泛型和 where 子句；
    • 带其他属性；
    • 函数体中有显式 return。

    13. 错误处理：不要优先 panic¶

    过程宏中 panic! 会变成编译错误，但体验通常不好。推荐使用 syn::Error 生成带 Span 的错误。

    不推荐：

    if !is_valid {
    panic!("expected named fields");
}

    推荐：

    if !is_valid {
    return syn::Error::new_spanned(
        input.ident,
        "expected a struct with named fields",
    )
    .to_compile_error()
    .into();
}

    多个错误可以合并：

    let mut errors: Option<syn::Error> = None;

for field in fields {
    if should_report_error(field) {
        let err = syn::Error::new_spanned(field, "unsupported field");

        if let Some(errors) = &mut errors {
            errors.combine(err);
        } else {
            errors = Some(err);
        }
    }
}

if let Some(errors) = errors {
    return errors.to_compile_error().into();
}

    这样一次编译能报告多个字段错误，而不是修一个报一个。

    14. 调试 TokenStream 的方法¶

    14.1 打印输入输出¶

    #[proc_macro_derive(MyMacro)]
pub fn my_macro(input: TokenStream) -> TokenStream {
    eprintln!("input = {}", input);

    let output = quote! {
        // generated code
    };

    eprintln!("output = {}", output);
    output.into()
}

    注意：TokenStream::to_string() 只适合调试，不适合作为稳定格式使用。它可能改变空格格式，也不保证完全还原原始源码。

    14.2 使用 cargo expand 看展开结果¶

    cargo install cargo-expand
cargo expand

    如果宏展开后的代码编译失败，先用 cargo expand 看最终生成了什么，通常比盯着 quote! 模板更容易定位问题。

    14.3 用 trybuild 测试编译错误¶

    过程宏经常需要测试“应该编译失败”的情况，可以使用 trybuild：

    #[test]
fn ui_tests() {
    let t = trybuild::TestCases::new();
    t.pass("tests/ui/pass/*.rs");
    t.compile_fail("tests/ui/fail/*.rs");
}

    这样可以保证错误信息和错误位置不会在重构后退化。

    15. 常见坑与实践建议¶

    问题 原因 建议
    把 TokenStream 当字符串拼 容易生成非法 Rust 代码 使用 quote! 和 format_ident!
    在过程宏里依赖类型信息 宏运行在类型检查前 只做语法级分析，类型约束交给生成代码和编译器
    错误位置不准确 手动 panic! 或丢失 Span 使用 syn::Error::new_spanned
    生成代码依赖用户 import 用户未必 use 了对应类型 使用 ::std::...、::core::... 等绝对路径
    忘记保留属性宏原 item 属性宏返回值会替换原 item quote! { #input_fn ... } 或手动重建原 item
    忘记处理泛型 impl #name 对泛型类型不够 使用 let (impl_generics, ty_generics, where_clause) = generics.split_for_impl();
    混用 parse_macro_input! 和 parse_nested_meta 一个解析完整输入，一个解析属性内部 meta 完整 item / DSL 用 parse_macro_input!；key = value 属性配置用 parse_nested_meta
    quote! 重复语法写错 #(...)* 和 #(...),* 语义不同 列表用逗号重复，语句用无分隔重复
    生成临时变量冲突 用户代码可能同名 使用低冲突前缀，必要时重新组织作用域
    只测简单输入 宏输入语法组合很多 增加泛型、属性、where、async、错误输入测试

    泛型处理是 derive 宏里非常常见的坑。错误写法：

    quote! {
    impl MyTrait for #name {}
}

    如果用户类型是：

    struct User<T>
where
    T: Clone,
{
    value: T,
}

    就需要生成：

    impl<T> MyTrait for User<T>
where
    T: Clone,
{}

    推荐写法：

    let name = &input.ident;
let generics = &input.generics;
let (impl_generics, ty_generics, where_clause) = generics.split_for_impl();

let tokens = quote! {
    impl #impl_generics MyTrait for #name #ty_generics #where_clause {
        // methods
    }
};

    16. 一句话总结¶

    TokenStream 是过程宏和编译器之间交换代码的标准格式：输入时，它表示用户写给宏的语法 Token；输出时，它表示宏生成的新 Rust 代码。实际开发中，通常用 syn 把它解析成 AST，用 quote 生成新的 TokenStream，用 syn::Error 产出友好的编译错误，并通过 cargo expand / trybuild 验证展开结果。

    六、两种宏类型对比¶

    维度 声明宏 macro_rules! 过程宏 proc_macro
    定义位置 当前 crate 内 独立的 proc-macro crate
    实现方式 模式匹配（类似 match） Rust 函数操作 TokenStream
    复杂度 简单，适合重复代码模板 复杂，可解析任意语法
    调试难度 较难（编译器报错指向展开后） 相对容易（可打印 TokenStream）
    典型用途 vec![], println!(), match! #[derive(...)], #[route(...)]
    递归能力 支持递归匹配 不支持递归（单次展开）

    八、常见标准宏分析¶

    宏 类型 实现原理
    vec![] 声明宏 重复模式 vec![$($x),*]
    println!() 声明宏 调用 std::io::_print(format_args!(...))
    format!() 声明宏 构建 Arguments 对象
    assert_eq!() 声明宏 展开为 if a != b { panic!(...) }
    derive(Debug) 过程宏 derive 为类型生成 impl Debug
    tokio::main 过程宏 attribute 将 fn main 包装为 fn main() { tokio::runtime::Runtime::new().block_on(async { ... }) }
    sqlx::query!() 过程宏 function-like 编译时连接数据库验证 SQL，生成类型安全的查询代码

    九、最佳实践¶

    实践 说明
    优先用声明宏 简单场景用 macro_rules!，复杂场景才用过程宏
    避免过度使用 宏增加编译时间，降低可读性，调试困难
    提供清晰错误 用 compile_error! 或 panic! 给出友好的编译错误
    文档化输入格式 宏的"接口"是模式，必须文档说明
    测试展开结果 用 macrotest crate 做快照测试
