    1. 概述¶

    Rust 的工具生态以 rustup、cargo 和官方组件为核心，并通过大量 cargo-* 子命令扩展开发、测试、审计、发布、跨平台构建和 WebAssembly 等能力。一个完整的 Rust 项目通常会组合使用以下几类工具：

    分类 常用工具 主要用途
    工具链与包管理 rustup、cargo、cargo-binstall 安装 Rust、管理版本、构建、测试、安装 CLI 工具
    格式化与静态检查 rustfmt、clippy、pre-commit 统一代码风格、发现潜在问题、提交前质量门禁
    编辑器与开发体验 rust-analyzer 补全、跳转、诊断、重构
    任务运行与开发循环 just、cargo-watch 统一项目命令、文件变更自动执行
    依赖管理 cargo-edit、cargo-outdated、cargo-udeps 添加、移除、升级和清理依赖
    测试与覆盖率 cargo-nextest、miri、cargo-llvm-cov、cargo-tarpaulin 测试加速、未定义行为检测、覆盖率统计
    文档与宏调试 cargo doc、cargo-expand 生成文档、查看宏展开结果
    性能与体积分析 criterion、cargo-bloat、flamegraph、samply 基准测试、二进制体积分析、性能剖析
    安全与合规 cargo-audit、cargo-deny、cargo-vet 漏洞扫描、许可证与供应链治理
    交叉编译与发布 cross、cargo-zigbuild、cargo-release、cargo-dist 跨平台构建、版本发布、二进制分发
    FFI 与原生集成 bindgen、cbindgen、cc C/C++ 绑定生成、构建原生代码
    WebAssembly wasm-pack、trunk、wasm-bindgen-cli WASM 构建、打包、前端开发服务器
    嵌入式 probe-rs、cargo-embed、defmt 烧录、调试、嵌入式日志

    2. 基础工具链¶

    2.1 rustup¶

    rustup 是 Rust 官方推荐的工具链安装器和版本管理器，负责安装 stable、beta、nightly 等工具链，也可以安装组件、添加编译目标和配置项目级工具链。

    核心功能：

    • 安装、更新和切换 Rust 工具链。
    • 管理 rustfmt、clippy、miri 等组件。
    • 添加交叉编译目标，例如 wasm32-unknown-unknown、x86_64-unknown-linux-musl。
    • 通过 rust-toolchain.toml 或 rustup override 固定项目工具链。

    常用命令：

    rustup update
rustup toolchain install stable nightly
rustup default stable
rustup override set nightly
rustup component add rustfmt clippy
rustup target add wasm32-unknown-unknown
rustup target list --installed

    项目推荐配置 rust-toolchain.toml：

    [toolchain]
channel = "stable"
components = ["rustfmt", "clippy"]
targets = ["wasm32-unknown-unknown"]

    适用场景：所有 Rust 项目；团队统一工具链；CI 固定编译环境；需要 nightly、WASM 或交叉编译 target 的项目。

    2.2 cargo¶

    cargo 是 Rust 官方包管理器和构建系统，是 Rust 项目的统一入口。

    核心功能：

    • 创建、构建、运行、测试 Rust 项目。
    • 管理 Cargo.toml 依赖与 Cargo.lock 锁文件。
    • 生成文档、运行 benchmark、发布 crate。
    • 支持 workspace、feature、profile、build script。

    常用命令：

    cargo new my_app
cargo build
cargo build --release
cargo run
cargo test
cargo check
cargo doc --open
cargo publish

    常用参数：

    cargo test --all-features
cargo check --workspace --all-targets
cargo build -p crate_name
cargo run --bin server

    适用场景：Rust 项目的构建、测试、文档和发布全流程。

    2.3 cargo-binstall¶

    cargo-binstall 是 Rust CLI 工具的二进制安装器。相比 cargo install 从源码编译，它会优先下载预编译二进制，因此安装速度通常更快。

    安装：

    cargo install cargo-binstall

    常用命令：

    cargo binstall just
cargo binstall cargo-nextest
cargo binstall cargo-deny
cargo binstall cargo-release

    适用场景：快速搭建开发环境；CI 中安装大量 Rust 工具；避免本地长时间编译 CLI 工具。

    3. 格式化、Lint 与编辑器¶

    3.1 rustfmt¶

    rustfmt 是 Rust 官方格式化工具，用于统一代码风格。

    安装：

    rustup component add rustfmt

    常用命令：

    cargo fmt
cargo fmt --check
rustfmt src/main.rs

    配置文件 .rustfmt.toml 示例：

    edition = "2021"
max_width = 100

    适用场景：提交前格式化、CI 风格检查、团队统一代码风格。

    3.2 clippy¶

    clippy 是 Rust 官方 lint 工具，可以发现潜在 bug、不够惯用的写法、可读性问题和性能隐患。

    官方文档：https://doc.rust-lang.org/clippy/

    安装：

    rustup update
rustup component add clippy

    常用命令：

    # 更新当前 Rust 工具链，避免 clippy 版本过旧
rustup update

# 安装 clippy 组件；如果 rust-toolchain.toml 已声明 components，也可由 rustup 自动安装
rustup component add clippy

# 对当前包执行默认 lint 检查
cargo clippy

# 检查 workspace 中所有 target 和所有 feature，适合本地完整检查或 CI
cargo clippy --all-targets --all-features

# 将所有 warning 提升为 error，常用于 CI 质量门禁
cargo clippy --all-targets --all-features -- -D warnings

# 自动应用 clippy 能安全修复的建议；建议在提交前或工作区干净时使用
cargo clippy --fix --allow-dirty --allow-staged

# 只检查指定包，适合 workspace 中局部开发
cargo clippy -p my_crate

# 检查指定 feature 组合，适合排查条件编译问题
cargo clippy --no-default-features --features "feature_a feature_b"

# 启用更严格的 clippy lint 组；pedantic 噪声较多，建议按项目选择性启用
cargo clippy -- -W clippy::pedantic

# 对指定 lint 直接拒绝，通过命令行临时加强检查
cargo clippy -- -D clippy::unwrap_used -D clippy::expect_used

    常见参数说明：

    • --all-targets：同时检查 lib、bin、example、test、bench 等目标。
    • --all-features：启用所有 feature，适合 CI 中发现 feature 组合问题。
    • --no-default-features：关闭默认 feature，适合验证最小依赖构建。
    • --features "a b"：启用指定 feature 组合，适合多 feature 库。
    • -p crate_name：只检查 workspace 中的指定 crate。
    • -- -D warnings：把 lint warning 提升为错误，适合作为质量门禁。
    • -- -W clippy::pedantic：启用更严格的建议类 lint，适合库代码或高质量代码库。
    • --fix：自动应用可安全修复的建议，执行前建议先确认工作区干净。
    • --allow-dirty：允许在有未提交修改时执行 --fix。
    • --allow-staged：允许在有已暂存文件时执行 --fix。

    命令行中的 -- 用于把参数从 cargo clippy 转交给底层 clippy-driver / rustc，例如 -D warnings、-W clippy::pedantic、-A clippy::too_many_arguments 等都应放在 -- 之后。

    clippy.toml 示例：

    # 允许 clippy 对公开 API 给出可能破坏兼容性的建议。
# 库项目通常建议保持 true 或默认值；应用项目可以设为 false。
avoid-breaking-exported-api = false

# 用于 disallowed_names lint，禁止示例名、占位名或团队不希望出现的变量名。
disallowed-names = ["foo", "bar", "baz"]

# 测试代码中是否允许 dbg!、expect、println!/print!、unwrap。
# 生产代码建议限制这些用法，测试代码中可以适当放宽。
allow-dbg-in-tests = true
allow-expect-in-tests = true
allow-print-in-tests = true
allow-unwrap-in-tests = true

# 允许的点文件名，配合相关 lint 约束项目中可访问或包含的隐藏文件。
allowed-dotfiles = [".env.example", ".cargo/config.toml"]

# too-many-arguments lint 的阈值，超过该参数数量时提示拆分结构体或 builder。
too-many-arguments-threshold = 7

# type-complexity lint 的阈值，用于提示过于复杂的类型签名。
type-complexity-threshold = 250

# enum-variant-size-threshold lint 的阈值，枚举变体差异过大时提示 Box 化大字段。
enum-variant-size-threshold = 200

# cognitive-complexity lint 的阈值，函数分支和嵌套过多时提示拆分。
cognitive-complexity-threshold = 25

# large-error-threshold lint 的阈值，错误类型过大时提示 Box 化。
large-error-threshold = 128

# trivial-copy-size-limit 控制多大以内的 Copy 类型可按值传递。
trivial-copy-size-limit = 64

# single-char-binding-names-threshold 控制过多单字符变量名时触发提示。
single-char-binding-names-threshold = 4

# literal-representation-threshold 控制较大数字字面量是否建议改用分隔符提升可读性。
literal-representation-threshold = 16384

# 允许在 panic/expect/unwrap 信息中使用的占位符关键字。
allowed-idents-below-min-chars = ["id", "tx", "rx", "db", "ui"]

    常见配置项说明：

    配置项 作用 建议
    avoid-breaking-exported-api 控制 clippy 是否避免提出可能破坏公开 API 的建议 库项目偏保守；应用项目可设为 false
    disallowed-names 配合 disallowed_names lint，禁止 foo、bar 等占位命名 团队可按命名规范维护列表
    allow-dbg-in-tests 是否允许测试代码使用 dbg! 测试中可设为 true，生产代码仍应避免
    allow-expect-in-tests 是否允许测试代码使用 expect 测试中通常可允许
    allow-print-in-tests 是否允许测试代码使用 print! / println! 调试型测试可允许，稳定测试建议少用
    allow-unwrap-in-tests 是否允许测试代码使用 unwrap 测试中常见，但核心测试也可要求显式错误信息
    allowed-dotfiles 允许访问或引用的点文件列表 建议只放 .env.example 等安全文件，不放真实密钥文件
    too-many-arguments-threshold 函数参数数量阈值 超过阈值通常考虑配置结构体、builder 或拆分函数
    type-complexity-threshold 类型复杂度阈值 类型签名过长时考虑 type alias 或拆分抽象
    enum-variant-size-threshold 枚举变体大小差异阈值 大变体可考虑 Box<T>，避免整个枚举过大
    cognitive-complexity-threshold 认知复杂度阈值 分支、循环、嵌套过多时拆分函数
    large-error-threshold 错误类型体积阈值 大错误枚举可考虑 Box、Arc 或精简字段
    trivial-copy-size-limit 小型 Copy 类型按值传递的大小阈值 小结构体可按值传递，大结构体优先引用
    single-char-binding-names-threshold 单字符变量名数量阈值 算法局部变量可少量使用，业务代码应使用语义化命名
    literal-representation-threshold 数字字面量可读性阈值 大数字建议使用 _ 分隔，例如 10_000
    allowed-idents-below-min-chars 允许的短变量名白名单 可加入 id、db、tx、rx 等领域通用缩写

    除 clippy.toml 外，也可以在代码中局部控制 lint：

    #![deny(clippy::unwrap_used)]
#![warn(clippy::pedantic)]

#[allow(clippy::too_many_arguments)]
fn build_query(a: i32, b: i32, c: i32, d: i32, e: i32, f: i32, g: i32, h: i32) {
    // 示例：确实需要保留多参数签名时，可以局部放行并说明原因。
}

    常用 lint 级别：

    • allow：关闭某个 lint。
    • warn：产生警告但不阻断构建。
    • deny：产生错误并阻断构建。
    • forbid：彻底禁止，后续代码不能再 allow 覆盖，需谨慎使用。

    常用 lint 组：

    • clippy::all：默认常用 lint 组，cargo clippy 通常会启用。
    • clippy::correctness：偏 bug 和错误行为，建议始终关注。
    • clippy::suspicious：可疑代码模式，建议在 CI 中保留。
    • clippy::style：风格建议，适合提升一致性。
    • clippy::complexity：复杂度建议，适合控制可维护性。
    • clippy::perf：性能相关建议。
    • clippy::pedantic：更严格、噪声更高，适合选择性启用。
    • clippy::nursery：实验性 lint，稳定性和误报率可能变化。
    • clippy::restriction：限制性很强，不建议整体启用，只适合挑选单项 lint。

    如果目标是优化 release 产物体积，应放在 Cargo.toml 的 profile 中，而不是 clippy.toml：

    [profile.release]
codegen-units = 1
opt-level = "z"
panic = "abort"
lto = true
strip = true

    常见用途：

    • 在 CI 中将 warning 当作错误。
    • 辅助代码审查。
    • 提升代码的 Rust 惯用程度。

    适用场景：几乎所有 Rust 项目，特别适合作为 CI 质量门禁。

    3.3 rust-analyzer¶

    rust-analyzer 是当前 Rust 编辑器生态的事实标准 LSP。

    核心功能：

    • 代码补全、跳转定义、引用查找。
    • 类型提示、内联参数提示、诊断信息。
    • 重构、重命名、自动导入。
    • 与 VS Code、Neovim、Emacs、Helix、Zed 等编辑器集成。

    典型使用：

    在编辑器中安装并启用 rust-analyzer 插件。

    常见配置方向：

    • 启用保存时 cargo check。
    • 配置 allFeatures 或指定 feature。
    • 配合 rustfmt 实现保存时格式化。

    VS Code settings.json 示例：

    {
  // 排除不需要分析的大型目录，显著减轻负担
  "rust-analyzer.files.excludeDirs": [
    "target",           // 构建输出，通常很大
    ".git",             // 版本控制文件
    "node_modules"      // 前端依赖
  ],
  // 如果项目不使用派生宏（如`#[derive(...)]`）等过程宏，可以关闭
  "rust-analyzer.procMacro.enabled": false,

  // 启用磁盘缓存，避免每次启动重新分析
  "rust-analyzer.cacheOnDisk": true,

  // 限制检查的范围，仅检查当前包（对小项目很有效）
  "rust-analyzer.check.command": "check",   // 使用`cargo check`而非`clippy`，更快
  "rust-analyzer.check.allTargets": false,  // 只检查当前编译目标

  // 预加载
  "rust-analyzer.cachePriming.enable": false,
  "rust-analyzer.cachePriming.numThreads": 2,
  "rust-analyzer.cargo.extraEnv": {
    "CARGO_BUILD_JOBS": "3"
  },
  "[rust]": {
    "editor.defaultFormatter": "rust-lang.rust-analyzer",
    "editor.formatOnSave": true,
    "editor.formatOnPaste": true,
    "editor.formatOnType": true,
    "editor.tabSize": 4
  }
}

    性能调优建议：

    • 大型仓库可以排除 target、.git、node_modules 等目录，减少扫描量。
    • 开发时可使用 rust-analyzer.check.command = "check"，比持续运行 clippy 更快。
    • 如果项目过程宏很多，关闭 procMacro 会提升性能，但会损失宏展开、补全和诊断准确性，通常不建议默认关闭。

    命令行诊断：

    # 分析内存使用
rust-analyzer analysis-stats --memory-usage .

    适用场景：日常 Rust 开发主力工具。

    4. 任务运行与开发循环¶

    4.1 just¶

    just 是一个现代化命令运行器，类似更简洁的 make。它通过项目根目录的 justfile 统一管理常用命令，适合把构建、测试、格式化、审计、发布等流程封装为团队统一入口。

    安装：

    cargo binstall just
# 或
cargo install just

    常用命令：

    just
just --list
just test
just fmt
just release

    justfile 示例：

    default:
    just --list

fmt:
    cargo fmt --all

lint:
    cargo clippy --workspace --all-targets --all-features -- -D warnings

test:
    cargo nextest run --workspace --all-features

coverage:
    cargo llvm-cov --workspace --html

ci: fmt lint test

    核心功能：

    • 支持任务依赖、参数、默认任务、环境变量和 .env。
    • 命令语法比 Makefile 更直接，避免大量 Make 特殊语义。
    • 适合把复杂命令封装为短命令。

    适用场景：团队协作、CI 与本地命令统一、替代复杂 shell 脚本或 Makefile。

    4.2 cargo-watch¶

cargo watch -x fmt -x clippy

    适用场景：开发时自动运行 cargo check、单元测试或格式化命令。

    6. 测试、覆盖率与正确性验证¶

    6.1 cargo-nextest¶

    cargo-nextest 是下一代 Rust 测试运行器，相比 cargo test 通常提供更好的并行执行、测试过滤、失败重试和 CI 报告能力。

    安装：

    cargo binstall cargo-nextest
# 或
cargo install cargo-nextest

    常用命令：

    cargo nextest run
cargo nextest run --workspace --all-features
cargo nextest run -p my_crate
cargo nextest run --retries 2
cargo nextest archive

    适用场景：中大型 Rust 项目、CI 测试加速、需要更稳定测试报告和失败重试的项目。

    6.2 miri¶

    miri 是 Rust 的解释器和未定义行为检测工具，尤其适合检查 unsafe 代码中的内存问题。

    安装：

    rustup +nightly component add miri

    常用命令：

    cargo +nightly miri test
cargo +nightly miri run

    可以发现的问题包括：

    • 越界访问。
    • 使用悬垂引用。
    • 部分未定义行为。
    • 部分数据竞争和内存模型问题。

    适用场景：包含 unsafe 的库、底层抽象、FFI 边界、需要增强正确性信心的核心代码。

    6.3 cargo-llvm-cov¶

    cargo-llvm-cov 是基于 LLVM 的 Rust 覆盖率工具，覆盖率结果较准确，支持生成 HTML、LCOV、Cobertura 等报告格式。

    安装：

    cargo install cargo-llvm-cov

    常用命令：

    cargo llvm-cov
cargo llvm-cov --workspace --all-features
cargo llvm-cov --html
cargo llvm-cov --lcov --output-path lcov.info

    适用场景：CI 覆盖率统计、上传 Codecov/Coveralls、需要标准覆盖率格式的项目。

    6.4 cargo-tarpaulin¶

    cargo-tarpaulin 是常用 Rust 覆盖率工具，尤其在 Linux 环境中使用广泛。

    安装：

    cargo install cargo-tarpaulin

    常用命令：

    cargo tarpaulin
cargo tarpaulin --out Html
cargo tarpaulin --out Xml
cargo tarpaulin --out Lcov

    适用场景：Linux CI、快速生成覆盖率报表。若需要更标准或更精确的 LLVM 覆盖率数据，优先考虑 cargo-llvm-cov。

    6.5 proptest 与 quickcheck¶

    proptest 和 quickcheck 是属性测试工具，用于自动生成大量输入验证程序性质。

    典型依赖：

    [dev-dependencies]
proptest = "1"

    示例：

    use proptest::prelude::*;

proptest! {
    #[test]
    fn reverse_twice_is_original(xs in proptest::collection::vec(any::<i32>(), 0..100)) {
        let ys: Vec<_> = xs.iter().rev().copied().collect();
        let zs: Vec<_> = ys.iter().rev().copied().collect();
        prop_assert_eq!(xs, zs);
    }
}

    适用场景：解析器、序列化、算法、状态机、边界条件较多的代码。

    8. 基准测试、性能剖析与体积分析¶

    8.1 criterion¶

criterion = "0.5"

name = "my_benchmark"
harness = false

fn bench_add(c: &mut Criterion) {

criterion_group!(benches, bench_add);
criterion_main!(benches);

    cargo bench

    11. FFI 与原生集成¶

    11.1 bindgen¶

    bindgen 可以根据 C/C++ 头文件生成 Rust FFI 绑定代码。

    安装：

    cargo install bindgen-cli

    常用命令：

    bindgen wrapper.h -o src/bindings.rs

    build.rs 中集成示例：

    fn main() {
    let bindings = bindgen::Builder::default()
        .header("wrapper.h")
        .generate()
        .expect("generate bindings");

    bindings
        .write_to_file("src/bindings.rs")
        .expect("write bindings");
}

    适用场景：调用 C/C++ 库、系统 API、硬件 SDK。

    11.2 cbindgen¶

    cbindgen 与 bindgen 方向相反，用于根据 Rust 代码生成 C/C++ 头文件，便于其他语言调用 Rust 库。

    安装：

    cargo install cbindgen

    常用命令：

    cbindgen --crate my_crate --output include/my_crate.h

    适用场景：Rust 编写核心库，向 C/C++、Swift、Kotlin Native 或其他 FFI 调用方暴露 ABI。

    11.3 cc¶

    cc 是常用 build dependency，用于在 build.rs 中编译 C/C++ 源码并链接到 Rust 项目。

    依赖配置：

    [build-dependencies]
cc = "1"

    build.rs 示例：

    fn main() {
    cc::Build::new()
        .file("src/native/helper.c")
        .compile("helper");
}

    适用场景：混合 Rust 与 C/C++ 源码、封装小型原生库。

    12. WebAssembly 与前端开发¶

    12.1 wasm-pack¶

    wasm-pack 用于构建、测试和发布 Rust WebAssembly 包，通常配合 wasm-bindgen 使用。

    安装：

    cargo install wasm-pack

    常用命令：

    wasm-pack build
wasm-pack build --target web
wasm-pack test --headless --chrome
wasm-pack publish

    适用场景：发布 npm WASM 包、浏览器或 Node.js 中调用 Rust 逻辑。

    12.2 trunk¶

    trunk 是 Rust WASM Web 应用构建器和开发服务器，常用于 Yew、Leptos、Dioxus 等前端框架。

    安装：

    cargo install trunk

    常用命令：

    trunk serve
trunk build --release
trunk watch

    适用场景：Rust 前端应用开发、静态资源打包、热更新开发服务器。

    12.3 wasm-bindgen-cli¶

    wasm-bindgen-cli 提供底层 wasm-bindgen 命令，用于生成 JS glue code 和 TypeScript 声明。

    安装：

    cargo install wasm-bindgen-cli

    常用命令：

    wasm-bindgen target/wasm32-unknown-unknown/release/app.wasm --out-dir pkg --target web

    适用场景：需要手动控制 WASM 绑定生成过程，或构建系统不使用 wasm-pack 时。

    13. 嵌入式开发工具¶

    13.1 probe-rs¶

    probe-rs 是 Rust 嵌入式生态中常用的调试、烧录和芯片访问工具。

    安装：

    cargo install probe-rs-tools

    常用命令：

    probe-rs info
probe-rs run --chip STM32F407VG target/thumbv7em-none-eabihf/debug/app

    适用场景：ARM/RISC-V 等嵌入式开发，替代或补充 OpenOCD、厂商烧录工具。

    13.2 cargo-embed¶

    cargo-embed 用于构建、烧录和调试嵌入式程序，通常基于 probe-rs。

    安装：

    cargo install cargo-embed

    常用命令：

    cargo embed
cargo embed --release

    适用场景：嵌入式项目本地开发、烧录、RTT 日志查看。

    13.3 defmt¶

    defmt 是面向资源受限设备的高效日志框架，通过压缩日志格式减少固件体积和串口输出开销。

    常用依赖：

    [dependencies]
defmt = "0.3"
defmt-rtt = "0.4"

    适用场景：嵌入式日志、RTT 调试、低资源设备诊断。

    14. 推荐工具组合¶

    14.1 通用 Rust 项目¶

    rustup component add rustfmt clippy
cargo binstall just cargo-nextest cargo-deny cargo-llvm-cov

    推荐组合：

    • rustup：固定工具链。
    • cargo：构建和包管理。
    • rustfmt + clippy：格式化与 lint。
    • rust-analyzer：编辑器体验。
    • just：统一项目命令。
    • cargo-nextest：更快测试。
    • cargo-deny 或 cargo-audit：依赖安全检查。
    • cargo-llvm-cov：覆盖率统计。

    14.2 后端服务项目¶

    推荐工具：

    • cargo-watch：保存后自动 check 或 test。
    • cargo-nextest：CI 测试。
    • cargo-deny：依赖许可证和漏洞治理。
    • flamegraph 或 samply：性能热点分析。
    • cross 或 cargo-zigbuild：构建 Linux 发布产物。

    14.3 CLI 工具项目¶

    推荐工具：

    • just：封装 fmt、lint、test、release。
    • cargo-bloat：分析二进制体积。
    • cargo-dist：生成多平台 release。
    • cargo-release：管理版本与发布 crate。

    14.4 WebAssembly 项目¶

    推荐工具：

    • wasm-pack：构建可发布 WASM 包。
    • trunk：构建 Rust 前端应用。
    • wasm-bindgen-cli：底层绑定生成。
    • cargo-llvm-cov：测试覆盖率。

    14.5 嵌入式项目¶

    推荐工具：

    • rustup target add thumbv7em-none-eabihf：添加目标平台。
    • probe-rs / cargo-embed：烧录与调试。
    • defmt：高效日志。
    • cargo-bloat：分析固件体积。
    • miri：验证部分 unsafe 抽象。

    15. CI 示例¶

    一个典型 CI 可以包含格式化、lint、测试、审计和覆盖率：

    cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo nextest run --workspace --all-features
cargo deny check
cargo llvm-cov --workspace --all-features --lcov --output-path lcov.info

    配合 justfile 后可以统一为：

    just ci

    17. 最小推荐实践¶

    对于大多数 Rust 项目，建议至少建立以下实践：

    1. 使用 rust-toolchain.toml 固定工具链和组件。
    2. 使用 cargo fmt --check 和 cargo clippy -- -D warnings 作为 CI 门禁。
    3. 使用 justfile 统一本地和 CI 命令入口。
    4. 中大型项目使用 cargo-nextest 替代或补充 cargo test。
    5. 使用 cargo-deny 或 cargo-audit 做依赖安全检查。
    6. 使用 cargo-llvm-cov 输出覆盖率报告。
    7. 发布 crate 时使用 cargo-release 规范化版本流程。
    8. 发布 CLI 二进制时考虑 cargo-dist、cross 或 cargo-zigbuild。
