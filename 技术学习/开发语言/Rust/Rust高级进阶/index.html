    1.生命周期¶

    1.1. 生命周期是什么？¶

    生命周期（Lifetime）是 Rust 借用检查器用来描述引用有效范围的静态信息。它并不会改变变量真实的存活时间，也不会在运行时产生额外开销，而是在编译期帮助编译器判断：某个引用在被使用时，指向的数据是否仍然有效。

    Rust 的生命周期系统解决的是「悬垂引用」问题：

    fn main() {
    let r;

    {
        let x = 5;
        r = &x; // x 在内部作用域结束后被释放
    }

    // println!("{}", r); // ❌ r 指向已经失效的 x
}

    生命周期的核心原则：引用的生命周期不能长于被引用值的生命周期。

    1.2. 生命周期标注的本质¶

    生命周期标注不是在「延长」引用生命周期，而是在告诉编译器多个引用之间的生命周期关系。

    fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}

    这里的 'a 表示：

    • x 和 y 至少在某个共同作用域 'a 内有效；
    • 返回值引用也只能在这个共同作用域 'a 内有效；
    • 实际调用时，'a 会被推断为两个参数生命周期中较短的那个。

    生命周期标注描述的是「关系」，不是「时长」。'a 不代表一个固定时间段，而是由调用上下文推断出来的最小安全范围。

    1.3. 生命周期省略规则¶

    Rust 为常见函数签名提供生命周期省略规则，因此很多代码不需要显式写生命周期。

    编译器按以下规则推断：

    1. 每个引用参数都会获得自己的生命周期参数；
    2. 如果只有一个输入生命周期，它会被赋给所有输出生命周期；
    3. 如果方法参数中有 &self 或 &mut self，输出生命周期默认与 self 绑定。
    // 显式写法
fn first<'a>(s: &'a str) -> &'a str {
    &s[..1]
}

// 省略写法，等价于上面
fn first_short(s: &str) -> &str {
    &s[..1]
}

    但当返回值可能来自多个输入引用时，编译器无法判断关系，就必须手动标注：

    fn pick<'a>(a: &'a str, b: &'a str, use_a: bool) -> &'a str {
    if use_a { a } else { b }
}

    1.4. 结构体中的生命周期¶

    当结构体字段保存引用时，结构体必须声明生命周期参数，表示该结构体实例不能比它引用的数据活得更久。

    struct UserView<'a> {
    name: &'a str,
}

fn main() {
    let name = String::from("Alice");
    let view = UserView { name: &name };
    println!("{}", view.name);
}

    含引用字段的结构体适合表达「借用视图」，例如解析器中的切片、配置读取视图、零拷贝反序列化结果等。若结构体需要独立拥有数据，应优先使用 String、Vec<T> 等拥有所有权的类型。

    1.5. 方法与 impl 中的生命周期¶

    为带生命周期的结构体实现方法时，生命周期参数写在 impl 后面：

    struct Parser<'a> {
    input: &'a str,
}

impl<'a> Parser<'a> {
    fn new(input: &'a str) -> Self {
        Self { input }
    }

    fn remaining(&self) -> &str {
        self.input
    }
}

    remaining 不需要显式生命周期，因为方法省略规则会把返回值生命周期绑定到 &self。

    1.6. 生命周期约束与 where¶

    1. 生命周期约束形式¶

    生命周期约束主要有两种形式：

    ① 'a: 'b —— “'a 活得比 'b 长（或一样长）”¶

    生命周期可以像类型参数一样添加约束，常见形式是 'a: 'b，表示 'a 至少和 'b 一样长（即 'a outlives 'b）。

    当你有“引用的引用”，或某个结构包含多个相关的引用时，这种约束经常出现。

    struct RefPair<'a, 'b, T>
where
    'a: 'b,
{
    long: &'a T,
    short: &'b T,
}

// 外层引用 &'a 指向一个 &'b  i32，要保证 &'b 在内层使用时仍然有效
// 就必须要求 'b: 'a （内部引用活得更长）
struct DoubleRef<'a, 'b> {
    r: &'a &'b i32,
}

// 编译器不会自动加上 'b: 'a，需要我们显式写出来：
impl<'a, 'b> DoubleRef<'a, 'b> {
    fn new(r: &'a &'b i32) -> Self
    where
        'b: 'a,   // 必须加这个约束，否则编译不过
    {
        DoubleRef { r }
    }
}
    ② T: 'a —— “类型 T 中的所有引用都比 'a 活得长”¶

    泛型类型中也常见 T: 'a：表示泛型类型 T 内部可能包含引用，且这些引用的生命周期必须至少是 'a。

    当我们要把 T 存入一个被 'a 限定的上下文（如结构体带有生命周期 'a）时，就需要这个约束，以保证不会出现悬垂引用。

    struct Container<'a, T> {
    data: &'a T,            // &'a T 要求 T: 'a
}

// 在 impl 中，这个约束必须显式声明
impl<'a, T> Container<'a, T>
where
    T: 'a,                 // 声明 T 能安全地被 'a 引用
{
    fn get(&self) -> &'a T {
        self.data
    }
}

    如果 T 是 i32 这类不含引用的类型，T: 'a 自动成立；但编译器仍要求你写明这个约束，以保证泛型代码对所有 T 都安全。

    2. where 子句¶

    生命周期约束可以直接写在尖括号 <> 里，也可以移到 where 子句中。两者的语义完全相同，但 where 让签名更易读，尤其是约束较多时。

    没有 where，全挤在尖括号里：

    fn foo<'a, 'b: 'a, T: 'a>(x: &'a T, y: &'b T) { }

    用 where 重写：

    fn foo<'a, 'b, T>(x: &'a T, y: &'b T)
where
    'b: 'a,
    T: 'a,
{ }

    可读性明显提升，约束条件被独立出来，一眼就能看清关系。

    • where 不仅用于函数，所有能声明约束的地方都可以用，如：结构体定义、接受闭包作为参数的高阶函数等场景。

    • where 只是语法糖，但强烈建议在约束多时使用，尤其是当函数签名中既有类型 trait bound 又有生命周期 bound 时，能极大提升可读性。

    1.7. 高阶生命周期约束 HRTB¶

    HRTB（Higher-Ranked Trait Bounds）用于表达「对任意生命周期都成立」的约束，语法是 for<'a>。

    fn apply_to_str<F>(f: F)
where
    F: for<'a> Fn(&'a str),
{
    let s = String::from("rust");
    f(&s);
}

    类型 F 代表的闭包 / 函数，对任意生命周期 'a 都满足：接收 &'a str

    这里表示 F 必须能接受任意生命周期的 &str，而不是只接受某个特定生命周期的引用。

    HRTB 常见于闭包、trait object、序列化框架和异步抽象中。

    更典型的高级写法是对引用本身施加 trait 约束：

    fn compare_with_zero<T>(value: T)
where
    for<'a> &'a T: PartialEq<i32>,
{
    if &value == 0 {
        println!("zero");
    }
}

    for<'a> &'a T: PartialEq<i32> 的含义是：任意生命周期的 &T 都必须能和 i32 比较。如果不用 HRTB，只在函数上声明某个具体生命周期，往往无法覆盖函数内部临时借用产生的更短生命周期。

    1.8. 静态生命周期 'static¶

    1. 'static¶

    'static 表示引用在整个程序运行期间都有效，最典型的是字符串字面量：

    let s: &'static str = "hello";

    需要注意：T: 'static 不等于「这个值永远不释放」，而是表示类型 T 中不包含短生命周期引用，或者包含的引用都是 'static。例如 String 满足 T: 'static，因为它拥有堆上数据，不借用外部短生命周期数据。

    fn spawn_task<T>(value: T)
where
    T: Send + 'static,
{
    std::thread::spawn(move || drop(value));
}

    线程可能比当前函数活得更久，因此闭包捕获的数据必须可安全移动到线程中，并且不能借用当前栈帧中的短生命周期引用。

    2. &'static —— 静态生命周期的引用¶

    &'static T 表示一个具有 'static 生命周期的不可变引用（也有 &'static mut T）。

    它指向的数据必须存活整个程序，因此这个引用可以安全地在任何地方使用，不会悬垂。

    &'static 对于生命周期有着非常强的要求：一个引用必须要活得跟剩下的程序一样久，才能被标注为 &'static。

    let s: &'static str = "hello";   // 字符串字面量默认就是 &'static str

static GREETING: &str = "Hi";    // GREETING 本身是 'static 的，它内部引用也是 'static
let g: &'static str = GREETING;

    使用场景:

    • 全局错误信息：如 std::io::Error::new 经常接受 &'static str，因为错误描述不应持有局部数据的引用。

    • 类型描述：std::any::type_name::<T>() 返回 &'static str。

    • 配置信息：如果你的结构体只需要引用外部的静态配置，可以存 &'static Config。

    • 从泄漏获得可变静态引用（谨慎使用）：

    let x: &'static mut i32 = Box::leak(Box::new(42));
*x = 100; // 整个程序期间有效，但内存永不释放

    3. T: 'static —— 类型上的 'static 约束¶

    这是最容易产生误解的地方。

    T: 'static 不是指 T 的生命周期是 'static，而是指 T 内部可以安全地存活任意长时间——具体来说，T 中不包含任何生命周期小于 'static 的引用。

    换句话说：

    • T 要么是拥有所有权的类型（如 String, Vec<i32>, i32），
    • 要么虽然包含引用，但这些引用全部是 'static 的（如 &'static str）。

    当你需要确保一个值可以被无时间限制地持有时，就必须添加这个约束。最典型的例子是 std::thread::spawn：

    pub fn spawn<F, T>(f: F) -> JoinHandle<T>
where
    F: FnOnce() -> T,
    F: Send + 'static,     // ← 闭包必须满足 'static
    T: Send + 'static,

    新线程可能比创建它的线程活得更久，所以线程闭包捕获的所有数据都必须能自己存活任意长时间——即必须满足 F: 'static 和 T: 'static。

    如果你在线程闭包中尝试使用一个局部变量的引用，就会编译失败：

    let x = 42;
std::thread::spawn(move || {
    println!("{}", x); // x 是 i32，拥有所有权，满足 'static —— 没问题
    // println!("{}", &x); // 引用了栈上的 x，不满足 'static —— 会报错
});

    T: 'static 在实际代码中的使用:

    • Trait 约束：当你的结构体打算存放 T，并且这个结构体可能被传递到要求 'static 的上下文中时，可以加上 where T: 'static。
    • 动态分发 Box<dyn Any>：Any 要求 dyn Any + 'static，如果你想对非 'static 类型使用，需要 + 'a。
    • 异步编程：async 块或 tokio::spawn 通常要求 future 是 'static，因此捕获的所有数据必须满足 'static。

    1.9. NLL：非词法生命周期¶

    NLL（Non-Lexical Lifetime，非词法生命周期）是现代 Rust 借用检查的重要改进：引用的生命周期不再机械地持续到词法作用域结束，而是持续到最后一次使用。

    fn main() {
    let mut s = String::from("hello");

    let r1 = &s;
    let r2 = &s;
    println!("{r1}, {r2}"); // r1、r2 最后一次使用在这里

    let r3 = &mut s; // ✅ NLL 能识别前面的不可变借用已经结束
    r3.push_str(" rust");
}

    如果按照早期「借用持续到作用域末尾」的规则，上面的 &mut s 会和 r1/r2 冲突；NLL 会把借用范围缩短到最后一次使用处，因此让更多符合直觉的代码通过编译。

    需要注意：NLL 只是让借用检查更精确，并没有放宽 Rust 的别名规则。任意时刻仍然只能满足以下二选一：

    1. 多个不可变引用；
    2. 一个可变引用。

    1.10. Reborrow：再借用¶

    再借用（Reborrow）是指从一个已有引用上继续创建更短生命周期的新引用。最常见的是从 &mut T 再借用出 &T。

    #[derive(Debug)]
struct Point {
    x: i32,
    y: i32,
}

impl Point {
    fn move_to(&mut self, x: i32, y: i32) {
        self.x = x;
        self.y = y;
    }
}

fn main() {
    let mut p = Point { x: 0, y: 0 };
    let r = &mut p;  // 可变引用 r

    let rr: &Point = &*r; // 从可变引用再借用为不可变引用（rr 是对 r 的再借用）
    println!("{:?}", rr); // rr 最后一次使用在这里，但不能在它的生命周期内再使用原来的借用 r

    r.move_to(10, 10); // ✅ rr 结束后，原来的可变引用 r 可继续使用
}

    再借用的关键规则：再借用存在期间，原引用会被临时冻结。例如 rr 存活时，不能通过 r 修改 p；等 rr 最后一次使用后，r 才能恢复可变访问能力。

    函数调用中也经常发生隐式再借用：

    fn len(v: &Vec<String>) -> usize {
    v.len()
}

fn push_after_read(v: &mut Vec<String>) {
    let n = len(v); // &mut Vec<String> 被临时再借用为 &Vec<String>
    v.push(format!("len={n}"));
}

    1.11. 生命周期系统“不够聪明”的场景¶

    Rust 的生命周期系统是保守的静态分析。它必须在不运行程序的前提下证明引用安全，因此某些人类看来安全的代码，也可能因为借用范围被推断得过长而无法通过编译。

    典型问题一：方法签名把 &mut self 和返回引用绑定到同一个生命周期，导致可变借用被延长。

    struct Foo;

impl Foo {
    fn mutate_and_share<'a>(&'a mut self) -> &'a Self {
        self
    }

    fn share(&self) {}
}

fn main() {
    let mut foo = Foo;
    let loan = foo.mutate_and_share();
    println!("{:p}", loan);
    // foo.share(); // 某些设计下会因为前面的可变借用过长而冲突
}

    典型问题二：容器查询和插入混在同一段控制流中，旧版或复杂场景下借用可能被延长。

    use std::collections::HashMap;

fn get_default(map: &mut HashMap<String, String>, key: String) -> &mut String {
    if map.contains_key(&key) {
        map.get_mut(&key).unwrap()
    } else {
        map.insert(key.clone(), String::new());
        map.get_mut(&key).unwrap()
    }
}

    这种代码的优化方向通常不是继续加生命周期标注，而是改写控制流，让借用范围更短、更明确。例如优先使用标准库提供的 entry API：

    use std::collections::HashMap;

fn get_default_entry(map: &mut HashMap<String, String>, key: String) -> &mut String {
    map.entry(key).or_default()
}

    高阶 Rust 中要形成一个判断：当生命周期标注越来越复杂时，往往不是缺少某个 'a，而是 API 把借用关系设计得过紧。

    1.12. 无界生命周期与 unsafe¶

    无界生命周期（Unbounded Lifetime）通常出现在 unsafe 中：代码从裸指针解引用凭空构造引用，而输出生命周期没有被任何输入约束。

    unsafe fn from_raw_unbounded<'a, T>(ptr: *const T) -> &'a T {
    unsafe { &*ptr }
}

    这个函数的风险在于：调用者可以把返回值当成任意生命周期使用，甚至当成 'static 使用，但编译器并不知道裸指针背后的数据到底能活多久。

    更安全的设计是让输出生命周期来自输入引用，从而把生命周期关系交给借用检查器：

    fn first<T>(slice: &[T]) -> Option<&T> {
    slice.get(0)
}

    如果必须封装裸指针，应尽量让 unsafe 边界变小，并通过函数参数或封装类型表达真实所有权关系：

    use std::marker::PhantomData;

struct RawRef<'a, T> {
    ptr: *const T,
    _marker: PhantomData<&'a T>,
}

    PhantomData<&'a T> 不存储真实引用，但能告诉编译器：RawRef<'a, T> 在类型语义上借用了一个生命周期为 'a 的 T。

    1.13. 闭包、函数指针与生命周期消除差异¶

    普通函数可以使用生命周期消除规则，编译器能直接把输入引用和输出引用关联起来：

    fn identity(x: &i32) -> &i32 {
    x
}

    但闭包的生命周期推断更复杂，尤其是显式写返回引用类型时，编译器不一定能把参数生命周期和返回值生命周期建立成通用关系。

    // 某些场景下闭包不如普通函数容易推断：
// let f = |x: &i32| -> &i32 { x };

    如果需要表达「对任意生命周期的引用输入，都返回同生命周期引用」，普通函数项通常更合适：

    fn use_identity(f: for<'a> fn(&'a i32) -> &'a i32) {
    let n = 1;
    assert_eq!(*f(&n), 1);
}

use_identity(identity);

    闭包适合捕获环境和局部组合；当 API 需要精确表达引用输入输出关系时，普通函数、显式 trait bound 或 HRTB 往往更清晰。

    1.14. Trait Object 的默认生命周期¶

    Trait object 隐含生命周期。Box<dyn Trait> 在很多位置默认等价于 Box<dyn Trait + 'static>，这意味着对象内部不能包含短生命周期借用。

    trait Render {
    fn render(&self) -> &str;
}

struct Borrowed<'a> {
    text: &'a str,
}

impl<'a> Render for Borrowed<'a> {
    fn render(&self) -> &str {
        self.text
    }
}

    如果要保存借用数据，需要把 trait object 的生命周期显式写出来：

    fn boxed_render<'a>(text: &'a str) -> Box<dyn Render + 'a> {
    Box::new(Borrowed { text })
}

    高级 Rust 中看到 dyn Trait + 'a 时，应理解为：这个 trait object 可能借用了生命周期为 'a 的数据，因此它不能比 'a 活得更久。

    1.15. impl Trait 与生命周期捕获¶

    impl Trait 用于隐藏具体返回类型，但它仍然必须遵守生命周期规则。返回值如果借用了输入数据，需要在签名中体现这种关系。

    fn words<'a>(s: &'a str) -> impl Iterator<Item = &'a str> {
    s.split_whitespace()
}

    这里返回的迭代器内部借用了 s，因此迭代器不能比 s 活得更久。

    对于闭包返回值，常见写法是结合 move 和 impl Fn：

    fn prefixer<'a>(prefix: &'a str) -> impl Fn(&str) -> String + 'a {
    move |s| format!("{prefix}{s}")
}

    返回类型末尾的 + 'a 表示：这个闭包对象可能捕获了生命周期为 'a 的引用，调用者不能把它保存到超过 'a 的地方。

    1.16. 不要把结构体生命周期绑到方法借用上¶

    高级生命周期设计中，一个常见错误是把方法接收者的借用生命周期写成结构体自己的生命周期，导致 self 被借用得过久。

    struct Manager<'a> {
    text: &'a str,
}

struct List<'a> {
    manager: Manager<'a>,
}

struct Interface<'b, 'a> {
    manager: &'b mut Manager<'a>,
}

impl<'a> List<'a> {
    fn get_interface<'b>(&'b mut self) -> Interface<'b, 'a>
    where
        'a: 'b,
    {
        Interface {
            manager: &mut self.manager,
        }
    }
}

    这里不要写成 fn get_interface(&'a mut self) -> Interface<'a, 'a>，否则会把 self 的可变借用强行延长到 List<'a> 的整个生命周期。正确做法是引入更短的 'b 表示「本次方法调用期间的借用」，再用 'a: 'b 表示 manager 中的数据至少能覆盖这次借用。

    这类问题是高阶 Rust API 设计的重点：

    1. 结构体生命周期描述字段中借用数据的来源；
    2. 方法生命周期描述本次调用产生的临时借用；
    3. 两者不应无脑使用同一个 'a；
    4. 生命周期越短，API 越容易组合。

    1.17. 生命周期消除规则补充¶

    除了基础三条生命周期消除规则，现代 Rust 还支持一些常见简写：

    trait Reader {}

struct BufReader<'a> {
    buf: &'a [u8],
}

impl Reader for BufReader<'_> {}

    '_ 是匿名生命周期，表示「这里确实有生命周期参数，但让编译器推断」。它适合在 impl、路径类型和返回类型中减少无意义命名。

    T: 'a 约束也经常可以省略：

    // 旧式写法
struct RefOld<'a, T: 'a> {
    value: &'a T,
}

// 现代 Rust 通常可写为
struct RefNew<'a, T> {
    value: &'a T,
}

    编译器能从字段 &'a T 推导出 T 中的引用必须满足相应生命周期要求，因此无需手动重复写 T: 'a。

    1.18. 生命周期常见误区¶

    1. 生命周期不能修复所有权错误，只能描述引用关系；
    2. 不要为了通过编译盲目添加 'static，这通常会把问题扩大为不必要的所有权约束；
    3. 能拥有数据时不要过度借用，复杂生命周期往往意味着模型需要重新设计；
    4. 返回引用时，引用必须来自输入参数或结构体字段，不能返回函数内部局部变量的引用。
    // ❌ 错误：返回了局部变量的引用
// fn bad<'a>() -> &'a str {
//     let s = String::from("temp");
//     &s
// }

    生命周期学习重点不是「背语法」，而是理解 Rust 如何在编译期证明引用始终有效。

    1.19. 生命周期 API 设计重构思路¶

    当生命周期标注越来越多、函数签名越来越难读时，通常不是“还缺一个 'a”，而是 API 暴露了过强的借用关系。工程中可以按以下顺序重构：

    问题表现 优先重构方向 说明
    返回值长期借用输入，调用方无法继续修改原对象 缩短借用范围 用局部代码块、提前计算结果、拆分查询与修改步骤
    结构体只是为了省一次分配而到处带生命周期 改为拥有数据 使用 String、Vec<T>、PathBuf 等，降低 API 复杂度
    大多数情况借用，少数情况需要修改或生成新值 使用 Cow<'a, T> 让调用方在零拷贝和拥有数据之间平滑切换
    图、缓存、注册表等对象互相引用困难 使用索引/句柄 用 usize、Id、Key 表示关系，由容器统一管理所有权
    方法把 &mut self 借用延长过久 分离短借用和长生命周期 方法借用使用新的短生命周期，不要直接复用结构体字段生命周期 
    use std::borrow::Cow;

fn normalize_name(input: &str) -> Cow<'_, str> {
    let trimmed = input.trim();
    if trimmed == input {
        Cow::Borrowed(input)
    } else {
        Cow::Owned(trimmed.to_string())
    }
}

    对于图、树、缓存这类结构，也可以用索引代替自引用结构：

    struct Node {
    name: String,
    parent: Option<usize>,
    children: Vec<usize>,
}

struct Tree {
    nodes: Vec<Node>,
}

    这种设计把所有权集中在 Tree 中，节点之间只保存稳定的逻辑关系，通常比在结构体里直接保存 &Node 更容易维护。

    2.泛型与特征¶

    2.1. 泛型与特征在 Rust 类型系统中的位置¶

    泛型（Generics）和特征（Traits）是 Rust 零成本抽象的核心：泛型负责把“同一套逻辑适用于多种类型”表达出来，特征负责把“类型必须具备什么能力”表达出来。二者结合后，Rust 可以在编译期完成类型检查、约束求解和代码生成，同时尽量避免运行时开销。

    可以把它们理解为三层能力：

    层次 关注点 典型语法 作用
    参数化 代码不绑定具体类型 fn f<T>(x: T)、struct Boxed<T> 复用数据结构和算法
    行为约束 类型必须支持某些操作 T: Clone、T: Iterator 保证泛型代码内部可调用特定方法
    抽象边界 API 暴露静态或动态抽象 impl Trait、dyn Trait 平衡性能、封装性与灵活性 
    fn max_by_key<T, K, F>(items: &[T], mut key: F) -> Option<&T>
where
    K: Ord,
    F: FnMut(&T) -> K,
{
    items.iter().max_by_key(|item| key(item))
}

    这段代码没有固定元素类型 T，也没有固定排序键类型 K，只要求 K 可以比较大小、F 可以从 &T 计算出 K。调用方获得的是接近手写版本的性能，编译器则在具体调用点生成对应类型的机器码。

    2.2. 泛型函数、结构体与枚举¶

    泛型可以出现在函数、结构体、枚举、方法实现和特征定义中。最常见的形式是把类型参数放在名称后的尖括号里：

    fn identity<T>(value: T) -> T {
    value
}

struct Pair<T> {
    left: T,
    right: T,
}

enum Either<L, R> {
    Left(L),
    Right(R),
}

    泛型类型参数本身不代表“任意操作都可用”。在没有约束时，泛型代码只能做对所有类型都成立的事情，例如移动值、借用值、把值放进容器，不能直接比较、打印、克隆或相加。

    fn choose_first<T>(first: T, _second: T) -> T {
    first
}

// 错误思路：T 未必支持 > 运算。
// fn larger<T>(a: T, b: T) -> T {
//     if a > b { a } else { b }
// }

    需要使用比较能力时，应显式添加 trait bound：

    fn larger<T: Ord>(a: T, b: T) -> T {
    if a >= b { a } else { b }
}

    对结构体实现方法时，impl<T> 中的 T 是为实现块声明的类型参数，Pair<T> 中的 T 是被实现的具体泛型类型：

    impl<T> Pair<T> {
    fn new(left: T, right: T) -> Self {
        Self { left, right }
    }

    fn into_tuple(self) -> (T, T) {
        (self.left, self.right)
    }
}

    也可以只为满足某些约束的实例提供方法：

    impl<T: Clone> Pair<T> {
    fn duplicated_left(&self) -> T {
        self.left.clone()
    }
}

    这意味着 Pair<String> 可以调用 duplicated_left，但 Pair<NonCloneType> 不能调用。Rust 的方法集合会随具体类型参数和约束而变化。

    2.3. Trait 的本质：行为契约¶

    Trait 定义了一组类型可以实现的行为。它类似“接口”，但比传统接口更贴近 Rust 类型系统：trait 可以包含关联类型、关联常量、默认方法、泛型方法，也可以被用于静态分发或动态分发。

    trait Summary {
    fn title(&self) -> &str;

    fn summarize(&self) -> String {
        format!("{}", self.title())
    }
}

struct Article {
    title: String,
    body: String,
}

impl Summary for Article {
    fn title(&self) -> &str {
        &self.title
    }
}

    默认方法适合表达“基于最小必需能力的通用逻辑”。实现者只需要提供核心方法，就能获得默认行为。如果默认行为不适合某个类型，也可以在 impl 中覆盖。

    Trait 不是“继承父类”，而是“声明能力”。一个类型可以实现多个 trait，trait 也可以为外部类型实现外部行为，但必须遵守孤儿规则。

    2.4. Trait Bound 与 where 子句¶

    Trait bound 用来声明泛型参数必须满足的能力要求。简单约束可以直接写在类型参数后面：

    fn print_twice<T: std::fmt::Display>(value: T) {
    println!("{value}");
    println!("{value}");
}

    多个约束可以使用 + 组合：

    fn log_value<T: std::fmt::Display + Clone>(value: T) {
    let copied = value.clone();
    println!("{value} / {copied}");
}

    当约束较多、涉及多个类型参数或生命周期时，优先使用 where 子句。它能显著提高签名可读性：

    use std::fmt::{Debug, Display};

fn compare_and_log<T, U>(left: T, right: U)
where
    T: Display + Clone,
    U: Display + Debug,
{
    println!("left = {}", left.clone());
    println!("right = {right:?}");
}

    where 子句还可以约束“派生出来的类型”，这是内联 bound 难以清晰表达的场景：

    fn collect_debug<I>(iter: I) -> Vec<String>
where
    I: IntoIterator,
    I::Item: std::fmt::Debug,
{
    iter.into_iter().map(|item| format!("{item:?}")).collect()
}

    工程实践中，复杂泛型 API 通常应遵循：函数名表达目的，参数名表达角色，where 子句集中表达约束。不要为了“看起来高级”把过多约束塞进一行签名里。

    2.5. Rust 标准库核心 Trait 分类¶

    标准库 trait 可以按“语言能力”而不是按模块名来理解。一个 trait 往往对应一种编译器可识别的行为边界：值能否复制、能否比较、能否解引用、能否参与运算、能否格式化、能否迭代、能否进行 I/O、能否作为错误传播、能否作为回调调用等。

    本节将标准库核心 trait 归纳为六大类：

    分类 代表 Trait 解决的问题
    基础标记 Trait Copy、Clone、Default、Drop、Sized、Send、Sync、Unpin、Eq 描述类型的基础语义、内存/线程安全边界和可派生能力
    解引用 / 访问 Trait Deref、DerefMut、AsRef、AsMut、Borrow、BorrowMut、Index、IndexMut 统一“如何从一个值访问另一个值”的方式
    运算符重载 Trait Add、Sub、Mul、Div、Rem、Neg、Not、BitAnd、AddAssign 等 把领域对象接入 Rust 运算符语法
    格式化 / 转换 Trait Debug、Display、From、Into、TryFrom、TryInto、FromStr、ToString 控制文本表现、类型转换和字符串解析
    迭代器 Trait Iterator、IntoIterator、FromIterator、Extend、DoubleEndedIterator、ExactSizeIterator 支撑 for 循环、惰性链式处理和集合构造
    I/O / 错误 / 函数 Trait Read、Write、BufRead、Seek、Error、Fn、FnMut、FnOnce 抽象字节流、错误传播和可调用对象

    很多 Rust 语法糖都能对应到这些 trait：for 循环依赖 IntoIterator，+ 依赖 Add，value[index] 依赖 Index，println!("{value}") 依赖 Display，println!("{value:?}") 依赖 Debug，? 常配合 From 完成错误类型转换。

    2.5.1. 基础标记 Trait¶

    基础标记 trait 描述类型最底层的语义：值如何复制、如何初始化、如何析构、是否有确定大小、能否跨线程、能否参与全等比较等。它们通常不直接体现业务行为，却会影响泛型约束、派生能力、线程边界和资源安全。

    Trait 定义 / 核心语义 使用场景 示例
    Copy 按位复制后原值仍可继续使用，标记 trait 小型纯值类型、句柄 ID、坐标、枚举标志 #[derive(Copy, Clone)]
    Clone 显式创建一个逻辑副本 String、Vec<T>、Arc<T>、配置对象 value.clone()
    Default 提供类型默认值 配置、builder、集合初始化、测试数据 T::default()
    Drop 离开作用域时执行清理逻辑 文件、锁、连接、临时目录、作用域守卫 impl Drop for Guard
    Sized 编译期大小已知，泛型参数默认满足它 普通按值参数、栈上局部变量 T: Sized
    ?Sized 放宽默认 Sized 约束 接收 str、[T]、dyn Trait 的引用 T: ?Sized
    Send 值可以安全移动到其他线程 thread::spawn、多线程任务输入 T: Send + 'static
    Sync &T 可以安全在线程间共享 Arc<T> 共享服务、并发只读状态 T: Send + Sync
    Unpin 固定后仍可安全移动 普通类型、部分 Future 组合 T: Unpin
    Eq 完整等价关系，标记 trait HashMap/HashSet 键、确定性值对象 T: Eq + Hash 
    #[derive(Debug, Clone, Copy, Default, PartialEq, Eq, Hash)]
struct UserId(u64);

let a = UserId(1);
let b = a;
let c = a;
assert_eq!(b, c);

    Copy 必须建立在 Clone 之上，并且不能和自定义 Drop 同时出现。原因是 Drop 类型通常代表某种资源所有权；如果允许隐式按位复制，多个副本可能在析构时重复释放同一资源。

    struct ScopeLog(&'static str);

impl Drop for ScopeLog {
    fn drop(&mut self) {
        println!("leave {}", self.0);
    }
}

    Send 和 Sync 多数情况下由编译器自动推导：Rc<T> 不是线程安全引用计数，因此通常不是 Send/Sync；Arc<T> 使用原子引用计数，可以跨线程共享，但仍要求内部的 T 满足相应线程安全约束。

    use std::sync::Arc;
use std::thread;

fn share<T>(value: Arc<T>)
where
    T: Send + Sync + 'static,
{
    thread::spawn(move || drop(value));
}

    基础标记 trait 的设计原则是：能派生时优先派生；涉及资源管理、线程安全或 unsafe 不变量时不要为了通过编译而随意实现，尤其不要轻易写 unsafe impl Send / unsafe impl Sync。

    2.5.2. 解引用 / 访问 Trait¶

    解引用和访问类 trait 解决的问题是：如何从一个包装值、拥有值、引用值或集合中得到另一个值。它们大量出现在智能指针、路径/字符串参数、集合查询和索引访问中。

    Trait 定义 / 核心语义 使用场景 示例
    Deref 定义不可变解引用目标，参与 *x 和方法自动解引用 智能指针、透明 newtype Box<T>、Rc<T>
    DerefMut 定义可变解引用目标 独占智能指针、锁守卫 Box<T>、MutexGuard<T>
    AsRef<T> 低成本转换为 &T 接收路径、字符串、切片等多形态参数 impl AsRef<Path>
    AsMut<T> 低成本转换为 &mut T 泛型修改缓冲区或容器内部值 value.as_mut()
    Borrow<T> 按等价语义借用为 T 集合键查询，拥有形式和借用形式一致 HashMap<String, V>::get(&str)
    BorrowMut<T> 可变版本的 Borrow 需要等价语义的可变借用 value.borrow_mut()
    Index 定义 value[index] 的不可变访问 容器、矩阵、切片包装 items[0]
    IndexMut 定义 value[index] = ... 的可变访问 可变容器、矩阵写入 items[0] = x

    AsRef 适合写在 API 入口，让调用方可以传入 String、&str、PathBuf、&Path 等不同形式：

    use std::path::{Path, PathBuf};

fn file_name(path: impl AsRef<Path>) -> Option<String> {
    path.as_ref()
        .file_name()
        .map(|name| name.to_string_lossy().into_owned())
}

let owned = PathBuf::from("src/main.rs");
assert_eq!(file_name(&owned).as_deref(), Some("main.rs"));
assert_eq!(file_name("Cargo.toml").as_deref(), Some("Cargo.toml"));

    Borrow 比 AsRef 更强调“等价语义”。例如 HashMap<String, V> 可以用 &str 查询，是因为 String 能以等价的哈希和相等语义借用为 str：

    use std::collections::HashMap;

let mut counts = HashMap::<String, usize>::new();
counts.insert("rust".to_string(), 1);
assert_eq!(counts.get("rust"), Some(&1));

    Deref 不应该被当作“继承”机制滥用。它适合智能指针和非常透明的包装类型；如果只是为了少写 .field 或暴露内部对象所有方法，通常会让 API 来源变得模糊。

    Index 和 IndexMut 适合表达廉价、确定的索引访问。如果访问可能失败，优先提供 get / get_mut 返回 Option；如果访问会触发 I/O、查询数据库或复杂计算，就不应伪装成索引运算。

    use std::ops::{Index, IndexMut};

struct Matrix<T> {
    cols: usize,
    data: Vec<T>,
}

impl<T> Index<(usize, usize)> for Matrix<T> {
    type Output = T;

    fn index(&self, index: (usize, usize)) -> &Self::Output {
        &self.data[index.0 * self.cols + index.1]
    }
}

impl<T> IndexMut<(usize, usize)> for Matrix<T> {
    fn index_mut(&mut self, index: (usize, usize)) -> &mut Self::Output {
        &mut self.data[index.0 * self.cols + index.1]
    }
}

    2.5.3. 运算符重载 Trait¶

    Rust 的运算符重载通过 std::ops 中的 trait 实现。实现这些 trait 可以让领域对象使用自然的运算语法，但也要求语义足够直观，避免把复杂副作用隐藏在运算符中。

    Trait 对应语法 定义 / 核心语义 使用场景
    Add / Sub / Mul / Div / Rem + - * / % 二元算术或组合运算，通常带 Output 关联类型 向量、矩阵、金额、时长
    AddAssign / SubAssign 等 += -= *= /= %= 原地更新运算 累加器、数值容器、状态聚合
    Neg / Not -x / !x 一元取负或逻辑/位取反 数值、布尔包装、标志位
    BitAnd / BitOr / BitXor & | ^ 位运算或集合式组合 bitflags、权限集合、集合交并
    Shl / Shr << >> 位移或领域内移位语义 位操作、缓冲区、编码结构
    RangeBounds ..、a..b、..=b 等范围边界抽象 接收多种范围参数 区间查询、集合范围视图 
    use std::ops::Add;

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
struct Millimeters(u32);

#[derive(Debug, Clone, Copy)]
struct Meters(u32);

impl Add<Meters> for Millimeters {
    type Output = Millimeters;

    fn add(self, rhs: Meters) -> Self::Output {
        Millimeters(self.0 + rhs.0 * 1000)
    }
}

assert_eq!(Millimeters(500) + Meters(2), Millimeters(2500));

    Output 不一定必须等于 Self。上例中右操作数是 Meters，输出是 Millimeters；这正是 Rust 运算符 trait 比许多语言更精确的地方。

    范围相关 API 可以用 RangeBounds 同时接受 ..、1..、1..=3 等形式：

    use std::ops::{Bound, RangeBounds};

fn describe_range<R>(range: R) -> String
where
    R: RangeBounds<usize>,
{
    let start = match range.start_bound() {
        Bound::Included(value) => format!("from {value}"),
        Bound::Excluded(value) => format!("after {value}"),
        Bound::Unbounded => "from start".to_string(),
    };

    let end = match range.end_bound() {
        Bound::Included(value) => format!("through {value}"),
        Bound::Excluded(value) => format!("before {value}"),
        Bound::Unbounded => "to end".to_string(),
    };

    format!("{start}, {end}")
}

    运算符 trait 的实践原则：+ 应该像加法或组合，* 应该像乘法或缩放，Index 应该是访问而不是查询，AddAssign 应该与 Add 的语义一致。不要为了语法漂亮而牺牲可预测性。

    2.5.4. 格式化 / 转换 Trait¶

    格式化 / 转换类 trait 负责“类型如何呈现为文本”以及“类型之间如何转换”。它们直接影响日志、错误信息、CLI 输出、配置解析和公共 API 易用性。

    Trait 定义 / 核心语义 使用场景 示例
    Debug 面向开发者的调试输出，使用 {:?} / {:#?} 日志、断言、临时排查，常用 derive println!("{value:?}")
    Display 面向用户的友好文本，使用 {} CLI 输出、错误展示、业务文本 format!("{user}")
    fmt::Write 向字符串缓冲区写格式化文本 构建字符串、实现自定义格式化器 write!(&mut s, "{}", x)
    Binary / Octal / LowerHex / UpperHex 数字进制格式化 调试协议、位标志、地址展示 format!("{n:#x}")
    From<T> 从 T 无失败转换为 Self 错误聚合、newtype 构造、类型升级 String::from("hi")
    Into<T> 消费 Self 转成 T，通常由 From 自动提供 泛型 API 接收多种输入 value.into()
    TryFrom<T> / TryInto<T> 可能失败的转换 数值收窄、校验型构造 u8::try_from(n)
    FromStr 从字符串解析，常配合 parse CLI 参数、配置、协议字段 "42".parse::<u16>()
    ToString 转为 String，对所有 Display 类型自动实现 文本输出、简单序列化 value.to_string()

    Debug 适合派生，保留结构信息；Display 通常手写，因为它表达的是用户或领域应该看到的文本。

    use std::fmt;

#[derive(Debug)]
struct UserId(u64);

impl fmt::Display for UserId {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "user-{}", self.0)
    }
}

let id = UserId(42);
assert_eq!(format!("{id}"), "user-42");
assert_eq!(format!("{id:?}"), "UserId(42)");

    转换 trait 的核心取舍是：转换是否可能失败、是否会丢失信息、是否符合直觉。无失败、无信息丢失、语义自然时用 From；需要校验或可能失败时用 TryFrom；从字符串解析时实现 FromStr。

    use std::convert::TryFrom;
use std::str::FromStr;

#[derive(Debug, PartialEq, Eq)]
struct Port(u16);

impl TryFrom<u32> for Port {
    type Error = String;

    fn try_from(value: u32) -> Result<Self, Self::Error> {
        u16::try_from(value)
            .map(Port)
            .map_err(|_| format!("port out of range: {value}"))
    }
}

impl FromStr for Port {
    type Err = String;

    fn from_str(input: &str) -> Result<Self, Self::Err> {
        input
            .parse::<u32>()
            .map_err(|err| err.to_string())
            .and_then(Port::try_from)
    }
}

let port: Port = "8080".parse()?;

    公共 API 接收参数时可以使用 impl Into<T> 提升易用性，但不要滥用到让类型推断变差。返回值一般不建议返回 impl Into<T>，而应返回明确的领域类型或 impl Trait。

    2.5.5. 迭代器 Trait¶

    迭代器 trait 是 Rust 集合处理、函数式链式调用和 for 循环的基础。它们把“如何产生元素”“如何消费元素”“如何从元素构造集合”拆成不同抽象。

    Trait 定义 / 核心语义 使用场景 示例
    Iterator 逐个产生 Item，核心方法是 next 惰性处理、链式转换、适配器组合 iter.map(...).filter(...)
    IntoIterator 把值转换为迭代器，for 循环入口 泛型接收任意可迭代对象 for x in items
    FromIterator 从迭代器构造集合 collect 的目标类型 collect::<Vec<_>>()
    Extend 用迭代器扩展已有集合 批量追加、复用已分配集合 vec.extend(iter)
    DoubleEndedIterator 支持从后往前迭代 反向遍历、双端消费 iter.rev()
    ExactSizeIterator 可准确知道剩余长度 预分配、进度显示、优化 iter.len()
    FusedIterator 返回 None 后永远返回 None 迭代器适配器可靠组合 iter.fuse()

    API 参数通常优先使用 impl IntoIterator，这样调用方既可以传数组、Vec<T>，也可以传已有迭代器：

    fn normalize_words<I, S>(words: I) -> Vec<String>
where
    I: IntoIterator<Item = S>,
    S: AsRef<str>,
{
    words
        .into_iter()
        .map(|word| word.as_ref().trim().to_lowercase())
        .filter(|word| !word.is_empty())
        .collect()
}

let words = normalize_words([" Rust ", "", "Trait"]);
assert_eq!(words, vec!["rust", "trait"]);

    实现自定义迭代器时，通常只需要实现 Iterator::next，其他大量方法由默认实现提供：

    struct Countdown(u8);

impl Iterator for Countdown {
    type Item = u8;

    fn next(&mut self) -> Option<Self::Item> {
        let current = self.0;
        if current == 0 {
            None
        } else {
            self.0 -= 1;
            Some(current)
        }
    }
}

assert_eq!(Countdown(3).collect::<Vec<_>>(), vec![3, 2, 1]);

    返回迭代器时，优先考虑 impl Iterator<Item = T>。它隐藏内部复杂类型，保留静态分发和内联机会：

    fn even_numbers(limit: i32) -> impl Iterator<Item = i32> {
    (0..limit).filter(|value| value % 2 == 0)
}

    如果一个集合类型要接入 collect，实现 FromIterator；如果要支持向已有集合批量追加，实现 Extend。这两个 trait 是集合生态互操作的关键。

    2.5.6. I/O / 错误 / 函数 Trait¶

    这一类 trait 覆盖三种工程边界：字节流读写、错误抽象、可调用对象。它们经常出现在应用框架、命令行工具、网络服务、异步任务和回调式 API 中。

    子类 Trait 定义 / 核心语义 使用场景
    I/O Read 从字节流读取数据 文件、TCP、内存缓冲区
    I/O Write 向字节流写数据 文件输出、网络发送、缓冲构造
    I/O BufRead 带缓冲读取，支持按行读取 文本协议、日志、配置
    I/O Seek 调整读写位置 随机访问文件、二进制格式
    错误 std::error::Error 标准错误抽象，通常结合 Debug + Display 公共错误类型、错误链
    错误 From 错误类型转换 ? 传播时聚合底层错误
    函数 FnOnce 至少可调用一次，可能消耗捕获值 线程入口、一次性回调
    函数 FnMut 可多次调用，可能修改捕获状态 重试逻辑、迭代器适配器
    函数 Fn 可多次共享调用，不修改捕获状态 纯回调、共享处理器

    I/O trait 让函数不绑定具体输入输出来源，从而同时支持文件、网络、标准输入输出和内存缓冲区：

    use std::io::{self, BufRead, Write};

fn copy_non_empty_lines<R, W>(reader: R, mut writer: W) -> io::Result<usize>
where
    R: BufRead,
    W: Write,
{
    let mut count = 0;
    for line in reader.lines() {
        let line = line?;
        if !line.trim().is_empty() {
            writeln!(writer, "{line}")?;
            count += 1;
        }
    }
    Ok(count)
}

    标准错误类型通常需要 Debug、Display 和 Error，再用 From 接入 ? 的错误转换链：

    use std::error::Error;
use std::fmt;
use std::io;

#[derive(Debug)]
enum AppError {
    Io(io::Error),
    InvalidConfig(String),
}

impl fmt::Display for AppError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            AppError::Io(err) => write!(f, "io error: {err}"),
            AppError::InvalidConfig(msg) => write!(f, "invalid config: {msg}"),
        }
    }
}

impl Error for AppError {
    fn source(&self) -> Option<&(dyn Error + 'static)> {
        match self {
            AppError::Io(err) => Some(err),
            AppError::InvalidConfig(_) => None,
        }
    }
}

impl From<io::Error> for AppError {
    fn from(err: io::Error) -> Self {
        AppError::Io(err)
    }
}

fn read_config(path: &str) -> Result<String, AppError> {
    Ok(std::fs::read_to_string(path)?)
}

    闭包会根据捕获方式自动实现 Fn、FnMut、FnOnce 中的一个或多个。API 应选择最小必要约束：只调用一次用 FnOnce，需要修改捕获状态用 FnMut，只共享读取用 Fn。

    fn retry<T, E, F>(times: usize, mut f: F) -> Result<T, E>
where
    F: FnMut() -> Result<T, E>,
{
    let mut last = None;
    for _ in 0..times {
        match f() {
            Ok(value) => return Ok(value),
            Err(err) => last = Some(err),
        }
    }
    Err(last.expect("times must be greater than zero"))
}

let mut attempts = 0;
let result = retry(3, || {
    attempts += 1;
    if attempts == 2 { Ok("ok") } else { Err("not yet") }
});
assert_eq!(result, Ok("ok"));

    如果回调需要跨线程运行，通常还要叠加 Send + 'static；如果要作为共享处理器放入 Arc，可能需要 Sync 或使用 Arc<dyn Fn(...) + Send + Sync>。

    2.5.7. 六大类 Trait 选型速查¶

    你想表达的能力 所属分类 优先考虑的 trait
    小型值可以隐式复制 基础标记 Trait Copy + Clone
    值可以显式复制一份 基础标记 Trait Clone
    类型有合理默认值 基础标记 Trait Default

    集合键支持借用查询 解引用 / 访问 Trait Borrow<T>
    包装类型像智能指针一样访问内部值 解引用 / 访问 Trait Deref / DerefMut
    自定义类型支持 +、-、* 等 运算符重载 Trait Add / Sub / Mul 等

    可以打印给用户看 格式化 / 转换 Trait Display

    类型之间可能失败转换 格式化 / 转换 Trait TryFrom / TryInto

    接收回调或闭包 I/O / 错误 / 函数 Trait Fn / FnMut / FnOnce

    标准库 trait 的使用原则可以概括为：用最小 trait 表达真实能力，用组合 trait 描述边界需求，用 derive 处理机械语义，用手写实现表达领域语义。分类只是帮助记忆；真正写泛型约束时，应回到函数体实际需要调用的方法和 API 边界真正承诺的能力。

    2.6. 静态分发、单态化与零成本抽象¶

    Rust 泛型默认使用静态分发。编译器会在编译期根据实际类型生成具体版本，这个过程称为单态化（Monomorphization）。

    fn add_one<T>(value: T) -> T
where
    T: std::ops::Add<Output = T> + From<u8>,
{
    value + T::from(1)
}

let a = add_one(1_u32);
let b = add_one(1_i64);

    对 u32 和 i64 的调用会生成不同版本的机器码，因此泛型调用通常不需要虚表查找，也容易被内联优化。这就是 Rust “零成本抽象”的重要来源。

    静态分发的代价主要有两个：

    代价 说明 应对方式
    编译时间增加 复杂泛型会增加类型检查和代码生成成本 减少不必要的泛型层级，抽出非泛型核心逻辑
    二进制体积膨胀 多个具体类型会生成多份代码 对冷路径使用 trait object，或把共通逻辑放到非泛型函数中

    常见优化思路是把“类型相关的薄包装”保留为泛型，把“类型无关的重逻辑”下沉到普通函数：

    fn parse_lines<R>(reader: R) -> usize
where
    R: std::io::BufRead,
{
    count_non_empty(reader.lines().map_while(Result::ok))
}

fn count_non_empty<I>(lines: I) -> usize
where
    I: IntoIterator<Item = String>,
{
    lines.into_iter().filter(|line| !line.trim().is_empty()).count()
}

    2.7. impl Trait：参数简写与返回值封装¶

    impl Trait 可以出现在参数位置和返回值位置，但含义略有不同。

    参数位置的 impl Trait 是匿名泛型参数，适合简化不需要命名的泛型：

    fn notify(message: impl std::fmt::Display) {
    println!("{message}");
}

    它大致等价于：

    fn notify_generic<T: std::fmt::Display>(message: T) {
    println!("{message}");
}

    返回值位置的 impl Trait 表示“返回某个实现了 trait 的具体类型，但调用方不需要知道它的名字”：

    fn even_numbers() -> impl Iterator<Item = i32> {
    (0..).filter(|value| value % 2 == 0)
}

    返回 impl Trait 时，同一个函数的所有返回路径必须归一到同一个具体类型。下面的写法通常无法通过编译，因为两个分支的迭代器类型不同：

    // fn numbers(reverse: bool) -> impl Iterator<Item = i32> {
//     if reverse {
//         (0..10).rev()
//     } else {
//         0..10
//     }
// }

    遇到这种情况，可以使用枚举统一类型、装箱为 Box<dyn Iterator<Item = i32>>，或调整 API 让调用方选择策略。

    impl Trait 的核心价值是封装复杂具体类型，尤其是迭代器、闭包和异步函数返回的状态机类型。它保留静态分发性能，同时减少公开 API 对内部实现的暴露。

    2.8. dyn Trait 与动态分发¶

    dyn Trait 表示 trait object。它把不同具体类型擦除为统一的运行时抽象，通过胖指针保存数据指针和虚表指针，在调用方法时进行动态分发。

    trait Draw {
    fn draw(&self);
}

struct Button;
struct TextField;

impl Draw for Button {
    fn draw(&self) {
        println!("draw button");
    }
}

impl Draw for TextField {
    fn draw(&self) {
        println!("draw text field");
    }
}

let widgets: Vec<Box<dyn Draw>> = vec![Box::new(Button), Box::new(TextField)];
for widget in widgets {
    widget.draw();
}

    动态分发适合这些场景：

    场景 为什么适合 dyn Trait
    异构集合 一个集合中存放多种具体类型
    插件/策略对象 运行时选择不同实现
    降低泛型扩散 避免复杂泛型参数污染大量 API
    控制二进制体积 冷路径可接受虚调用成本

    选择 impl Trait 还是 dyn Trait 时，可以按以下思路判断：

    维度 impl Trait / 泛型 dyn Trait
    分发方式 编译期静态分发 运行时动态分发
    性能 易内联，通常更快 有一次虚表调用成本
    类型数量 每个具体类型生成代码 多个类型共享一套调用边界
    API 表达 调用方或编译器知道具体类型 调用方只知道 trait
    典型用途 热路径、迭代器、泛型算法 异构集合、插件、运行时多态

    2.9. 对象安全：哪些 Trait 能变成 dyn Trait¶

    不是所有 trait 都能作为 trait object 使用。能被转换成 dyn Trait 的 trait 需要满足对象安全（object safety）规则。核心原因是：动态分发时，编译器必须能通过虚表确定要调用的函数签名。

    通常会破坏对象安全的设计包括：

    设计 问题 常见修复
    方法返回 Self dyn Trait 不知道具体返回类型 加 where Self: Sized，或返回 boxed trait object
    泛型方法 虚表无法为无限多个类型参数列出入口 把泛型移到 trait 参数或使用枚举/闭包封装
    按值接收 self 且未限制 Sized trait object 大小未知 使用 Box<Self>、&self、&mut self 或 where Self: Sized 
    trait CloneableName {
    fn name(&self) -> &str;

    fn clone_box(&self) -> Box<dyn CloneableName>
    where
        Self: Sized,
    {
        Box::new(SimpleName(self.name().to_string()))
    }
}

struct SimpleName(String);

impl CloneableName for SimpleName {
    fn name(&self) -> &str {
        &self.0
    }
}

    where Self: Sized 的含义是：这个方法只对具体类型可用，不放进 trait object 的虚表中。这样既能保留便利方法，又不会破坏对象安全。

    2.10. 关联类型与泛型参数的取舍¶

    Trait 中可以使用泛型参数，也可以使用关联类型。二者都能表达“某个类型与另一个类型相关”，但语义不同。

    关联类型表示“实现者决定并固定的输出类型”：

    trait Parser {
    type Output;

    fn parse(&self, input: &str) -> Result<Self::Output, String>;
}

struct NumberParser;

impl Parser for NumberParser {
    type Output = i64;

    fn parse(&self, input: &str) -> Result<Self::Output, String> {
        input.parse().map_err(|err| format!("{err}"))
    }
}

    泛型参数表示“同一个实现可以面向多个输入类型或目标类型”：

    trait Convert<T> {
    fn convert(self) -> T;
}

impl Convert<String> for i32 {
    fn convert(self) -> String {
        self.to_string()
    }
}

impl Convert<i64> for i32 {
    fn convert(self) -> i64 {
        self as i64
    }
}

    经验规则：

    问题 更适合
    每个实现只有一个自然结果类型 关联类型
    同一个实现需要支持多个目标类型 泛型参数
    调用方经常需要显式选择目标类型 泛型参数
    API 希望减少重复类型参数 关联类型

    Iterator 使用关联类型 Item，因为一个迭代器实现通常只有一个自然的元素类型：

    fn sum_i32<I>(iter: I) -> i32
where
    I: Iterator<Item = i32>,
{
    iter.sum()
}

    2.11. 关联常量与默认类型参数¶

    Trait 可以定义关联常量，用于把类型级别的固定配置放入 trait 契约中：

    trait Packet {
    const HEADER_LEN: usize;

    fn payload(&self) -> &[u8];

    fn total_len(&self) -> usize {
        Self::HEADER_LEN + self.payload().len()
    }
}

    关联常量适合表达与类型绑定、编译期已知的值，例如协议头长度、算法块大小、固定维度等。

    泛型类型和 trait 也可以有默认类型参数。标准库中的 Add trait 就使用默认类型参数 Rhs = Self，表示默认与同类型相加：

    use std::ops::Add;

#[derive(Debug, Clone, Copy)]
struct Point {
    x: i32,
    y: i32,
}

impl Add for Point {
    type Output = Point;

    fn add(self, rhs: Point) -> Self::Output {
        Point {
            x: self.x + rhs.x,
            y: self.y + rhs.y,
        }
    }
}

    如果需要和不同类型相加，可以显式指定右侧类型：

    impl Add<(i32, i32)> for Point {
    type Output = Point;

    fn add(self, rhs: (i32, i32)) -> Self::Output {
        Point {
            x: self.x + rhs.0,
            y: self.y + rhs.1,
        }
    }
}

    2.12. Supertrait 与能力组合¶

    Supertrait 表示“实现某个 trait 的类型必须同时实现另一个 trait”。它适合表达能力组合，而不是继承层级。

    use std::fmt::Display;

trait PrettyPrint: Display {
    fn pretty(&self) -> String {
        format!("*** {self} ***")
    }
}

impl<T> PrettyPrint for T where T: Display {}

    这里任何实现了 Display 的类型都可以获得 PrettyPrint 的默认实现。Supertrait 常见于框架边界，例如要求某个类型同时具备调试、发送、同步或生命周期能力：

    trait Service: Send + Sync + 'static {
    fn name(&self) -> &str;
    fn call(&self, request: String) -> String;
}

    这类约束通常用于多线程服务注册表、异步任务、插件系统等场景。需要注意的是，组合能力越多，API 的适用范围越窄；只有当边界确实需要这些能力时才应放到 trait 定义上。

    2.13. Blanket Impl 与扩展 Trait¶

    Blanket impl 是对所有满足条件的类型统一实现某个 trait。它是 Rust 生态中非常常见的扩展方式。

    trait StringExt {
    fn quoted(&self) -> String;
}

impl<T> StringExt for T
where
    T: AsRef<str>,
{
    fn quoted(&self) -> String {
        format!("\"{}\"", self.as_ref())
    }
}

    这样 String、&str、Cow<'_, str> 等所有实现 AsRef<str> 的类型都能调用 quoted。

    Blanket impl 的优点是覆盖面广、复用性强；风险是可能与未来实现冲突，尤其是在公共库中要谨慎设计。标准库中有许多重要的 blanket impl，例如：

    // 概念示意：任何实现 Display 的类型都自动实现 ToString。
// impl<T: Display + ?Sized> ToString for T { ... }

    扩展 trait 常用于给外部类型添加方法。由于不能直接为外部类型定义固有方法，可以定义本地 trait，再为外部类型实现它：

    trait VecExt<T> {
    fn second(&self) -> Option<&T>;
}

impl<T> VecExt<T> for Vec<T> {
    fn second(&self) -> Option<&T> {
        self.get(1)
    }
}

    2.14. 孤儿规则与一致性¶

    Rust 的孤儿规则（orphan rule）要求：为某个类型实现某个 trait 时，trait 或类型至少有一个必须定义在当前 crate 中。这个规则保证全局一致性，避免不同 crate 对同一组 trait/type 写出互相冲突的实现。

    允许的例子：

    trait LocalTrait {
    fn mark(&self) -> String;
}

impl LocalTrait for String {
    fn mark(&self) -> String {
        format!("local:{self}")
    }
}

    不允许的例子：

    // 错误：Display 和 Vec<T> 都来自外部 crate/std。
// impl std::fmt::Display for Vec<String> { ... }

    常见解决方案：

    目标 做法
    给外部类型添加外部 trait 实现 使用 newtype 包装
    给外部类型添加方法 定义本地扩展 trait
    避免实现冲突 在本 crate 中定义明确的适配类型

    Newtype 是最常见、最符合 Rust 设计的做法：

    use std::fmt;

struct DisplayVec<T>(Vec<T>);

impl<T: fmt::Display> fmt::Display for DisplayVec<T> {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        let joined = self.0.iter().map(ToString::to_string).collect::<Vec<_>>().join(", ");
        write!(f, "[{joined}]")
    }
}

    2.15. Sized、?Sized 与动态大小类型¶

    Rust 默认假设泛型参数是 Sized，即编译期大小已知：

    fn consume<T>(value: T) {
    drop(value);
}

    这等价于：

    fn consume_sized<T: Sized>(value: T) {
    drop(value);
}

    有些类型大小在编译期未知，例如 str、[T]、dyn Trait。它们通常必须通过引用、智能指针或其他胖指针间接使用。?Sized 用来放宽默认的 Sized 约束：

    fn print_debug<T: std::fmt::Debug + ?Sized>(value: &T) {
    println!("{value:?}");
}

print_debug("hello");
print_debug(&[1, 2, 3]);

    ?Sized 常用于库代码，尤其是希望函数同时接受 String/str、Vec<T>/[T]、具体类型/dyn Trait 的引用时。它通常与引用或指针一起出现，因为无法直接按值传递大小未知的类型。

    2.16. 自动 Trait、标记 Trait 与线程安全边界¶

    Rust 有一些由编译器自动推导的 trait，例如 Send 和 Sync。它们不描述普通方法，而描述类型是否可以安全地跨线程移动或共享。

    Trait 含义 简化理解
    Send 值可以安全移动到另一个线程 所有权跨线程转移安全
    Sync &T 可以安全在线程间共享 多线程共享引用安全
    Unpin 值可以在固定后安全移动 与 Pin/异步状态机相关 
    use std::sync::Arc;
use std::thread;

fn run_in_background<T>(value: T)
where
    T: Send + 'static,
{
    thread::spawn(move || drop(value));
}

fn share_between_threads<T>(value: Arc<T>)
where
    T: Send + Sync + 'static,
{
    thread::spawn(move || drop(value));
}

    Send + Sync + 'static 经常出现在多线程和异步任务边界。它不表示值一定“永远存活”，而表示该值不包含短生命周期借用，可以安全交给可能长期运行的任务持有。

    Marker trait 通常没有方法，只表达类型层面的性质。自定义 marker trait 时要谨慎，因为一旦作为公共 API 暴露，就会影响下游类型能否接入该抽象。

    2.17. 泛型生命周期与 HRTB¶

    泛型不仅可以参数化类型，也可以参数化生命周期。生命周期参数表达的是引用之间的有效性关系，而不是延长某个值的存活时间。

    fn first<'a, T>(items: &'a [T]) -> Option<&'a T> {
    items.first()
}

    当一个闭包或函数需要“对任意生命周期都成立”时，会用到高阶生命周期约束（Higher-Ranked Trait Bounds, HRTB）：

    fn apply_to_str<F>(f: F)
where
    F: for<'a> Fn(&'a str),
{
    f("temporary");
}

    for<'a> 的含义是：F 不能只适配某一个特定生命周期，而必须能接受任意生命周期的 &str。这在回调、解析器、访问器、trait object 和借用型 API 中非常重要。

    更现实的例子是把借用限制在回调内部，避免把内部引用泄漏出去：

    struct Registry {
    names: Vec<String>,
}

impl Registry {
    fn with_each<F>(&self, mut f: F)
    where
        F: for<'a> FnMut(&'a str),
    {
        for name in &self.names {
            f(name);
        }
    }
}

    HRTB 的阅读重点是“对所有生命周期成立”，不是“存在一个生命周期”。这与普通的 F: Fn(&'a str) 有本质差别。

    2.18. GAT：泛型关联类型¶

    泛型关联类型（Generic Associated Types, GAT）允许关联类型自身带泛型参数，最典型的用途是表达“返回值借用了 self”的迭代或访问模式。

    trait LendingIterator {
    type Item<'a>
    where
        Self: 'a;

    fn next<'a>(&'a mut self) -> Option<Self::Item<'a>>;
}

    普通 Iterator 的 Item 不能借用迭代器自身，因此很难表达“每次迭代返回指向内部缓冲区的引用”。GAT 可以把 Item 与调用 next 时的借用生命周期关联起来。

    一个简化示例：

    struct WindowsMut<'a, T> {
    slice: &'a mut [T],
    size: usize,
}

trait WindowSource {
    type Window<'a>
    where
        Self: 'a;

    fn first_window<'a>(&'a mut self) -> Option<Self::Window<'a>>;
}

impl<'s, T> WindowSource for WindowsMut<'s, T> {
    type Window<'a> = &'a mut [T] where Self: 'a;

    fn first_window<'a>(&'a mut self) -> Option<Self::Window<'a>> {
        self.slice.get_mut(..self.size)
    }
}

    GAT 能显著提升库抽象能力，但也会提高签名复杂度。只有当普通关联类型、回调或拥有型返回值无法表达需求时，才应引入 GAT。

    2.19. 常量泛型¶

    常量泛型允许把编译期常量作为泛型参数。它常用于数组长度、矩阵维度、协议字段大小、固定容量容器等场景。

    struct Matrix<T, const ROWS: usize, const COLS: usize> {
    data: [[T; COLS]; ROWS],
}

impl<T, const ROWS: usize, const COLS: usize> Matrix<T, ROWS, COLS> {
    fn rows(&self) -> usize {
        ROWS
    }

    fn cols(&self) -> usize {
        COLS
    }
}

    常量泛型把一部分运行时错误前移到编译期。例如两个维度不匹配的矩阵可以在类型层面被区分：

    fn multiply<T, const M: usize, const N: usize, const P: usize>(
    _left: Matrix<T, M, N>,
    _right: Matrix<T, N, P>,
) -> Matrix<T, M, P>
where
    T: Default + Copy,
{
    Matrix {
        data: [[T::default(); P]; M],
    }
}

    常量泛型适合表达真正稳定、有限、编译期有意义的约束。不要把大量业务配置都塞进类型参数，否则会导致类型爆炸、编译变慢、错误信息难读。

    2.20. PhantomData 与类型状态模式¶

    PhantomData<T> 表示“这个类型在逻辑上拥有或关联 T，即使字段中没有真正存储 T”。它会影响方差、drop check、自动 trait 推导和类型语义。

    use std::marker::PhantomData;

struct Id<T> {
    raw: u64,
    _marker: PhantomData<T>,
}

struct User;
struct Order;

type UserId = Id<User>;
type OrderId = Id<Order>;

    UserId 和 OrderId 运行时都只是 u64，但类型系统会阻止它们被混用。

    类型状态模式（typestate pattern）使用泛型参数表达对象所处状态，把非法调用变成编译错误：

    struct Disconnected;
struct Connected;

struct Client<State> {
    address: String,
    _state: PhantomData<State>,
}

impl Client<Disconnected> {
    fn connect(self) -> Client<Connected> {
        Client {
            address: self.address,
            _state: PhantomData,
        }
    }
}

impl Client<Connected> {
    fn send(&self, body: &str) {
        println!("send to {}: {body}", self.address);
    }
}

    这种模式适合协议握手、构建器、资源生命周期、权限状态等强约束场景。代价是类型数量和 API 复杂度上升，不适合简单业务流程滥用。

    2.21. 泛型错误处理与抽象边界¶

    泛型错误处理要在“保留具体错误信息”和“简化调用边界”之间取舍。库内部通常保留具体错误类型，应用边界可以使用统一错误类型。

    fn parse_all<T, E>(items: &[&str]) -> Result<Vec<T>, E>
where
    T: std::str::FromStr<Err = E>,
{
    items.iter().map(|item| item.parse()).collect()
}

    这里错误类型 E 来自 T::Err，调用方可以获得精确错误。若这是应用层命令处理函数，可能更适合转换成统一错误：

    fn parse_ports(items: &[&str]) -> Result<Vec<u16>, String> {
    items
        .iter()
        .map(|item| item.parse::<u16>().map_err(|err| format!("invalid port {item}: {err}")))
        .collect()
}

    设计原则：

    层级 建议
    底层库 暴露结构化、可匹配的具体错误类型
    中间抽象 使用 From/Into 聚合错误，保留来源
    应用边界 转成人类可读信息或统一错误报告
    trait API 谨慎选择关联错误类型或泛型错误参数

    2.22. 泛型 API 的可读性与演进¶

    泛型能力越强，越需要控制 API 表面积。一个专业的泛型 API 不只是“能编译”，还要让调用方容易理解错误信息、推断类型并完成组合。

    实用建议：

    建议 说明
    优先从具体类型开始 先验证行为，再提炼泛型抽象
    让约束靠近真实需求 不要提前要求 Clone、Send、Sync、'static
    使用 where 子句整理复杂约束 签名可读性比炫技更重要
    用类型别名或 newtype 收束复杂类型 降低错误信息和文档负担
    公开 API 少暴露实现细节 返回 impl Trait 或领域类型，而不是复杂组合类型
    为常见场景提供便利函数 不要让用户每次都手写完整泛型参数

    例如，内部可以使用复杂泛型保持灵活，外部提供简单入口：

    fn load_with<R, P>(reader: R, parser: P) -> Result<Vec<P::Output>, P::Error>
where
    R: std::io::BufRead,
    P: LineParser,
{
    reader.lines().map(|line| parser.parse(&line?)).collect()
}

trait LineParser {
    type Output;
    type Error: From<std::io::Error>;

    fn parse(&self, line: &str) -> Result<Self::Output, Self::Error>;
}

    如果这样的签名开始影响使用体验，可以进一步提供领域化包装函数，把复杂度封装在库内部。

    2.23. 常见编译错误的理解方式¶

    泛型与 trait 相关错误往往很长，但通常可以归纳为几类：

    错误类型 常见原因 排查方向
    trait bound not satisfied 泛型参数缺少能力约束 找到实际调用的方法，为类型参数补充最小 bound
    cannot infer type 编译器缺少足够上下文 添加类型标注、turbofish 或拆分表达式
    mismatched types 不同分支或泛型实例返回类型不一致 用枚举、trait object 或统一返回类型
    not object safe trait 不能变成 dyn Trait 检查 Self 返回、泛型方法、Sized 约束
    lifetime may not live long enough 借用关系被泛型签名表达错 回到数据所有权，确认返回值是否真的借用输入

    turbofish 语法 ::<T> 用于在方法或函数调用处显式指定泛型参数：

    let value = "42".parse::<i32>()?;
let numbers = collect_debug::<Vec<_>>(vec![1, 2, 3]);

    当错误信息过长时，可以按步骤缩小范围：先把链式调用拆成中间变量，再给关键变量添加类型标注，最后根据真实使用的方法补充 trait bound。不要在不了解原因时盲目添加 Clone + Send + Sync + 'static，这会把 API 约束越推越重。

    2.24. 实战选型：泛型、impl Trait、dyn Trait 与枚举¶

    同一类抽象通常有多种表达方式。选择时应同时考虑性能、可读性、演进能力和调用方体验。

    需求 推荐方式 原因
    热路径算法适配多种类型 泛型 + trait bound 静态分发、可内联
    返回复杂但单一的具体类型 impl Trait 隐藏实现细节且保持零成本
    一个集合容纳多种实现 Box<dyn Trait> / Arc<dyn Trait> 类型擦除，运行时多态
    有限几种已知实现 枚举 无虚调用，模式匹配清晰
    公共库需要稳定 ABI 风格边界 trait object 或领域类型 减少泛型扩散和破坏性变更
    类型表达协议状态 typestate + PhantomData 编译期阻止非法顺序

    一个常见演进路径是：先写具体实现；发现重复后提取泛型函数；当泛型签名扩散影响使用体验时，用 impl Trait 或领域类型封装；当确实需要运行时替换实现时，再引入 dyn Trait。

    2.25. 小结¶

    泛型与特征的核心不是语法堆叠，而是用类型系统表达真实约束：

    • 泛型让算法和数据结构摆脱具体类型，但不会自动赋予类型任何能力。
    • Trait bound 应表达泛型代码真正需要的最小能力，复杂约束优先放进 where 子句。
    • 静态分发适合性能敏感和类型已知的场景，动态分发适合异构集合、插件和运行时策略切换。
    • 关联类型、GAT、常量泛型、PhantomData 等能力适合库设计和强约束建模，但需要控制复杂度。
    • 好的泛型 API 应该让正确用法自然、错误信息可理解、后续演进有余地。

    3.函数式编程¶

    3.1. Rust 中的函数式编程定位¶

    Rust 不是纯函数式语言，但大量吸收了函数式编程思想：不可变性、表达式、闭包、高阶函数、模式匹配、代数数据类型、迭代器链式处理等。

    Rust 的函数式编程强调：用类型系统和所有权模型，在保持零成本抽象的前提下，写出安全、组合性强、可推理的代码。

    let sum: i32 = (1..=10)
    .filter(|x| x % 2 == 0)
    .map(|x| x * x)
    .sum();

assert_eq!(sum, 220);

    这段代码会被编译器优化为接近手写循环的机器码，不会因为链式调用产生额外集合分配。

    3.2. 表达式导向¶

    Rust 中大多数语法都是表达式，if、match、代码块都可以返回值。

    let level = 8;

let label = if level >= 9 {
    "excellent"
} else if level >= 6 {
    "good"
} else {
    "keep going"
};

let value = {
    let base = 10;
    base * 2
};

    表达式导向可以减少临时可变变量，让代码更接近「数据转换管道」。

    3.3. 闭包与环境捕获¶

    闭包是可以捕获环境的匿名函数，语法为 |参数| 表达式 或 |参数| { 代码块 }。

    let factor = 3;
let multiply = |x| x * factor;

assert_eq!(multiply(4), 12);

    闭包根据捕获方式自动实现不同 trait：

    Trait 捕获方式 调用能力 典型场景
    Fn 不可变借用 可多次调用 只读环境、回调
    FnMut 可变借用 可多次调用 修改捕获状态
    FnOnce 获取所有权 至少调用一次 消费捕获值、线程闭包 
    let mut count = 0;

let mut inc = || {
    count += 1;
    count
};

assert_eq!(inc(), 1);
assert_eq!(inc(), 2);

    如果要把闭包移动到线程或异步任务中，通常需要使用 move：

    let data = vec![1, 2, 3];

std::thread::spawn(move || {
    println!("{:?}", data);
});

    3.4. 高阶函数¶

    高阶函数是接收函数/闭包作为参数，或返回函数/闭包的函数。

    fn apply_twice<F>(mut f: F, value: i32) -> i32
where
    F: FnMut(i32) -> i32,
{
    let value = f(value);
    f(value)
}

assert_eq!(apply_twice(|x| x + 1, 10), 12);

    返回闭包时，通常使用 impl Trait：

    fn make_adder(n: i32) -> impl Fn(i32) -> i32 {
    move |x| x + n
}

let add_three = make_adder(3);
assert_eq!(add_three(7), 10);

    3.5. 迭代器与惰性求值¶

    Rust 迭代器是函数式编程中最常用的工具。map、filter、take、skip 等适配器都是惰性的，只有遇到消费器才会真正执行。

    适配器是 Iterator trait 提供的方法，接收原迭代器，返回全新迭代器，不会立刻消费元素，属于惰性求值。

    特点：

    1. 不立即遍历，仅包装迭代逻辑；
    2. 链式调用，可无限拼接；
    3. 只有调用消费器（collect/for/sum/count）才会真正执行迭代。

    区分几个概念：

    • 生成器：迭代器转换（ iter() / iter_mut() / into_iter() ）
    • 作用：把集合（Vec / 数组 / HashMap 等）转换成迭代器，是「迭代流程的起点」。
      • 调用主体：容器（Vec、数组、BTreeMap 等）；
      • 返回值：实现 Iterator trait 的迭代器对象；
      • 只负责 “造迭代器”，不做元素处理、不终止遍历。
    • 适配器：产生新迭代器（map/filter/flat_map）；
    • 作用：接收一个迭代器，返回新迭代器，惰性包装遍历逻辑；
      • 调用主体：已经生成好的迭代器；
      • 返回值：全新包装迭代器，依然是 Iterator；
      • 仅增加处理规则，不会真正遍历、消耗元素。
    • 消费器：消耗迭代器、产出最终结果（collect/fold/any）。
    • 作用：消耗迭代器，真正遍历所有元素，产出最终结果，链式调用终点；
      • 调用主体：迭代器；
      • 返回值：不是迭代器，是业务数据（Vec、数字、布尔等）；
      • 一旦调用，迭代器被销毁，无法继续链式调用。

    生成器：

    • iter()：产生不可变引用迭代器 &T，不转移所有权，原容器保留；
    • iter_mut()：产生可变引用迭代器 &mut T，可修改容器内元素；
    • into_iter()：拿走容器所有权，产出元素本身 T，迭代后原容器失效；
    let result: Vec<_> = vec![1, 2, 3, 4, 5]
    .into_iter()
    .filter(|x| x % 2 == 1)
    .map(|x| x * 10)
    .collect();

assert_eq!(result, vec![10, 30, 50]);

    常见的适配器：

    • map() / flat_map(): 映射，元素转换
    • enumerate()：给每个元素拼接下标 (usize, Item)
    • rev()：反转迭代顺序，要求迭代器支持双向遍历。
    • filter() / filter_map()：过滤筛选
    • take() / take_while()：截取元素，停止迭代
    • skip() / skip_while()：跳过元素
    • zip()：两个迭代器一一配对，取最短长度，多余元素丢弃。
    • chain()：拼接两个迭代器，先消费第一个迭代器，再按顺序消费第二个迭代器。
    • 去重：标准 Iterator 没有通用的 dedup() 适配器；相邻元素去重可先收集到 Vec 后使用 Vec::dedup()，或使用 itertools::Itertools::dedup()。
    • windows(n) / chunks(n)：窗口

    常见消费器：

    • collect()：收集为集合；
    • count()：统计元素数量
    • sum() / product()：聚合计算；
    • fold() / reduce()：归约；
    • any() / all()：条件判断；
    • find() / position()：查找元素。
    • nth(n)：取第 n 个元素
    • max() / min()：最值
    let total = [1, 2, 3, 4]
    .iter()
    .fold(0, |acc, x| acc + x);

assert_eq!(total, 10);

    3.6. Option 与 Result 的函数式组合¶

    Rust 鼓励用 Option 表达可能为空，用 Result 表达可能失败，并通过组合子消除大量嵌套判断。

    fn parse_port(input: &str) -> Option<u16> {
    input
        .trim()
        .parse::<u16>()
        .ok()
        .filter(|port| *port > 0)
}

    1. Option<T> — 值的有无¶

    enum Option<T> {
    None,      // 没有值
    Some(T),   // 有值，包裹在 Some 中
}

    用途：处理可能为空的场景（如查找、可选字段）。

    2. Result<T, E> — 操作的成功或失败¶

    enum Result<T, E> {
    Ok(T),     // 成功，携带结果值
    Err(E),    // 失败，携带错误信息
}

    用途：处理可能失败的操作（如 I/O、解析、网络请求）。

    3. 核心对比¶

    维度 Option<T> Result<T, E>
    语义 "可能有值" "可能失败"
    变体 None / Some(T) Ok(T) / Err(E)
    错误信息 无（None 不携带原因） 有（Err 携带 E）
    典型场景 查找、缓存、可选配置 I/O、解析、验证、外部调用
    转换关系 Option<T> → Result<T, E> Result<T, E> → Option<T>

    4. Option 与 Result 的互转¶

    Option → Result¶
    方法 输入 输出 说明
    ok_or(err) Some(x) Ok(x) None → Err(err)
    ok_or_else(f) Some(x) Ok(x) None → Err(f())（惰性）
    transpose() Option<Result<T, E>> Result<Option<T>, E> 嵌套转换 
    let opt: Option<Result<i32, &str>> = Some(Ok(42));
let res: Result<Option<i32>, &str> = opt.transpose();  // Ok(Some(42))

let opt: Option<Result<i32, &str>> = Some(Err("fail"));
let res: Result<Option<i32>, &str> = opt.transpose();  // Err("fail")
    Result → Option¶
    方法 输入 输出 说明
    ok() Ok(x) Some(x) 丢弃错误
    err() Err(e) Some(e) 保留错误，丢弃成功值
    transpose() Result<Option<T>, E> Option<Result<T, E>> 嵌套转换 
    let res: Result<Option<i32>, &str> = Ok(Some(42));
let opt: Option<Result<i32, &str>> = res.transpose();  // Some(Ok(42))

    5. 链式操作（组合子）¶

    Option 组合子¶

    • map: Option<T> -> Option<U> 通过函数 T -> U。

    • and_then (flatmap): Option<T> -> Option<U> 通过函数 T -> Option<U>，用于链式操作可能失败。

    • or_else: 当是None时，通过函数生成另一个Option。
    • map_or: 对Some应用函数，对None返回默认值。
    • map_or_else: 类似，但默认值由函数产生。
    • unwrap_or / unwrap_or_else: 提取值或提供默认值。
    • filter: 过滤Some中的值，如果不满足谓词转为None。
    • flatten: Option<Option<T>> -> Option<T>。
    • 转换：ok_or, ok_or_else (转为Result)。
    • 运算符 ?：在返回 Option<T> 的函数或闭包中可以直接传播 None；在返回 Result<T, E> 的函数中若要处理 Option，通常先用 ok_or / ok_or_else 转成 Result。
    Result 组合子¶
    • map: Result<T,E> -> Result<U,E> 对Ok应用。
    • map_err: 对Err应用函数转换错误类型。
    • and_then: 对Ok应用返回Result的函数，链式操作。
    • or_else: 对Err应用生成Result的函数，用于错误恢复。
    • map_or / map_or_else: 对Ok应用函数，否则提供默认值（注意签名区别：map_or(default, f) 应用于Ok值；需传递一个默认值用于Err情况）。
    • unwrap_or / unwrap_or_else: 提取Ok或默认值。
    • ok: Result<T,E> -> Option<T>，丢弃错误。
    • err: Result<T,E> -> Option<E>，丢弃成功值。
    • transpose: Result<Option<T>,E> <-> Option<Result<T,E>>。
    • flatten: Result<Result<T,E>,E> -> Result<T,E>。
    • 运算符 ? 用于传播错误。

    ? 的返回类型必须兼容当前函数的返回类型：

    fn first_char(s: &str) -> Option<char> {
    let first = s.chars().next()?;
    Some(first)
}

fn parse_required(input: Option<&str>) -> Result<i32, String> {
    let text = input.ok_or_else(|| "缺少输入".to_string())?;
    text.parse::<i32>().map_err(|err| format!("解析失败: {err}"))
}

    filter(p) Some(v) 若 p(&v) 为假则变 None（对 Option 内部值做条件过滤） -
    unwrap_or(d) 提取值或返回 d（提供默认值） 提取值或返回 d（提供默认值）
    unwrap_or_else(f) 提取值或调用 f 提取值或调用 f
    map_or(d, f) Some -> f(v)，None -> d Ok -> f(v)，Err -> d
    map_or_else(def, f) None 时调用 def Err 时调用 def
    ok_or(err) 转为 Result -
    ok() - 转为 Option，丢弃错误
    err() - 转为 Option，丢弃 Ok

    transpose() Option<Result<T,E>> ↔ Result<Option<T>,E> 双向 
    fn read_number(s: &str) -> Result<i32, String> {
    s.trim()
        .parse::<i32>()
        .map(|n| n * 2)
        .map_err(|err| format!("解析失败: {err}"))
}

    3.7. 模式匹配与代数数据类型¶

    枚举和 match 是 Rust 函数式风格的核心。枚举表达状态空间，match 强制穷尽处理每一种状态。

    enum Command {
    Start,
    Stop,
    Write(String),
}

fn handle(cmd: Command) -> String {
    match cmd {
        Command::Start => "start".into(),
        Command::Stop => "stop".into(),
        Command::Write(text) => format!("write: {text}"),
    }
}

    这类设计比大量布尔值和可空字段更安全，因为非法状态无法被构造出来。

    1. 代数数据类型（ADT）¶

    代数数据类型这个名称来自数学，指的是由 积类型（Product Types）和 和类型（Sum Types）通过代数运算组合而成的类型系统。

    在 Rust 中：

    • 积类型（product types）：把多个值同时组合在一起。类似数学中的“乘积”，字段数量决定可能的状态数。 Rust 的结构体和元组都是积类型。
    // 结构体是积类型
struct Point { x: f64, y: f64 } // x 和 y 必须同时存在
let p = Point { x: 1.0, y: 2.0 };

// 元组也是积类型
type PointTuple = (f64, f64);  // (f64, f64) = f64 × f64

// 嵌套积类型
struct Rectangle {
    top_left: Point,    // Point = f64 × f64
    bottom_right: Point,  // Rectangle = Point × Point = f64⁴
}

    代数解释：struct A { b: B, c: C } 的可能取值数量 = |B| × |C|

    • 和类型（sum types）：一个值可以是多种可能中的一种，类似数学中的“和” （多个类型中选其一，只能有一个变体被激活）。 Rust 的 枚举 就是和类型，它明确列出了所有可能的 变体（variants）— "或"关系。
    // 枚举是和类型
enum WebEvent {
    PageLoad,                 // 无数据
    KeyPress(char),           // 携带一个字符
    Click { x: i64, y: i64 }, // 携带命名字段
}

// Option 是和类型：Option<T> = Some(T) | None
enum Option<T> {
    Some(T),
    None,
}

// Result 是和类型：Result<T, E> = Ok(T) | Err(E)
enum Result<T, E> {
    Ok(T),
    Err(E),
}

    代数解释：enum A { B, C } 的可能取值数量 = |B| + |C|

    一个枚举的每个变体又可以包含积类型（元组或结构体），形成嵌套的代数数据类型。这让 Rust 能够精确地描述“一个值可能是这样，或者那样，并且每种情况都可能携带不同的数据”。

    2. 模式匹配（Pattern Matching）¶

    模式匹配 是解构 ADT 的语法机制，编译器会 穷尽检查（Exhaustiveness Check）确保所有情况都被处理。

    就是对值的结构进行“形状检测”并同时提取内部数据的手段。

    Rust 的核心匹配结构是 match，但其他很多地方（if let、while let、let、函数参数）都可以使用模式。

    2.1. match 表达式¶

    match 会按顺序检查各个模式，第一个匹配成功的分支被执行。穷尽性检查会强制你处理所有可能的变体，否则编译失败。

    enum Message {
    Quit,
    Move { x: i32, y: i32 },
    Write(String),
}

fn process(msg: Message) {
    match msg {
        Message::Quit => println!("退出"),
        Message::Move { x, y } => println!("移动到 ({}, {})", x, y),
        Message::Write(text) => println!("信息: {}", text),
    }
}

    match 的每个分支都是一个模式，可以在模式中解构变体携带的数据。如果忘记处理某个变体，编译器会报错，这从根本上避免了遗忘情况导致的逻辑错误。

    2.2. 穷尽性检查：安全性的关键¶

    Rust 编译器的穷尽性检查会分析枚举定义，保证 match 覆盖了所有变体。对于特别大的枚举，你可以使用通配符 _ 或 other（变量模式）来处理“其余所有情况”。

    let number = Some(7);
match number {
    Some(5) => println!("是 5"),
    _ => println!("不是 5"), // 使用 _ 匹配所有剩余情况
}

    这种检查对于 Option 和 Result 尤为重要，因为它强制你在使用值之前必须处理 None 或 Err 的可能性，从而把许多空值遗漏、错误遗漏提前暴露为编译期问题。

    2.3. 解构模式¶

    作用：拆解复合容器（元组、数组、结构体、枚举、切片）内部字段，直接绑定变量。

    1. 元组解构¶
    let t = (10, "hello", true);
// 完整解构
let (a, b, c) = t;

// match 中元组解构 + 部分忽略
match t {
    (num, _, flag) => println!("{} {}", num, flag),
}
    2. 结构体解构¶
    struct User {
    id: u64,
    name: String,
    is_admin: bool,
}
let u = User { id: 1, name: "alice".into(), is_admin: true };

// let 解构
let User { id, ref name, .. } = u;
println!("{} {}", id, name);

// match 结构体，字段绑定+重命名
match &u {
    User { id: uid, is_admin: true, .. } => println!("admin:{}", uid),
    User { .. } => {}
}

    .. 忽略剩余所有字段，_ 忽略单个字段。

    3. 枚举解构（业务高频，如 Option/Result）¶
    let opt: Option<i32> = Some(100);
// if let 枚举解构
if let Some(val) = opt {
    println!("{}", val);
}

// Result 嵌套解构（你项目大量使用）
let res: Result<Option<()>, &str> = Ok(Some(()));
match res {
    Ok(Some(())) => println!("cli 执行完毕"),
    Ok(None) => println!("启动web服务"),
    Err(e) => eprintln!("err:{}", e),
}
    4. 定长数组解构¶
    let arr = [1, 2, 3];
let [x, y, z] = arr;

// 匹配固定长度数组，其余忽略
match arr {
    [first, ..] => println!("first:{}", first),
}
    5. 切片不定长解构（.. 匹配任意多个中间元素）¶

    仅切片 / 数组支持 .. 捕获一段元素：

    let s = &[10, 20, 30, 40];
match s {
    [head, .., tail] => println!("{} {}", head, tail),
    [single] => println!("only one"),
    [] => println!("empty"),
}
    2.4. 区间范围模式 ..= / ..¶

    匹配一段连续值，仅支持数字、字符。

    • a..=b：闭区间 [a, b] 包含两端
    • a..：从 a 到无穷大
    let n = 7;
match n {
    1..=5 => println!("小数字"),
    6..=10 => println!("中等数字"),
    11.. => println!("大数字"),
    _ => {}
}

// 字符区间
let c = 'c';
match c {
    'a'..='z' => println!("小写字母"),
    'A'..='Z' => println!("大写字母"),
    _ => {}
}
    2.5. 多分支或模式 |（Or 模式）¶

    一个分支匹配多个并列模式，用 | 分隔。

    let num = 2;
match num {
    1 | 2 | 3 => println!("1/2/3"),
    4..=10 => println!("4~10"),
    _ => {}
}

// 结构体嵌套Or
enum Op { Add(i32), Sub(i32), Mul(i32) }
let op = Op::Add(10);
match op {
    Op::Add(x) | Op::Sub(x) => println!("加减:{}", x),
    Op::Mul(x) => println!("乘:{}", x),
}
    2.6. 模式守卫 if 条件¶

    匹配成功后附加布尔过滤条件，语法：模式 if 表达式。

    经典示例：

    let env_res = std::env::var("RUST_LOG");
match env_res {
    Ok(val) if !val.is_empty() => {
        // 变量存在且非空才进入
    }
    _ => {}
}

    复杂嵌套守卫：

    let user = (18, true);
match user {
    (age, is_vip) if age >= 18 && is_vip => println!("成年会员"),
    _ => {}
}
    2.7. 绑定模式 @（自匹配绑定）¶

    变量 @ 子模式：既把匹配到的值绑定给变量，同时对子模式做限制。

    基础用法¶
    let num = 15;
match num {
    n @ 1..=10 => println!("1~10:{}", n),
    n @ 11..=20 => println!("11~20:{}", n),
    _ => {}
}
    结构体 / 枚举嵌套绑定（高级）¶
    #[derive(Debug)]
enum Msg { Text(String), Num(u32) }
let m = Msg::Num(99);
match m {
    msg @ Msg::Num(n @ 90..=100) => println!("{:?}, value:{}", msg, n),
    _ => {}  // 其他情况忽略
}

    优势：同时拿到完整枚举实例 + 内部字段，不用重复解构。

    2.8. 引用 / 解引用模式：&、ref、ref mut¶

    处理带引用的值匹配，区分匹配引用和捕获引用。

    1. &模式：匹配引用类型，解引用¶
    let x = &10;
match x {
    &v => println!("{}", v), // 解引用，v是i32
}
    2. ref / ref mut：匹配所有权值，捕获内部引用¶

    当匹配自有类型，不想拿走所有权，借用内部字段：

    struct User { name: String }
let u = User { name: "test".into() };

match &u {
    // 匹配引用时，name 是 &String，不转移所有权
    User { name } => println!("{}", name),
}
// u 仍然可用

let mut u2 = User { name: "a".into() };
match u2 {
    User { ref mut name } => name.push_str("bc"),
}

    等价简写（Rust 自动推导）：

    let User { ref name } = u;
// 简写
let User { name: ref name } = u;

    区分两个易混写法:

    1. &v：匹配引用变量，取出内部值；
    2. ref v：匹配自有变量，对内部字段创建引用。
    2.9. 忽略模式进阶：_、..、..=¶
    1. _：忽略单个值，不绑定变量；
    2. ..：忽略一组 / 全部剩余字段（结构体、元组、切片）；
    3. _v：合法绑定但编译器标记未使用，无警告。
    let (_, b, ..) = (1, 2, 3, 4);
struct Data { a: i32, b: String, c: bool }
let Data { a, .. } = Data { a:1, b:"".into(), c:false };

    3.8. =>胖箭头¶

    => 读作 胖箭头，常见于 match 分支和 macro_rules! 规则中，在不同位置含义不同。它不是闭包、if let、while let 或 for 的语法。

    场景 1：match 匹配分支（最常用）¶

    语法结构¶
    match 待匹配值 {
    模式1 => 表达式1,
    模式2 if 守卫 => 表达式2,
    _ => 默认表达式,
}
    含义¶

    分隔「匹配模式」和「匹配成功后执行的代码」:

    • 左边：匹配规则（字面量、解构、区间、|、@、守卫等模式）
    • 右边：当前分支匹配命中时，要运行的逻辑（单个表达式、代码块 {}）
    let res: Result<Option<()>, String> = Ok(Some(()));
match res {
    Ok(opt @ Some(())) if true => return Ok(()),
    Ok(None) => start_server(),
    Err(e) => eprintln!("{}", e),
}

    场景 2：宏 macro_rules! 分支匹配¶

    语法结构¶
    macro_rules! 宏名 {
    (匹配模板) => { 展开代码 };
    (另一模板) => { 另一套代码 };
}
    含义¶

    分隔宏匹配模板 和 宏展开生成的代码

    编译器按从上到下顺序匹配传入 token，匹配左侧模板后，展开右侧大括号内的 Rust 代码。

    示例：自定义错误宏¶
    macro_rules! app_err {
    ($msg:literal) => {
        crate::error::AppError::Msg($msg.to_string())
    };
    ($fmt:literal, $($args:expr),*) => {
        crate::error::AppError::Msg(format!($fmt, $($args),*))
    };
}
    • 左侧 ($msg:literal)：宏接收参数的匹配模式
    • => { ... }：匹配成功后替换生成的源码

    3.9. 函数式风格的取舍¶

    ✅ 适合使用函数式风格的场景：

    1. 数据转换管道清晰；
    2. 错误处理可以通过 Result 组合；
    3. 需要减少可变状态；
    4. 迭代处理可以自然表达为 map/filter/fold。

    ❌ 不适合强行函数式化的场景：

    1. 控制流非常复杂，链式调用反而降低可读性；
    2. 需要提前退出、细粒度日志或调试；
    3. 借用关系复杂，闭包捕获导致生命周期更难理解；
    4. 简单循环更直观时，应优先使用 for。

    Rust 的最佳实践不是「全函数式」，而是根据表达力选择：转换链路用迭代器，复杂流程用清晰的命令式代码。

    4.智能指针¶

    4.1. 智能指针是什么？¶

    1. 核心概念¶

    裸指针（*const T / *mut T）：仅存储内存地址，无所有权、无自动释放，手动管理内存，不安全。

    智能指针（Smart Pointer）是拥有额外元数据和行为的指针类型。它们通常不仅保存地址，还负责所有权管理、引用计数、内部可变性、线程安全或自定义释放逻辑。

    Rust 智能指针的核心基础是两个 trait：

    • Deref：自动解引用，让智能指针可以像引用一样访问内部值；

    • Drop：在值离开作用域时自动执行清理逻辑，例如释放堆内存、关闭文件、释放锁。它能自动执行析构，但不能保证所有资源一定都会按预期释放；mem::forget、引用循环、进程提前退出等情况仍可能造成泄漏或清理缺失。

    本质：带附加逻辑的堆内存管理器，Rust 标准库三大核心智能指针：

    Box<T>、Rc<T>/Weak<T>、Arc<T>/Weak<T>，还有可变容器 RefCell<T>/Mutex<T>。

    use std::ops::Deref;

struct MyBox<T>(T);

impl<T> Deref for MyBox<T> {
    type Target = T;

    fn deref(&self) -> &Self::Target {
        &self.0
    }
}

    2. 两大关键 trait（智能指针底层基石）¶

    (1) Deref 解引用自动转换¶

    实现 Deref 的类型支持 * 解引用、自动隐式解引用（函数传参）。

    trait Deref {
    type Target;
    fn deref(&self) -> &Self::Target;
}

    作用：智能指针可以像普通引用一样访问内部数据。

    (2) Drop 析构自动回收¶

    离开作用域时自动执行 drop，释放堆内存、关闭文件、释放锁，无需手动 free。

    trait Drop {
    fn drop(&mut self);
}

    4.2. Box<T>：堆分配与唯一所有权（堆内存独占所有权）¶

    1. 定义与特性¶

    Box<T> 表示在堆上分配一个值，并拥有该值的唯一所有权。Box<T> 本身存放在栈上，指向堆上的数据。

    核心特性：

    1. 独占所有权：同一时间只有一个 Box 拥有堆数据
    2. 分配数据到堆，栈只存指针，适合：
    3. 大小不确定、递归类型（链表 / 树）
    4. 超大数据避免栈溢出（栈空间有限）
    5. 转移所有权，只移动指针不拷贝大数据
    6. 无引用计数，性能开销低；是否能跨线程移动取决于内部类型是否满足 Send / Sync，并不是只能在单线程中使用。

    典型用途：

    1. 存放编译期大小未知的递归类型；
    2. 转移大对象所有权时避免栈上拷贝过大；
    3. 使用 trait object 实现动态分发。

    2. 使用场景¶

    场景 1：递归类型（必须用 Box）¶

    递归类型必须通过 Box 间接存储，否则编译器无法计算类型大小，Rust 编译器要求编译期确定结构体大小，递归结构体直接定义会无限递归，用 Box 包裹：

    // 链表节点
#[derive(Debug)]
enum List {
    Cons(i32, Box<List>),
    Nil,
}

fn main() {
    let list = List::Cons(1, Box::new(List::Cons(2, Box::new(List::Nil))));
}
    场景 2：栈放不下的大对象¶
    struct BigData([u8; 1024 * 1024]); // 1MB 数组，放栈会栈溢出
fn main() {
    let heap_data = Box::new(BigData([0; 1024 * 1024])); // 分配堆
}

    动态分发示例：

    trait Draw {
    fn draw(&self);
}

struct Button;

impl Draw for Button {
    fn draw(&self) {
        println!("draw button");
    }
}

let widget: Box<dyn Draw> = Box::new(Button);
widget.draw();

    4.3. Rc<T>：单线程多所有权（引用计数）¶

    全称 Reference Counted，单线程共享所有权

    1. 核心特性¶

    1. 堆上存数据 + 引用计数器（栈上每个 Rc 仅存指针）
    2. Rc::clone()：增加引用计数，不会深拷贝数据，只复制指针
    3. 所有持有者离开作用域、计数归零才释放内存
    4. 不支持多线程，无同步锁，多线程必须用 Arc

    2. 使用场景：多个所有者共享只读数据（单线程）¶

    Rc<T>（Reference Counted）允许多个所有者共享同一份只读数据。每次 clone 只增加引用计数，不会深拷贝内部数据。

    use std::rc::Rc;

let a = Rc::new(String::from("shared"));
let b = Rc::clone(&a);
let c = Rc::clone(&a);

assert_eq!(Rc::strong_count(&a), 3);

    Rc<T> 只能用于单线程，因为它的引用计数更新不是原子操作。多线程共享所有权应使用 Arc<T>。

    4.4. Arc<T>：多线程共享所有权（原子引用计数）¶

    全称 Atomic Reference Counted，Rc 的线程安全版本

    核心特性：

    1. 引用计数使用原子操作，支持多线程跨所有权共享
    2. 性能略低于 Rc（原子指令开销）
    3. 同样搭配 Weak<T> 解决循环引用
    4. 只读；多线程可变需要配合 Mutex<T> / RwLock<T>

    Arc<T>（Atomically Reference Counted）是线程安全版本的 Rc<T>，引用计数使用原子操作维护。

    use std::sync::Arc;
use std::thread;

let data = Arc::new(vec![1, 2, 3]);
let mut handles = vec![];

for _ in 0..3 {
    let data = Arc::clone(&data);
    handles.push(thread::spawn(move || {
        println!("{:?}", data);
    }));
}

for handle in handles {
    handle.join().unwrap();
}

    Arc<T> 只解决「多线程共享所有权」，不自动提供可变访问。如果需要多线程修改共享数据，通常组合 Arc<Mutex<T>> 或 Arc<RwLock<T>>。

    4.5. Weak<T>：打破引用循环¶

    Rc<T> 和 Arc<T> 使用强引用计数。若两个对象 互相持有强引用，计数永远不会归零，导致 内存泄漏。

    Weak<T> 是 弱引用，不增加强计数，不拥有数据，不阻止内存释放；std::rc::Weak 可升级为 Rc，std::sync::Weak 可升级为 Arc。

    use std::cell::RefCell;
use std::rc::{Rc, Weak};

struct Node {
    value: i32,
    parent: RefCell<Weak<Node>>,
    children: RefCell<Vec<Rc<Node>>>,
}

    典型建模：父节点用 Weak 指向子节点的父级，子节点集合用 Rc 持有所有权，避免父子互相强引用。

    访问弱引用时需要 upgrade：

    if let Some(parent) = node.parent.borrow().upgrade() {
    println!("parent value = {}", parent.value);
} else {
    // 父节点已经释放，弱引用无法再升级
}

    upgrade() 返回 Option<Rc<T>> 或 Option<Arc<T>>，因此必须处理升级失败。工程中不要假设弱引用一定有效，尤其是缓存、观察者、父子树结构中，被观察对象可能已经被释放。

    4.6. 内部可变性智能指针：RefCell / Mutex¶

    Rust 所有权规则：同一时间要么多个只读引用，要么一个可变引用。

    但有时候需要：外部不可变，内部可修改 → 内部可变性，靠这两个智能指针实现。

    1. RefCell<T>：单线程内部可变性¶

    RefCell<T> 将借用检查从编译期推迟到运行时，允许在外部只有不可变引用时修改内部值。

    use std::cell::RefCell;

let value = RefCell::new(1);

*value.borrow_mut() += 1;
assert_eq!(*value.borrow(), 2);

    RefCell<T> 仍然遵守 Rust 借用规则：任意时刻可以有多个不可变借用，或一个可变借用。如果运行时违反规则，会触发 panic。

    let cell = RefCell::new(10);
let _a = cell.borrow_mut();
// let _b = cell.borrow_mut(); // ❌ 运行时 panic

    适合场景：

    • mock 对象记录调用次数；
    • 单线程图结构或树结构中需要局部修改；
    • 对外暴露不可变 API，但内部需要缓存或延迟初始化。

    2. Mutex<T>：多线程内部可变性¶

    多线程下的内部可变性，搭配 Arc 使用：

    1. 加锁保证同一时间只有一个可变访问
    2. lock() 获取可变守卫，守卫自动释放锁（Drop）
    use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];

    for _ in 0..5 {
        let cnt = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            let mut inner = cnt.lock().unwrap();
            *inner += 1;
        }));
    }
    for h in handles { h.join().unwrap(); }
    println!("{}", counter.lock().unwrap()); // 5
}

    补充：RwLock<T> 读写分离锁，读多写少场景性能优于 Mutex。

    4.7. Cell<T>：按值复制的内部可变性¶

    Cell<T> 适合 Copy 类型，它不返回内部值的引用，而是通过 get / set 按值读写。

    use std::cell::Cell;

let counter = Cell::new(0);
counter.set(counter.get() + 1);

assert_eq!(counter.get(), 1);

    因为不会产生内部引用，Cell<T> 比 RefCell<T> 更简单，也不会出现运行时借用冲突。

    4.8. Cow<'a, T>：写时克隆¶

    Cow（Clone On Write）可以同时表示借用数据和拥有数据。只有在需要修改时，才会克隆为拥有数据。

    use std::borrow::Cow;

fn normalize(input: &str) -> Cow<'_, str> {
    if input.contains(' ') {
        Cow::Owned(input.replace(' ', "_"))
    } else {
        Cow::Borrowed(input)
    }
}

    Cow 常用于减少不必要分配：当输入无需修改时直接返回借用，需要修改时才分配新对象。

    4.9. 智能指针选型¶

    类型 场景 线程安全 是否共享所有权 是否允许内部可变
    Box<T> 堆分配、递归类型、trait object 取决于 T 否 否
    Rc<T> 单线程共享只读数据 否 是 否
    Arc<T> 多线程共享只读数据 是 是 否
    RefCell<T> 单线程运行时借用检查 否 否 是
    Mutex<T> 多线程共享可变状态 是 是 加锁可变
    Cell<T> Copy 值的内部可变性 否 否 是
    Weak<T> 避免引用循环 取决于 Rc/Arc 否 否
    Cow<'a, T> 借用优先，必要时拥有 取决于 T 否 需要时克隆

    常见组合：

    • Rc<RefCell<T>>：单线程共享可变数据；
    • Arc<Mutex<T>>：多线程共享可变数据；
    • Arc<RwLock<T>>：多读少写的共享数据；
    • Box<dyn Trait>：运行时多态。

    智能指针不是越多越好。优先使用普通所有权和借用，只有当所有权关系确实需要共享、堆分配或内部可变性时，再引入智能指针。

    4.10. 常见组合的边界条件¶

    组合 适合场景 主要风险 实践建议
    Rc<RefCell<T>> 单线程树、图、UI 状态、测试桩 借用冲突从编译期推迟到运行时，冲突时 panic 缩短 borrow_mut() 作用域，不要在回调或复杂调用链中长期持有 RefMut
    Arc<Mutex<T>> 多线程共享少量可变状态 锁竞争、死锁、poisoned lock 临界区只做内存操作，不在持锁期间执行 I/O、阻塞等待或调用未知回调
    Arc<RwLock<T>> 读远多于写的配置、缓存、路由表 写者饥饿、读写切换成本高 写入频繁时退回 Mutex；读锁内不要做耗时计算
    Arc<Atomic*> 计数器、开关、简单状态位 内存序难推理，无法表达复合不变量 默认从锁开始，只有性能瓶颈明确且状态足够简单时再使用原子
    Weak<T> 父指针、缓存弱引用、观察者列表 upgrade() 可能失败 每次升级都按 Option 处理，失败表示对象生命周期已经结束

    锁粒度的核心原则是：保护不变量，而不是保护代码块。如果多个字段必须一起保持一致，就用同一把锁；如果字段彼此独立且高频访问，可以拆分锁，但要固定加锁顺序，避免死锁。

    4.11. 如何选择智能指针？¶

    需求 推荐智能指针
    单个所有者的堆分配 Box<T>
    递归数据结构 Box<T>
    trait 对象动态分发 Box<dyn Trait> 或 Arc<dyn Trait>
    单线程内多个所有者只读共享 Rc<T>
    单线程内多个所有者需要修改 Rc<RefCell<T>>
    多线程多个所有者只读共享 Arc<T>
    多线程多个所有者需要修改 Arc<Mutex<T>> / Arc<RwLock<T>>
    避免 Rc/Arc 循环引用 Weak<T>
    借用与所有权的灵活切换，偶尔修改 Cow<T>
    简单值类型需要运行时修改 Cell<T>
    更复杂内部修改（非 Copy） RefCell<T>

    5.多线程编程¶

    多线程编程关注的是：把工作分配到多个 OS 线程上执行，利用多核 CPU 或隔离阻塞操作。Rust 的优势是用所有权、借用规则和 Send / Sync 在编译期消除数据竞争。

    5.1. 线程模型与适用场景¶

    模型 特点 适合场景
    多线程阻塞 一个任务可能占用一个线程 CPU 密集、简单并发、阻塞库
    数据并行 自动拆分数据到线程池 大批量计算、过滤、归约
    异步非阻塞 大量任务复用少量线程 高并发 I/O

    多线程适合：

    1. CPU 密集计算，需要真正并行；
    2. 调用同步阻塞库，需要隔离阻塞；
    3. 与系统线程、线程局部状态、线程优先级等平台能力交互；
    4. 使用 rayon、crossbeam 等成熟线程并发库。

    5.2. 线程基础：std::thread¶

    1. 创建线程¶

    标准库使用 std::thread::spawn 创建系统线程。传入的闭包通常需要 move，将捕获数据移动到新线程中。

    use std::thread;

let data = vec![1, 2, 3];

let handle = thread::spawn(move || {
    println!("{:?}", data);
});

handle.join().unwrap();

    join() 会等待子线程结束，并返回线程执行结果。如果子线程 panic，join() 返回 Err。

    2. 线程与所有权¶

    use std::thread;

fn main() {
    let v = vec![1, 2, 3];

    // ❌ 错误：闭包捕获 v 的引用，但线程可能比主线程活得久
    // let handle = thread::spawn(|| {
    //     println!("{:?}", v);
    // });

    // ✅ 正确：move 转移所有权到线程
    let handle = thread::spawn(move || {
        println!("{:?}", v);  // v 的所有权转移到子线程
    });

    // ❌ v 已不可用
    // println!("{:?}", v);

    handle.join().unwrap();
}

    普通 thread::spawn 要求闭包满足 'static，因为线程可能比当前栈帧活得更久。如果要在线程中使用局部数据，通常要移动所有权，或使用作用域线程。

    5.3. 作用域线程¶

    thread::scope 允许创建不会逃出当前作用域的线程，因此可以安全借用局部变量。

    use std::thread;

let nums = vec![1, 2, 3];

thread::scope(|s| {
    s.spawn(|| {
        println!("{:?}", nums);
    });
});

    作用域结束前，所有 scoped 线程都会完成，因此借用局部变量是安全的。

    5.4. 共享状态：Arc<Mutex<T>>¶

    Mutex<T> 提供互斥访问，任意时刻只允许一个线程修改内部数据；Arc<T> 负责在线程间共享所有权。

    use std::sync::{Arc, Mutex};
use std::thread;

let counter = Arc::new(Mutex::new(0));
let mut handles = vec![];

for _ in 0..10 {
    let counter = Arc::clone(&counter);
    handles.push(thread::spawn(move || {
        let mut num = counter.lock().unwrap();
        *num += 1;
    }));
}

for handle in handles {
    handle.join().unwrap();
}

assert_eq!(*counter.lock().unwrap(), 10);

    lock() 返回 MutexGuard，它实现了 Deref 和 DerefMut，离开作用域时自动释放锁。

    注意：如果持锁线程 panic，锁会被标记为 poisoned，之后 lock() 返回 PoisonError。示例中 unwrap() 会直接传播 panic，生产代码可以根据业务选择恢复或终止。

    5.5. 多读少写：RwLock<T>¶

    RwLock<T> 允许多个读者同时访问，或一个写者独占访问，适合读多写少的场景。

    use std::sync::RwLock;

let lock = RwLock::new(vec![1, 2, 3]);

{
    let read = lock.read().unwrap();
    assert_eq!(read.len(), 3);
}

{
    let mut write = lock.write().unwrap();
    write.push(4);
}

    如果写操作频繁，RwLock 不一定比 Mutex 更快，甚至可能因为调度成本更高而更慢。

    5.6. 线程间消息传递：Channel¶

    Rust 标准库提供 std::sync::mpsc，表示多生产者、单消费者通道。通过消息传递可以减少共享状态。

    use std::sync::mpsc;
use std::thread;

let (tx, rx) = mpsc::channel();

thread::spawn(move || {
    tx.send(String::from("hello")).unwrap();
});

let msg = rx.recv().unwrap();
assert_eq!(msg, "hello");

    多生产者通过克隆发送端实现：

    let (tx, rx) = mpsc::channel();

for i in 0..3 {
    let tx = tx.clone();
    thread::spawn(move || tx.send(i).unwrap());
}

drop(tx); // 关闭原始发送端，否则接收端迭代可能一直等待

let values: Vec<_> = rx.iter().collect();

    5.7. 原子类型¶

    原子类型适合简单的无锁共享状态，如计数器、标志位。常见类型包括 AtomicBool、AtomicUsize、AtomicI64 等。

    use std::sync::atomic::{AtomicUsize, Ordering};

let counter = AtomicUsize::new(0);
counter.fetch_add(1, Ordering::Relaxed);

assert_eq!(counter.load(Ordering::Relaxed), 1);

    Ordering 描述内存可见性约束：

    • Relaxed：只保证单个原子操作本身原子性；
    • Acquire / Release：建立读写同步关系；
    • AcqRel：同时具备 acquire 和 release；
    • SeqCst：最强顺序一致性，最容易推理但可能成本更高。

    原子编程容易出错，除简单计数器和标志位外，应优先使用锁或成熟并发库。

    并非所有目标平台都支持所有原子宽度。AtomicUsize 通常跟指针宽度一致，但 AtomicU64、AtomicI64、AtomicU128 等可能受硬件和目标平台限制。编写跨平台库时，可以用 #[cfg(target_has_atomic = "64")]、#[cfg(target_has_atomic = "ptr")] 做条件编译，或在不支持的平台退回锁实现。

    5.8. 线程同步原语¶

    原语 用途 示例
    std::sync::Barrier 线程栅栏，等待所有线程到达 barrier.wait()
    std::sync::Condvar 条件变量，等待特定条件 condvar.wait(lock)
    crossbeam::channel 高性能通道，多生产多消费 tx.send(v)

    标准库没有稳定的 std::sync::Semaphore。需要信号量时，线程场景通常选择 parking_lot、crossbeam 或自定义 Mutex + Condvar；异步场景使用 tokio::sync::Semaphore。

    5.9. 并行迭代：rayon¶

    rayon 是数据并行库，会自动将迭代工作分配到线程池。

    use rayon::prelude::*;

fn main() {
    let nums: Vec<i32> = (1..=1000000).collect();

    // 串行
    let sum1: i32 = nums.iter().map(|x| x * x).sum();

    // 并行（自动利用多核）
    let sum2: i32 = nums.par_iter().map(|x| x * x).sum();

    // 并行过滤 + 归约
    let result: Vec<i32> = nums
        .par_iter()
        .filter(|&&x| x % 2 == 0)
        .map(|x| x * 2)
        .collect();
}

    5.10. 死锁、饥饿与锁设计¶

    问题 典型原因 Rust 中的表现 规避方式
    死锁 多把锁加锁顺序不一致，或持锁等待另一个资源 线程永久阻塞，程序无 panic 但不再推进 全局固定加锁顺序；尽量只持有一把锁；用 try_lock、超时或消息传递拆解等待
    活锁 任务不断让步或重试，但没有实际进展 CPU 有活动，业务状态不变化 给重试加退避、随机抖动和最大次数；记录重试指标
    饥饿 某类任务长期拿不到锁或执行机会 延迟长尾明显，少数请求一直等待 缩短临界区；避免读锁长期占用；必要时使用公平锁或队列化处理
    优先级反转 低优先级任务持有高优先级任务需要的锁 高优先级任务被间接阻塞 减少共享锁；将关键状态交给单独 worker/actor；避免持锁执行不可控代码

    当共享状态需要复杂协调时，Arc<Mutex<T>> 往往不是最终答案。可以考虑把状态放进一个专门线程或 actor 中，其他线程通过 channel 发送命令；这样锁被消息队列替代，所有状态修改在一个地方顺序执行，更容易维护不变量。

    5.11. 多线程实践建议¶

    1. CPU 密集任务优先考虑 rayon，手写线程只用于生命周期、调度或隔离需求明确的场景；
    2. 共享只读数据使用 Arc<T>；
    3. 共享可变数据使用 Arc<Mutex<T>> 或 Arc<RwLock<T>>；
    4. 能用消息传递解决时，尽量少共享可变状态；
    5. 避免长时间持锁，尤其不要在持锁期间执行阻塞 I/O；
    6. 原子类型只用于简单计数器、标志位或性能瓶颈明确的底层组件。

    6.多进程编程¶

    多进程编程关注的是：通过多个独立进程完成任务隔离、权限隔离、崩溃隔离或外部命令集成。进程之间默认不共享内存，通信需要显式 IPC（Inter-Process Communication）。

    6.1. 进程与线程的区别¶

    维度 线程 进程
    地址空间 同一进程内共享地址空间 每个进程有独立地址空间
    创建成本 相对低 相对高
    通信方式 共享内存、锁、通道 管道、Socket、文件、共享内存
    隔离性 线程 panic 可能影响整个进程 子进程崩溃通常不影响父进程
    适合场景 CPU 并行、共享内存协作 命令执行、服务隔离、权限边界

    Rust 多进程通常通过 std::process::Command 启动子进程，通过标准输入输出或系统 IPC 交换数据。

    6.2. 启动子进程并获取输出¶

    use std::process::Command;

fn main() -> std::io::Result<()> {
    let output = Command::new("rustc")
        .arg("--version")
        .output()?;

    if output.status.success() {
        println!("{}", String::from_utf8_lossy(&output.stdout));
    } else {
        eprintln!("{}", String::from_utf8_lossy(&output.stderr));
    }

    Ok(())
}

    output() 会等待子进程结束，并一次性收集 stdout 和 stderr。输出很大时不要长期依赖 output()，否则可能占用大量内存。

    6.3. 配置环境变量与工作目录¶

    use std::process::Command;

fn main() -> std::io::Result<()> {
    let status = Command::new("cargo")
        .arg("test")
        .current_dir("./my_crate")
        .env("RUST_BACKTRACE", "1")
        .status()?;

    assert!(status.success());
    Ok(())
}

    常用方法：

    • arg / args：传入命令参数；
    • env / env_remove / env_clear：控制环境变量；
    • current_dir：设置子进程工作目录；
    • status：只关心退出码；
    • output：等待结束并收集输出；
    • spawn：启动后立即返回 Child，适合流式交互或后台进程。

    6.4. 管道与子进程交互¶

    使用 Stdio::piped() 可以把父进程和子进程的标准输入输出连接起来。

    use std::io::Write;
use std::process::{Command, Stdio};

fn main() -> std::io::Result<()> {
    let mut child = Command::new("wc")
        .arg("-c")
        .stdin(Stdio::piped())
        .stdout(Stdio::piped())
        .spawn()?;

    {
        let stdin = child.stdin.as_mut().expect("stdin is piped");
        stdin.write_all(b"hello")?;
    } // 关闭 stdin，否则 wc 可能一直等待 EOF

    let output = child.wait_with_output()?;
    println!("{}", String::from_utf8_lossy(&output.stdout));

    Ok(())
}

    注意：父进程必须及时关闭写端，否则依赖 EOF 的子进程会一直等待。

    6.5. 等待、终止与资源回收¶

    use std::process::Command;
use std::time::Duration;

fn main() -> std::io::Result<()> {
    let mut child = Command::new("sleep")
        .arg("10")
        .spawn()?;

    std::thread::sleep(Duration::from_millis(100));

    child.kill()?;
    let status = child.wait()?;
    println!("status = {status}");

    Ok(())
}

    kill() 只发送终止信号或执行平台等价操作，仍应调用 wait() 回收子进程资源，避免僵尸进程。

    6.6. 多进程 IPC 选型¶

    通信方式 特点 适合场景
    标准输入/输出 简单、跨平台、易组合 调用 CLI、父子进程管道
    文件 简单可靠，但延迟较高 批处理、结果落盘、审计日志
    TCP / Unix Socket 结构化、可长连接 服务间通信、本机守护进程
    共享内存 吞吐高，但同步复杂 高频数据交换、低延迟系统
    消息队列 解耦、可缓冲、可跨语言 后台任务、事件驱动系统

    Rust 标准库提供进程启动和标准管道，复杂 IPC 通常使用生态库，例如 tokio::process、interprocess、ipc-channel、nix 或平台 SDK。

    6.7. 异步进程：tokio::process¶

    异步服务中不要用阻塞方式长时间等待子进程。可以用 tokio::process::Command 与运行时集成。

    use tokio::process::Command;

#[tokio::main]
async fn main() -> std::io::Result<()> {
    let output = Command::new("rustc")
        .arg("--version")
        .output()
        .await?;

    println!("{}", String::from_utf8_lossy(&output.stdout));
    Ok(())
}

    如果子进程输出需要持续读取，应使用异步管道和 tokio::io，避免阻塞 Tokio 工作线程。

    6.8. 子进程工程实践：输出、超时与跨平台¶

    Command::output() 会等待子进程结束后一次性收集 stdout/stderr，适合短命令；它内部会收集管道输出，通常不会因为 stdout/stderr 管道无人读取而死锁。但长时间运行或输出量很大的子进程仍可能带来内存压力，也无法实时展示进度日志，此时更适合持续读取管道。

    use std::process::{Command, Stdio};
use std::io::{BufRead, BufReader};
use std::thread;

fn main() -> std::io::Result<()> {
    let mut child = Command::new("cargo")
        .arg("test")
        .stdout(Stdio::piped())
        .stderr(Stdio::piped())
        .spawn()?;

    let stdout = child.stdout.take().expect("stdout piped");
    let stderr = child.stderr.take().expect("stderr piped");

    let out_reader = thread::spawn(move || {
        for line in BufReader::new(stdout).lines() {
            println!("OUT: {}", line.unwrap_or_default());
        }
    });

    let err_reader = thread::spawn(move || {
        for line in BufReader::new(stderr).lines() {
            eprintln!("ERR: {}", line.unwrap_or_default());
        }
    });

    let status = child.wait()?;
    out_reader.join().unwrap();
    err_reader.join().unwrap();

    println!("status = {status}");
    Ok(())
}

    超时控制通常不要直接假设 wait() 会及时返回。同步代码可以循环 try_wait() 并结合 Instant 判断超时；异步代码可用 tokio::time::timeout() 包住 child.wait()。超时后应先尝试业务上的优雅退出（例如向 stdin 发送退出命令、HTTP 管理接口通知、Unix SIGTERM），再使用 kill() 做强制终止，并始终 wait() 回收资源。

    跨平台时要注意：

    1. 命令名、参数转义和 shell 语法不同，优先用 Command::arg() 逐个传参，不拼接 shell 字符串；
    2. Unix 的信号、进程组、文件描述符继承与 Windows 的 job object、handle 继承语义不同；
    3. 路径分隔符、可执行文件后缀、环境变量大小写在不同平台上可能不同；
    4. 如果必须依赖平台能力，使用 cfg(unix) / cfg(windows) 分开实现。

    7.异步编程¶

    异步编程解决的是高并发 I/O 问题：网络请求、数据库访问、文件 I/O、定时器、消息队列等。它的目标不是让 CPU 计算更快，而是在等待 I/O 时释放当前任务，让线程去执行其他任务。

    7.1. 异步编程解决什么问题？¶

    对于 I/O 密集型任务，传统做法是为每个连接开一个线程。但每个线程有自己的栈（通常 2-8MB），成千上万的连接会导致内存压力和频繁上下文切换。

    异步模型将任务抽象为轻量级的 Future，运行时只需要少量 OS 线程就能驱动海量并发任务，且切换开销通常只是用户态的任务状态机跳转。

    模型 特点 适合场景
    多线程阻塞 一个请求可能占用一个线程 CPU 密集、简单并发
    异步非阻塞 大量任务复用少量线程 高并发 I/O

    Rust 异步的特点：零成本抽象、无强制内置运行时、编译期保证内存安全。常见运行时包括 tokio、async-std、smol。

    7.2. async / await 的本质¶

    async fn 不会立即执行函数体，而是返回一个实现了 Future 的状态机。只有当这个 Future 被运行时轮询（poll）时，代码才会推进执行。

    async fn fetch_user(id: u64) -> String {
    format!("user-{id}")
}

// 调用 async fn 得到 Future，而不是直接得到 String
let future = fetch_user(1);

    .await 表示等待另一个 Future 完成。如果等待的 I/O 尚未就绪，当前任务会让出执行权，线程可以去运行其他任务。

    async fn print_user() {
    let user = fetch_user(1).await;
    println!("{user}");
}

    也可以把真实 I/O 写成同步风格的代码：

    async fn fetch_url(url: &str) -> Result<String, reqwest::Error> {
    let body = reqwest::get(url).await?.text().await?;
    Ok(body)
}

    每个 .await 都是一个暂停点（yield point）。在 .await 之间，代码像同步代码一样顺序执行，但不会阻塞 OS 线程。

    7.3. Future、poll、Waker 与状态机¶

    Rust 异步的基石是 std::future::Future trait：

    use std::future::Future;
use std::pin::Pin;
use std::task::{Context, Poll};

trait SimpleFuture {
    type Output;

    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

    poll 的返回值：

    • Poll::Ready(value)：任务完成，返回结果；
    • Poll::Pending：任务尚未完成，需要稍后再次 poll。

    关键点：

    • Output 是异步操作完成时产出的值；
    • poll 必须迅速返回，不能阻塞；
    • Context 包含 Waker，当任务可以继续时，通过 waker.wake() 通知执行器再次调度；
    • 编译器会把 async 代码转换为状态机，每个 .await 都是可能暂停和恢复的位置。

    你几乎不需要手动实现 Future；async/await 语法会为你生成状态机。

    7.4. Pin 与自引用问题¶

    async fn 生成的状态机可能包含自引用结构：某个字段引用另一个字段。这样的 Future 一旦被移动，内部引用可能失效。

    Pin 的作用是：保证被固定的数据不会再被移动，从而让自引用 Future 可以安全地被轮询。

    日常开发中通常不需要手写 Pin，因为 .await、运行时和宏会处理绝大多数细节。但理解 Pin 有助于理解为什么 Future::poll 的签名是 self: Pin<&mut Self>。

    7.5. 异步运行时与 Tokio¶

    Rust 语言本身只提供 Future trait 和 async/await 语法，不提供完整调度器。实际项目通常使用 Tokio。

    Tokio 核心组件：

    • 多线程工作窃取调度器：驱动 Future，利用多核；
    • I/O 驱动：基于 epoll / kqueue / IOCP 等平台能力；
    • 定时器：tokio::time::sleep 等；
    • 同步原语：tokio::sync::Mutex、mpsc、broadcast 等；
    • 阻塞线程池：通过 spawn_blocking 隔离同步阻塞任务。

    添加依赖：cargo add tokio --features full，并将 main 改为 #[tokio::main]。

    use tokio::time::{sleep, Duration};

#[tokio::main]  // 宏设置异步运行时
async fn main() {
    // async 函数返回 Future，不会立即执行
    let future = my_async_function();

    // await 挂起当前任务，让出线程执行其他任务
    let result = future.await;
    println!("{}", result);
}

async fn my_async_function() -> String {
    sleep(Duration::from_secs(1)).await;  // 非阻塞等待
    "Hello".to_string()
}

    #[tokio::main] 是一个属性宏，它会把异步 main 包装成创建运行时并阻塞等待 Future 完成的同步入口。

    #[tokio::main]
async fn main() {
    let body = reqwest::get("https://www.rust-lang.org")
        .await
        .unwrap()
        .text()
        .await
        .unwrap();

    println!("length = {}", body.len());
}

    7.6. 并发执行 Future：顺序、join! 与 spawn¶

    连续 .await 是顺序执行：

    let a = task_a().await;
let b = task_b().await;

    如果两个任务互不依赖，可以并发等待：

    let (a, b) = tokio::join!(task_a(), task_b());

    tokio::join! 同时驱动多个 Future，所有都完成后返回一个元组。它是在同一个异步任务内并发轮询多个 Future，不等于自动创建新线程。

    use tokio::join;

async fn fetch_url(url: &str) -> String {
    // HTTP 请求
    reqwest::get(url).await.unwrap().text().await.unwrap()
}

#[tokio::main]
async fn main() {
    let url1 = "https://api1.example.com";
    let url2 = "https://api2.example.com";

    // 顺序执行（慢）
    // let res1 = fetch_url(url1).await;
    // let res2 = fetch_url(url2).await;

    // 并发执行（快）
    let (res1, res2) = join!(
        fetch_url(url1),
        fetch_url(url2),
    );

    println!("{} {}", res1.len(), res2.len());
}

    tokio::spawn 将一个 Future 提交到运行时，作为独立任务在后台执行，并返回 JoinHandle。任务可在不同工作线程上运行。

    let handle = tokio::spawn(async {
    42
});

let value = handle.await.unwrap();
assert_eq!(value, 42);

    更接近真实业务的写法：

    let handle = tokio::spawn(async {
    // 独立任务
    fetch_url(url).await
});
// 主任务可以继续做别的事
let result = handle.await.unwrap(); // 等待任务完成并获取结果

    被 tokio::spawn 的 Future 通常要求 Send + 'static，因为它可能在线程池中跨线程移动，并且生命周期不能依赖当前栈帧。

    7.7. select!：竞争等待与超时控制¶

    tokio::select! 同时监听多个 Future，一旦某个先完成就取消其他分支。

    use tokio::select;
use tokio::time::{sleep, Duration};

#[tokio::main]
async fn main() {
    let future1 = sleep(Duration::from_secs(1));
    let future2 = sleep(Duration::from_secs(2));

    select! {
        _ = future1 => println!("future1 先完成"),
        _ = future2 => println!("future2 先完成"),
    }
}

    常用于超时控制：

    tokio::select! {
    _ = tokio::time::sleep(Duration::from_secs(5)) => {
        println!("timeout");
    }
    res = fetch_url(url) => {
        println!("done: {:?}", res);
    }
}

    select! 的未选中分支会被取消，因此分支中的 Future 应能安全取消。对外部副作用、部分写入、事务等操作，要显式设计取消语义。

    7.8. 异步中的所有权与生命周期¶

    异步代码中最常见的问题是：Future 可能在 .await 处暂停，因此跨 .await 保存的引用必须始终有效。

    async fn use_ref(s: &str) {
    println!("{s}");
}

    这种函数本身可以成立，但如果要 tokio::spawn(use_ref(&s))，通常会失败，因为任务要求 'static，而 s 是当前栈帧中的借用。

    解决方式通常是移动拥有所有权的数据：

    let s = String::from("hello");

tokio::spawn(async move {
    println!("{s}");
});

    实践规则：需要交给运行时独立调度的任务，优先传入 String、Arc<T>、Vec<T> 等自有数据，而不是借用当前栈帧。

    7.9. 不要在异步任务中阻塞线程¶

    异步运行时依赖少量线程调度大量任务。如果在异步任务中调用阻塞操作，会占住运行时工作线程，导致其他任务无法推进。

    不推荐：

    async fn bad() {
    std::thread::sleep(std::time::Duration::from_secs(1));
}

    推荐：

    async fn good() {
    tokio::time::sleep(std::time::Duration::from_secs(1)).await;
}

    对于 CPU 密集或必须阻塞的任务，应使用专门的阻塞线程池：

    let result = tokio::task::spawn_blocking(|| {
    // CPU 密集计算或阻塞式库调用
    1 + 1
})
.await
.unwrap();

    block_in_place vs spawn_blocking¶

    维度 block_in_place spawn_blocking
    线程切换 不切换线程，在当前线程阻塞 切换到专用线程执行
    运行时影响 当前任务阻塞当前线程，运行时会尽量迁移其他任务 不阻塞异步线程，协程继续调度
    返回值 直接返回阻塞操作的结果 返回 JoinHandle，需 .await
    使用场景 简短、快速的阻塞操作 长时间、CPU 密集型阻塞操作
    典型用例 文件元数据读取、快速锁获取 复杂计算、大量文件 IO、数据库查询

    spawn_blocking 基本使用¶

    spawn_blocking 会在单独的线程池中执行（默认 512 个 OS 线程），不阻塞异步工作线程。

    let result = tokio::task::spawn_blocking(|| {
    // 同步阻塞或 CPU 密集型操作
    expensive_cpu_task()
}).await.unwrap();

    block_in_place 基本使用¶

    block_in_place 只适用于 Tokio 多线程运行时，不适用于 current_thread 运行时；它适合短小阻塞片段，长时间阻塞或 CPU 密集任务仍应使用 spawn_blocking。

    在异步上下文中调用一个暂时阻塞的同步 I/O 时，可以使用 tokio::task::block_in_place 告知运行时将当前工作线程让给其他任务，避免饥饿。

    use tokio::task;

let result = task::block_in_place(|| {
    // 同步/阻塞代码
    blocking_operation()
});

    示例：

    use tokio::task;
use std::time::Duration;

#[tokio::main]
async fn main() {
    // 模拟：需要在异步上下文中执行快速阻塞操作
    let metadata = task::block_in_place(|| {
        // 阻塞操作：读取文件元数据
        std::fs::metadata("/etc/passwd")
    }).unwrap();

    println!("文件大小: {}", metadata.len());

    // 继续异步代码
    tokio::time::sleep(Duration::from_millis(100)).await;
}

    7.10. 异步锁与共享状态¶

    在异步代码中应谨慎使用 std::sync::Mutex。如果持有同步锁跨越 .await，可能造成任务调度阻塞甚至死锁。

    一般规则：

    • 锁只保护短小的同步临界区，可以使用 std::sync::Mutex；
    • 锁可能跨 .await，应使用 tokio::sync::Mutex；
    • 尽量不要持锁 .await，更推荐先取出数据、释放锁，再执行异步操作。
    use std::sync::Arc;
use tokio::sync::Mutex;

let state = Arc::new(Mutex::new(0));

let state2 = Arc::clone(&state);
tokio::spawn(async move {
    let mut guard = state2.lock().await;
    *guard += 1;
});

    完整计数器示例：

    use tokio::sync::Mutex;  // 异步版本的 Mutex
use std::sync::Arc;

#[tokio::main]
async fn main() {
    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];

    for _ in 0..10 {
        let counter = Arc::clone(&counter);

        let handle = tokio::spawn(async move {
            let mut num = counter.lock().await;  // .await 非阻塞获取锁
            *num += 1;
        });

        handles.push(handle);
    }

    for h in handles {
        h.await.unwrap();
    }

    println!("{}", *counter.lock().await);
}

    tokio::sync::Mutex vs std::sync::Mutex：前者 .await 让出线程，后者阻塞线程。

    Send Future 常见踩坑¶

    tokio::spawn 在多线程运行时上通常要求 Future 是 Send + 'static。如果某个非 Send 值跨越 .await 被保存进状态机，整个 Future 就不是 Send。

    use std::rc::Rc;

async fn bad() {
    let data = Rc::new(String::from("hello"));

    tokio::time::sleep(std::time::Duration::from_millis(10)).await;

    // Rc 跨越了 .await，Future 不能被 tokio::spawn 发送到其他线程
    println!("{}", data);
}

    常见修复方式：

    use std::sync::Arc;

async fn good() {
    let data = Arc::new(String::from("hello"));
    tokio::time::sleep(std::time::Duration::from_millis(10)).await;
    println!("{}", data);
}

    如果确实需要使用 Rc、RefCell 等单线程类型，可以把它们限制在 .await 之前的短作用域内，确保不跨暂停点；或者使用 LocalSet / spawn_local 在单线程本地任务集中运行。

    7.11. 异步通道：mpsc、oneshot、broadcast、watch¶

    异步通道是协程间通信、协程与线程桥接的重要工具。

    维度 同步通道（std::sync::mpsc） 异步通道（tokio::sync::mpsc）
    发送行为 channel 的 send 通常不因容量阻塞，sync_channel 满时会阻塞 send().await 挂起，让出线程
    接收行为 recv 阻塞直到有消息 recv().await 挂起，让出线程
    线程占用 阻塞时占用 OS 线程 挂起时不占用线程，可执行其他任务
    适用场景 线程间通信 协程间通信、协程与线程间通信
    缓冲区 有界/无界 有界/无界

    异步通道类型：

    类型 模块 特点
    mpsc tokio::sync::mpsc 多生产者，单消费者
    oneshot tokio::sync::oneshot 单值通道，一次性单发单收
    broadcast tokio::sync::broadcast 多播，多生产者、多消费者（订阅广播）
    watch tokio::sync::watch 状态监听，只保留最新值（单生产者、多消费者）
    Semaphore tokio::sync::Semaphore 信号量，限制并发

    基础示例：

    let (tx, mut rx) = tokio::sync::mpsc::channel(32);
tokio::spawn(async move {
    tx.send("hello").await.unwrap();
});
let msg = rx.recv().await.unwrap();

    mpsc 基本使用：

    use tokio::sync::mpsc;

#[tokio::main]
async fn main() {
    // 创建异步通道：buffer 为 32
    let (tx, mut rx) = mpsc::channel::<String>(32);

    // 生产者协程
    tokio::spawn(async move {
        for i in 0..5 {
            // .await 挂起，不阻塞线程
            if let Err(e) = tx.send(format!("消息 {}", i)).await {
                println!("发送失败: {}", e);
                return;
            }
        }
        // tx 在这里 drop，通道关闭
    });

    // 消费者协程
    while let Some(msg) = rx.recv().await {
        println!("收到: {}", msg);
    }

    println!("通道关闭");
}

    oneshot / broadcast / watch 示例：

    use tokio::sync::{mpsc, oneshot, broadcast, watch};

// oneshot: 请求-响应模式
async fn request_response() {
    let (tx, rx) = oneshot::channel();

    tokio::spawn(async move {
        // 处理请求
        tx.send("响应").unwrap();
    });

    let response = rx.await.unwrap();
}

// broadcast: 事件广播
async fn event_broadcast() {
    let (tx, _rx1) = broadcast::channel(16);
    let mut rx2 = tx.subscribe();
    let mut rx3 = tx.subscribe();

    tokio::spawn(async move {
        tx.send("事件").unwrap();
    });

    let msg2 = rx2.recv().await.unwrap();
    let msg3 = rx3.recv().await.unwrap();
}

// watch: 状态共享
async fn state_watch() {
    let (tx, mut rx) = watch::channel("初始值");

    tokio::spawn(async move {
        tx.send("新值").unwrap();
    });

    rx.changed().await.unwrap();
    println!("{}", *rx.borrow());
}

    7.12. Stream：异步迭代器¶

    Stream 可以理解为异步版本的 Iterator：它不是一次返回一个值，而是异步地产生多个值。

    use futures::StreamExt;

async fn consume_stream<S>(mut stream: S)
where
    S: futures::Stream<Item = i32> + Unpin,
{
    while let Some(item) = stream.next().await {
        println!("{item}");
    }
}

    常见场景：WebSocket 消息、分页数据、订阅事件、异步文件行读取等。

    处理大量异步操作时，可以使用 buffer_unordered(n) 保持固定并发度：

    use futures::stream::{self, StreamExt};

let urls = vec!["url1", "url2", "url3"];
let fetches = stream::iter(urls)
    .map(|url| async move { reqwest::get(url).await?.text().await })
    .buffer_unordered(10); // 同时最多并发10个请求

tokio::pin!(fetches);
while let Some(result) = fetches.next().await {
    match result {
        Ok(body) => println!("{}", body.len()),
        Err(e) => eprintln!("Error: {}", e),
    }
}

    buffer_unordered(n) 会保持 n 个并发 Future，每完成一个就补充下一个，适合批量请求、批量任务处理和限流场景。

    7.13. 取消安全与背压¶

    Rust 异步取消通常通过 drop Future 实现。select! 未选中的分支、超时包装中被放弃的 Future、任务句柄被 abort 时，都可能让异步操作停在任意 .await 之前或之后。因此，涉及外部副作用的代码要明确取消语义。

    场景 风险 设计建议
    分多次写 socket / 文件 只写入前半段，协议或文件处于中间状态 使用长度前缀、事务文件、临时文件再 rename，或让接收端支持幂等重试
    数据库事务 Future 被取消时事务未提交 使用事务对象的 drop 回滚语义，并避免把提交过程拆成不可恢复的多步副作用
    mpsc::send().await 等待容量期间被取消，消息没有发送 业务上允许丢弃时可直接取消；必须发送时用重试队列或确认机制
    select! 竞争多个分支 未选中分支立即被 drop 只把取消安全的 Future 放进分支，或把不可取消操作放到独立任务中并通过消息观察结果

    背压（backpressure）是指下游处理不过来时，上游必须减速或丢弃。无界队列能隐藏问题，但会把压力转化为内存增长。工程上优先使用有界 mpsc、Semaphore、buffer_unordered(n) 或批处理窗口，让系统在容量边界处表现可预测。

    7.14. 异步编程最佳实践¶

    1. I/O 密集使用 async，CPU 密集优先使用线程池或 rayon；
    2. 不要在 async 中调用长时间阻塞函数；
    3. 避免持锁跨 .await；
    4. 使用 join! 并发等待互不依赖的 Future；
    5. 使用 spawn 时注意 Send + 'static 约束；
    6. 需要限制并发时使用 Semaphore 或 StreamExt::buffer_unordered(n)；
    7. 需要超时、取消或竞争等待时使用 select!，并确认取消安全；
    8. 错误处理继续使用 Result 和 ?，不要在任务中随意 unwrap()；
    9. 优先选择生态成熟的 runtime 和库组合，例如 tokio + reqwest + sqlx。

    Rust 异步的难点不在语法，而在理解 Future 是惰性的状态机，以及 .await 处可能暂停、切换和恢复执行。

    8.并发编程¶

    并发编程关注的是：多个任务在逻辑上同时推进，并正确处理通信、同步、取消、背压和资源竞争。它可以由多线程实现，也可以由异步任务实现，还可以跨进程实现。

    8.1. 并发、并行、异步与同步¶

    术语 含义 Rust 中的体现
    并发（Concurrency） 任务交替执行，逻辑上同时推进 async/await、任务调度、通道
    并行（Parallelism） 任务真正同时执行，利用多核 std::thread、线程池、rayon
    异步（Async） 非阻塞等待，单线程内多任务切换 tokio、async-std
    同步（Sync） 阻塞等待，顺序执行 Mutex、RwLock

    Rust 并发编程的目标是：在编译期消除数据竞争。它并不阻止所有逻辑层面的并发 bug，但能保证不会出现未定义行为级别的数据竞争。

    Rust 依赖 三套机制 实现 并发安全：

    1. 所有权：数据移动到线程或任务后，原位置不能继续违规使用；
    2. 借用规则：可变访问和共享访问不能同时存在；
    3. Send / Sync trait：类型级别标记跨线程移动和共享是否安全。

    8.2. Send 与 Sync¶

    Send 和 Sync 是 Rust 并发安全的核心标记 trait。

    Trait 含义
    Send 类型的所有权可以安全移动到另一个线程
    Sync 类型的共享引用 &T 可以安全在线程间共享

    关系：如果 T: Sync，则 &T: Send。

    常见结论：

    • Rc<T> 不是 Send / Sync，不能跨线程共享；
    • Arc<T> 是线程安全引用计数，可跨线程共享；
    • RefCell<T> 不是 Sync，多线程内部可变性应使用 Mutex<T> 或 RwLock<T>；
    • 大多数基础类型、String、Vec<T> 在 T: Send 时也是 Send；
    • tokio::spawn 通常要求 Future 为 Send + 'static，因为任务可能被移动到不同工作线程。

    8.3. 并发通信模型¶

    并发程序有两种主流协作方式：

    1. 共享内存：多个执行单元访问同一份状态，用锁或原子控制访问；
    2. 消息传递：执行单元之间通过通道传递所有权，降低共享可变状态复杂度。
    场景 线程同步版本 异步版本
    互斥状态 Arc<Mutex<T>> Arc<tokio::sync::Mutex<T>>
    多读少写 Arc<RwLock<T>> Arc<tokio::sync::RwLock<T>>
    单消费者通道 std::sync::mpsc tokio::sync::mpsc
    广播 crossbeam / 自定义订阅 tokio::sync::broadcast
    状态监听 Arc<Mutex<T>> + Condvar tokio::sync::watch
    限制并发 信号量或线程池大小 tokio::sync::Semaphore

    选择原则：能用消息传递表达所有权流动时，优先消息传递；状态天然共享且访问频繁时，才使用锁或原子。

    8.4. 异步并发的关键模式¶

    异步并发不是“开很多线程”，而是让大量任务在等待 I/O 时让出执行权。常见模式如下：

    模式 工具 语义
    同时等待 tokio::join! 所有 Future 都完成才继续
    后台任务 tokio::spawn 提交独立任务，返回 JoinHandle
    竞争等待 tokio::select! 第一个分支完成后继续
    批量限流 buffer_unordered(n) 保持最多 n 个任务并发
    任务通信 mpsc / oneshot / watch 用消息连接任务

    并发控制示例：

    use futures::stream::{self, StreamExt};

async fn fetch(url: String) -> Result<String, reqwest::Error> {
    reqwest::get(url).await?.text().await
}

async fn fetch_all(urls: Vec<String>) {
    let results = stream::iter(urls)
        .map(fetch)
        .buffer_unordered(20);

    tokio::pin!(results);
    while let Some(result) = results.next().await {
        match result {
            Ok(body) => println!("{}", body.len()),
            Err(err) => eprintln!("{err}"),
        }
    }
}

    8.5. 协程与线程的结合¶

    Rust 的 async 是协作式调度，std::thread 是 OS 抢占式调度。二者结合的关键是：

    Tokio 运行时管理线程池，协程（task）在线程上执行；通过通道和 spawn_blocking 实现协程与阻塞任务的协作。

    异步代码中绝不能运行长时间 CPU 密集或同步阻塞操作，否则会饿死其他任务。如果必须做，交给专门的线程池或独立线程。

    方案 1：异步业务 + 阻塞 CPU 计算（spawn_blocking）¶

    场景：异步 Web 服务中包含大量同步计算、解析、压缩等 CPU 密集逻辑。

    use tokio::sync::mpsc;
use tokio::task;

#[tokio::main]
async fn main() {
    let (tx, mut rx) = mpsc::channel(100);

    // 在线程中执行阻塞操作，通过通道与协程通信
    task::spawn_blocking(move || {
        // 这是真实的 OS 线程，可以执行阻塞 IO
        for i in 0..10 {
            let data = heavy_blocking_computation(i);
            // 同步发送（spawn_blocking 中是同步环境）
            tx.blocking_send(data).unwrap();
        }
    });

    // 协程消费数据
    while let Some(data) = rx.recv().await {
        process_async(data).await;
    }
}

fn heavy_blocking_computation(i: i32) -> String {
    std::thread::sleep(std::time::Duration::from_millis(100));
    format!("结果 {}", i)
}

async fn process_async(data: String) {
    println!("处理: {}", data);
}

    方案 2：原生 std::thread 同步线程 ↔ Tokio 异步协程互通¶

    场景：遗留同步多线程代码，需要和异步服务互相传数据。

    两种通道配合：

    • 同步线程内部：std::sync::mpsc（同步通道）；
    • 同步 ↔ 异步桥接：使用 tokio::sync::mpsc 配合 blocking_recv，或 oneshot 桥接。
    use std::thread;
use tokio::sync::oneshot;

// 原生OS同步线程
fn sync_thread(tx: oneshot::Sender<u32>) {
    thread::sleep(std::time::Duration::from_millis(100));
    tx.send(99).unwrap();
}

#[tokio::main]
async fn main() {
    let (tx, rx) = oneshot::channel();
    // 启动原生OS线程
    thread::spawn(move || sync_thread(tx));
    // 异步等待同步线程返回数据
    let val = rx.await.unwrap();
    println!("来自同步线程的数据：{}", val);
}

    方案 3：多异步 Runtime 分离（独立线程运行独立 Runtime）¶

    场景：需要两套独立异步运行时隔离业务（例如独立后台任务 Runtime、HTTP 服务 Runtime），每个 Runtime 跑在单独 OS 线程。

    use std::thread;
use tokio::runtime::Runtime;

fn create_sub_runtime() {
    // 新建独立Tokio运行时
    let rt = Runtime::new().unwrap();
    rt.block_on(async {
        println!("子Runtime协程运行");
        tokio::time::sleep(tokio::time::Duration::from_millis(50)).await;
    });
}

fn main() {
    // 单独OS线程承载一套独立异步Runtime
    thread::spawn(create_sub_runtime).join().unwrap();
}

    三者关系：

    1. 普通 Worker 线程（Tokio 多线程池）：只跑纯异步代码，禁止长时间同步阻塞；
    2. Blocking 阻塞线程池（spawn_blocking）：承载 CPU 密集、同步阻塞代码，隔离阻塞不影响 I/O 协程；
    3. 用户手动创建 std::thread 原生线程：适合遗留同步逻辑、第三方阻塞库；通过 oneshot / mpsc 和协程通信。

    8.6. join!、spawn 与 select! 选择表¶

    工具 语义 适合场景 注意点
    tokio::join! 同一任务内并发轮询，等待全部完成 多个互不依赖的子步骤，生命周期仍由当前函数管理 某个分支阻塞会影响同一任务内其他分支推进
    tokio::try_join! 任一分支返回错误时提前返回 多个都必须成功的 I/O 操作 提前返回会取消未完成分支，需确认取消安全
    tokio::spawn 创建独立后台任务，返回 JoinHandle 任务生命周期独立，可能跨线程执行 Future 通常要 Send + 'static，错误不能被悄悄丢弃
    tokio::select! 多个分支竞争，先完成者获胜 超时、取消、监听多个事件源 未选中分支会被取消，副作用要可恢复或可重试

    8.7. 并发设计建议与选型¶

    1. 优先选择不可变数据和所有权移动；
    2. 能用消息传递解决时，尽量少共享可变状态；
    3. 共享只读数据使用 Arc<T>；
    4. 共享可变数据使用 Arc<Mutex<T>> 或 Arc<RwLock<T>>；
    5. 避免长时间持锁，尤其不要在持锁期间执行阻塞 I/O 或 .await；
    6. 多线程 CPU 密集任务可考虑 rayon，异步 I/O 任务应使用 async runtime；
    7. 跨进程需要显式 IPC，不要假设内存可共享；
    8. 需要取消、超时、限流和背压时，要把它们作为协议的一部分设计。

    选型决策：

    需要并发还是并行？
├── 并行（CPU 密集型）→ std::thread / rayon
│   ├── 数据并行 → rayon::par_iter
│   └── 任务并行 → std::thread::spawn
│
├── 隔离（崩溃/权限/外部命令）→ std::process / tokio::process
│   ├── 调用命令 → Command::output / status
│   ├── 流式交互 → Stdio::piped
│   └── 服务隔离 → Socket / IPC
│
└── 并发（IO 密集型）→ async/await + tokio
    ├── 网络服务 → tokio + hyper/axum
    ├── 数据库 → sqlx / tokio-postgres
    └── 文件 IO → tokio::fs

需要共享状态？
├── 只读 → Arc<T>
├── 读写 → Arc<RwLock<T>>
├── 频繁写 → Arc<Mutex<T>>
└── 计数器/标志 → Atomic*

需要通信？
├── 线程间一对一/多对一 → std::sync::mpsc
├── 异步任务多对一 → tokio::sync::mpsc
├── 请求-响应 → oneshot
├── 广播事件 → broadcast
├── 状态同步 → watch
└── 竞争等待/超时 → select!

    9.元编程¶

    9.1. 元编程是什么？¶

    元编程的本质是：编写能「生成 / 操作 / 扩展 Rust 代码」的代码。

    常规 Rust 代码是「告诉编译器做什么」，元编程代码是「告诉编译器如何生成代码」，最终编译器会把元编程生成的代码与你的业务代码合并，一起编译为二进制可执行文件。

    9.2. Rust 元编程的核心边界¶

    Rust 不支持「运行时反射 (Reflection)」，这是刻意的设计选择：

    • 反射会带来运行时性能损耗、二进制体积膨胀、类型安全弱化；
    • 反射的核心能力（获取类型元信息、动态调用方法等），在 Rust 中都通过「编译期元编程」实现，且做到了零运行时成本的等价替代。

    9.3. Rust元编程中的宏¶

    1.简介¶

    在 Rust 中宏分为两大类：声明式宏( declarative macros ) macro_rules! 和三种过程宏( procedural macros ):

    • 派生宏：#[derive]，可以为目标结构体或枚举派生指定的代码，如 #[derive(Debug, Clone)]

    • 类属性宏(Attribute-like macro)：用于为目标添加自定义的属性

    // 假设有一个路由属性宏
#[route(GET, "/users")]
fn get_users() { /* ... */ }
// 宏可以读取 GET 和 "/users"，并生成相应的路由注册代码
    • 类函数宏(Function-like macro)：看上去就像是函数调用
    // 定义
#[proc_macro]
pub fn sql(input: TokenStream) -> TokenStream { /* 解析 SQL 字符串并生成代码 */ }
// 使用
let query = sql!("SELECT * FROM users WHERE id = 1");
    方式 入口 展开阶段 能力 例子
    声明宏 macro_rules! 词法/模式匹配 编译前端 AST 前 文本级替换、可变参数 println! / vec!
    过程宏 #[derive(...)] 函数（操作 AST） 编译中段 AST → AST 类型级代码生成、复杂逻辑 #[derive(Serialize)] / #[tokio::main]

    宏展开 早于类型检查，因此可以「先拼代码，再让 rustc 检查」。

    2.声明宏 (macro_rules!)¶

    声明式宏（关键字 macro_rules!）是 Rust 内置、原生支持的元编程，无需任何外部依赖，是 Rust 程序员最先接触的元编程形式，也是标准库中 vec!/println!/vec![]/format! 等核心宏的实现方式。

    官方命名：Macro by Example (MBE) —— 基于「示例匹配 + 代码展开」的宏，这精准概括了它的工作原理。

    2.1.核心语法与定义方式¶
    // 标准声明式宏定义模板
#[macro_export] // 关键：将宏导出到当前crate的根命名空间，跨模块可用
macro_rules! 宏名称 {
    // 匹配规则1: 模式 => { 展开的代码 }
    (匹配模式1) => { 展开代码块1 };
    // 匹配规则2: 支持多规则重载（类似函数重载）
    (匹配模式2) => { 展开代码块2 };
}
    • #[macro_export] 作用：不加则宏仅在当前模块可见，加上后全局可见（如标准库的宏）；
    • 匹配模式的分隔符是括号 / 方括号 / 大括号，三者等价，只是语法习惯（如 vec![]、println!()）。

    示例:

    // 定义一个简单的宏：创建向量
macro_rules! my_vec {
    // 匹配：my_vec![1, 2, 3]
    ($($x:expr),*) => {
        {
            let mut temp_vec = Vec::new();
            $(temp_vec.push($x);)* // 对每个匹配到的表达式执行 push
            temp_vec
        }
    };
}
// 使用
let v = my_vec![1, 2, 3];
    2.2.核心工作原理：模式匹配 + 代码展开¶

    声明式宏的核心逻辑只有两步，无任何执行逻辑，纯静态匹配：

    1. 匹配阶段：编译器将你调用宏时传入的代码片段，与宏定义中的「匹配模式」做AST 语法树片段匹配（不是字符串匹配！）；
    2. 展开阶段：匹配成功后，编译器将宏的调用处，替换为模式对应的「展开代码块」。

    ✅ 关键区别：Rust 的声明式宏是 AST 片段匹配，而非 C/C++ 的字符串替换，这是 Rust 宏的安全性核心 —— 不会出现字符串替换的语法漏洞，匹配失败会直接编译报错。

    2.3.核心特性：重复匹配（最常用能力）¶

    声明式宏的核心威力来自 重复匹配语法：$(...) sep rep，这是实现「可变参数」的唯一方式，几乎所有实用的声明式宏都依赖它。

    • $(...)：包裹需要重复匹配的代码片段；
    • sep：可选，分隔符（如 , 逗号，最常用）；
    • rep：必须，重复修饰符，只有两种取值：*（零次或多次）、+（一次或多次）。
    #[macro_export]
macro_rules! my_vec {
    // 匹配规则1: my_vec![] —— 空调用，生成空Vec
    () => { Vec::new() };
    // 匹配规则2: my_vec![1, 2, 3] —— 带可变参数的调用，生成初始化Vec
    ($($elem:expr),*) => {{
        let mut v = Vec::new();
        $(v.push($elem);)* // 重复展开：每一个$elem都执行一次push
        v
    }};
}

// 调用
fn main() {
    let v1 = my_vec![]; // 展开为 Vec::new()
    let v2 = my_vec![1,2,3]; // 展开为 push三次的代码
    assert_eq!(v2, vec![1,2,3]);
}
    • $elem:expr：表示匹配「任意表达式 (expression)」，expr 是 Rust 内置的片段指定符，还有 ident(标识符)、ty(类型) 等；
    • 重复匹配是「双向的」：$(...) 匹配了多少个片段，$() 展开就会生成多少行代码。
    2.4.声明式宏的优缺点（选型必看）¶

    ✅ 优点：

    1. 零依赖，原生支持，无需任何 Cargo 配置；
    2. 语法简洁，编写成本低，适合简单场景；
    3. 编译速度快，无额外编译开销；
    4. 安全，AST 匹配无字符串替换漏洞。

    ❌ 缺点：

    1. 能力有限：仅能做「匹配 + 展开」，无逻辑判断、无类型检查、无代码修改能力；
    2. 嵌套复杂：多层匹配会导致宏定义可读性极差；
    3. 无类型感知：无法根据传入的类型做差异化展开。

    3.过程宏¶

    过程宏是 Rust 最强大、最核心的元编程能力，没有之一，也是 Rust 生态繁荣的核心驱动力（serde::Serialize、tokio::main、derive(Debug) 都是过程宏实现）。

    3.1.核心定义¶

    过程宏本质是：一个在编译期被编译器调用的、合法的 Rust 函数。

    它的核心逻辑是：编译器将你标记了宏注解的代码（如结构体、函数），解析为语法树 Token 流 (TokenStream)，传入这个 Rust 函数；函数对 TokenStream 做任意逻辑处理（解析 / 修改 / 生成），最后返回新的 TokenStream；编译器将返回的 TokenStream 直接注入到源代码中，完成编译。

    3.2.过程宏的三大「标配依赖」（缺一不可）¶

    过程宏需要解析 TokenStream（编译器的语法单元），Rust 官方提供了三个核心库，所有过程宏开发都基于它们，被称为「过程宏三板斧」，必须在 Cargo.toml 中引入：

    # 过程宏的Cargo依赖标配
[dependencies]
proc-macro2 = "1.0"  # 兼容标准库proc_macro的TokenStream，增强版
syn = "2.0"          # 核心：将TokenStream解析为Rust语法树(AST)，支持遍历/修改
quote = "1.0"        # 核心：将Rust语法树(AST)转回TokenStream，代码生成神器

    三者分工：syn 负责「读」语法树，quote 负责「写」语法树，proc-macro2 负责「桥接」编译器。

    3.3.硬性要求：过程宏必须是独立的 crate¶

    这是 Rust 编译器的强制规则，无任何例外：

    你的过程宏代码，必须放在一个独立的 Rust 库项目（crate）中，且在 Cargo.toml 中声明 proc-macro = true。

    原因：编译器需要将过程宏编译为「编译器插件」，与业务代码隔离编译，避免循环依赖和编译期污染。

    过程宏 crate 的 标准配置

    # 过程宏专属Cargo.toml，必须写这两行
[lib]
proc-macro = true  # 声明这是一个过程宏crate，编译器会特殊处理
    3.4.三类过程宏¶
    类型 签名 典型用途
    派生宏 #[derive(MyTrait)] fn derive(input: TokenStream) -> TokenStream 自动实现 Serialize / Clone / Debug
    属性宏 #[my_attr(args)] fn attr(args: TokenStream, input: TokenStream) -> TokenStream 注入代码、路由注册 #[get("/")]
    类函数宏 my_macro!(...) fn my_macro(input: TokenStream) -> TokenStream 任意语法块 → 新代码

    最小派生示例：

    use proc_macro::TokenStream;
use quote::quote;
use syn::{parse_macro_input, DeriveInput};

#[proc_macro_derive(Hello)]
pub fn derive_hello(input: TokenStream) -> TokenStream {
    let ast = parse_macro_input!(input as DeriveInput);
    let name = &ast.ident;
    let gen = quote! {
        impl #name {
            pub fn hello(&self) -> &'static str {
                concat!("Hello, I am ", stringify!(#name))
            }
        }
    };
    gen.into()
}

    使用：

    #[derive(Hello)]
struct Cat;

fn main() {
    println!("{}", Cat.hello());   // → Hello, I am Cat
}
    • syn 负责把 TokenStream 解析成结构化 AST
    • quote! 用模板生成新 AST
    • 全程在 编译期 完成，零运行时成本。
    1.派生宏 (Derive Macros) —— 最常用的过程宏¶

    注解语法：#[derive(自定义宏名)]，对标 Rust 原生的 #[derive(Debug, Clone)]。

    核心场景：为结构体 / 枚举 / 联合体，自动生成指定 trait 的实现代码。

    核心特点：标记在 struct/enum/union 上，输入是该类型的语法树，输出是该类型的 trait 实现代码。

    经典示例：实现一个自定义派生宏 #[derive(Hello)]

    作用：为任意结构体自动生成一个 hello() 方法，打印结构体名称。

    // 步骤1：在独立的proc-macro crate中编写派生宏
use proc_macro::TokenStream;
use quote::quote;
use syn::{parse_macro_input, DeriveInput};

// 核心：派生宏的入口函数，#[proc_macro_derive(宏名)] 是固定注解
#[proc_macro_derive(Hello)]
pub fn derive_hello(input: TokenStream) -> TokenStream {
    // 1. 将编译器传入的TokenStream解析为Rust语法树(结构体/枚举)
    let input = parse_macro_input!(input as DeriveInput);
    // 2. 获取结构体/枚举的名称
    let name = input.ident;
    // 3. 生成代码：为该类型实现Hello trait + hello方法
    let gen = quote! {
        pub trait Hello {
            fn hello(&self);
        }

        impl Hello for #name {
            fn hello(&self) {
                println!("Hello, I'm a {}!", stringify!(#name));
            }
        }
    };
    // 4. 将生成的代码转回TokenStream返回给编译器
    gen.into()
}

// 步骤2：在业务crate中调用
#[derive(Hello)]
struct Person { name: String, age: u8 }

fn main() {
    let p = Person { name: "Tom".into(), age: 18 };
    p.hello(); // 自动生成的方法，输出：Hello, I'm a Person!
}

    这就是 serde::Serialize/serde::Deserialize 的核心原理：通过派生宏为你的结构体自动生成序列化 / 反序列化的代码。

    2.属性宏 (Attribute Macros)¶

    注解语法：#[自定义宏名] 或 #[自定义宏名(参数)]，对标 Rust 原生的 #[inline]/#[allow(dead_code)]。

    核心场景：为任意 Rust 语法项（函数、结构体、枚举、模块、变量等）添加自定义注解，实现「装饰器」逻辑，比如：日志打印、性能统计、权限校验、代码注入等。

    核心特点：无限制标记位置，输入是被标记项的语法树，输出是修改后的语法树（可增删改查）。

    经典示例：实现一个日志属性宏 #[log]

    作用：为任意函数自动在执行前后打印「函数名 + 执行开始 / 结束」日志。

    #[proc_macro_attribute] // 固定注解：属性宏的入口标记
pub fn log(_attr: TokenStream, item: TokenStream) -> TokenStream {
    // _attr: 注解的参数（如#[log(debug)]中的debug）
    // item: 被标记的语法项（这里是函数）
    let input = parse_macro_input!(item as ItemFn);
    let name = input.sig.ident; // 获取函数名
    let block = input.block;    // 获取函数体

    // 生成代码：在函数执行前后注入日志打印
    let gen = quote! {
        fn #name() {
            println!("函数 {} 开始执行", stringify!(#name));
            #block
            println!("函数 {} 执行结束", stringify!(#name));
        }
    };
    gen.into()
}

// 调用
#[log]
fn say_hi() {
    println!("Hello World!");
}
// 调用say_hi()会输出：
// 函数 say_hi 开始执行
// Hello World!
// 函数 say_hi 执行结束

    tokio::main/tokio::test 就是属性宏，它的作用是将普通函数包装为异步运行时的入口函数。

    3.函数式宏 (Function-like Macros)¶

    调用语法：自定义宏名!(参数)，对标 Rust 原生的 vec!()/println!()。

    核心场景：替代声明式宏，实现「更复杂的宏调用逻辑」，比如需要类型检查、条件生成的宏。

    核心特点：调用方式和声明式宏一致，但内部是完整的 Rust 函数逻辑，能力远超声明式宏。

    注解标记：#[proc_macro]

    3.5.过程宏的优缺点（选型核心）¶

    ✅ 优点（绝对主流）：

    1. 能力很强：可以实现复杂代码生成、语法校验和样板代码消除，是 Rust 元编程的核心；
    2. 语法结构感知：能解析语法树、做语法校验并生成结构化代码；生成代码最终仍由 rustc 做类型检查；
    3. 生态核心：几乎所有 Rust 优秀库都依赖过程宏，是 Rust 生态的基石；
    4. 可维护性强：用 Rust 编写逻辑，比嵌套的声明式宏可读性高得多。

    ❌ 缺点：

    1. 有一定学习成本：需要掌握 syn/quote 的使用；
    2. 编译速度稍慢：过程宏是编译期执行的函数，复杂逻辑会增加编译时间；
    3. 必须独立 crate：增加了项目的工程复杂度。

    9.4. 宏展开调试与过程宏边界¶

    宏的调试重点是看清“展开后到底生成了什么代码”。常用方法：

    1. cargo expand：查看宏展开后的源码，是调试 macro_rules! 和过程宏最常用的工具；
    2. RUSTFLAGS="-Z macro-backtrace"：在 nightly 上查看更完整的宏调用栈；
    3. 在过程宏中用 syn::Error::new_spanned(...).to_compile_error() 返回友好的编译错误；
    4. 对复杂过程宏，把解析、校验、代码生成拆成普通函数，并为这些函数写单元测试。

    过程宏的边界也要清楚：宏展开发生在类型检查之前，过程宏看到的是语法结构，不是完整类型信息。它可以根据字段名、属性、泛型参数生成代码，但不能像运行时反射那样查询“这个表达式实际类型是什么”。类型正确性最终仍交给 rustc 检查。

    return syn::Error::new_spanned(
    field,
    "#[derive(MyMacro)] requires every field to have a name",
)
.to_compile_error()
.into();

    工程建议：宏生成的代码越多，越要关注错误信息质量。优秀的宏不仅能生成正确代码，还应在用户写错输入时指向准确位置，并解释如何修改。

    9.5.类型级编程¶

    1.核心定位与定义¶

    这是 Rust 元编程中非常重要的一类能力：用类型、trait、关联类型、泛型和常量泛型表达约束，让编译器在编译阶段提前检查更多问题。

    类型级编程：完全利用 Rust 的类型系统，在「编译阶段」完成计算、逻辑判断、数据存储和状态表达。

    简单说：把「类型」当作「值」来用，把「trait 约束 / 关联类型 / 泛型」当作「逻辑」来用。这能把一部分运行时错误提前暴露为编译错误，并且很多约束在运行时没有额外开销。

    2 核心本质与核心载体¶

    2.1. 类型级编程的本质：编译期的类型计算¶

    Rust 的类型系统表达能力很强，可以通过 trait 递归、关联类型和常量泛型表达复杂编译期关系。但工程实践中不应为了“炫技”把大量业务逻辑塞进类型系统，因为这会显著增加编译时间和错误信息复杂度。

    类型级编程的核心价值：将运行时的逻辑，提前到编译期完成验证和计算，比如：

    • 用常量泛型表达矩阵维度、数组长度、协议版本等静态参数；
    • 用 trait 约束表达“这个类型必须支持某种能力”；
    • 用关联类型把输入类型和输出类型绑定在同一个抽象中；
    • 用类型状态模式表达对象从草稿、已验证到已发布的状态流转。
    2.2. 类型级编程的核心载体（无外部依赖，原生支持）¶

    常见类型级编程主要基于 Rust 原生类型系统特性，复杂场景也可能配合宏或第三方 crate。核心载体包括：

    ✅ 关联类型 (Associated Types)

    ✅ 常量泛型 (Const Generics)

    ✅ Trait 约束 (Trait Bounds)

    ✅ 类型别名 (Type Aliases)

    ✅ 零大小类型 (ZST, Zero-Sized Types)

    3.示例¶

    3.1. 常量泛型表达矩阵维度¶
    use std::ops::Add;

#[derive(Debug, Clone, PartialEq)]
struct Matrix<T, const ROWS: usize, const COLS: usize> {
    data: [[T; COLS]; ROWS],
}

impl<T, const R: usize, const C: usize> Add for Matrix<T, R, C>
where
    T: Copy + Add<Output = T>,
{
    type Output = Matrix<T, R, C>;

    fn add(self, rhs: Self) -> Self::Output {
        let mut data = self.data;
        for r in 0..R {
            for c in 0..C {
                data[r][c] = data[r][c] + rhs.data[r][c];
            }
        }
        Matrix { data }
    }
}

fn main() {
    let a = Matrix { data: [[1, 2], [3, 4]] };
    let b = Matrix { data: [[10, 20], [30, 40]] };

    let c = a + b; // 只能和同维度矩阵相加
    assert_eq!(c.data, [[11, 22], [33, 44]]);

    // Matrix<i32, 2, 2> 不能直接与 Matrix<i32, 3, 2> 相加，维度错误会变成编译错误。
}
    3.2. 关联类型绑定输入与输出¶
    trait Parser {
    type Output;

    fn parse(&self, input: &str) -> Result<Self::Output, String>;
}

struct U64Parser;

impl Parser for U64Parser {
    type Output = u64;

    fn parse(&self, input: &str) -> Result<Self::Output, String> {
        input.parse::<u64>().map_err(|e| e.to_string())
    }
}

fn parse_twice<P: Parser>(parser: P, a: &str, b: &str) -> Result<(P::Output, P::Output), String> {
    Ok((parser.parse(a)?, parser.parse(b)?))
}

    Parser::Output 把“解析器类型”和“解析结果类型”绑定起来。调用方不需要额外传泛型参数，编译器会根据实现自动推导输出类型。

    3.3. 类型状态模式约束状态流转¶
    struct Draft;
struct Published;

struct Post<State> {
    title: String,
    body: String,
    state: std::marker::PhantomData<State>,
}

impl Post<Draft> {
    fn new(title: String, body: String) -> Self {
        Self { title, body, state: std::marker::PhantomData }
    }

    fn publish(self) -> Post<Published> {
        Post { title: self.title, body: self.body, state: std::marker::PhantomData }
    }
}

impl Post<Published> {
    fn url(&self) -> String {
        format!("/posts/{}", self.title)
    }
}

let draft = Post::<Draft>::new("rust".into(), "content".into());
// draft.url(); // 编译错误：草稿没有 url 方法
let published = draft.publish();
println!("{}", published.url());

    类型状态模式把“哪些状态允许哪些操作”编码进类型。错误的调用顺序会在编译期暴露，而不是等到运行时再检查状态字段。

    3.4. 常量泛型的稳定边界¶

    稳定 Rust 已经支持常量泛型参数（如 const N: usize），但对“任意 const 表达式约束”的支持仍有限。例如“数组长度必须大于 0”这类约束，不能简单依靠 assert!(N > 0) 变成编译期错误；assert! 在普通函数体中仍是运行时检查。

    工程上常见做法：

    1. 用构造函数封装检查，让非法值无法绕过公共 API；
    2. 对必须编译期验证的场景，使用宏生成有限集合的实现；
    3. 使用 typenum、generic-array 等成熟 crate 表达更复杂的类型级数字；
    4. 如果运行时检查足够清晰可靠，就不要强行搬到类型系统里。

    4.类型级编程的优缺点¶

    ✅ 优点：

    1. 性能友好：许多约束和分发关系可在编译期确定，运行时通常不需要额外检查；
    2. 提前暴露错误：把一部分非法状态和非法调用顺序变成编译错误；
    3. 接口表达力强：类型签名能直接说明维度、状态、能力约束等不变量；
    4. 运行时负担低：很多检查在编译期完成或由类型系统保证。

    ❌ 缺点：

    1. 学习成本高：需要对 Rust 类型系统有深入理解；
    2. 语法繁琐：复杂逻辑会导致类型嵌套过深；
    3. 编译速度：极复杂的类型计算会增加编译时间；
    4. 错误信息复杂：过度类型级编程会让调用方难以理解编译错误。
