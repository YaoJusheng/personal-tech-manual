    GPU 集群调度方案可按技术路线分为 HPC 传统调度、云原生容器编排、混合架构 与 GPU 虚拟化/专用调度 四大类。以下是目前主流方案的汇总与对比分析。

    一、主流方案概览¶

    方案 定位 核心能力 典型场景 官网/项目地址
    Slurm HPC 作业调度器 批处理队列、MPI 亲和、精确资源绑定 科学计算、大规模分布式训练 https://slurm.schedmd.com/
    Kubernetes + DRA/GPU Operator 云原生容器编排 动态资源分配、MIG/vGPU、弹性伸缩 推理服务、微服务化 AI 平台 https://github.com/NVIDIA/gpu-operator
    Volcano K8s 批调度增强 Gang 调度、拓扑感知、队列优先级 分布式训练（PyTorch/MPI） https://volcano.sh/
    YuniKorn K8s 资源调度器 公平共享、多租户队列、Web 可视化 多租户 AI 平台、大数据 https://yunikorn.apache.org/
    KAI Scheduler NVIDIA 专用 AI 调度器 Bin-packing、拓扑感知、GPU 亲和 homogeneous NVIDIA 大规模集群 https://github.com/kai-scheduler/KAI-Scheduler
    YARN 大数据生态调度 GPU 资源隔离（cgroups/Docker） Hadoop/Spark 生态内的 GPU 作业 https://hadoop.apache.org/
    K8s + Slurm 混合 分层统一调度 在线服务(K8s) + 离线训练(Slurm) 超大规模 AI 基础设施（如 DeepSeek） https://github.com/SlinkyProject/slurm-operator
    HAMi GPU 虚拟化调度层 vGPU 超售、显存隔离、跨厂商支持 多租户推理、GPU 利用率提升 https://project-hami.io/

    二、核心维度对比¶

    1. 调度语义与作业类型¶

    维度 Slurm K8s + Volcano K8s + YuniKorn K8s 原生
    作业模型 批处理脚本（有明确起止） PodGroup / Job 队列 + 应用 Pod / Deployment
    Gang 调度 原生支持（全有或全无） ✅ 核心特性 ✅ 支持 ❌ 需借助 Operator
    MPI 支持 原生，大规模扩展成熟 需 MPI Operator 有限 弱（>80 rank 易出问题）
    拓扑感知 节点级绑定、网络拓扑 NVLink/PCIe 感知调度 基础亲和性 节点级，无 GPU 拓扑
    队列与优先级 公平共享、回填、QoS 优先级、抢占 多队列公平共享 基础 PriorityClass

    Slurm 的调度策略以 固定集群 + 无限队列 为假设，优先级和回填机制非常成熟；而 Kubernetes 默认假设 无限资源 + 有限工作负载，对批处理的原生支持较弱，因此需要 Volcano 或 YuniKorn 补充 Gang 调度与队列能力。

    2. GPU 资源抽象与隔离¶

    能力 Slurm K8s + DRA HAMi YARN
    整卡分配 ✅ ✅ ✅ ✅
    MIG 实例 有限 ✅ GA（K8s 1.34+） ✅ ❌
    vGPU / 时间片 ❌ 需插件 ✅ 核心能力 ❌
    显存隔离 无 无 ✅ 无
    多厂商 GPU 需手动配置 需 Device Plugin ✅ 昇腾/昆仑/NVIDIA 仅 NVIDIA

    Kubernetes 1.34+ 的 Dynamic Resource Allocation (DRA) 已 GA，替代了旧的 Device Plugin 整数计数模型，支持通过 CEL 表达式进行属性过滤、优先回退分配和 Pod 内 GPU 共享。

    HAMi 作为 CNCF 生态中的 GPU 虚拟化方案，在贝壳找房的生产环境中将 GPU 利用率从 13% 提升至 37%，支持 10,000+ Pod 并发。

    3. 异构与扩展性¶

    方案 异构支持 万卡级扩展 通信优化
    Slurm 分区机制，需预配置 ✅ 成熟 原生 IB/RoCE 支持
    K8s + Volcano NFD 标签 + 调度策略 ✅ 50,000+ GPU 有案例 拓扑感知避免跨节点
    K8s + KAI 主要针对 NVIDIA ✅ homogeneous 场景 NVLink/PCIe 感知
    混合调度 分层抽象，统一池化 ✅ 动态资源分配 Slurm 管训练，K8s 管推理

    在超大规模场景下，OpenAI 在多个 Kubernetes 集群中编排 25,000 GPU 训练 GPT，通过自定义 Operator 处理故障和负载重平衡，在平均每 2.5 小时一次硬件故障的情况下保持 97% 利用率。Anthropic 在 8 个 K8s 集群 4,000 GPU 上实现 94% 利用率。

    4. 部署与运维复杂度¶

    方案 部署难度 运维工具链 学习曲线
    Slurm 中等（传统 Linux 环境） sinfo/squeue/sacct 低（HPC 领域熟悉）
    K8s + Volcano 高（容器化全栈） Prometheus/Grafana/DCGM 高
    YuniKorn 中（K8s 插件） Web UI + REST API 中
    混合架构 很高（双控制平面） 统一监控层 很高

    三、选型建议¶

    场景 推荐方案 理由
    高校/科研 HPC Slurm MPI 生态成熟，批处理队列完善，用户习惯根深蒂固
    云原生 AI 平台（训练+推理） K8s + Volcano + HAMi Gang 调度保障训练不饿死，vGPU 提升推理密度
    多租户企业 AI 中台 K8s + YuniKorn + DRA 公平共享、队列隔离、DRA 细粒度分配
    纯 NVIDIA 大规模训练集群 K8s + KAI Scheduler / DRA Bin-packing + 拓扑感知最大化 NVLink 利用率
    超大规模（万卡+） K8s + Slurm 混合 在线推理用 K8s，离线训练用 Slurm，统一资源池动态分配
    已有 Hadoop/Spark 生态 YARN GPU 无需引入新调度层，但功能较基础

    完整对比矩阵:

    方案 类型 Gang 调度 GPU 共享 异构支持 拓扑感知 多集群 开源 适用规模
    Slurm HPC 调度器 ✅ ❌ 分区机制 节点级 ❌ ✅ 万卡级
    K8s + Volcano 云原生批调度 ✅ 需插件 NFD 标签 NVLink/PCIe ❌ ✅ 千-万卡
    K8s + YuniKorn 云原生公平调度 ✅ 需插件 基础 基础 ✅ ✅ 多租户中台
    KAI Scheduler NVIDIA 专用调度 ✅（自动） 分数 GPU NVIDIA 为主 ✅ ❌ ✅ 大规模 NVIDIA
    Run:ai 企业 GPU 平台 ✅ 强制隔离 NVIDIA 为主 ✅ ✅ ❌ 企业级
    Ray/KubeRay AI 分布式框架 ✅（自动） 资源声明 CPU/GPU/TPU 节点级 ❌ ✅ 弹性推理/RL
    HAMi GPU 虚拟化层 — vGPU 超售 多厂商 — — ✅ 推理密度提升
    Fluid 数据编排 — — — 数据亲和 — ✅ 数据密集型
    SITS/FLASH 研究型调度 ✅ — 异构混训 通信拓扑 — 学术 前沿探索

    决策树:

    1. 你的主要工作负载类型？
   ├─ 科学计算/MPI → Slurm
   ├─ 分布式训练（PyTorch/MPI）→ K8s + Volcano 或 K8s + KAI
   ├─ 推理服务/弹性扩缩容 → K8s + DRA + HAMi
   └─ 超参数搜索/RL → Ray/KubeRay

2. 集群规模？
   ├─ < 100 GPU → K8s + Volcano/YuniKorn 足够
   ├─ 100-1000 GPU → KAI Scheduler 或 Run:ai
   └─ > 1000 GPU → 混合架构（K8s 推理 + Slurm 训练）或 Run:ai 企业版

3. 是否需要多租户隔离？
   ├─ 是 → YuniKorn（公平共享）或 Run:ai（强制隔离）
   └─ 否 → Volcano 或 KAI

4. 是否已有 NVIDIA AI Enterprise 授权？
   ├─ 是 → Run:ai（已捆绑）
   └─ 否 → KAI Scheduler（免费）+ 自建监控

5. 是否需要跨厂商 GPU（昇腾/昆仑）？
   ├─ 是 → HAMi + 自研调度策略
   └─ 否 → NVIDIA 生态（KAI/Run:ai/DRA）

    四、各调度工具示例与说明¶

    本章为每一种调度方案提供 部署要点 + 示例 + 说明 的三段式实操参考。示例以 PyTorch（Python） 训练作业为主要载体，并辅以 Go 编写的 GPU 探测/作业提交工具示例。

    通用训练脚本：后续多个示例会复用下面这个最小 PyTorch 分布式训练脚本 train.py，它通过环境变量自动适配单机/多机多卡（torchrun 与各调度器注入的 RANK/WORLD_SIZE/MASTER_ADDR 协同）。

    # train.py —— 最小 DDP 训练骨架，兼容 torchrun / Slurm / K8s
import os
import torch
import torch.distributed as dist
import torch.nn as nn
from torch.nn.parallel import DistributedDataParallel as DDP

def main():
    # 各调度器通过环境变量注入分布式拓扑信息
    rank = int(os.environ.get("RANK", 0))
    world_size = int(os.environ.get("WORLD_SIZE", 1))
    local_rank = int(os.environ.get("LOCAL_RANK", 0))

    dist.init_process_group(backend="nccl")        # GPU 通信用 NCCL
    torch.cuda.set_device(local_rank)
    print(f"[rank {rank}/{world_size}] 绑定 GPU cuda:{local_rank} "
          f"-> {torch.cuda.get_device_name(local_rank)}")

    model = nn.Linear(1024, 1024).cuda(local_rank)
    model = DDP(model, device_ids=[local_rank])
    optimizer = torch.optim.SGD(model.parameters(), lr=0.01)

    for step in range(100):
        x = torch.randn(64, 1024).cuda(local_rank)
        loss = model(x).sum()
        loss.backward()
        optimizer.step()
        optimizer.zero_grad()
        if rank == 0 and step % 20 == 0:
            print(f"step={step} loss={loss.item():.4f}")

    dist.destroy_process_group()

if __name__ == "__main__":
    main()

    通用 GPU 探测工具（Go）：用于在作业启动前确认容器/节点内可见的 GPU，许多调度器示例可在 initContainer 或作业入口调用它做自检。

    // gpucheck.go —— 调用 nvidia-smi 输出可见 GPU，校验调度器分配结果
package main

import (
    "fmt"
    "os"
    "os/exec"
    "strings"
)

func main() {
    out, err := exec.Command("nvidia-smi",
        "--query-gpu=index,name,memory.total",
        "--format=csv,noheader").Output()
    if err != nil {
        fmt.Fprintf(os.Stderr, "未检测到 GPU 或 nvidia-smi 不可用: %v\n", err)
        os.Exit(1)
    }
    gpus := strings.Split(strings.TrimSpace(string(out)), "\n")
    fmt.Printf("调度器分配到 %d 张 GPU:\n", len(gpus))
    for _, g := range gpus {
        fmt.Printf("  - %s\n", g)
    }
    // CUDA_VISIBLE_DEVICES 由调度器/设备插件注入，决定容器内可见的卡
    fmt.Printf("CUDA_VISIBLE_DEVICES=%s\n", os.Getenv("CUDA_VISIBLE_DEVICES"))
}

    1.Slurm 示例¶

    部署要点：在传统 Linux 集群上安装 slurmctld（控制节点）+ slurmd（计算节点），在 gres.conf 中声明 GPU 资源（Name=gpu Type=a100 File=/dev/nvidia[0-7]），并在 slurm.conf 中启用 GresTypes=gpu。

    示例：用 sbatch 提交一个 2 节点、每节点 8 卡的分布式训练作业。

    #!/bin/bash
#SBATCH --job-name=ddp-train
#SBATCH --partition=gpu          # GPU 分区
#SBATCH --nodes=2                 # 2 个节点
#SBATCH --ntasks-per-node=8       # 每节点 8 个任务（对应 8 卡）
#SBATCH --gres=gpu:8              # 每节点申请 8 张 GPU
#SBATCH --cpus-per-task=8
#SBATCH --time=02:00:00
#SBATCH --output=%x-%j.log

# Slurm 注入的变量映射到 PyTorch 分布式所需环境变量
export MASTER_ADDR=$(scontrol show hostnames "$SLURM_JOB_NODELIST" | head -n1)
export MASTER_PORT=29500
export WORLD_SIZE=$((SLURM_NNODES * SLURM_NTASKS_PER_NODE))

# srun 在每个任务上启动一个进程，RANK/LOCAL_RANK 由 Slurm 提供
srun bash -c '
  export RANK=$SLURM_PROCID
  export LOCAL_RANK=$SLURM_LOCALID
  python train.py
'

    提交与查看：

    sbatch train.slurm          # 提交作业，返回 JobID
squeue -u $USER             # 查看排队/运行状态
sinfo -p gpu -o "%n %G"     # 查看 GPU 分区各节点的 GRES（GPU）资源
sacct -j <JobID> --format=JobID,JobName,AllocGRES,State,Elapsed   # 作业资源审计
scancel <JobID>             # 取消作业

    说明：Slurm 通过 GRES（Generic RESource） 抽象 GPU，--gres=gpu:N 精确申请整卡并自动设置 CUDA_VISIBLE_DEVICES。其 Gang 语义天然存在——作业要么拿到全部请求的节点/卡一起启动，要么排队，非常适合 MPI/NCCL 这类"全有或全无"的同步训练。sacct 提供细粒度的资源使用审计，是 HPC 计费与复盘的基础。

    2.Kubernetes + DRA / GPU Operator 示例¶

    部署要点：用 Helm 安装 NVIDIA GPU Operator，它会自动部署驱动、container-toolkit、Device Plugin、DCGM-Exporter 等组件：

    helm repo add nvidia https://helm.ngc.nvidia.com/nvidia && helm repo update
helm install --wait gpu-operator nvidia/gpu-operator \
  -n gpu-operator --create-namespace

    示例 1：传统 Device Plugin 模型（整数计数，nvidia.com/gpu），跑前面的 PyTorch 训练：

    apiVersion: v1
kind: Pod
metadata:
  name: torch-train
spec:
  restartPolicy: Never
  containers:
    - name: trainer
      image: pytorch/pytorch:2.4.0-cuda12.1-cudnn9-runtime
      command: ["torchrun", "--nproc_per_node=2", "train.py"]
      resources:
        limits:
          nvidia.com/gpu: 2        # 申请 2 张整卡

    示例 2：DRA 模型（K8s 1.34+ GA），通过 ResourceClaim 声明式申请并支持属性过滤、Pod 内共享：

    apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata:
  name: single-gpu
spec:
  spec:
    devices:
      requests:
        - name: gpu
          exactly:
            deviceClassName: gpu.nvidia.com
            # 用 CEL 表达式按属性过滤：仅选显存≥40G 的卡
            selectors:
              - cel:
                  expression: "device.capacity['memory'].compareTo(quantity('40Gi')) >= 0"
---
apiVersion: v1
kind: Pod
metadata:
  name: torch-train-dra
spec:
  restartPolicy: Never
  resourceClaims:
    - name: gpu
      resourceClaimTemplateName: single-gpu
  containers:
    - name: trainer
      image: pytorch/pytorch:2.4.0-cuda12.1-cudnn9-runtime
      command: ["python", "train.py"]
      resources:
        claims:
          - name: gpu

    提交与查看：

    kubectl apply -f torch-train.yaml
kubectl describe node <gpu-node> | grep -A5 "Allocatable"   # 查看 nvidia.com/gpu 容量
kubectl get resourceclaims                                  # DRA：查看资源声明绑定情况
kubectl logs torch-train -f

    说明：旧的 Device Plugin 把 GPU 当作不可分割的整数计数资源（nvidia.com/gpu: N），无法表达"显存 40G 的卡"这类属性需求。DRA（Dynamic Resource Allocation） 在 K8s 1.34+ GA，引入 DeviceClass/ResourceClaim 声明式模型，支持 CEL 属性过滤、优先回退分配、Pod 内多容器共享同一 GPU，是云原生 GPU 调度的未来方向。

    3.Volcano 示例¶

    部署要点：Volcano 是 CNCF 批调度器，作为 K8s 的第二调度器安装：

    kubectl apply -f https://raw.githubusercontent.com/volcano-sh/volcano/master/installer/volcano-development.yaml

    示例：用 Volcano Job 跑 4 卡分布式训练，minAvailable 触发 Gang 调度（4 个 Pod 必须同时就绪才启动）：

    apiVersion: batch.volcano.sh/v1alpha1
kind: Job
metadata:
  name: ddp-train
spec:
  minAvailable: 4              # Gang：至少 4 个 Pod 同时调度成功才运行
  schedulerName: volcano
  queue: training             # 指定队列
  plugins:
    pytorch: ["--master=master", "--worker=worker", "--port=23456"]  # 自动注入 DDP 环境变量
  tasks:
    - replicas: 1
      name: master
      template:
        spec:
          containers:
            - name: trainer
              image: pytorch/pytorch:2.4.0-cuda12.1-cudnn9-runtime
              command: ["python", "train.py"]
              resources:
                limits:
                  nvidia.com/gpu: 1
          restartPolicy: OnFailure
    - replicas: 3
      name: worker
      template:
        spec:
          containers:
            - name: trainer
              image: pytorch/pytorch:2.4.0-cuda12.1-cudnn9-runtime
              command: ["python", "train.py"]
              resources:
                limits:
                  nvidia.com/gpu: 1
          restartPolicy: OnFailure

    配套队列定义：

    apiVersion: scheduling.volcano.sh/v1beta1
kind: Queue
metadata:
  name: training
spec:
  weight: 4                   # 权重决定多队列间的资源分配比例
  reclaimable: true           # 空闲资源可被其他队列借用，需要时回收

    提交与查看：

    kubectl apply -f volcano-queue.yaml && kubectl apply -f ddp-job.yaml
kubectl get vcjob ddp-train -o wide          # 查看 Volcano Job 状态
kubectl get podgroup                         # 查看 PodGroup（Gang 调度单元）
kubectl get queue training -o yaml           # 查看队列资源占用

    说明：Volcano 的核心价值是补齐 K8s 原生缺失的 批处理能力。minAvailable 实现 Gang 调度，避免分布式训练"部分 Pod 拿到卡、部分饿死导致整体死锁并空占 GPU"的问题；pytorch plugin 自动注入 MASTER_ADDR/RANK/WORLD_SIZE，无需手写。配合 Queue 的权重与 reclaimable，可实现多团队公平共享与资源回收，是云原生分布式训练最主流的调度增强。

    // yarn_gpu.go —— 通过 ResourceManager REST API 查询集群 GPU 容量与占用
package main

import (
    "encoding/json"
    "fmt"
    "net/http"
)

func main() {
    // YARN ResourceManager 指标接口
    resp, err := http.Get("http://rm-host:8088/ws/v1/cluster/metrics")
    if err != nil {
        panic(err)
    }
    defer resp.Body.Close()

    var data struct {
        ClusterMetrics struct {
            AllocatedGpus int `json:"allocatedGpus"`
            AvailableGpus int `json:"availableGpus"`
            TotalGpus     int `json:"totalGpus"`
        } `json:"clusterMetrics"`
    }
    json.NewDecoder(resp.Body).Decode(&data)
    m := data.ClusterMetrics
    fmt.Printf("GPU 总数=%d 已分配=%d 可用=%d\n",
        m.TotalGpus, m.AllocatedGpus, m.AvailableGpus)
}

    yarn application -list                         # 查看运行中的应用
yarn node -list -showDetails | grep gpu        # 查看各节点 GPU 资源

    说明：YARN 通过 yarn.io/gpu 资源类型 + cgroups 实现 GPU 的 分配与隔离，自动为容器设置 CUDA_VISIBLE_DEVICES。其优势是 无需引入新调度层即可在既有 Hadoop/Spark 生态内调度 GPU 作业，适合数据处理与训练同栈的场景；但功能相对基础——不支持 MIG/vGPU 切分、拓扑感知较弱，不适合作为纯 AI 训练平台的首选调度器。

    7.Kubernetes + Slurm 混合架构示例¶

    部署要点：混合架构没有单一标准产品，主流路线是用 Slinky（SchedMD 官方）/ slurm-operator 在 K8s 上运行 Slurm，从而"一套硬件、两种调度面"——K8s 调在线推理，Slurm 调离线训练。

    # 用 Slinky slurm-operator 在 K8s 上部署 Slurm 集群（控制器 + 计算节点 Pod）
helm install slurm-operator oci://ghcr.io/slinkyproject/charts/slurm-operator \
  -n slinky --create-namespace

    示例：资源分池思路（节点打标签，K8s 与 Slurm 各自管理一组节点池）：

    # 在线推理节点池：标记给 K8s 常规调度
apiVersion: v1
kind: Node
metadata:
  labels:
    workload-tier: online        # 在线服务池
    nvidia.com/gpu.product: A100
---
# 通过 nodeSelector 让推理服务只落在在线池
apiVersion: apps/v1
kind: Deployment
metadata:
  name: llm-inference
spec:
  replicas: 4
  template:
    spec:
      nodeSelector:
        workload-tier: online
      containers:
        - name: vllm
          image: vllm/vllm-openai:latest
          resources:
            limits:
              nvidia.com/gpu: 1

    示例：用 Go 实现简易的"潮汐调度"控制器骨架（夜间把在线池节点借给训练池）：

    // tidal.go —— 按时段在 online/training 两个池间迁移节点标签（潮汐借还）
package main

import (
    "fmt"
    "time"
)

func rebalance(hour int) string {
    // 业务低谷（00:00-08:00）把在线 GPU 借给离线训练，提升整体利用率
    if hour >= 0 && hour < 8 {
        return "training"   // 给 Slurm 训练池
    }
    return "online"         // 白天还给 K8s 在线服务池
}

func main() {
    for {
        tier := rebalance(time.Now().Hour())
        // 实际实现：调用 K8s API 给空闲节点打 workload-tier=<tier> 标签，
        // 并通知 Slurm/ K8s 纳管，这里仅打印决策结果
        fmt.Printf("[%s] 空闲节点划归: %s 池\n",
            time.Now().Format("15:04"), tier)
        time.Sleep(1 * time.Hour)
    }
}

    说明：混合架构是 超大规模（万卡+） 的工业级实践（如 DeepSeek）。核心思想是 统一资源池 + 分层调度：K8s 凭弹性与生态管在线推理/微服务，Slurm 凭成熟的 MPI/批处理与 sacct 计费管离线训练；通过节点标签分池与潮汐调度，在业务低谷把在线 GPU 借给训练，显著提升整体利用率。代价是 双控制平面 带来很高的运维复杂度，需要专门的平台团队。

    8.HAMi 示例¶

    部署要点：HAMi 是 CNCF Sandbox 的 GPU 虚拟化中间件。给 GPU 节点打标签后用 Helm 安装：

    apiVersion: v1

metadata:
  name: infer-vgpu

  containers:

    示例 2：用 Python 验证容器内被隔离的显存上限（应只看到约 3GB 而非整卡）：

    # verify_vgpu.py —— 在 HAMi 容器内验证显存隔离是否生效
import torch

free, total = torch.cuda.mem_get_info()
print(f"容器内可见显存上限: {total / 1024**2:.0f} MiB")   # 预期≈3000，而非整卡 40G/80G

# 尝试分配超过配额的显存，应触发 OOM，证明硬隔离生效
try:
    _ = torch.empty(int(4 * 1024**3 // 4), dtype=torch.float32, device="cuda")  # ~4GB
    print("警告：分配 4GB 成功，隔离可能未生效")
except RuntimeError as e:

kubectl get svc -n kube-system | grep hami

    说明：HAMi 在 不修改应用代码 的前提下实现 GPU 的 软虚拟化——通过 nvidia.com/gpumem（显存硬隔离）和 nvidia.com/gpucores（算力时间片）把一张物理卡切给多个 Pod，使容器内 nvidia-smi 和 CUDA 运行时只看到分配到的配额。它支持 NVIDIA / 昇腾 / 寒武纪 / 海光等多厂商，并可与 Volcano 等调度器协同。典型收益是把低利用率的整卡分配转为按需切分，大幅提升推理密度与整体 GPU 利用率（文档前述贝壳案例从 13% 提升至 37%）。

    五、2026 年技术趋势¶

    1. DRA 全面替代 Device Plugin：K8s 1.34+ 的 DRA 支持显存级申请、按属性过滤，成为云原生 GPU 调度的事实标准。
    2. 异构混训成为常态：GPU + NPU + CPU 的混合调度要求调度器具备 算子图感知 和 设备亲和性 能力，如 SITS 2026 的语义感知批构建。
    3. GPU 虚拟化从"能用"到"可运营"：HAMi 等方案证明 vGPU 必须在可治理的契约（利用率、隔离度、策略可测量）下才有经济价值。
    4. 通信感知的调度下沉：FLASH 等方案将 All-to-All 通信的 incast 与 straggler 问题纳入调度决策，调度器开始感知网络拓扑带宽层级（NVLink vs PCIe vs IB）。

    总结：没有"银弹"调度器。Slurm 在 HPC 批处理领域不可替代；Kubernetes 生态凭借云原生弹性和丰富的插件体系，成为 AI 基础设施的主流底座；超大规模场景下，K8s 管在线服务 + Slurm 管离线训练 的混合架构（如 DeepSeek）已成为工业级最佳实践。

    六、常用命令与排障速查¶

    1.GPU 资源排查¶

    目的 命令
    查看 GPU 型号/显存/利用率 nvidia-smi，持续刷新 nvidia-smi -l 1
    查看 MIG 实例 nvidia-smi mig -lgi
    查看进程级显存占用 nvidia-smi --query-compute-apps=pid,used_memory --format=csv
    K8s 节点 GPU 容量 kubectl describe node <node> \| grep -A3 nvidia.com/gpu
    K8s 集群级 GPU 监控 DCGM-Exporter + Prometheus（GPU Operator 默认部署）

    2.常见问题定位¶

    现象 可能原因与排查方向
    Pod 一直 Pending 拿不到 GPU 节点无可用卡 / Device Plugin 未就绪 / 队列配额耗尽；查 kubectl describe pod 的 Events 与调度器日志
    分布式训练卡在初始化 Gang 调度未满足 minAvailable 而部分 Pod 空占卡；查 kubectl get podgroup
    容器内 nvidia-smi 看不到卡 container runtime 未设为 nvidia / CUDA_VISIBLE_DEVICES 为空；查节点 runtime 配置
    HAMi 显存隔离不生效 节点未打 gpu=on 标签 / 未用 HAMi 调度器 / 镜像 CUDA 版本不兼容
    多机 NCCL 通信超时 网络/IB 配置或 MASTER_ADDR 错误；设 NCCL_DEBUG=INFO 看建链日志

    3.各调度器状态查看一览¶

    调度器 查看作业/队列命令
    Slurm squeue / sinfo / sacct
    K8s 原生 / DRA kubectl get pod,resourceclaims
    Volcano kubectl get vcjob,podgroup,queue
    YuniKorn Web UI（9889）/ curl .../ws/v1/.../queues
    KAI Scheduler kubectl get queue + Pod 的 Events
    YARN yarn application -list / yarn node -list
    HAMi kubectl exec <pod> -- nvidia-smi + 监控端口 31993

    排障通则：先确认硬件层（nvidia-smi 正常）→ 再确认设备插件/调度器组件运行（相关 namespace 的 Pod Running）→ 最后看作业事件（kubectl describe / 调度器日志）。逐层向上定位，避免在应用层反复试错。
