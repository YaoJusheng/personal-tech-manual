    前置知识：本文假设读者已掌握模型训练的基本概念（详见 训练简介.md），了解 GPU 调度与集群方案（详见 GPU调度.md），并熟悉 PyTorch/TensorFlow 框架基础（详见 深度学习框架理解与使用.md）。

    核心问题：我有 4 个任务，每个只需要 12GB 显存，但我有 4 张 80GB 的 A100——为什么我不能在一张卡上同时跑 4 个任务？为什么第一个任务就把整张卡的显存全占了？

    一、问题背景与挑战¶

    1.1 现象：一个任务吃掉整张卡¶

    当你在一张 A100-80GB 上启动一个 PyTorch 训练脚本时，即使模型和数据只需要 12GB 显存，nvidia-smi 也会显示接近 80GB 全部被占用。第二个任务尝试使用同一张卡时直接 OOM（Out of Memory）崩溃。

    $ nvidia-smi
+-----------------------------------------------------------------------------+
| GPU  Name        Persistence-M| Bus-Id        Disp.A | Volatile Uncorr. ECC |
| 0   A100 80GB    On           | 00000000:00:04.0 Off |                    0 |
| Processes:                                                                  |
|  PID   Type   Process name                         Usage                    |
| 12345  C      python3 train.py                      79269MiB  ← 几乎占满     |
|  (另一个任务无法启动 → CUDA out of memory)                                     |
+-----------------------------------------------------------------------------+

    根因：PyTorch 的 CUDA 缓存分配器（Caching Allocator）在进程启动时预分配大量 GPU 显存，且一旦分配永远不会归还给操作系统。这不是用户代码的错误，而是框架层面的有意设计。

    1.2 核心挑战¶

    # 挑战 说明
    1 CUDA 显存碎片化 反复分配/释放导致显存空洞，可用的总显存虽大但无法满足连续大块分配
    2 缓存分配器预分配不释放 PyTorch 的分配器为加速 cudaMalloc 调用，预先申请大块显存并缓存，进程终止前不归还
    3 框架级内存管理行为 PyTorch / TensorFlow 各有不同的内存策略，默认行为对多任务不友好
    4 多进程 GPU 共享冲突 多个进程同时操作同一 GPU 时，互不知晓对方的内存占用，缺乏协调机制
    5 多租户集群超售场景 集群调度器分配 GPU 整卡，但无法感知进程内实际显存使用量；超售时发生冲突

    1.3 真实场景¶

    • 训练 + 评估共享 GPU：训练进程占用几乎所有显存，评估进程因 OOM 无法启动
    • 推理服务 + 训练任务混部：在线推理需要稳定低延迟，但训练任务的内存颠簸导致推理抖动
    • 多租户实验环境：多个研究员共享一张 GPU，每人跑一个小模型微调，但第一个启动的任务独占所有显存
    • CI/CD 测试流水线：多个测试用例需要 GPU，串行执行浪费时间，并行执行立即 OOM

    1.4 CPU vs GPU 内存管理对比¶

    理解这个问题的关键：CPU 内存是需求分页（Demand Paging）的，GPU 显存是预分配的。

    维度 CPU 内存 GPU 显存
    分配策略 按需分配（Demand Paging），申请时才分配物理页 预分配大块缓存（Caching Allocator），提前预留
    释放行为 free() 立即归还给系统 cudaFree() 归还给缓存池，不归还给 OS
    超售支持 支持 Overcommit（SWAP 交换空间） 不支持 Overcommit，无交换机制
    碎片处理 内核的 Buddy System + SLUB 分配器抗碎片 用户态分配器，碎片由分配器自身管理
    进程隔离 硬件 MMU + 虚拟地址空间天然隔离 GPU 地址空间全局共享，无硬件隔离
    上下文切换 页表切换成本低 CUDA context 切换成本极高（~秒级）

    二、GPU 显存架构基础¶

    2.1 显存层级¶

    GPU 显存是一个多层级结构，理解带宽差异有助于优化分配策略：

    层级 类型 典型容量 典型带宽 作用
    HBM HBM2e / HBM3 A100: 80GB / H100: 80-94GB A100: 2 TB/s / H100: 3.35 TB/s 张量存储主区域
    L2 缓存 SRAM A100: 40MB / H100: 50MB ~10-20 TB/s 数据复用，减少 HBM 访问
    L1 缓存/共享内存 SRAM A100: 192KB per SM / H100: 256KB per SM ~50 TB/s 线程块内数据共享
    寄存器文件 寄存器 A100: 256KB per SM / H100: 256KB per SM 最高 线程私有数据

    关键结论：HBM 是宝贵的、有限的、高延迟的资源。缓存分配器的目标是减少对 HBM 的频繁 cudaMalloc/cudaFree，但这带来了多任务隔离问题。

    2.2 GPU 显存使用者¶

    以一个典型的 7B 参数模型训练（FP16 混合精度，AdamW 优化器，序列长度 4096，Global Batch Size 64）为例：

    使用类别 内容 典型占用量 说明
    模型参数 Weights + biases ~14 GB（FP16） 7B × 2 bytes = 14 GB
    优化器状态 Adam momentum + variance ~28 GB（FP32） 7B × 4 bytes × 2 个状态 = 56 GB？此处为 ZeRO 分片后的单卡量
    梯度 Gradient tensors ~14 GB（FP16） 与参数大小相同
    激活值 Intermediate activations ~20-40 GB 依赖序列长度、batch size、重计算策略
    临时缓冲区 通信 buffer、临时计算 ~2-8 GB all-reduce buffer、flash attention workspace
    CUDA 上下文 Kernel 库、驱动、cuBLAS handle ~1-2 GB 每个 CUDA 进程独占

    实际使用中，不带 ZeRO/FSDP 的 7B 全参数训练在 A100-80GB 上基本占满；开启 ZeRO-3 后可降至 ~40-50 GB。

    2.3 CUDA 缓存分配器机制（核心问题）¶

    2.3.1 PyTorch Caching Allocator 工作原理¶

    PyTorch 进程启动
       │
       ▼
  分配器初始化：创建空的内存池 (Memory Pool)
       │
  ┌────┴──────────────────────────────────────┐
  │  第一次张量分配（如模型加载）                 │
  │  → 分配器检查缓存池中是否有可用 block         │
  │  → 无 → cudaMalloc 一个大块 (e.g. 20GB)    │
  │  → 从大块中切分一个小块给张量                 │
  │  → 剩余部分留在池中等待后续分配               │
  └───────────────────────────────────────────┘
       │
  ┌────┴──────────────────────────────────────┐
  │  更多张量分配                               │
  │  → 分配器优先复用池中的空闲块                 │
  │  → 池中无合适块 → 再次 cudaMalloc 扩大池     │
  │  → 直到池占满所有可见 GPU 显存               │
  └───────────────────────────────────────────┘
       │
  ┌────┴──────────────────────────────────────┐
  │  张量释放 (tensor.del / a.grad = None)     │
  │  → 分配器将 block 标记为可用，归还到池        │
  │  → **不调用 cudaFree**，不归还给系统         │
  └───────────────────────────────────────────┘
       │
  ┌────┴──────────────────────────────────────┐
  │  其他进程尝试分配                            │
  │  → CUDA driver: 该 GPU 显存已被占用          │
  │  → CUDA OOM                               │
  └───────────────────────────────────────────┘

    2.3.2 为什么这样设计¶

    原因 说明
    cudaMalloc 开销高 cudaMalloc 是同步操作，需要与驱动交互、更新页表，一次调用约 10-100μs，而池内分配仅 ~0.1μs
    碎片控制 频繁的 cudaMalloc/cudaFree 会加剧显存碎片化
    批分配模式 深度学习训练有明确的阶段性：模型加载 → 前向 → 反向 → 优化器更新，内存模式可预测，池分配高效

    2.3.3 torch.cuda.empty_cache() 为什么不管用¶

    这是最常见的误解：

    torch.cuda.empty_cache()
# ✅ 效果：清空分配器缓存池中的空闲 block，使这些 block 可被 CUDA driver 复用
# ✅ 对本进程后续分配：无影响（需要时会重新 cudaMalloc）
# ❌ 不释放显存给其他进程：cudaFree 没有被调用，显存仍在当前进程的地址空间中
# ❌ 不释放 CUDA context：CUDA context 仍占用 ~1-2GB

    empty_cache() 之前:        empty_cache() 之后:
┌───────────────────┐       ┌──────────────────┐
│ 模型参数  (14GB)   │       │ 模型参数  (14GB)   │
│ 优化器状态 (28GB)  │       │ 优化器状态 (28GB)  │
│ 梯度     (14GB)   │       │ 梯度     (14GB)   │
│ 激活值   (20GB)   │       │ 激活值   (20GB)    │
│ [空闲块] (4GB)    │  →    │ (已清理空闲块)      │ ← 这些被清掉
│ ──────────────── │       │ ───────────────   │
│ 总占用: 80GB      │       │ 总占用: 76GB       │ ← 仍然很多
└──────────────────┘       └───────────────────┘

    结论：empty_cache() 只能释放缓存池中尚未使用的空闲块，对已分配给张量的内存无效。在训练过程中，由于大部分显存都在使用中，它几乎不起作用。

    2.3.4 expandable_segments（PyTorch 2.0+）¶

    PyTorch 2.0 引入了 expandable_segments 特性，改变了分配器的行为：

    export PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True

    原理：传统的分配器一次分配一个大块（比如 20GB），然后从中切分。expandable_segments 改为分配多个较小的段（Segment），并且这些段可以非连续地扩展。

    对比 传统分配器 expandable_segments
    初始分配 一次性大块 cudaMalloc 多个小段逐步分配
    碎片化 大块内部碎片可能严重 小段更灵活，抗碎片
    内存释放 段内空闲块不能跨段回收 空闲小段可以整体释放
    多任务友好度 低（占满不释放） 中（可部分释放）
    性能影响 基准 部分场景有小幅提升

    注意：expandable_segments 改善了碎片化和灵活性，但仍然不解决跨进程的内存隔离问题。

    2.3.5 max_split_size_mb 配置¶

    export PYTORCH_CUDA_ALLOC_CONF=max_split_size_mb:128

    控制分配器在拆分大块时的最小拆分粒度。较小值有助于减少碎片，但可能增加分配次数。

    2.3.6 garbage_collection_threshold¶

    export PYTORCH_CUDA_ALLOC_CONF=garbage_collection_threshold:0.6

    当空闲内存占总分配超过 60% 时，触发内部垃圾回收，尝试将空闲块合并回段中甚至释放段。这可以让显存占用更动态，但回收本身有性能开销。

    三、导致单任务独占整卡的根因分析¶

    3.1 框架层面¶

    PyTorch Caching Allocator 默认行为¶

    行为 原因 后果
    预分配大块显存 减少 cudaMalloc 调用次数 即使不需要，也先占满
    不主动释放 避免 cudaFree 的重分配成本 其他进程无法获取显存
    缓存池膨胀 模型越大、训练越久，池越大 进程不会主动缩池
    碎片累积 反复分配/释放不同大小的 tensor 可用显存总量减少

    核心矛盾：PyTorch 的设计假设是"一个进程独占一张 GPU"，所有优化都围绕这个假设展开。在多进程共享 GPU 的场景下，这些优化变成了障碍。

    torch.cuda.set_per_process_memory_fraction(fraction, device)¶

    这是 PyTorch 提供的唯一原生跨进程显存限制手段：

    import torch

# 限制当前进程在 device 0 上最多使用 50% 的显存（40GB on A100-80GB）
torch.cuda.set_per_process_memory_fraction(0.5, device=0)

    工作机制：

    • 在 CUDA allocator 层拦截 cudaMalloc 调用
    • 当分配总量超过 fraction 上限时，直接报 OOM
    • 上限是硬限制：一旦达到，任何新分配都会失败

    实际效果验证：

    def test_memory_limit():
    torch.cuda.set_per_process_memory_fraction(0.25, device=0)  # 20GB
    total = torch.cuda.get_device_properties(0).total_memory
    print(f"Total GPU memory: {total / 1e9:.1f} GB")
    print(f"Per-process limit: {total * 0.25 / 1e9:.1f} GB")

    # 尝试分配超过限制的张量
    try:
        # 尝试分配 25GB → 应失败
        x = torch.empty(25 * 1024**3 // 4, dtype=torch.float32, device='cuda')
        print("Allocation succeeded (unexpected)")
    except RuntimeError as e:
        print(f"OOM as expected: {e}")

test_memory_limit()

    输出:

Per-process limit: 20.0 GB
OOM as expected: CUDA out of memory. ...

    3.2 CUDA Driver 层面¶

    概念 说明 对显存占用的影响
    CUDA Context 每个 CUDA 进程与驱动之间的会话状态 ~1-2 GB（包含 cuBLAS handle、CUDA module、kernel 缓存等）
    Primary Context 每个 GPU 设备只有一个 primary context，但每个进程都有独立的 context 多个进程 → 多个 context → 至少 1-2GB × 进程数
    Context 迁移 切换 GPU context 时，驱动需要保存/恢复状态 开销极大（秒级），不利于快速切换
    CUDA MPS 多进程共享一个 CUDA context 减少 context 数量，降低内存开销

    3.3 OS / Driver 层面¶

    特性 说明 问题
    时间片调度（Time-Slicing） NVIDIA driver 默认以时间片方式在多个 CUDA 进程间切换计算 无内存隔离，一个进程 OOM 全崩
    计算抢占（Compute Preemption） Volta+ 支持 kernel 级计算抢占 可打断长 kernel，但不解决内存问题
    内存不可抢占 GPU 显存没有任何形式的交换机制（对比 CPU 的 SWAP） 一旦分配，除非进程主动释放，否则永远占用
    UVM (Unified Virtual Memory) 支持 GPU 访问 CPU 内存，但 CPU 内存不能作为 GPU 显存的交换空间 仅单向，不能缓解显存压力 
    CPU 内存模型:
进程A: [████████████░░░░░░]  80% 占用, 20% 空闲
进程B: [████░░░░░░░░░░░░░]  30% 占用
→ 系统总内存: (80% + 30%) > 100%? 没关系, SWAP 换出即可

GPU 显存模型:
进程A: [██████████████████]  100% 占用 (实际只用 20%, 但缓存分配器占满)
进程B: 尝试分配 → CUDA OOM ❌
→ 无 SWAP, 无 Overcommit, 无法换出

    4.2 NVIDIA MIG（Multi-Instance GPU）—— 最强隔离¶

    4.2.1 原理¶

    MIG 将一张物理 GPU 划分为多个独立的 GPU 实例，每个实例拥有完全隔离的：

    • HBM 显存：独占的分区，不会被其他实例使用
    • SM（流式多处理器）：专用计算单元
    • L2 缓存：每实例独立 L2 cache slice
    • 内存带宽：独享带宽路径
    • 错误隔离：一个实例的 ECC 错误不影响其他实例

    4.2.2 MIG Profile 详解¶

    A100 80GB 支持的 MIG Profile：

    Instance Profile GPU Memory Compute Units (SM) 占比 最大实例数
    1g.10gb 10 GB 1/8 SMs (14 SM) 12.5% 7
    1g.10gb+me 10 GB 1/8 SMs + 1 Media Engine 12.5% 4 + 3
    2g.20gb 20 GB 2/8 SMs (28 SM) 25% 3
    3g.40gb 40 GB 3/8 SMs (42 SM) 37.5% 2
    4g.40gb 40 GB 4/8 SMs (56 SM) 50% 1
    7g.80gb 80 GB 7/8 SMs (98 SM) 87.5% 1

    H100 80GB/94GB 支持的 MIG Profile（示例）：

    Instance Profile GPU Memory Compute Units 说明
    1g.10gb 10 GB 1/7 SMs 比 A100 更灵活的分区
    1g.20gb 20 GB 1/7 SMs 更多显存选项
    2g.20gb 20 GB 2/7 SMs
    3g.40gb 40 GB 3/7 SMs
    4g.40gb 40 GB 4/7 SMs
    7g.80gb 80 GB 全部 不启用 MIG 模式

    4.2.5 MIG 的局限性¶

    局限性 说明 影响
    仅高端数据中心卡 不支持 RTX 系列、V100 消费级用户无法使用
    需要重启机器 开启 MIG 模式需要 reboot 运维成本

    4.3 NVIDIA MPS（Multi-Process Service）¶

    4.3.1 原理¶

    MPS 启动一个守护进程，将多个 CUDA 进程的上下文合并到一个 CUDA address space 中，从而实现：

    • CUDA context 共享：多个进程共用同一组 cuBLAS/cuDNN handle，减少显存开销
    • kernel 合并调度：提高 GPU 利用率（小 kernel 场景尤其明显）
    • 减少内存冗余：相同 CUDA module（kernel 代码）只加载一次
    无 MPS:                               有 MPS:
进程A ─── CUDA Context A ─── GPU      进程A ─┐
进程B ─── CUDA Context B ─── GPU     进程B ──┼── MPS Daemon ─── GPU
进程C ─── CUDA Context C ─── GPU     进程C ──┘
                                        ↑ 共享一个 Context

    4.3.2 配置与使用¶

    # 启动 MPS 守护进程
export CUDA_MPS_PIPE_DIRECTORY=/tmp/mps  # IPC 管道目录
export CUDA_MPS_LOG_DIRECTORY=/tmp/mps/log
nvidia-cuda-mps-control -d  # 后台启动

# 检查 MPS 状态
ps aux | grep mps
echo "start_server -uid $(id -u)" | nvidia-cuda-mps-control

# 运行共享进程（正常启动，自动连入 MPS）
CUDA_VISIBLE_DEVICES=0 python train_a.py &
CUDA_VISIBLE_DEVICES=0 python train_b.py &

# 停止 MPS
echo "quit" | nvidia-cuda-mps-control

    4.3.3 MPS + 显存限制结合¶

    MPS 本身不提供任何内存隔离，因此必须配合 set_per_process_memory_fraction 使用：

    import os
import torch

gpu_id = int(os.environ.get('LOCAL_RANK', 0))
# 每个进程限制 20GB，已确保 MPS 共享池不被某个进程耗尽
torch.cuda.set_per_process_memory_fraction(20.0 / 80.0, device=gpu_id)

    4.3.4 MPS 适用场景¶

    场景 效果 推荐度
    大量小推理任务（如 batch=1 的在线推理） 显著提升吞吐 强烈推荐
    多个微调训练任务 减少冗余，但隔离性差 谨慎使用
    不同用户共享 GPU 无隔离，不适合 不推荐
    显存敏感场景 需搭配 fraction 使用 需配套

    4.7 时间片调度（Time-Slicing）¶

    4.7.1 原理¶

    时间片调度是 NVIDIA K8s Device Plugin 支持的一种 GPU 共享方案。它在时间域上共享计算：

    时间线 ─────────────────────────────────────────────────────>
GPU   ┌──任务A──┐  ┌──任务B──┐  ┌──任务C──┐  ┌──任务A──┐  ┌──
       ↓ 10ms    ↓ 10ms    ↓ 10ms    ↓ 10ms

    特点：

    • 多个 Pod 可以共享同一张 GPU
    • 配置简单（无需重启 GPU）
    • 无显存隔离：所有 Pod 共享总显存，一个 OOM 全崩
    • 无计算隔离：任务互相抢占

    4.7.2 配置¶

    # 在 K8s 集群中配置 GPU Time-Slicing

# 1. 创建 ConfigMap

  name: time-slicing-config
  namespace: gpu-operator
data:
  gpu-time-slicing: |-
    version: v1
    flags:
      default: 1
    sharing:
      timeSlicing:
        resources:
        - name: nvidia.com/gpu
          replicas: 4  # 一张卡暴露为 4 个可调度的 GPU
          annotate: true

    6.2 PyTorch 内存分析工具链¶

    import torch

# 在日常训练脚本中添加诊断回调
class MemoryDiagnosticCallback:
    """训练过程中的显存诊断回调"""
    def __init__(self, log_interval=100):
        self.log_interval = log_interval
        self.step = 0

    def on_step_end(self):
        self.step += 1
        if self.step % self.log_interval != 0:
            return

        device = torch.cuda.current_device()
        allocated = torch.cuda.memory_allocated(device) / 1e9
        reserved = torch.cuda.memory_reserved(device) / 1e9
        peak = torch.cuda.max_memory_allocated(device) / 1e9

        print(f"[Step {self.step}] "
              f"allocated={allocated:.2f}GB "
              f"reserved={reserved:.2f}GB "
              f"peak={peak:.2f}GB "
              f"util={allocated/reserved*100:.1f}%" if reserved > 0 else "")

    def get_fragmentation(self):
        """估算碎片化程度"""
        reserved = torch.cuda.memory_reserved()
        allocated = torch.cuda.memory_allocated()
        if reserved == 0:
            return 0.0
        return 1.0 - allocated / reserved

    8.1 通用原则¶

    1. 先诊断，后限制
    2. 用 nvidia-smi 和 memory_summary() 摸清当前显存分配情况

    7. K8s 提供资源声明 + 自动调度

    8.4 常见误区¶

    误区 纠正
    empty_cache() 能释放显存给其他进程 只释放进程缓存池中的空闲 block，不归还 OS，其他进程仍无法使用
    CUDA_VISIBLE_DEVICES=0 就能完全隔离 只是逻辑隔离（让进程只能"看到"某张卡），不限制显存用量
    Docker --memory=32g 能限制 GPU 显存 Docker --memory 只限制 CPU 内存，对 GPU 显存完全无效
    nvidia-smi 显示的显存占用就是真实分配量 nvidia-smi 显示的是 CUDA 缓存池大小，不是实际 tensor 占用量
    模型参数占 14GB 那训练就只用 14GB 实际需要参数+梯度+优化器状态+激活值+缓冲区，通常为参数量的 4-12 倍
    MIG 可以动态调整分区 MIG 分区必须预先规划，创建/删除需要重置 GPU 状态
    torch.cuda.reset_peak_memory_stats() 能释放显存 只重置统计计数器，不释放任何显存

    8.5 快速检查清单¶

    □ 确认 GPU 型号和总显存
□ 检查是否开启 MIG 模式（如果 A100/H100）
□ 测量每个任务的峰值显存占用
□ 计算总需求 + 20% 余量 ≤ 总显存
□ 选择隔离方案：
  ├─ MIG → 规划 Profile → nvidia-smi mig -cgi
  ├─ per_process_fraction → 计算 fraction → 代码中设置
  └─ HAMi → 部署 HAMi → 配置 K8s resource
□ 设置 PYTORCH_CUDA_ALLOC_CONF 环境变量
□ 测试并行启动，监控 nvidia-smi
□ 验证所有任务都能正常运行且无 OOM
□ 设置 DCGM / Prometheus 告警（显存使用 > 90%）
