    一、消息队列简介¶

    消息队列（Message Queue，MQ）是一种异步通信中间件，生产者（Producer）将消息发送到队列，消费者（Consumer）从队列中取出消息处理，二者无需同时在线、互不感知，从而实现系统间的解耦。

    三大核心价值：

    价值 说明 典型场景
    异步 耗时操作放入队列后立即返回，提升响应速度 下单后异步发短信、发积分、写日志
    解耦 上下游通过消息契约通信，新增消费方无需改动生产方 订单服务发事件，库存/物流/风控各自订阅
    削峰填谷 突发流量先入队，消费端按自身能力匀速处理 秒杀、抢购、大促洪峰

    典型应用场景： 异步任务处理、应用解耦、流量削峰、日志收集、事件驱动架构（EDA）、数据同步（CDC）、跨系统集成、实时流计算入口。

    代价：引入 MQ 也带来了系统复杂度上升（多了一个需高可用的中间件）、消息一致性问题（丢失/重复/乱序）以及调用链变长导致的排查难度，需结合后文的可靠性方案权衡使用。

    二、核心概念与模型¶

    2.1.核心角色与术语¶

    概念 含义
    Producer（生产者） 发送消息的一方
    Consumer（消费者） 接收并处理消息的一方
    Broker 消息服务器，负责接收、存储、转发消息
    Topic（主题） 消息的逻辑分类，生产/消费按 Topic 进行
    Partition（分区） Topic 的物理分片，是并行消费与水平扩展的基础
    Offset（偏移量） 消息在分区内的位置序号，消费进度由 Offset 标记
    Consumer Group 消费者组，组内成员分摊分区，组间互不影响（广播效果）
    ACK（确认） 消费者处理成功后回执，Broker 据此推进消费进度
    Backlog / Lag 消息积压量（未被消费的消息数），是核心健康指标

    2.2.两种消息模型¶

    • 点对点（P2P，队列模型）：一条消息只被一个消费者消费，消费后即"出队"。适合任务分发（如订单处理流水线）。
    • 发布/订阅（Pub/Sub，主题模型）：一条消息可被多个订阅者各自消费一份。适合事件广播（如一个订单事件被多个下游系统订阅）。

    现代 MQ（Kafka/RocketMQ/Pulsar）通过 Consumer Group + Offset 统一了两种模型：组内是点对点（负载均衡），组间是发布订阅（广播）。

    2.3.推模式 vs 拉模式¶

    模式 说明 优缺点
    Push（推） Broker 主动推送给消费者 实时性好；但消费端可能被压垮，需配合流控
    Pull（拉） 消费者主动拉取 消费端按自身节奏拉取、天然背压；实时性略低，可用长轮询缓解

    Kafka、RocketMQ 以 Pull 为主（长轮询）；RabbitMQ 支持 Push（basic.consume）与 Pull（basic.get）。

    三、工作原理与工作流程¶

    3.1.通用工作流程¶

    一条消息从生产到消费，经历"发送 → 路由分区 → 持久化 → 投递 → 消费 → 确认"的完整链路：

    flowchart LR
    P[Producer 生产者] -->|1.发送+ack确认| B[Broker]
    subgraph B[Broker 消息服务器]
        R[2.路由/分区选择] --> S[3.顺序写日志/入队]
        S --> IDX[4.建立索引/偏移]
    end
    B -->|5.推送或拉取| C[Consumer 消费者]
    C -->|6.处理成功| CMT[7.提交Offset/ACK]
    CMT -->|推进消费进度| B
    • 发送：生产者将消息发往 Broker，按可靠性要求选择是否等待 ack（同步/异步）。
    • 路由/分区：Broker 按 Topic + key 哈希（或轮询）决定写入哪个分区/队列。
    • 持久化：现代 MQ 普遍采用顺序写磁盘日志（append-only），配合 Page Cache 与零拷贝实现高吞吐。
    • 投递：Pull 模式消费者主动拉取（长轮询），Push 模式 Broker 主动推送。
    • 消费 + 确认：消费者处理成功后提交 Offset（日志型）或回 ACK（队列型），Broker 据此推进进度。

    3.2.两种存储模型¶

    模型 代表 机制 特点
    日志型（Log-based） Kafka、RocketMQ、Pulsar 消息顺序追加到分区日志，消费仅移动 Offset，消息不因消费而删除，按保留期清理 高吞吐、可回溯、多消费组独立消费、堆积能力强
    队列型（Queue-based） RabbitMQ、传统 MQ 消息进入队列，被确认消费后即从队列删除 路由灵活、单条管理精细、堆积能力弱、不可回溯

    这是两类 MQ 最本质的差异：日志型像"可重复播放的录像带"，队列型像"取走即少一份的快递柜"。它直接决定了回溯、堆积、广播消费等能力的有无。

    3.3.主流 MQ 内部机制图解¶

    Kafka：Topic 分区化，每分区是一个有序日志，多副本（Leader/Follower）通过 ISR 保证可靠：

    flowchart TB
    PR[Producer] -->|按key哈希分区| T
    subgraph T[Topic]
        P0[Partition0 Leader] --- P0F[Follower副本]
        P1[Partition1 Leader] --- P1F[Follower副本]
    end
    P0 --> CG
    P1 --> CG
    subgraph CG[Consumer Group]
        C0[Consumer0]
        C1[Consumer1]
    end

    RocketMQ：写入统一的 CommitLog（顺序写），再异步分发到各 ConsumeQueue 作为消费索引：

    flowchart LR
    PR[Producer] --> CL[(CommitLog 顺序写)]
    CL -->|异步分发| CQ0[ConsumeQueue-TopicA-Q0]
    CL -->|异步分发| CQ1[ConsumeQueue-TopicA-Q1]
    CQ0 --> C0[Consumer]
    CQ1 --> C1[Consumer]

    RabbitMQ：消息先到 Exchange，按 Binding 规则路由到一个或多个 Queue：

    flowchart LR
    PR[Producer] --> EX{Exchange}
    EX -->|routing key=order.*| Q1[Queue: order]
    EX -->|fanout 广播| Q2[Queue: log]
    EX -->|fanout 广播| Q3[Queue: audit]
    Q1 --> C1[Consumer]
    Q2 --> C2[Consumer]
    Q3 --> C3[Consumer]

    Pulsar：存算分离，Broker 无状态只负责服务，数据持久化在 BookKeeper：

    flowchart TB
    PR[Producer] --> BR[Broker 无状态层]
    BR --> BK
    subgraph BK[BookKeeper 存储层]
        B1[Bookie1]
        B2[Bookie2]
        B3[Bookie3]
    end
    BR --> CS[Consumer]

    机制差异决定能力差异：Kafka/RocketMQ 的顺序日志带来高吞吐与回溯；RabbitMQ 的 Exchange 路由带来灵活的分发；Pulsar 的存算分离带来弹性扩缩与跨地域。

    四、主流消息队列对比与选型¶

    4.1.主流产品对比¶

    维度 Kafka RocketMQ RabbitMQ Pulsar NATS / JetStream Redis Stream
    出品方 Apache（LinkedIn） Apache（阿里） VMware（Erlang） Apache（Yahoo） CNCF（Synadia） Redis
    吞吐 极高（百万级/s） 高（十万级/s） 中（万级/s） 极高 极高 高
    延迟 毫秒级 毫秒级 微秒~毫秒 毫秒级 微秒级 微秒~毫秒
    持久化 强（磁盘日志） 强 支持 强（存算分离 BookKeeper） JetStream 支持 AOF/RDB
    顺序消息 分区内有序 支持（顺序/分区） 队列内有序 分区内有序 有序 有序
    事务消息 支持（幂等/事务） 支持（半消息两阶段） 不原生支持 支持 有限 不支持
    延迟消息 不原生（需变通） 原生支持（多级） 插件支持 原生支持 有限 不原生
    堆积能力 极强 极强 较弱 极强 中 中
    协议 自有 自有/HTTP AMQP/MQTT/STOMP 自有/Kafka 兼容 自有 RESP
    典型场景 日志/流处理/大数据 金融级业务/电商 复杂路由/传统企业 云原生/多租户 微服务/IoT 低延迟 轻量异步任务

    4.2.选型参考¶

    需求场景 推荐
    海量日志、流式数据、数据管道、对接大数据（Flink/Spark） Kafka / Pulsar
    金融级业务（订单/支付），需事务消息、定时延迟消息、严格顺序 RocketMQ
    复杂路由（topic/direct/fanout/headers）、传统企业集成、协议丰富 RabbitMQ
    云原生、存算分离、多租户、跨地域复制、需弹性扩缩 Pulsar
    微服务内部低延迟通信、IoT、边缘、轻量部署 NATS / JetStream
    已有 Redis、轻量异步任务、不想引入重型中间件 Redis Stream

    架构演进趋势：Kafka 自 3.x 起以 KRaft（自带 Raft 元数据，去 ZooKeeper）简化运维并已在新版本默认；同时社区出现 Redpanda（C++ 重写、兼容 Kafka 协议、无 JVM/无 ZK）等高性能替代。Pulsar 的存算分离架构（Broker 无状态 + BookKeeper 存储）代表了云原生弹性方向。

    4.3.处理过程的差异¶

    同样是"收发消息"，不同 MQ 在处理过程的关键环节上机制迥异，直接影响其能力边界：

    处理环节 Kafka RocketMQ RabbitMQ Pulsar
    存储结构 每分区独立日志文件 统一 CommitLog + ConsumeQueue 索引 内存/磁盘队列，确认后删除 BookKeeper Ledger 分片存储
    写入方式 顺序追加分区日志 全部顺序写一个 CommitLog（写最优） 路由到队列，逐条管理 写多个 Bookie（多副本并行）
    消费模型 拉模式 + Offset，组内分区独占 拉为主，支持广播/集群两种消费 推为主，多消费者竞争同队列 拉 + 多种订阅模式（独占/共享/故障转移/key共享）
    消费进度 Offset 由消费者/Broker 维护，可重置回溯 Offset 由 Broker 维护，可按时间回溯 无 Offset，确认即删除，不可回溯 Cursor 由 Broker 维护，可重置
    顺序保证 分区内有序 顺序消息（同 queue 串行投递） 单队列单消费者有序 分区内有序 / Key_Shared
    事务实现 幂等 Producer + 事务（跨分区原子写） 半消息两阶段提交 + 事务回查 不原生支持（靠 publisher confirm + 业务补偿） 原生事务（跨分区/主题）
    延迟消息 不原生，靠时间轮/分级 Topic 变通 原生多级延迟（固定级别 + 任意精度） 靠 TTL + 死信交换机变通 原生定时/延迟投递
    重试/死信 需自建重试 Topic + DLQ 内置重试队列 %RETRY% + 死信 %DLQ% 内置 DLX 死信交换机 内置重试字母/死信主题
    扩容影响 加分区会改变 key 路由，影响顺序 加 queue 类似 加队列/消费者较灵活 Broker 无状态，扩容平滑

    4.4.逐工具优劣与使用建议¶

    Kafka:

    • ✅ 优势：吞吐天花板最高、生态最成熟（Connect/Streams/Flink）、可回溯、堆积能力极强。
    • ❌ 劣势：延迟消息/事务消息支持弱、单条消息治理（重试/死信）需自建、运维相对重。
    • 💡 建议：日志采集、流式数据管道、大数据对接、事件溯源的首选；不要用它做需要精细单条治理或复杂延迟的业务消息。

    RocketMQ:

    • ✅ 优势：金融级可靠、原生事务消息 + 任意精度延迟消息、顺序消息成熟、运维友好（中文生态）。
    • ❌ 劣势：生态与跨语言支持不如 Kafka 广、海外社区相对小。
    • 💡 建议：电商/金融核心业务消息（订单、支付、库存）首选，尤其需要事务、延迟、顺序时。

    RabbitMQ:

    • ✅ 优势：路由能力最灵活（direct/topic/fanout/headers）、协议丰富（AMQP/MQTT/STOMP）、低延迟、成熟稳定。
    • ❌ 劣势：吞吐与堆积能力弱、不可回溯、海量堆积时性能下降明显。
    • 💡 建议：业务解耦、复杂路由分发、传统企业集成、中小流量任务队列首选；不适合海量日志流。

    Pulsar:

    • ✅ 优势：存算分离带来弹性扩缩与平滑运维、原生多租户、跨地域复制、统一支持队列与流两种语义。
    • ❌ 劣势：架构组件多（Broker + BookKeeper + ZK/etcd）、运维门槛高、生态较新。
    • 💡 建议：云原生、多租户 SaaS、超大规模且需弹性伸缩的场景；团队需具备较强运维能力。

    五、系统接入方式¶

    业务系统接入 MQ 有多种方式，需根据团队技术栈、运维能力与可移植性要求选择。

    5.1.主流接入模式¶

    接入方式 说明 代表 适用场景
    原生 SDK 直连 直接使用官方客户端库收发消息 kafka-clients、rocketmq-client、pika、pulsar-client 控制力强、性能最优；与 MQ 强绑定
    框架集成（Starter） 框架封装统一注解/模板，简化样板代码 spring-kafka、spring-amqp、rocketmq-spring-boot-starter Spring 技术栈，快速开发
    统一消息抽象 屏蔽底层 MQ 差异，一套代码切换中间件 Spring Cloud Stream（Binder）、Apache Camel 需多 MQ 共存或未来可能切换
    云托管服务 云厂商全托管，免运维、按量付费 阿里云 RocketMQ/Kafka、AWS MSK/SQS、Confluent Cloud 不想自建运维、弹性需求
    Sidecar / 运行时 通过边车进程屏蔽 MQ SDK，多语言统一 Dapr Pub/Sub、Service Mesh 多语言异构、云原生、Serverless

    5.2.接入设计要点¶

    • 连接管理：复用连接/通道（Channel），避免频繁创建；客户端配置连接池与心跳保活。
    • 序列化：约定统一序列化协议（JSON 易调试 / Avro/Protobuf 高效且强 Schema），配合 Schema Registry 管理契约演进。
    • 可靠性配置：生产端开启确认（acks/confirm）+ 失败重试；消费端手动提交 + 幂等；按业务等级权衡吞吐与可靠性。
    • 错误处理：消费异常分类——可重试（网络抖动，退避重试）vs 不可重试（脏数据，直接转 DLQ），避免毒消息阻塞。
    • 优雅停机：停机前停止拉取、处理完在途消息、提交位点再关闭连接，避免消息丢失或重复。
    • 配置外置：连接地址、Topic、消费组、并发度等通过配置中心管理，支持动态调整。
    • 可观测埋点：消息头透传 trace_id/span_id，打通生产到消费的全链路追踪。

    接入抽象的价值与代价：Spring Cloud Stream / Dapr 等抽象层让业务代码与具体 MQ 解耦、便于切换和多语言统一，但会牺牲部分中间件特有能力（如 RocketMQ 事务消息、Kafka 精确一次），需在"可移植性"与"特性深度"之间权衡。

    六、核心问题与解决方案¶

    使用 MQ 必然要面对四类经典问题：消息丢失、重复消费、消息顺序、消息积压。

    6.1.消息丢失（如何保证不丢）¶

    消息可能在三个阶段丢失，需逐段加固：

    阶段 丢失原因 解决方案
    生产端 发送后未确认 Broker 已落盘 使用同步发送 + 确认机制（Kafka acks=all、RocketMQ 同步发送 + 重试），失败重试
    Broker 端 消息只在内存/单副本，宕机丢失 持久化刷盘（同步刷盘）+ 多副本（Kafka min.insync.replicas≥2、副本因子≥3）
    消费端 拉到消息但处理失败却已提交 Offset 先处理成功，再手动提交 Offset/ACK；禁用自动提交

    三段都做到位即可实现"不丢"，但代价是吞吐与延迟下降，需按业务等级（金融 vs 日志）取舍。

    6.2.重复消费与幂等¶

    可靠投递通常是 At-Least-Once（至少一次） 语义，重试与 Rebalance 会导致重复。消费端幂等是通用解法：

    • 唯一键去重：业务唯一 ID（订单号/消息 ID）+ 数据库唯一约束 / 去重表。
    • 状态机校验：仅在合法状态流转时处理（如"待支付→已支付"，重复请求被拒）。
    • Redis 去重：SETNX msgId 标记已处理，配合 TTL。
    • Exactly-Once：Kafka 提供事务 + 幂等 Producer 实现端到端精确一次，但有性能开销，多数场景用"至少一次 + 幂等"更经济。

    6.3.消息顺序¶

    • 全局顺序：单分区单消费者，牺牲并发，少用。
    • 局部顺序（推荐）：按业务键（如订单 ID）哈希到固定分区，保证同一实体的消息有序，分区间并行。
    • 注意：消费端若用多线程处理同一分区会破坏顺序，需按 key 路由到同一线程。

    6.4.消息积压（Backlog/Lag）¶

    突发或消费端故障会导致大量积压，应对：

    1. 扩容消费者：增加消费者实例（不超过分区数），临时加分区提升并行度。
    2. 提升单条处理效率：批量拉取、批量写库、异步化、缩短处理逻辑。
    3. 降级旁路：紧急时先将堆积消息快速转存（如写入临时 Topic/库），事后慢慢回放。
    4. 根因排查：消费端是否变慢、下游是否抖动、是否有毒消息阻塞（转 DLQ）。

    七、高级特性¶

    特性 说明 代表实现
    事务消息 保证"本地事务"与"消息发送"的原子性，避免发了消息但业务回滚 RocketMQ 半消息两阶段提交、Kafka 事务
    延迟/定时消息 消息延迟一段时间或到指定时间才可被消费 RocketMQ 原生延迟级别、Pulsar 定时投递、RabbitMQ 死信+TTL
    死信队列（DLQ） 多次消费失败的消息转入专门队列，避免阻塞正常消费并便于排查 RocketMQ %DLQ%、RabbitMQ DLX、Kafka 需自建
    消息回溯 按 Offset/时间戳重置消费位点，重新消费历史消息 Kafka seek、RocketMQ 按时间回溯
    优先级队列 高优先级消息优先被消费 RabbitMQ priority 队列

    八、消息一致性模式¶

    在分布式事务中，MQ 常作为最终一致性的关键一环（与《三高设计》第十章、《微服务与分布式》第六章呼应）：

    • Outbox 模式：业务数据与"待发消息"写入同一本地事务的 outbox 表，再由独立进程/CDC 投递到 MQ，解决"业务提交了但消息没发出"的不一致。
    • CDC（变更数据捕获）：基于数据库 binlog（如 Debezium）捕获变更，投递到 Kafka，下游订阅，无侵入。
    • 事务消息：RocketMQ 半消息机制，先发"半消息"→执行本地事务→提交/回滚消息，是 Outbox 的中间件原生替代。
    方案 优点 缺点
    Outbox 不依赖 MQ 事务能力、通用 需额外表与投递进程
    CDC 业务零侵入 依赖 binlog、有延迟、运维成本
    事务消息 中间件原生、链路简单 仅 RocketMQ 等少数支持，绑定特定 MQ

    九、架构实践模式¶

    • 削峰填谷：网关/服务收到突发请求后写入 MQ，后端按固定速率消费，保护数据库与下游（秒杀场景标配）。
    • 异步解耦：主流程只发事件（如"订单已创建"），发短信、加积分、推荐更新等由各订阅方异步完成，主链路 RT 大幅下降。
    • 事件驱动架构（EDA）：以"事件"为系统集成的一等公民，服务间通过事件流协作；配合 Schema Registry（Avro/Protobuf）管理事件契约的向后兼容。
    • 流处理入口：MQ（尤其 Kafka/Pulsar）作为实时数仓与流计算（Flink/Spark Streaming）的统一数据总线，下游物化到 Lakehouse（Iceberg/Hudi/Delta）。

    十、运维与可观测性¶

    • 核心指标：
    • Lag（消费积压）：最关键的健康指标，持续增长说明消费跟不上生产。
    • 生产/消费 TPS、端到端延迟、Broker 磁盘/网络水位、副本同步状态（ISR）。
    • 告警：基于 Lag 阈值、消费停滞（Offset 不前进）、DLQ 消息突增、Broker 节点掉线。
    • 容量规划：按峰值 TPS × 消息大小估算磁盘与带宽；分区数 ≥ 目标消费并行度；保留期（retention）权衡回溯能力与存储成本。
    • 工具：Kafka 用 Kafka-UI / Burrow（Lag 监控）/ Cruise Control（均衡）；RocketMQ Dashboard；Prometheus + Grafana 统一采集。

def on_delivery(err, msg):

p.produce("orders", key="order-1001", value=b'{"id":1001}', callback=on_delivery)

from confluent_kafka import Consumer

c = Consumer({
    "bootstrap.servers": "localhost:9092",
    "group.id": "order-consumers",
    "auto.offset.reset": "earliest",
    "enable.auto.commit": False,   # 关闭自动提交
})
c.subscribe(["orders"])

while True:
    msg = c.poll(1.0)
    if msg is None or msg.error():
        continue
    handle(msg.value())   # 1. 先处理（需保证幂等）
    c.commit(msg)         # 2. 处理成功后再提交位点

import pika

conn = pika.BlockingConnection(pika.ConnectionParameters("localhost"))
ch = conn.channel()
ch.queue_declare(queue="tasks", durable=True)
ch.basic_qos(prefetch_count=1)   # 一次只取一条，处理完再取，避免忙闲不均

    process(body)                              # 处理（需幂等）
    ch.basic_ack(delivery_tag=method.delivery_tag)  # 成功后手动 ACK

ch.basic_consume(queue="tasks", on_message_callback=callback)
ch.start_consuming()

    11.3.Kafka（Go，segmentio/kafka-go）¶

    go get github.com/segmentio/kafka-go

    package main

import (
    "context"
    "log"

    "github.com/segmentio/kafka-go"
)

func produce() {
    w := &kafka.Writer{
        Addr:         kafka.TCP("localhost:9092"),
        Topic:        "orders",
        Balancer:     &kafka.Hash{},          // 按 key 哈希分区，保证局部顺序
        RequiredAcks: kafka.RequireAll,        // acks=all，保证不丢
    }
    defer w.Close()

    err := w.WriteMessages(context.Background(), kafka.Message{
        Key:   []byte("order-1001"),
        Value: []byte(`{"id":1001}`),
    })
    if err != nil {
        log.Fatalf("写入失败，需重试: %v", err)
    }
}

    func consume() {
    r := kafka.NewReader(kafka.ReaderConfig{
        Brokers:  []string{"localhost:9092"},
        Topic:    "orders",
        GroupID:  "order-consumers",
        MinBytes: 1, MaxBytes: 10e6,
    })
    defer r.Close()

    for {
        // FetchMessage 不自动提交位点
        m, err := r.FetchMessage(context.Background())
        if err != nil {
            break
        }
        handle(m.Value)              // 1. 先处理（需幂等）
        r.CommitMessages(context.Background(), m)  // 2. 处理成功后再提交
    }
}

msg.set_body('{"id":1001}')
ret = producer.send_sync(msg)   # 同步发送
print(f"发送状态: {ret.status}, msgId: {ret.msg_id}")
producer.shutdown()

    # 消费者：集群模式 + 手动确认（CONSUME_SUCCESS 才推进进度）
from rocketmq.client import PushConsumer, ConsumeStatus

def callback(msg):
    try:
        handle(msg.body)                 # 处理（需幂等）
        return ConsumeStatus.CONSUME_SUCCESS
    except Exception:
        return ConsumeStatus.RECONSUME_LATER   # 失败稍后重试，超次进 %DLQ%

consumer = PushConsumer("order-consumer-group")
consumer.set_namesrv_addr("localhost:9876")
consumer.subscribe("orders", callback, expression="create")  # 按 Tag 过滤
consumer.start()

    RocketMQ 特色：send_sync 返回结果保证可靠；失败返回 RECONSUME_LATER 自动进入重试队列，超过重试次数转入死信队列 %DLQ%；事务消息用 send_message_in_transaction 配合本地事务回查。

client = pulsar.Client("pulsar://localhost:6650")

consumer = client.subscribe(
    "persistent://public/default/orders",
    subscription_name="order-sub",
    consumer_type=pulsar.ConsumerType.Shared,   # 也可用 Exclusive / Failover / KeyShared
)

while True:
    msg = consumer.receive()
    try:
        handle(msg.data())          # 处理（需幂等）
        consumer.acknowledge(msg)   # 成功后确认
    except Exception:
        consumer.negative_acknowledge(msg)  # 失败 nack，稍后重投

    以上示例均体现了"不丢"的关键三要素：生产端确认、Broker 持久化、消费端先处理后提交。生产环境还需叠加幂等去重以应对"至少一次"带来的重复。

async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let conn = Connection::connect(
        "amqp://guest:guest@localhost:5672/%2f",
        ConnectionProperties::default(),
    ).await?;

    let channel = conn.create_channel().await?;

    let _queue = channel.queue_declare(
        "order_queue",
        QueueDeclareOptions {
            durable: true,
            ..QueueDeclareOptions::default()
        },
        FieldTable::default(),
    ).await?;

    // 发送消息
    let order = Order {
        order_id: "ORD-2024-001".to_string(),
        user_id: "USER-1001".to_string(),
        amount: 99.99,
    };

    let payload = serde_json::to_vec(&order)?;

    channel.basic_publish(
        "",
        "order_queue",
        BasicPublishOptions::default(),
        &payload,
        BasicProperties::default()
            .with_delivery_mode(2) // 消息持久化
            .with_content_type("application/json".into()),
    ).await?.await?;

    println!("订单已发送: {}", order.order_id);

    conn.close().await?;
    Ok(())

    // 消费者（手动确认）
use lapin::{
    options::*,
    types::FieldTable,
    Connection, ConnectionProperties,
};
use serde::{Deserialize, Serialize};
use tokio;

#[derive(Serialize, Deserialize)]
struct Order {
    order_id: String,
    user_id: String,
    amount: f64,
}

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let conn = Connection::connect(
        "amqp://guest:guest@localhost:5672/%2f",
        ConnectionProperties::default(),
    ).await?;

    let channel = conn.create_channel().await?;

    // 公平分发
    channel.basic_qos(1, BasicQosOptions::default()).await?;

    // 消费消息
    let mut consumer = channel.basic_consume(
        "order_queue",
        "order_consumer",
        BasicConsumeOptions {
            no_ack: false,
            ..BasicConsumeOptions::default()
        },
        FieldTable::default(),
    ).await?;

    println!("等待消息...");

    while let Some(delivery) = consumer.next().await {
        let delivery = delivery?;

        let order: Order = serde_json::from_slice(&delivery.data)?;
        println!("处理订单: {}", order.order_id);

        // 确认消费
        channel.basic_ack(
            delivery.delivery_tag,
            BasicAckOptions::default(),
        ).await?;

        println!("订单处理完成: {}", order.order_id);
    }

    Ok(())
}

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let mut producer = DefaultMQProducer::new(

    // 消费者
use rocketmq_rust::client::consumer::default_mq_push_consumer::DefaultMQPushConsumer;
use rocketmq_rust::common::message::MessageExt;
use rocketmq_rust::client::consumer::consumer_push_listener::ConsumeConcurrentlyStatus;
use tokio;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let mut consumer = DefaultMQPushConsumer::new(

        None,

            ConsumeConcurrentlyStatus::ConsumeSuccessfully
        })
    );

    consumer.start().await?;
