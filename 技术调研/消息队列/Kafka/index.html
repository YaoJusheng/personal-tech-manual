    一、Kafka 简介¶

    1.1 什么是 Kafka？¶

    Kafka 是一个开源的分布式事件流平台，由 LinkedIn 开发，现为 Apache 顶级项目。它具有高吞吐、低延迟、高可用、可扩展的特性，广泛应用于日志收集、流处理、数据管道等场景。

    1.2 核心特点¶

    • 极高吞吐：百万级消息/秒，支持水平扩展
    • 持久化存储：消息持久化到磁盘，支持回溯消费
    • 分布式架构：分区、副本、消费组实现高可用
    • 流处理生态：Kafka Streams、Connect、Schema Registry
    • Exactly-Once 语义：事务 + 幂等 Producer 支持精确一次

    1.3 架构组件¶

    flowchart TB
    subgraph Producer Cluster
        P1[Producer 1]
        P2[Producer 2]
    end

    subgraph Kafka Cluster
        B1[Broker 1]
        B2[Broker 2]
        B3[Broker 3]
    end

    subgraph Consumer Group
        C1[Consumer 1]
        C2[Consumer 2]
    end

    P1 --> B1
    P2 --> B2
    B1 --> C1
    B2 --> C2

    核心组件：

    组件 说明
    Producer 消息生产者，发送消息到指定 Topic
    Broker 消息代理服务器，存储和转发消息
    Topic 消息主题，逻辑分类容器
    Partition 分区，Topic 的物理分片，并行消费基础
    Consumer 消息消费者，从 Partition 读取消息
    Consumer Group 消费者组，组内成员分摊分区
    Offset 偏移量，消费进度标记
    ZooKeeper/KRaft 元数据管理（新版本支持 KRaft 去 ZK）

    二、核心概念详解¶

    2.1 Topic 与 Partition¶

    flowchart TB
    subgraph Topic: orders
        P0[Partition 0]
        P1[Partition 1]
        P2[Partition 2]
    end

    P0 --> L0[Leader]
    P0 --> F0[Follower]

    P1 --> L1[Leader]
    P1 --> F1[Follower]

    P2 --> L2[Leader]
    P2 --> F2[Follower]
    • Topic：消息的逻辑分类，类似于数据库的表
    • Partition：Topic 的物理分片，每个 Partition 是一个有序日志
    • Replica：分区副本，Leader 处理读写，Follower 同步数据
    • ISR（In-Sync Replicas）：保持同步的副本集合

    2.2 Offset 与消费位点¶

    flowchart LR
    subgraph Partition 0
        M0[msg-0]
        M1[msg-1]
        M2[msg-2]
        M3[msg-3]
        M4[msg-4]
    end

    C[Consumer] -->|当前位点=3| M3
    • Offset：消息在 Partition 内的位置序号，从 0 开始
    • Consumer Offset：消费者当前消费到的 Offset 位置
    • Offset 保存：消费者定期提交 Offset 到 __consumer_offsets Topic

    2.3 消费组与 Rebalance¶

    flowchart TB
    subgraph Consumer Group: order-consumers
        C1[Consumer 1]
        C2[Consumer 2]
    end

    subgraph Topic: orders
        P0[Partition 0] --> C1
        P1[Partition 1] --> C2
        P2[Partition 2] --> C1
    end
    • 消费组：多个消费者组成一个消费组，共享消费进度
    • 分区分配：每个 Partition 只能被消费组内一个消费者消费
    • Rebalance：消费者加入/退出时重新分配 Partition
    • 协作再均衡：Kafka 2.4+ 支持增量再均衡，减少影响

    2.4 副本与高可用¶

    flowchart LR
    P[Producer] --> L[Leader]
    L --> F1[Follower 1]
    L --> F2[Follower 2]
    F1 --> L
    F2 --> L
    C[Consumer] --> L
    • Leader/Follower：Leader 处理读写，Follower 同步数据
    • ISR：保持同步的副本集合，Leader 从 ISR 中选举
    • acks 配置：
    • acks=0：不等待确认，可能丢失
    • acks=1：Leader 写入成功即返回
    • acks=all：所有 ISR 写入成功才返回（推荐）

    三、工作原理¶

    3.1 消息写入流程¶

    sequenceDiagram
    participant P as Producer
    participant B as Broker
    participant ZK as ZooKeeper/KRaft

    P->>B: 1. 获取 Leader Partition
    B-->>P: 返回 Leader 信息
    P->>B: 2. 发送消息
    B->>B: 3. 追加到日志文件
    B->>B: 4. 同步到 Follower
    B-->>P: 5. 返回确认（acks=all）
    P->>B: 6. 提交 Offset

    3.2 消息消费流程¶

    sequenceDiagram
    participant C as Consumer
    participant B as Broker

    C->>B: 1. Fetch（拉取消息）
    B-->>C: 2. 返回消息批次
    C->>C: 3. 处理消息
    C->>B: 4. 提交 Offset

    3.3 高性能原理¶

    技术 说明
    顺序写磁盘 Append-Only 日志，磁盘顺序写接近内存速度
    Page Cache 利用操作系统页缓存，减少磁盘 IO
    零拷贝 sendfile() 系统调用，减少数据拷贝次数
    批量处理 生产者批量发送，消费者批量拉取
    压缩 支持 gzip/snappy/lz4/zstd 压缩

    四、安装与部署¶

    4.1 Docker 部署¶

    # docker-compose.yml
version: '3'
services:
  zookeeper:
    image: confluentinc/cp-zookeeper:7.5.0
    container_name: zookeeper
    environment:
      ZOOKEEPER_CLIENT_PORT: 2181
    ports:
      - "2181:2181"

  kafka:
    image: confluentinc/cp-kafka:7.5.0
    container_name: kafka
    depends_on:
      - zookeeper
    ports:
      - "9092:9092"
    environment:
      KAFKA_BROKER_ID: 1
      KAFKA_ZOOKEEPER_CONNECT: zookeeper:2181
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://localhost:9092
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
      KAFKA_AUTO_CREATE_TOPICS_ENABLE: "true"

    4.2 K8s 部署¶

    # kafka-statefulset.yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: kafka
  namespace: messaging
spec:
  serviceName: kafka
  replicas: 3
  selector:
    matchLabels:
      app: kafka
  template:
    metadata:
      labels:
        app: kafka
    spec:
      containers:
      - name: kafka
        image: confluentinc/cp-kafka:7.5.0
        ports:
        - containerPort: 9092
        env:
        - name: KAFKA_BROKER_ID
          valueFrom:
            fieldRef:
              fieldPath: metadata.name
        - name: KAFKA_ZOOKEEPER_CONNECT
          value: "zookeeper:2181"
        - name: KAFKA_ADVERTISED_LISTENERS
          value: "PLAINTEXT://kafka-$(KAFKA_BROKER_ID).kafka.messaging.svc.cluster.local:9092"
        - name: KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR
          value: "3"
        resources:
          limits:
            cpu: 2000m
            memory: 2Gi
          requests:
            cpu: 1000m
            memory: 1Gi
        volumeMounts:
        - name: kafka-data
          mountPath: /var/lib/kafka/data
  volumeClaimTemplates:
  - metadata:
      name: kafka-data
    spec:
      accessModes: [ "ReadWriteOnce" ]
      storageClassName: "standard"
      resources:
        requests:
          storage: 50Gi

    4.3 KRaft 模式（无需 ZooKeeper）¶

    # kafka-kraft-config.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: kafka-kraft-config
data:
  server.properties: |
    node.id=1
    process.roles=broker,controller
    controller.quorum.voters=1@kafka-0.kafka:9093,2@kafka-1.kafka:9093,3@kafka-2.kafka:9093
    listeners=PLAINTEXT://:9092,CONTROLLER://:9093
    advertised.listeners=PLAINTEXT://kafka-0.kafka:9092
    log.dirs=/var/lib/kafka/data
    num.partitions=3
    default.replication.factor=3

    事务消息¶

    package main

import (
    "context"
    "encoding/json"
    "fmt"
    "log"

    "github.com/segmentio/kafka-go"
    "github.com/segmentio/kafka-go/protocol/transactional"
)

func main() {
    // 创建事务生产者
    writer := &kafka.Writer{
        Addr: kafka.TCP("localhost:9092"),
        Topic: "output-topic",
        Balancer: &kafka.Hash{},
        RequiredAcks: kafka.RequireAll,
        Transactional: &kafka.TransactionalConfig{
            TransactionalID: "my-transactional-id",
        },
    }
    defer writer.Close()

    // 初始化事务
    err := writer.InitTransactions(context.Background())
    if err != nil {
        log.Fatal("初始化事务失败:", err)
    }

    // 创建事务消费者
    reader := kafka.NewReader(kafka.ReaderConfig{
        Brokers: []string{"localhost:9092"},
        Topic:   "input-topic",
        GroupID: "tx-group",
        IsolationLevel: kafka.ReadCommitted,
    })
    defer reader.Close()

    for {
        msg, err := reader.FetchMessage(context.Background())
        if err != nil {
            continue
        }

        // 开始事务
        err = writer.BeginTransaction()
        if err != nil {
            continue
        }

        // 处理消息
        result := process(msg.Value)

        // 发送结果
        err = writer.WriteMessages(context.Background(),
            kafka.Message{
                Key:   msg.Key,
                Value: result,
            },
        )

        if err != nil {
            writer.AbortTransaction(context.Background())
            continue
        }

        // 提交事务
        err = writer.CommitTransaction(context.Background())
        if err != nil {
            log.Printf("提交失败: %v", err)
        }
    }
}

    八、最佳实践¶

    8.1 分区设计¶

    原则 说明
    分区数 >= 消费者数 保证并行度，避免消费者空闲
    分区数 = 目标吞吐 / 单分区吞吐 根据容量规划确定
    Key 设计 保证同一实体的消息路由到同一分区
    避免分区热点 均匀分配 Key，避免单分区压力过大

    8.2 副本配置¶

    配置 建议值 说明
    replication.factor >= 3 副本数，生产环境建议 3
    min.insync.replicas >= 2 最小同步副本数
    acks all 生产者确认级别

    8.3 消费者优化¶

    优化点 建议
    批量消费 合并多条消息处理
    异步处理 IO 操作异步化
    幂等设计 避免重复消费影响
    监控 Lag 及时发现消费能力不足

    8.4 性能调优¶

    参数 建议值 说明
    linger.ms 10-100 批量发送延迟
    batch.size 16384-65536 批量大小（字节）
    compression.type lz4/zstd 压缩算法
    buffer.memory 32MB-64MB 生产者缓冲区

    8.5 监控指标¶

    指标 说明 告警阈值
    Consumer Lag 消费积压 > 10000
    Under Replicated Partitions 副本不足分区 > 0
    ISR Shrink Rate ISR 缩减速率 > 0
    Request Latency 请求延迟 > 100ms
    Disk Usage 磁盘使用率 > 80%

    九、常见问题¶

    9.1 消息积压¶

    现象：Consumer Lag 持续增长

    解决方案：

    1. 增加消费者实例（不超过分区数）
    2. 临时增加分区数
    3. 优化消费逻辑，提升处理速度
    4. 检查下游依赖是否正常

    9.2 消息丢失¶

    现象：消息未被消费

    解决方案：

    1. 生产者设置 acks=all
    2. 消费者关闭自动提交，手动确认
    3. 检查 Broker 副本配置
    4. 监控 ISR 状态

    9.3 消息重复¶

    现象：同一条消息被消费多次

    解决方案：

    1. 消费端幂等处理（唯一键/状态机）
    2. 使用 Exactly-Once 语义（事务 + 幂等）
    3. 减少 Rebalance 频率

    9.4 消息乱序¶

    现象：消息顺序与发送顺序不一致

    解决方案：

    1. 同一实体使用相同 Key
    2. 确保分区数固定，避免频繁调整
    3. 消费端单线程处理同一分区

    9.5 分区再均衡¶

    现象：消费组频繁再均衡

    解决方案：

    1. 设置合理的 session.timeout.ms
    2. 使用粘性分配策略
    3. 启用协作再均衡（Cooperative Rebalance）
    4. 避免长时间处理消息

    十、与 RabbitMQ 对比¶

    维度 Kafka RabbitMQ
    架构模型 日志模型（消费不删除） 队列模型（取走即删除）
    吞吐量 百万级/s 万级/s
    延迟 毫秒级 微秒级
    消息回溯 支持（按 offset/时间） 不支持
    堆积能力 极强（无影响） 弱（影响性能）
    路由能力 弱（按 key hash） 强（Exchange 四种类型）
    事务消息 支持 支持（AMQP 事务）
    适用场景 日志、流处理、大数据 业务消息、复杂路由
