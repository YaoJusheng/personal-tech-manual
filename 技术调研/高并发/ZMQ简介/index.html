    一、ZeroMQ 简介¶

    1.1 什么是 ZeroMQ？¶

    ZeroMQ（ØMQ，ZMQ）是一个高性能异步消息库，而不是"带 Broker 的 MQ"。它提供套接字抽象之上的多种消息传递模式，可在进程内（inproc）、同机（ipc）与跨机器（tcp/pgm/epgm）通信，具备极低延迟和高吞吐的特点。

    常用于高并发系统的微服务通信、实时分发、管线化处理、代理/网关等场景。

    1.2 核心定位¶

    轻量消息传输内核，去中心化，无内置 Broker（可自行实现代理/中继）。

    特性 ZeroMQ 传统 MQ（Kafka/RabbitMQ）
    架构 无 Broker，去中心化 有 Broker，中心化
    持久化 无内置持久化 内置持久化
    延迟 微秒级 毫秒级
    吞吐 极高 高
    可靠性 端到端保证 Broker 保证
    适用场景 进程间通信、低延迟 业务消息、事件驱动

    1.3 核心优势¶

    • 零拷贝：消息传递无需复制，直接传输
    • 批量处理：支持消息合并，减少系统调用
    • 异步 I/O：非阻塞事件驱动，高并发
    • 跨语言：支持 C/C++、Python、Go、Rust、Java 等
    • 跨平台：Linux、Windows、macOS、嵌入式
    • 可嵌入：可作为库嵌入到应用程序中

    1.4 与其他技术的对比¶

    与 Kafka/RabbitMQ 不同，ZMQ 不负责持久化和队列存储；与 gRPC 相比，ZMQ 更偏消息模式与多播、低时延分发。

    维度 ZeroMQ Kafka RabbitMQ gRPC
    定位 消息内核 分布式事件流 消息中间件 RPC 框架
    架构 无 Broker 有 Broker 有 Broker 客户端-服务端
    延迟 微秒级 毫秒级 微秒-毫秒 毫秒级
    吞吐 极高 百万级/s 万级/s 高
    持久化 无 有 有 无
    消息模式 多种（PUB/SUB等） 发布订阅 路由队列 请求响应
    适用场景 进程间通信、实时 日志、流处理 业务消息 微服务 RPC

    二、核心概念与原理¶

    2.1 架构模型¶

    flowchart TB
    subgraph Application Layer
        APP1[应用 A]
        APP2[应用 B]
        APP3[应用 C]
    end

    subgraph ZMQ Layer
        S1[Socket A]
        S2[Socket B]
        S3[Socket C]
    end

    subgraph Transport Layer
        IPC[IPC]
        TCP[TCP]
        INPROC[InProc]
    end

    APP1 --> S1
    APP2 --> S2
    APP3 --> S3
    S1 --> IPC
    S1 --> TCP
    S2 --> TCP
    S3 --> INPROC

    2.2 套接字类型（Socket Types）¶

    类型 模式 特点 适用场景
    REQ 请求-应答 同步，严格一问一答 简单 RPC
    REP 请求-应答 同步，等待请求并回复 简单服务
    PUB 发布-订阅 广播，单向 事件通知、状态广播
    SUB 发布-订阅 订阅过滤，接收 监听事件
    PUSH 管线 单向发送，负载均衡 任务分发
    PULL 管线 单向接收，负载均衡 任务消费
    ROUTER 高级路由 可感知对端身份，异步 代理、网关
    DEALER 高级路由 异步 REQ，并发请求 异步 RPC
    PAIR 一对一 简单双向通信 线程间通信
    STREAM TCP 流 桥接非 ZMQ 客户端 协议转换

    2.3 传输方式（Transports）¶

    传输 说明 延迟 适用场景
    inproc 进程内线程间 极低 同进程多线程
    ipc 同机进程间 低 同机多进程
    tcp 跨机器网络 中 跨机器通信
    pgm/epgm 可靠多播 低 一对多广播
    ws WebSocket 中 Web 客户端

    2.4 消息队列与背压¶

    • 发送队列（SNDHWM）：控制发送缓冲区大小，超出后阻塞或丢弃
    • 接收队列（RCVHWM）：控制接收缓冲区大小，超出后阻塞或丢弃
    • LINGER：关闭 socket 时等待未发送消息的时间
    • 背压机制：队列满时自动产生背压，保护下游

    2.5 连接管理¶

    • 自动重连：连接断开后自动重连，指数退避
    • 心跳：ZMQ_HEARTBEAT_* 配置心跳检测
    • 握手：mechanism 配置认证机制（CURVE/NULL）

    2.6 可靠性与有序性¶

    • 同一对端连接上消息有序（FIFO）；多对端不保证全局顺序。
    • 无内置持久化，如需可靠落盘需配合持久化层或上层协议（如写入日志/数据库）。
    • 通过重连、重试、幂等等端策略提升端到端可靠性。

    三、消息模式详解¶

    3.1 REQ/REP（请求-应答）¶

    sequenceDiagram
    participant C as Client (REQ)
    participant S as Server (REP)

    C->>S: 1. 请求
    S->>C: 2. 响应
    Note over C,S: 严格一问一答

    特点：

    • 严格握手：发送请求后必须等待响应
    • 单线程：一个 REQ socket 同时只能处理一个请求
    • 易阻塞：慢服务会阻塞客户端

    代码示例见第六节

    3.2 PUB/SUB（发布-订阅）¶

    flowchart LR
    P[Publisher] -->|topic: price.AAPL| S1[Subscriber 1]
    P -->|topic: price.GOOGL| S2[Subscriber 2]
    P -->|topic: price.MSFT| S3[Subscriber 3]

    特点：

    • 广播：一条消息可被多个订阅者接收
    • 过滤：订阅者按主题前缀过滤
    • 解耦：发布者不知道订阅者

    注意事项：

    • 订阅延迟：先 SUBSCRIBE 后 connect，避免初始丢包
    • 消息丢失：订阅者断开期间的消息会丢失

    3.3 PUSH/PULL（管线）¶

    flowchart LR
    VENT[Ventilator] -->|分发| W1[Worker 1]
    VENT -->|分发| W2[Worker 2]
    VENT -->|分发| W3[Worker 3]
    W1 -->|结果| SINK[Sink]
    W2 -->|结果| SINK
    W3 -->|结果| SINK

    特点：

    • 负载均衡：多 PULL 自动平均分配任务
    • 管线化：适合流水线处理
    • 背压：队列满时自动阻塞

    3.4 ROUTER/DEALER（高级路由）¶

    flowchart TB
    C1[Client 1] --> R[ROUTER]
    C2[Client 2] --> R
    C3[Client 3] --> R
    R --> D[DEALER]
    D --> W1[Worker 1]
    D --> W2[Worker 2]

    特点：

    • 身份感知：ROUTER 可获取对端 identity
    • 异步路由：支持并发请求
    • 高级拓扑：构建代理、网关、负载均衡器

    3.5 PAIR（一对一）¶

    • 简单双向通信
    • 适合线程间通信
    • 不支持多对端

    import zmq
import threading

def router_proxy():
    """ROUTER/DEALER 代理"""
    ctx = zmq.Context()

    # 前端（ROUTER）
    frontend = ctx.socket(zmq.ROUTER)
    frontend.bind("tcp://*:5555")

    # 后端（DEALER）
    backend = ctx.socket(zmq.DEALER)
    backend.bind("tcp://*:5556")

    # 使用内置代理
    zmq.proxy(frontend, backend)

# 或者手动实现
def router_manual():
    ctx = zmq.Context()
    router = ctx.socket(zmq.ROUTER)
    dealer = ctx.socket(zmq.DEALER)

    router.bind("tcp://*:5555")
    dealer.bind("tcp://*:5556")

    # 转发消息
    poller = zmq.Poller()
    poller.register(router, zmq.POLLIN)
    poller.register(dealer, zmq.POLLIN)

    while True:
        socks = dict(poller.poll())

        if router in socks:
            msg = router.recv_multipart()
            dealer.send_multipart(msg)

        if dealer in socks:
            msg = dealer.recv_multipart()
            router.send_multipart(msg)

    package main

import (
    "encoding/json"

    ID  string `json:"id"`
    Op  string `json:"op"`

    Result string `json:"result"`

    socket, _ := zmq.NewSocket(zmq.REP)
    defer socket.Close()

    socket.Bind("tcp://*:5555")

    for {

        json.Unmarshal(msg, &req)
        fmt.Printf("收到请求: %+v\n", req)

        // 处理业务逻辑
        time.Sleep(100 * time.Millisecond)

        // 发送响应
        resp := Response{Status: "ok", Result: "processed"}
        data, _ := json.Marshal(resp)
        socket.SendBytes(data, 0)
    }
}

    defer socket.Close()

    socket.SetRcvtimeo(5000)
    socket.SetSndtimeo(5000)

        data, _ := json.Marshal(req)

        socket.SendBytes(data, 0)

        msg, err := socket.RecvBytes(0)
        if err != nil {
            fmt.Println("请求超时")
            continue
        }

        var resp Response
        json.Unmarshal(msg, &resp)
        fmt.Printf("收到响应: %+v\n", resp)

    }
}

fn client() -> Result<(), zmq::Error> {

    socket.set_rcvtimeo(Some(5000))?;
    socket.set_sndtimeo(Some(5000))?;

    for i in 0..10 {

            id: format!("req-{}", i),
            op: "ping".to_string(),

        socket.send_string(serde_json::to_string(&req).unwrap(), 0)?;

        match socket.recv_string(0) {
            Ok(Ok(msg)) => {
                let resp: Response = serde_json::from_str(&msg).unwrap();

            }
            _ => println!("请求超时"),
        }
    }

}

    ROUTER/DEALER 代理¶

    use zmq::{Context, Socket, SocketType, Poller, PollFlags};

fn router_proxy() -> Result<(), zmq::Error> {
    let ctx = Context::new();

    let frontend = ctx.socket(SocketType::ROUTER)?;
    let backend = ctx.socket(SocketType::DEALER)?;

    frontend.bind("tcp://*:5555")?;
    backend.bind("tcp://*:5556")?;

    let mut poller = Poller::new()?;
    poller.add(&frontend, PollFlags::POLLIN)?;
    poller.add(&backend, PollFlags::POLLIN)?;

    loop {
        let events = poller.poll(-1)?;

        for &(socket, _) in events.iter() {
            if socket == frontend.getsockopt_zmq_fd()? {
                let msgs = frontend.recv_multipart(0)?;
                backend.send_multipart(&msgs, 0)?;
            } else if socket == backend.getsockopt_zmq_fd()? {
                let msgs = backend.recv_multipart(0)?;
                frontend.send_multipart(&msgs, 0)?;
            }
        }
    }
}

    七、最佳实践¶

    7.1 模式选择¶

    场景 推荐模式 原因
    简单 RPC REQ/REP 简单直接
    事件广播 PUB/SUB 广播、解耦
    任务分发 PUSH/PULL 负载均衡、背压
    复杂路由 ROUTER/DEALER 灵活、异步
    线程间通信 PAIR 简单高效

    7.2 性能优化¶

    优化点 建议
    消息大小 合并小消息，减少系统调用
    传输选择 同机用 inproc/ipc，跨机用 tcp
    队列水位 根据吞吐调整 SNDHWM/RCVHWM
    批量发送 使用 multipart 消息
    异步处理 使用非阻塞 I/O + poll
    线程模型 多核拆分为多个 socket

    7.3 可靠性保障¶

    策略 说明
    心跳检测 配置 ZMQ_HEARTBEAT_* 探测故障
    重连机制 利用 ZMQ 自动重连
    幂等处理 消费端实现幂等
    超时设置 合理设置 RCVTIMEO/SNDTIMEO
    重试策略 实现指数退避重试

    7.4 安全最佳实践¶

    措施 说明
    CURVE 加密 启用 Curve25519 端到端加密
    密钥管理 妥善管理服务端白名单和客户端公钥
    心跳检测 及时发现断开连接
    消息大小限制 设置 ZMQ_MAXMSGSIZE 防滥用
    访问控制 限制连接来源

    八、监控与可观测性¶

    8.1 监控指标¶

    指标 说明 告警阈值
    队列深度 发送/接收队列长度 > HWM * 0.8
    重连次数 连接断开重连次数 持续增长
    处理时延 消息处理延迟 > 业务阈值
    水位触发 队列满触发次数 > 0
    连接状态 socket 连接状态 断开

    九、常见问题与解决方案¶

    9.1 REQ/REP 死锁¶

    现象：客户端发送请求后无响应

    原因：REQ socket 严格一问一答，违反序列会导致死锁

    解决方案：

    • 使用 DEALER/ROUTER 替代
    • 确保 REQ 客户端单线程使用

    9.2 PUB/SUB 订阅延迟丢消息¶

    现象：订阅者启动时丢失部分消息

    原因：先 connect 后 subscribe，订阅建立前的消息已发送

    解决方案：

    • 先 subscribe 后 connect
    • 启动后等待一段时间再接收

    9.3 消息丢失¶

    现象：消息未被接收

    原因：

    • PUB/SUB 订阅者断开
    • 队列满（HWM）
    • 未持久化

    解决方案：

    • 检查 HWM 设置
    • 重要数据配合持久化层
    • 实现端到端确认机制

    9.4 性能瓶颈¶

    现象：吞吐下降、延迟增加

    原因：

    • 消息过小，系统调用频繁
    • 队列水位设置不合理
    • 网络延迟

    解决方案：

    • 合并小消息
    • 调整 HWM
    • 优化网络配置

    10.2 吞吐量测试¶

    # 吞吐量测试示例
import zmq
import time

def throughput_test():
    ctx = zmq.Context()

    # PUB-SUB 模式
    pub = ctx.socket(zmq.PUB)
    sub = ctx.socket(zmq.SUB)

    pub.bind("tcp://*:5555")
    sub.connect("tcp://localhost:5555")
    sub.setsockopt(zmq.SUBSCRIBE, b"")

    time.sleep(0.1)  # 等待连接建立

    message = b"x" * 1024  # 1KB 消息
    count = 100000

    # 预热
    for _ in range(1000):
        pub.send(message)
    sub.recv()

    # 测试
    start = time.time()
    for _ in range(count):
        pub.send(message)
    for _ in range(count):
        sub.recv()
    elapsed = time.time() - start

    throughput = count / elapsed
    print(f"吞吐量: {throughput:.0f} msg/s")
    print(f"带宽: {throughput * 1024 / 1024 / 1024:.2f} GB/s")

    13.1 ZMQ + Redis¶

    import zmq
import redis

# 使用 Redis 做消息持久化
r = redis.Redis()

def pub_with_persistence(pub_socket, topic, message):
    """发布消息并持久化到 Redis"""
    # 持久化
    r.lpush(f"zmq:{topic}", message)

    # 发布
    pub_socket.send_multipart([topic.encode(), message])

def replay_messages(sub_socket, topic):
    """重放 Redis 中的历史消息"""
    messages = r.lrange(f"zmq:{topic}", 0, -1)
    for msg in messages:
        sub_socket.send(msg)

    13.2 ZMQ + Kafka¶

    import zmq
from kafka import KafkaProducer, KafkaConsumer

# ZMQ 接收消息，转发到 Kafka
def zmq_to_kafka_bridge():
    ctx = zmq.Context()
    sub = ctx.socket(zmq.SUB)
    sub.connect("tcp://zmq-source:5555")
    sub.setsockopt(zmq.SUBSCRIBE, b"")

    producer = KafkaProducer(bootstrap_servers='kafka:9092')

    while True:
        msg = sub.recv()
        producer.send('zmq-topic', msg)

# Kafka 消费消息，转发到 ZMQ
def kafka_to_zmq_bridge():
    ctx = zmq.Context()
    pub = ctx.socket(zmq.PUB)
    pub.bind("tcp://*:5556")

    consumer = KafkaConsumer('kafka-topic', bootstrap_servers='kafka:9092')

    for msg in consumer:
        pub.send(msg.value)

    13.3 ZMQ + OpenTelemetry¶

    import zmq
from opentelemetry import trace

tracer = trace.get_tracer("zmq-service")

def traced_send(socket, message, topic="default"):
    """带追踪的发送"""
    with tracer.start_as_current_span("zmq.send") as span:
        span.set_attribute("messaging.system", "zmq")
        span.set_attribute("messaging.destination", topic)
        span.set_attribute("messaging.message.size", len(message))

        socket.send_multipart([topic.encode(), message])

def traced_recv(socket):
    """带追踪的接收"""
    with tracer.start_as_current_span("zmq.recv") as span:
        topic, message = socket.recv_multipart()

        span.set_attribute("messaging.system", "zmq")
        span.set_attribute("messaging.source", topic.decode())
        span.set_attribute("messaging.message.size", len(message))

        return topic, message
