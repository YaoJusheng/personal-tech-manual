    一、高并发¶

    1.1.简介¶

    高并发（High Concurrency）指系统能够同时处理大量请求的能力，通常以 QPS（Queries Per Second，每秒查询率）、TPS（每秒事务数）、并发连接数、响应时间 等指标衡量系统承载能力。

    高并发的核心思路可归纳为两条主线：

    • 垂直扩展（Scale Up）：提升单机能力——更好的硬件、更高效的代码、更优的算法与数据结构。
    • 水平扩展（Scale Out）：通过集群分摊压力——负载均衡、无状态化、分库分表，是高并发的主流方向。

    1.2.核心手段¶

    手段 说明
    负载均衡 nginx / LVS / 网关分发流量。常用算法：轮询、随机、源地址哈希、加权轮询、加权随机、最小连接数、一致性哈希。
    多级缓存 客户端缓存 → CDN → 网关缓存 → 本地缓存（Caffeine）→ 分布式缓存（Redis），层层拦截，减少回源。
    池化技术 线程池、进程池、对象池、内存池、连接池、协程池，复用昂贵资源，避免频繁创建销毁。
    异步化 同步阻塞改异步非阻塞（消息队列削峰、事件驱动），缩短主链路 RT。
    读写分离 / 分库分表 主写从读分摊读压力；按业务/范围/哈希水平拆分，突破单库瓶颈。
    流量漏斗 逐层拦截无效流量：网关限流 → 风控 → 业务校验 → 缓存 → DB，越往后流量越小。
    网关与 WAF API 网关统一鉴权/限流/路由；WAF（Web 应用防火墙）拦截恶意流量。
    并发模型 协程（Goroutine/Async）、Reactor/Proactor 事件驱动、IO 多路复用（epoll），以少量线程支撑海量连接（C10K/C10M）。
    无锁化 CAS、原子操作、ThreadLocal、分段锁，降低锁竞争开销。

    1.3.高并发架构分层¶

    客户端 → CDN（静态资源）→ 负载均衡（Nginx/LVS）→ 网关（限流/鉴权/WAF）
      → 应用集群（无状态、水平扩展）→ 缓存（Redis 多级）→ MQ（削峰）
      → 数据库（读写分离/分库分表）

    高并发与高性能、高可用相辅相成：高并发靠水平扩展 + 削峰 + 缓存承接流量，高性能保证单请求快，高可用保证整体不挂。

    1.4.架构设计示例：秒杀/抢购系统¶

    秒杀是高并发的典型场景：瞬时洪峰、库存有限、超卖零容忍。核心思路是层层过滤流量 + 缓存预扣库存 + MQ 异步落库，让真正打到数据库的请求降到最低。

    flowchart TB
    U[海量用户] --> CDN[CDN 静态资源/活动页]
    CDN --> LB[负载均衡 Nginx/LVS]
    LB --> GW[网关: 限流/黑名单/防刷]
    GW --> APP[秒杀服务集群 无状态]
    APP -->|1.预扣库存 Lua原子操作| R[(Redis 库存)]
    R -->|库存不足| FAIL[快速失败返回]
    R -->|预扣成功| MQ[消息队列 削峰]
    MQ --> ORD[订单服务 匀速消费]
    ORD --> DB[(MySQL 真实下单)]
    ORD --> R2[回补/对账]

    设计要点：

    • 流量层层漏斗：CDN 扛静态页 → 网关限流防刷（按 IP/用户/设备）→ 应用层校验，无效流量越往后越少。
    • Redis 预扣库存：用 Lua 脚本保证"判断 + 扣减"原子性，避免超卖；库存售罄立即快速失败，不再下压数据库。
    • MQ 削峰：预扣成功的请求写入 MQ，订单服务按数据库承受能力匀速消费，把瞬时百万 QPS 平滑成稳定写入。
    • 最终一致：异步落库失败时回补 Redis 库存并告警；通过对账保证库存与订单一致（呼应《消息队列》一致性模式）。
    • 三高对应：流量漏斗 + 削峰（高并发）、Redis 原子操作 + 快速失败（高性能）、集群无状态 + 限流降级（高可用）。

    二、高性能¶

    2.1.简介¶

    高性能（High Performance）关注单次请求的处理速度与单位资源的吞吐能力，核心目标是降低延迟（Latency）、提升吞吐（Throughput）。

    影响因素：

    • 用户网络环境（RTT、带宽、丢包）
    • 请求/响应的数据包大小
    • 业务系统 CPU、内存、磁盘等性能
    • 业务链路的长度（串行调用越多越慢）
    • 下游系统的性能（木桶效应）
    • 算法实现是否高效（时间/空间复杂度）

    2.2.核心优化手段¶

    维度 优化手段
    缓存 本地缓存（Caffeine/Guava）+ 分布式缓存（Redis）多级；热点数据预热；防击穿（互斥锁/逻辑过期）、防穿透（布隆过滤器）、防雪崩（过期时间打散）。
    异步与并行 异步化非核心逻辑；CompletableFuture/协程并行调用多个下游，将串行 RT 降为并行最大值。
    批量处理 批量读写、合并请求（请求合并/Batch）、Pipeline，减少 IO 往返与系统调用。
    零拷贝 sendfile/mmap/DMA 减少内核态与用户态间数据拷贝（Kafka、Netty 广泛使用）。
    池化复用 连接池、线程池、对象池；HTTP Keep-Alive、连接多路复用（HTTP/2、gRPC）。
    计算下推/预计算 把过滤/聚合下推到存储层；离线预计算 + 在线查询，空间换时间。
    数据结构与算法 选用合适的数据结构（跳表、布隆过滤器、LSM-Tree）；降低复杂度。
    IO 优化 日志异步化/批量刷盘避免 IO 瓶颈；顺序写代替随机写；SSD/NVMe。
    JVM/运行时调优 GC 调优（G1/ZGC）、逃逸分析、JIT 预热；Go 的 GOMAXPROCS、内存逃逸控制。

    2.3.性能优化原则¶

    • 先度量后优化：基于 Profiling（火焰图、APM）定位瓶颈，避免凭感觉过早优化。
    • 抓主要矛盾：优先优化 P95/P99 长尾与热点路径，遵循二八定律。
    • 空间换时间 / 时间换空间：按资源约束权衡（缓存、预计算 vs 实时计算）。

    2.4.架构设计示例：多级缓存读架构¶

    读多写少的场景（商品详情、配置、热点内容）追求极致读性能，核心是多级缓存层层拦截 + 读写分离，并防住缓存三大风险。

    flowchart TB
    REQ[读请求] --> L1[本地缓存 Caffeine 进程内]
    L1 -->|命中| RESP[返回]
    L1 -->|未命中| L2[分布式缓存 Redis 集群]
    L2 -->|命中| RESP
    L2 -->|未命中| LOCK{分布式锁/单飞}
    LOCK -->|获得锁| RDB[(MySQL 从库 读)]
    LOCK -->|未获锁| WAIT[等待并重试读缓存]
    RDB --> FILL[回填 Redis + 本地缓存]
    FILL --> RESP
    WDB[(MySQL 主库 写)] -->|binlog 同步| RDB
    WDB -->|更新/删除缓存| L2

    设计要点：

    • 多级缓存：本地缓存（纳秒级、扛热点、降 Redis 压力）→ Redis（毫秒级、容量大、跨实例共享）→ 数据库（兜底）。
    • 读写分离：写走主库，读走从库；缓存未命中时读从库并回填，注意主从延迟带来的短暂不一致。
    • 缓存三防：
    • 穿透（查不存在的 key）：布隆过滤器拦截 + 缓存空值。
    • 击穿（热点 key 失效瞬间被打穿）：分布式锁/单飞（singleflight）只放一个请求回源，或热点 key 逻辑过期不删除。
    • 雪崩（大量 key 同时失效）：过期时间加随机抖动、多级缓存、限流降级兜底。
    • 一致性策略：更新时采用 Cache-Aside + 延迟双删 或基于 binlog（Canal）异步刷新缓存，权衡一致性与复杂度。
    • 三高对应：多级缓存承接读洪峰（高并发）、本地缓存 + 回填降低 RT（高性能）、缓存兜底 + 降级保护数据库（高可用）。

    三、高可用¶

    3.1.简介¶

    高可用（High Availability，HA）指系统在面对故障时仍能持续对外提供服务的能力，通常以可用性（如 99.99%） 衡量，核心是消除单点、快速故障转移、过载保护。

    可用性 年停机时间（约）
    99.9%（3 个 9） 8.76 小时
    99.99%（4 个 9） 52.6 分钟
    99.999%（5 个 9） 5.26 分钟

    3.2.核心手段¶

    手段 说明
    冗余与多活 多云架构、异地多活、异地备份；消除单点故障。
    主备切换 Redis、MySQL 等主备实时同步，主节点不可用时自动切换（如 Sentinel、MHA）。
    无状态化 + 集群 微服务无状态、集群化部署，配合心跳检测快速摘除不可用实例。
    限流 / 熔断 / 降级 过载保护三件套，详见第六章韧性模式。
    超时与重试 合理超时避免线程堆积；重试带退避抖动，配合幂等防止重复副作用。
    隔离 线程池/连接池隔离、舱壁模式，防止局部故障级联放大。

    3.3.Web 安全与过载保护¶

    1. 防御攻击与 XSS、CSRF、SQL 注入等
    2. 主备切换，缩减故障时间
    3. 熔断：依赖故障时快速失败，避免雪崩
    4. 限流：保护系统不被流量打垮
    5. 降级：峰值时关闭非核心功能（如推荐、画像），保住核心链路（下单、支付）

    限流、熔断、降级、隔离、幂等的具体算法与实现见 第六章 稳定性与韧性模式。

    3.4.架构设计示例：异地多活架构¶

    为消除机房级单点、实现就近接入与容灾，大型系统采用单元化 + 异地多活：每个地域是一个可独立提供完整服务的"单元"，通过全局流量调度就近分发，单元间数据双向同步。

    flowchart TB
    USER[全国用户] --> GSLB[GSLB/GeoDNS 全局流量调度]
    GSLB -->|华北用户就近| UA
    GSLB -->|华南用户就近| UB
    subgraph UA[单元A 北京机房]
        AGW[网关] --> AAPP[应用集群] --> ADB[(主库A)]
        AAPP --> AC[(Redis A)]
    end
    subgraph UB[单元B 深圳机房]
        BGW[网关] --> BAPP[应用集群] --> BDB[(主库B)]
        BAPP --> BC[(Redis B)]
    end
    ADB <-->|双向数据同步 DRC/binlog| BDB
    GSLB -.->|某单元故障 流量切换| UB

    设计要点：

    • 单元化（Set 化）：按用户维度（如 user_id 取模）将流量路由到固定单元，单元内闭环完成请求，减少跨机房调用。
    • 流量调度：GSLB/GeoDNS/Anycast 按地理位置与健康状态就近分发；某单元故障时秒级切流到其他单元。
    • 数据同步：单元间通过数据复制组件（如阿里 DRC、Canal、Kafka MirrorMaker）双向同步；跨单元写冲突用"写本单元 + 全局唯一 ID + 冲突解决规则"规避。
    • 多活模式选型：同城双活（低延迟、防机房故障）→ 两地三中心（防城市级灾难）→ 异地多活（极致容灾 + 就近接入），复杂度与成本递增。
    • RPO/RTO：核心库用半同步复制降低 RPO；配合自动故障转移（Sentinel/MHA）与演练缩短 RTO（详见第八章灾备与多活）。
    • 三高对应：多单元分摊流量（高并发）、就近接入降低延迟（高性能）、故障秒级切流 + 异地容灾（高可用）。

    四、容量规划与弹性伸缩¶

    • 容量估算：
    • 业务指标拆解：QPS、峰谷比、请求大小、处理耗时、并发连接数。
    • 资源测算：CPU/内存/网络/磁盘；按照 P95/P99 延迟目标反推并发度。
    • 冗余系数：考虑故障域（机架/机房）与双活/多活，留 30% 以上 buffer。
    • 弹性策略：
    • HPA（CPU/内存/自定义指标）、KEDA（基于队列长度、Kafka lag、Prom 指标）。
    • 预热与冷启动：镜像分层、JIT 预热、连接池预热、缓存预热。
    • 高峰前定时扩容、低谷定时缩容；引入速率限制避免抖动。

    五、可靠性工程（SLO/SLI/错误预算）¶

    • SLI：可用性、成功率、请求延迟（P95/P99）、吞吐、队列滞后、错误率。
    • SLO：按业务分层设定（核心下单 99.95%，次要模块 99.9%）。
    • 错误预算：将 SLO 之外的可容忍失败时间用于发布节奏、压测与演练；超支则收紧变更。

    六、稳定性与韧性模式¶

    • 限流：令牌桶、漏桶、滑动窗口；按租户/接口/下游维度限速。
    • 熔断：失败率与延迟阈值，半开探活（如 Resilience4j、Envoy/Istio）。
    • 降级：读缓存/静态内容、关闭非核心功能、返回近似值（如推荐、画像）。
    • 隔离：线程池/连接池隔离、优先级队列、超时与重试（带抖动），避免级联放大。
    • 幂等：请求幂等键、数据库唯一约束、去重表；结合消息队列至少一次语义。

    七、故障演练与混沌工程¶

    • 类型：节点宕机、网络分区、磁盘满、CPU 争用、慢下游、消息堆积。
    • 工具：Chaos Mesh、Litmus、Toxiproxy、tc/netem、Fault Injection Policy（Istio）。
    • 流程：演练计划→小流量→监控验证→自动化回滚→复盘改进。

    八、灾备与多活¶

    • RPO/RTO：
    • RPO（可接受数据丢失窗）与 RTO（恢复时间目标）驱动同步/异步复制策略。
    • 多活模式：
    • 同城双活、两地三中心、跨地域多活；流量调度（GeoDNS/GSLB/Anycast）。
    • 数据复制：数据库同步（半同步/双写）、异步复制 + 冲突解决；消息系统跨地域复制（Pulsar/Kafka Mirror）。
    • 切换：灰度与演练；故障域隔离、就近接入、读写分离。

    九、观测性与故障排查¶

    • 指标：RED（Rate/Errors/Duration）、USE（Utilization/Saturation/Errors）、自定义业务指标。
    • 日志：结构化、采样、隐私脱敏；集中检索与关联（trace_id/span_id）。
    • 追踪：OpenTelemetry 统一埋点，端到端调用链；采样策略与热点追踪。
    • 告警：基于 SLO 与异常检测（突增/突降）；分级告警与告警抑制。

    十、数据与缓存层实践¶

    • 数据库：读写分离、分库分表、热点键拆分、乐观锁/悲观锁策略。
    • 缓存：旁路缓存、写穿/写回、统一失效策略、热点保护（互斥锁/单飞）。
    • 队列/流：削峰填谷、回溯、DLQ；Outbox + CDC 保障一致性。

    十一、发布与回滚¶

    • 金丝雀/蓝绿发布：按流量/租户/区域灰度；实时监控回滚阈值。
    • 配置管理：集中配置、动态生效、放号开关。
    • 自动化：GitOps/Argo CD、Progressive Delivery（Argo Rollouts/Flagger）。
