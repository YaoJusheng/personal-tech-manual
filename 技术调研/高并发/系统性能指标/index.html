    文档定位：本文档系统性梳理性能指标分类、定义、计算公式、告警阈值和最佳实践，适用于系统设计、容量规划、性能调优和故障排查。

    一、性能指标体系概览¶

    1.1 指标分层模型¶

    flowchart TB
    subgraph 业务层
        B1[营收/订单量]
        B2[用户活跃度]
        B3[转化率]
    end

    subgraph 应用层
        A1[QPS/TPS]
        A2[延迟/RT]
        A3[并发数]
        A4[错误率]
    end

    subgraph 中间件层
        M1[数据库]
        M2[缓存]
        M3[消息队列]
        M4[RPC框架]
    end

    subgraph 基础设施层
        I1[CPU]
        I2[内存]
        I3[磁盘]
        I4[网络]
    end

    业务层 --> 应用层
    应用层 --> 中间件层
    中间件层 --> 基础设施层

    1.2 指标分类总览¶

    分类层 核心指标 关注点
    业务层 订单量、营收、转化率 业务健康度
    应用层 QPS、TPS、延迟、并发、错误率 服务处理能力
    中间件层 连接数、缓冲池、队列深度 组件健康度
    基础设施层 CPU、内存、磁盘、网络 资源使用率

    二、基础设施层指标¶

    黄金法则：高吞吐量 + 低资源利用率 = 高效系统；高吞吐量 + 高资源利用率 = 接近极限，需扩容。

    2.1 CPU 指标¶

    指标 定义 计算公式 健康阈值 瓶颈信号
    CPU 使用率 CPU 忙碌时间占比 (总时间 - 空闲时间) / 总时间 × 100% 平均 60%-70%，峰值 < 85% 持续 > 90% 说明计算密集型瓶颈
    用户态 CPU 用户进程占用 user% + nice% < 70% 应用代码热点
    系统态 CPU 内核占用 sys% + irq% + softirq% < 30% 系统调用频繁
    I/O 等待 等待 I/O 的时间占比 iowait% < 20% I/O Wait 高说明存储瓶颈
    负载均值 运行队列平均长度 load average (1/5/15 min) < CPU核数 × 1.5 > CPU核数 × 1.5 严重过载
    上下文切换 进程/线程切换次数 cs（context switch） < 10万次/秒 频繁切换导致性能下降
    中断次数 硬件/软件中断 in（硬中断）+ si（软中断） 异常增长 中断风暴
    GPU 利用率 计算单元 + 显存占用 GPU 使用率 训练 > 80%，推理视场景 利用率低说明调度或代码效率差

    CPU 使用率细分：

    # Linux 查看 CPU 使用率
top -bn1 | head -5
# 或
mpstat -P ALL 1 5

# 关键字段解读
# %user    - 用户空间占用
# %sys     - 内核空间占用
# %iowait  - I/O 等待
# %idle    - 空闲

    负载均值解读：

    负载/CPU核数 状态 说明
    < 0.7 正常 资源充足
    0.7 - 1.0 警告 资源紧张
    1.0 - 2.0 危险 需要扩容
    > 2.0 严重 可能已排队

    2.2 内存指标¶

    指标 定义 计算公式 健康阈值 瓶颈信号
    内存使用率 已用内存占比 (总内存 - 空闲内存) / 总内存 × 100% < 80% 接近 100% 触发 OOM 或频繁 Swap
    应用内存 进程实际使用 RSS (Resident Set Size) 根据应用设定 RSS 持续增长可能存在泄漏
    虚拟内存 进程申请的内存 VSS (Virtual Set Size) 参考值 VSS >> RSS 可能有问题
    Swap 使用率 Swap 使用占比 Used Swap / Total Swap × 100% < 10% 频繁 Swap 导致性能下降
    页缓存命中率 命中页缓存的比例 (1 - 磁盘读次数/内存读次数) × 100% < 90% 命中率低增加磁盘 I/O
    内存泄漏 内存持续增长 监控 RSS 趋势 稳定 持续增长需排查

    内存状态解读：

    # Linux 查看内存使用
free -h
# 或
cat /proc/meminfo

# 关键指标
# total   - 总内存
# used    - 已使用（不含 buffers/cache）
# free    - 完全空闲
# buff/cache - 缓冲/缓存（可回收）
# available - 实际可用（free + 可回收）

    内存告警策略：

    情况 处理建议
    available < 20% 检查内存泄漏，考虑扩容
    Swap 使用 > 10% 检查内存配置，优化应用
    OOM Killer 触发 检查进程内存，调整限制

    2.3 磁盘指标¶

    指标 定义 计算公式 健康阈值 瓶颈信号
    磁盘使用率 磁盘空间占用 已用空间 / 总空间 × 100% SSD < 70%，HDD < 50% 空间不足影响写入
    磁盘 IOPS 每秒 I/O 操作次数 读次数 + 写次数 根据磁盘规格 接近上限说明存储瓶颈
    磁盘吞吐 每秒读写数据量 读速率 + 写速率 根据磁盘规格 带宽饱和导致排队
    磁盘利用率 磁盘忙碌时间占比 磁盘繁忙时间 / 总时间 × 100% < 70% 接近 100% 严重过载
    平均 I/O 时间 单次 I/O 耗时 I/O 等待时间 < 10ms 响应变慢
    队列长度 等待 I/O 的请求数 avgqu-sz < 2 > 2 说明存储成为瓶颈

    磁盘性能基准：

    磁盘类型 IOPS 吞吐量 适用场景
    HDD (7200RPM) 100-200 100-200 MB/s 冷数据存储
    SATA SSD 10K-50K 500 MB/s 通用场景
    NVMe SSD 100K-1M 3-7 GB/s 高性能场景
    云盘 (gp3) 3K-16K 125-1000 MB/s 云环境 
    # Linux 查看磁盘 I/O
iostat -xz 1 5

# 关键字段
# %util    - 磁盘利用率
# r/s, w/s - 每秒读写次数
# rkB/s, wkB/s - 每秒读写速率
# await    - 平均 I/O 等待时间
# avgqu-sz - 平均队列长度

    2.4 网络指标¶

    指标 定义 计算公式 健康阈值 瓶颈信号
    带宽使用率 带宽占用比例 当前流量 / 带宽 × 100% < 70% 接近饱和导致排队延迟激增
    网络吞吐 每秒收发数据量 收包速率 + 发包速率 根据网卡规格 达到网卡上限
    TCP 连接数 活跃连接数量 ESTABLISHED 连接数 < 10万 连接数过多消耗资源
    TCP 重传率 重传包占比 重传包数 / 总包数 × 100% < 1% 网络质量问题
    丢包率 丢包比例 丢包数 / 总包数 × 100% < 0.1% 网络拥塞或故障
    延迟 网络往返时间 RTT (Round-Trip Time) < 100ms 延迟升高影响响应时间

    网络性能基准：

    网络类型 带宽 延迟 适用场景
    千兆内网 1 Gbps < 1ms 同机房通信
    万兆内网 10 Gbps < 1ms 高性能集群
    公网 10-100 Mbps 10-100ms 外部访问
    专线 100 Mbps-10 Gbps 1-10ms 跨地域通信

    三、应用层指标¶

    3.1 吞吐量指标¶

    指标 全称 定义 适用场景
    QPS Queries Per Second 每秒查询/请求数 读多写少场景
    TPS Transactions Per Second 每秒事务数 数据库事务
    RPS Requests Per Second 每秒请求数 HTTP 服务
    OPS Operations Per Second 每秒操作数 通用操作
    EPS Events Per Second 每秒事件数 日志/消息处理

    计算公式：

    QPS = 总请求数 / 总时间（秒）
TPS = 事务数 / 总时间（秒）
吞吐量 = 单次请求数据量 × QPS

    典型场景 QPS 参考：

    系统类型 单机 QPS 集群 QPS 说明
    Web 服务 1K-10K 10K-100K 简单 API
    电商系统 500-2K 10K-100K 复杂业务
    游戏服务器 1K-5K 10K-50K 实时交互
    数据分析 100-1K 1K-10K 计算密集

    3.2 延迟指标¶

    核心观点：平均延迟（Avg）具有欺骗性，尾延迟才是用户体验的杀手。

    指标 定义 计算方式 告警阈值
    平均延迟 所有请求的平均耗时 总耗时 / 请求数 业务决定（参考值）
    P50 延迟 50% 请求的耗时 中位数 典型用户体验
    P90 延迟 90% 请求的耗时 90 分位数 业务决定
    P95 延迟 95% 请求的耗时 95 分位数 长尾请求质量
    P99 延迟 99% 请求的耗时 99 分位数 业务决定
    P999 延迟 99.9% 请求的耗时 99.9 分位数 金融交易等严苛场景
    最大延迟 最慢请求的耗时 MAX(所有请求) 业务决定
    抖动（Jitter） 延迟的波动程度 标准差 / 方差 波动大说明系统不稳定（如 GC、锁竞争）

    尾延迟分析：

    示例：平均延迟 10ms 很美，但如果 P99 是 2s
意味着每 100 个用户就有 1 个遭遇严重卡顿

    延迟分位数解读：

    # 计算延迟分位数
import numpy as np

def calculate_percentiles(latencies):
    """计算延迟分位数"""
    return {
        'P50': np.percentile(latencies, 50),
        'P90': np.percentile(latencies, 90),
        'P95': np.percentile(latencies, 95),
        'P99': np.percentile(latencies, 99),
        'P999': np.percentile(latencies, 99.9),
        'Max': max(latencies),
        'Avg': np.mean(latencies),
    }

    延迟告警策略：

    场景 P99 阈值 处理建议
    内部 API < 100ms 优化慢查询
    外部 API < 500ms 检查网络/下游
    金融交易 < 1000ms 审查业务逻辑
    实时系统 < 10ms 优化链路

    3.3 并发指标¶

    指标 定义 适用场景
    并发用户数 同时在线的用户数 用户维度
    并发连接数 同时活跃的连接数 连接维度
    并发请求数 同时处理的请求数 请求维度
    并发线程数 同时运行的线程数 线程维度
    并发事务数 同时执行的事务数 数据库维度

    并发数计算：

    并发数 = QPS × 平均响应时间（秒）

例如：QPS = 1000，平均响应时间 = 100ms
并发数 = 1000 × 0.1 = 100

    并发容量规划：

    资源 计算方式 参考值
    Web 服务器 QPS / 单连接 QPS Nginx: 1万+
    应用服务器 QPS × 响应时间 / 线程池大小 根据线程模型
    数据库连接 QPS × 查询时间 / 连接池大小 MySQL: 100-500
    Redis 连接 QPS / 单连接 QPS Redis: 10万+

    3.4 错误率指标¶

    核心观点：性能再好，出错就归零。

    指标 定义 计算公式 健康阈值
    错误率 错误请求占比 错误请求数 / 总请求数 × 100% < 0.1%（优秀），< 1%（可接受）
    HTTP 错误率 HTTP 错误响应占比 HTTP 错误数 / 总请求数 × 100% > 1%
    5xx 错误率 服务器错误占比 5xx 数 / 总请求数 × 100% < 0.01%
    4xx 错误率 客户端错误占比 4xx 数 / 总请求数 × 100% > 5% 需关注
    超时率 超时请求占比 超时请求数 / 总请求数 × 100% < 0.1%
    异常率 异常抛出占比 异常数 / 总请求数 × 100% < 0.01%
    可用性（Uptime） 正常运行时间占比 正常运行时间 / 总时间 × 100% 99.9%（年停机 8.7h）
    MTBF 平均故障间隔时间 总运行时间 / 故障次数 越长越稳定
    MTTR 平均修复时间 总故障时间 / 故障次数 越短弹性越好

    错误分类处理：

    # 错误分类示例
class ErrorClassifier:
    def classify(self, error):
        if isinstance(error, TimeoutError):
            return {'type': 'timeout', 'retry': True}
        elif isinstance(error, ConnectionError):
            return {'type': 'connection', 'retry': True}
        elif isinstance(error, ValidationError):
            return {'type': 'validation', 'retry': False}
        elif isinstance(error, BusinessError):
            return {'type': 'business', 'retry': False}
        else:
            return {'type': 'unknown', 'retry': False}

    命中率 = 命中次数 / (命中次数 + 未命中次数) × 100%

    < 90% 差 优化缓存策略

    核心观点：现代高性能系统严重依赖缓存，缓存效率直接决定性能天花板。

    指标 定义 健康阈值 优化方向
    缓存命中率 命中次数 ÷ 总请求 > 95% 优秀 每降低 1% 可能意味着数据库压力翻倍
    L1/L2/L3 缓存命中率 CPU 缓存命中 根据应用特性 低说明数据局部性差，需优化数据结构和访问模式
    CDN 命中率 边缘节点命中比例 > 90% 低说明回源带宽浪费
    连接池复用率 复用连接 ÷ 新建连接 > 90% 低说明连接开销大，可能引发端口耗尽

    缓存优化策略：

    缓存层 优化方向
    CPU 缓存 优化数据结构对齐、减少缓存行失效
    应用缓存 多级缓存、热点数据缓存、缓存预热
    CDN 缓存 合理设置 TTL、预热热点资源
    数据库缓存 缓冲池大小、查询缓存

    十三、一句话总结各指标的核心作用¶

    • 吞吐量：系统能扛多少活？
    • 延迟：干一个活要多快？
    • 并发：能同时给多少人干活？
    • 资源利用率：干活时累不累？
    • 尾延迟：最倒霉的用户体验如何？
    • 错误率：干的活有多少是白干？
    • 饱和度：排队的人有多少？
    • 效率：花多少钱干多少活？

    生产环境建议：不要孤立看单个指标。一个健康的系统需要 "高吞吐 + 低延迟 + 低错误率 + 低饱和度 + 合理的资源利用率" 同时满足。如果必须牺牲一个，通常先牺牲延迟（异步化），但绝不能牺牲错误率。

    十四、容量规划¶

    14.1 容量评估公式¶

    所需机器数 = 峰值 QPS / 单机 QPS × 安全系数(1.5-2)

所需内存 = 预估并发数 × 单请求内存占用 × 安全系数

所需磁盘 = 日数据量 × 保留天数 × 压缩比

所需带宽 = 峰值 QPS × 平均请求大小 × 2（双向）

    14.2 容量规划表¶

    资源 评估方法 规划建议
    CPU 基准测试 + 2倍余量 峰值不超过 70%
    内存 应用内存 × 1.5 预留 20% 给 OS
    磁盘 日增量 × 保留天数 预留 30% 空间
    网络 峰值流量 × 2 带宽利用率 < 70%
    连接数 QPS × 响应时间 连接池 80% 使用率

    14.3 扩容策略¶

    策略 说明 适用场景
    垂直扩容 升级单机配置 简单、快速
    水平扩容 增加机器数量 复杂、可扩展
    自动扩容 根据指标自动调整 云环境
    预扩容 提前扩容应对峰值 大促活动
