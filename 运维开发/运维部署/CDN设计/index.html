    一、CDN在系统入口层的定位¶

    CDN（Content Delivery Network，内容分发网络）是互联网系统入口层的第一道流量承接层。它通过全球或全国边缘节点缓存静态资源、热点页面和部分可缓存接口，把用户请求就近分发到边缘节点，减少公网链路延迟、降低源站带宽和应用集群压力。

    在高并发系统中，入口层推荐链路如下：

    用户浏览器 / App
    ↓ DNS / HTTPDNS / GSLB
CDN 边缘节点（缓存、HTTPS、HTTP/2/3、WAF、限速、Bot 防护）
    ↓ 回源链路（专线 / 公网 HTTPS / 多源站）
源站入口层（SLB / LVS / Nginx / API Gateway）
    ↓
应用服务 → Redis / MQ / DB

    1.1.核心目标¶

    目标 说明 典型指标
    降低延迟 用户就近访问边缘节点，减少跨地域 RTT 首包时间 TTFB、P95/P99 延迟
    减少回源 静态资源、活动页、热点数据在边缘命中 CDN 命中率、回源 QPS、回源带宽
    抗流量洪峰 秒杀、活动、热点新闻等突发流量先由边缘承接 边缘 QPS、源站 QPS 削减比例
    入口安全 在最外层拦截 DDoS、CC、爬虫、异常 User-Agent WAF 拦截数、限流数、Bot 分数
    提升可用性 源站异常时返回过期缓存、静态降级页或切换源站 可用性、错误率、回源失败率

    1.2.CDN适合缓存什么¶

    内容类型 是否推荐上 CDN TTL 建议 说明
    JS / CSS / 图片 / 字体 强烈推荐 7 天 - 1 年 文件名带 hash，可设置长缓存和 immutable
    首页 / 活动页 HTML 推荐 10 秒 - 10 分钟 适合秒杀预热页、静态化页面
    商品详情公共信息 推荐 10 秒 - 5 分钟 库存、价格等强实时字段不要长缓存
    秒杀资格页 / 倒计时页 推荐 1 秒 - 60 秒 可用边缘短缓存吸收刷新流量
    登录态接口 / 下单接口 不推荐缓存 no-store 必须回源，配合边缘限流和风控
    SSE / WebSocket / 长轮询 不缓存 no-cache 需要透传或绕过 CDN 缓存

    原则：CDN 缓存公共、可复用、可容忍短暂不一致的内容；涉及用户身份、订单、支付、库存扣减等强一致链路必须回源。

    二、入口层CDN总体架构设计¶

    2.1.分层架构¶

    flowchart TB
    U[用户 Browser/App] --> DNS[权威 DNS / GSLB / HTTPDNS]
    DNS --> CDN[CDN 边缘节点]
    CDN -->|命中缓存| RESP[直接返回]
    CDN -->|未命中/动态请求| WAF[边缘 WAF / Bot / Rate Limit]
    WAF --> ORIGIN[回源 SLB / Nginx]
    ORIGIN --> GW[API Gateway]
    GW --> APP[应用集群]
    APP --> CACHE[(Redis / 本地缓存)]
    APP --> MQ[MQ 削峰]
    APP --> DB[(DB)]
    CDN -.源站故障.-> STALE[返回 stale 缓存 / 降级页]

    入口层 CDN 不只是静态资源加速，还应承担以下职责：

    1. 流量调度：通过 DNS、Anycast、GSLB 将用户调度到就近、健康、低负载节点。
    2. 协议优化：终止 HTTPS，开启 HTTP/2、HTTP/3、TLS 1.3、OCSP Stapling、Brotli/Gzip。
    3. 缓存加速：按路径、状态码、请求头、查询参数设置缓存策略。
    4. 安全防护：WAF、DDoS 防护、CC 防护、Bot 管理、IP 黑白名单、地域封禁。
    5. 源站保护：回源限速、连接复用、源站隐藏、回源鉴权、请求头规范化。
    6. 可观测性：提供边缘日志、命中率、状态码、回源耗时、缓存刷新审计。

    2.2.域名与资源规划¶

    建议把静态资源、页面、API 和管理后台拆分到不同域名，便于配置不同缓存和安全策略。

    域名 用途 CDN 策略 源站
    static.example.com JS、CSS、图片、字体 长 TTL、文件 hash、开启压缩 OSS/S3/对象存储
    www.example.com 首页、频道页、活动页 HTML 短 TTL、静态化、stale 兜底 Nginx/SSR 服务
    api.example.com 普通 API 默认不缓存、边缘限流、WAF API Gateway
    flash.example.com 秒杀活动入口 页面短缓存、资格页短缓存、下单接口绕缓存 秒杀网关
    admin.example.com 后台管理 不缓存、IP 白名单、强认证 管理后台

    2.3.DNS接入设计¶

    1. 在 CDN 控制台添加加速域名，如 static.example.com、flash.example.com。
    2. 配置源站：对象存储域名、SLB 公网域名或 Nginx 回源域名。
    3. CDN 生成 CNAME，例如 static.example.com.cdn-provider.net。
    4. 到权威 DNS 添加记录：
    static.example.com  CNAME  static.example.com.cdn-provider.net
flash.example.com   CNAME  flash.example.com.cdn-provider.net
    1. 降低切换期 DNS TTL，建议上线前设置为 60s - 300s；稳定后可调整到 600s - 1800s。
    2. 大型系统建议启用多 CDN 调度：DNS/GSLB 根据地域、运营商、健康状态返回不同 CDN 厂商 CNAME。

    2.4.回源设计¶

    回源设计决定 CDN 未命中时源站是否能稳定承接流量。

    设计项 推荐方案
    回源协议 HTTPS 回源，开启 TLS 1.2/1.3，避免明文传输
    回源 Host 显式指定源站 Host，避免多域名源站路由错误
    源站隐藏 源站安全组只允许 CDN 回源 IP 段访问
    多源站 主备源站或按权重回源，健康检查异常自动摘除
    回源连接 开启 Keep-Alive，减少 TCP/TLS 握手
    回源超时 连接 2s - 5s，读写 5s - 30s，按接口类型区分
    回源重试 只对幂等 GET/HEAD 开启，POST 下单接口禁止自动重试
    回源鉴权 CDN 添加签名请求头，源站校验 X-Origin-Auth

    源站 Nginx 只信任 CDN 回源 IP，并恢复真实客户端 IP：

    # /etc/nginx/conf.d/real-ip.conf
# 将示例 IP 段替换为 CDN 厂商公布的回源 IP 段，并定期自动同步。
set_real_ip_from 203.0.113.0/24;
set_real_ip_from 198.51.100.0/24;
real_ip_header X-Forwarded-For;
real_ip_recursive on;

server {
    listen 443 ssl http2;
    server_name flash-origin.example.com;

    location / {
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_pass http://flash_gateway;
    }
}

    三、缓存策略设计¶

    3.1.Cache-Control原则¶

    浏览器缓存和 CDN 共享缓存要分开设计。常用响应头：

    # 静态资源：文件名带 hash，浏览器和 CDN 都长缓存
Cache-Control: public, max-age=31536000, s-maxage=31536000, immutable

# 活动页 HTML：浏览器短缓存，CDN 共享缓存更短，便于快速更新
Cache-Control: public, max-age=30, s-maxage=60

# 登录态、订单、支付、下单接口：禁止缓存
Cache-Control: no-store, no-cache, must-revalidate

# 接口数据允许短缓存：仅限公共数据
Cache-Control: public, max-age=5, s-maxage=10

    字段说明：

    • max-age：浏览器本地缓存时间。
    • s-maxage：共享缓存时间，CDN 会优先使用它覆盖 max-age。
    • immutable：文件内容不会变化，适合带 hash 的静态资源。
    • no-store：不允许任何缓存保存响应，适合敏感数据。
    • stale-while-revalidate：允许边缘先返回旧缓存，同时后台刷新。
    • stale-if-error：源站错误时允许返回旧缓存，提升可用性。

    3.2.按路径配置缓存规则¶

    路径 缓存规则 查询参数 说明
    /assets/* 30 天 - 1 年 忽略无关参数 JS/CSS/图片，文件名带 hash
    /uploads/* 7 天 - 30 天 保留 version 用户上传图片，更新时改 URL 或版本号
    /activity/* 30 秒 - 5 分钟 保留活动 ID 活动页静态化，支持预热和快速刷新
    /api/products/* 5 秒 - 60 秒 只保留业务参数 公共商品信息短缓存
    /api/stock/* 0 秒或 1 秒 保留 SKU 库存展示可极短缓存，扣减必须回源
    /api/seckill/order 不缓存 全部保留 下单接口必须回源
    /api/user/* 不缓存 全部保留 登录态接口不缓存

    3.3.状态码缓存策略¶

    建议只缓存成功响应和少量可控错误，不缓存服务端错误。

    状态码 CDN TTL 说明
    200 / 204 / 206 按路径规则 正常内容缓存
    301 / 308 1 天 - 7 天 永久跳转缓存，配置前确认目标无误
    302 / 307 0 秒 - 5 分钟 临时跳转不要长缓存
    404 30 秒 - 5 分钟 防止不存在资源穿透源站
    403 0 秒 - 60 秒 权限类响应谨慎缓存
    429 0 秒 - 10 秒 限流响应不建议长缓存
    500 / 502 / 503 / 504 不缓存 可启用 stale-if-error 返回旧内容

    Cloudflare Cache Rules 示例：

    {
  "rules": [
    {
      "expression": "(http.host eq \"static.example.com\")",
      "description": "static assets long cache",
      "action": "set_cache_settings",
      "action_parameters": {
        "cache": true,
        "edge_ttl": {
          "mode": "override_origin",
          "default": 2592000,
          "status_code_ttl": [
            { "status_code_range": { "to": 299 }, "value": 2592000 },
            { "status_code_range": { "from": 300, "to": 499 }, "value": 300 },
            { "status_code_range": { "from": 500 }, "value": -1 }
          ]
        },
        "browser_ttl": {
          "mode": "override_origin",
          "default": 86400
        }
      }
    }
  ]
}

    3.4.缓存Key设计¶

    缓存 Key 决定同一个资源是否能复用，必须避免“误命中”和“低命中”。

    场景 Key 设计
    静态资源 scheme + host + path，忽略 utm_*、from 等营销参数
    图片裁剪 scheme + host + path + width + height + format
    多语言页面 加入 Accept-Language 或显式 lang 参数
    多端页面 加入 device=pc/mobile，不要直接按完整 User-Agent 分裂
    登录态内容 不缓存；不要把 Cookie 内容直接加入公共缓存 Key
    秒杀活动页 host + path + activity_id + version，发布新版本时修改 version

    错误示例：

    # 完整查询参数作为缓存 Key，导致 utm 参数打散缓存
/activity/flash-sale?id=1001&utm_source=a
/activity/flash-sale?id=1001&utm_source=b

# 正确：只保留业务参数
/activity/flash-sale?id=1001&version=20260609

    3.5.刷新与预热¶

    • 刷新（Purge）：让 CDN 删除旧缓存，下一次访问回源取新内容。
    • 预热（Preload/Prefetch）：提前让 CDN 节点回源拉取资源，避免大促开始时首批用户打到源站。

    推荐策略：

    1. 静态资源使用 hash 文件名，优先“发布新 URL”，少做全量刷新。
    2. HTML、配置 JSON、活动页使用 URL 刷新或目录刷新。
    3. 秒杀前 30 - 60 分钟对活动页、商品图、规则页、静态包进行预热。
    4. 禁止在大促开始前执行全站刷新，避免制造缓存雪崩。
    5. 刷新动作必须审计：记录操作者、资源、时间、原因、影响范围。

    刷新/预热脚本示例：

    #!/usr/bin/env bash
set -euo pipefail

CDN_API="https://cdn-provider.example.com/api/v1/cache"
TOKEN="${CDN_TOKEN:?missing CDN_TOKEN}"

curl -X POST "${CDN_API}/purge" \
  -H "Authorization: Bearer ${TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{
    "urls": [
      "https://flash.example.com/activity/1001/index.html",
      "https://flash.example.com/activity/1001/config.json"
    ]
  }'

curl -X POST "${CDN_API}/preload" \
  -H "Authorization: Bearer ${TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{
    "urls": [
      "https://static.example.com/assets/app.8f3a1c.js",
      "https://static.example.com/assets/app.91cc2b.css",
      "https://static.example.com/images/sku-1001.webp"
    ]
  }'

    四、秒杀系统中的CDN设计¶

    秒杀系统的核心问题是瞬时流量远大于真实库存。例如 100 万用户同时刷新活动页，但库存只有 1 万件。CDN 的价值是把“看页面、加载资源、刷新规则、展示库存”的绝大部分请求挡在边缘，只让“真正有资格、真正提交下单”的少量请求进入后端。

    4.1.秒杀入口链路¶

    sequenceDiagram
    participant U as 用户
    participant CDN as CDN边缘
    participant GW as 秒杀网关
    participant R as Redis
    participant MQ as MQ
    participant DB as DB

    U->>CDN: GET 活动页 / 商品图 / JS
    CDN-->>U: 边缘缓存命中
    U->>CDN: GET /api/seckill/config?activity_id=1001
    CDN-->>U: 短缓存配置和倒计时
    U->>CDN: POST /api/seckill/order
    CDN->>GW: 绕过缓存并执行边缘限流
    GW->>R: Lua 原子预扣库存
    R-->>GW: 成功 / 售罄
    GW->>MQ: 预扣成功写入下单消息
    MQ->>DB: 匀速创建订单

    4.2.秒杀CDN分层策略¶

    阶段 CDN 策略 源站策略
    预热期 T-60min 预热活动页、静态包、商品图、规则页 提前生成静态页和配置 JSON
    倒计时期 T-10min 活动页 30s 短缓存，配置接口 1s - 5s 短缓存 Redis 准备库存、网关扩容
    开抢瞬间 T0 静态资源长缓存，资格页短缓存，下单接口绕缓存并限流 Redis Lua 预扣、MQ 削峰
    售罄后 CDN 缓存售罄页 30s - 60s，减少反复回源 后端快速失败，关闭放量开关
    活动结束 刷新活动状态页，保留静态资源缓存 订单对账、库存回补

    4.3.秒杀可缓存内容¶

    1. 活动页 HTML：静态化生成，包含活动规则、商品展示、倒计时容器，不直接写死实时库存。
    2. 静态资源：JS、CSS、图片、字体、WebP/AVIF 商品图，全部长缓存。
    3. 活动配置 JSON：活动开始时间、结束时间、按钮状态、批次信息，使用 1s - 10s 短缓存。
    4. 售罄状态：售罄后可以短缓存，快速把刷新流量挡在边缘。
    5. 风控挑战页：对异常流量返回边缘挑战页或验证码页。

    不允许 CDN 缓存的内容：

    • 下单接口：POST /api/seckill/order
    • 支付接口：POST /api/pay/*
    • 用户资格强校验：GET /api/seckill/eligibility，除非响应不含用户信息且按 token 分区
    • 用户订单、地址、优惠券、登录态信息

    4.4.秒杀活动页静态化¶

    服务端提前生成活动页：

    <!doctype html>
<html lang="zh-CN">
<head>

  <title>秒杀活动</title>
</head>
<body>
  <main id="app" data-activity-id="1001" data-config-version="20260609"></main>

</html>

    活动配置接口示例：

    {

  "status": "countdown",
  "start_at": "2026-06-09T20:00:00+08:00",
  "end_at": "2026-06-09T20:10:00+08:00",

    4.5.秒杀边缘限流¶

    CDN 层限流应优先保护下单入口：

    维度 建议规则
    单 IP POST /api/seckill/order 每秒 1 - 3 次
    单用户 每个活动每用户只能提交 1 - 3 次，后端强校验
    单设备 结合设备指纹、UA、Cookie，异常设备提高挑战等级
    地域 非服务地域直接拦截或挑战
    Bot 无 JS 能力、异常 UA、请求间隔固定的流量进入验证码或黑名单
    全局 源站错误率升高时自动降低边缘放行 QPS

    Cloudflare WAF / Rate Limit 规则示例：

    表达式：
(http.host eq "flash.example.com") and
(http.request.uri.path eq "/api/seckill/order") and
(http.request.method eq "POST")

动作：
- 同一 IP 10 秒内超过 20 次：Managed Challenge
- 同一 IP 10 秒内超过 50 次：Block 10 分钟
- 源站 5xx 比例超过阈值：切换到更严格限流规则

    Nginx 源站兜底限流示例：

    http {
    limit_req_zone $binary_remote_addr zone=seckill_ip:20m rate=2r/s;
    limit_conn_zone $binary_remote_addr zone=seckill_conn:20m;

    server {
        listen 443 ssl http2;
        server_name flash-origin.example.com;

        location = /api/seckill/order {
            limit_req zone=seckill_ip burst=5 nodelay;
            limit_conn seckill_conn 5;
            proxy_no_cache 1;
            proxy_cache_bypass 1;
            proxy_set_header Cache-Control "no-store";
            proxy_pass http://seckill_gateway;
        }
    }
}

    4.6.秒杀库存展示策略¶

    库存展示不能和扣减库存混为一谈。

    1. 展示库存：可显示“库存紧张 / 即将售罄 / 已售罄”，不要展示精确实时库存。
    2. 库存缓存：展示状态可以 1s - 3s CDN 短缓存，减少用户频繁刷新回源。
    3. 扣减库存：必须在 Redis 使用 Lua 原子扣减或等价强一致机制，禁止 CDN 或前端直接决定。
    4. 售罄开关：Redis 发现库存为 0 后写入活动状态，CDN 缓存售罄状态 30s - 60s。
    5. 回补机制：订单失败、支付超时后回补 Redis，并刷新售罄状态或等待短 TTL 自动恢复。

    4.7.秒杀防缓存击穿¶

    秒杀开始瞬间最容易发生缓存击穿，处理方式：

    • 活动页和静态资源必须提前预热到 CDN。
    • 配置接口使用短 TTL + stale-while-revalidate，边缘刷新期间仍返回旧值。
    • 源站 Nginx 对活动页启用 proxy_cache_lock，同一资源只允许一个请求回源。
    • 后端对热点配置使用本地缓存 + Redis 缓存，避免 CDN 未命中直接打 DB。
    • 禁止同时刷新大量活动 URL；如必须刷新，按地域、目录、批次逐步执行。

    Nginx 代理缓存防击穿示例：

    proxy_cache_path /var/cache/nginx/seckill levels=1:2 keys_zone=SECKILL:100m inactive=10m max_size=5g;

server {
    listen 443 ssl http2;
    server_name flash-origin.example.com;

    location /activity/ {
        proxy_cache SECKILL;
        proxy_cache_key "$scheme$host$request_uri";
        proxy_cache_valid 200 60s;
        proxy_cache_valid 404 30s;
        proxy_cache_use_stale error timeout updating http_500 http_502 http_503 http_504;
        proxy_cache_lock on;
        proxy_cache_lock_timeout 5s;
        add_header X-Origin-Cache $upstream_cache_status always;
        proxy_pass http://activity_page_service;
    }
}

    五、安全设计¶

    5.1.源站保护¶

    1. 隐藏源站 IP：业务域名只暴露 CDN CNAME，源站 IP 不直接解析到公网业务域名。
    2. 安全组限制：源站只允许 CDN 回源 IP、堡垒机和监控节点访问。
    3. 回源鉴权：CDN 回源时添加签名头，源站校验，防止绕过 CDN 直打源站。
    4. 最小开放端口：公网只开放 80/443 或 SLB 入口端口，管理端口仅内网访问。
    5. 日志脱敏：边缘日志和源站日志不得记录完整 token、手机号、身份证等敏感信息。

    回源签名示例：

    # CDN 或边缘函数添加：X-Origin-Auth: HMAC(timestamp + path)
# 源站只接受带合法签名的请求。
map $http_x_origin_auth $origin_auth_valid {
    default 0;
    "expected-signature-placeholder" 1;
}

server {
    if ($origin_auth_valid = 0) {
        return 403;
    }
}

    实际生产不要在 Nginx 写死单个签名，应使用边缘函数、网关插件或 Lua/OpenResty 动态校验 HMAC。

    5.2.WAF与Bot防护¶

    风险 CDN层策略
    SQL 注入 / XSS 开启托管 WAF 规则，观察模式验证后再阻断
    CC 攻击 按路径、IP、ASN、国家、UA 做限速和挑战
    恶意爬虫 Bot 分数、JS Challenge、验证码、黑名单
    撞库 登录接口增加速率限制和失败阈值
    盗刷秒杀 设备指纹、行为校验、Token 预校验、下单接口严格限流
    盗链 Referer / Token 鉴权，图片资源启用防盗链

    5.3.Token与防盗链¶

    适合下载、图片、视频、活动私有资源：

    原始路径：/activity/1001/private-rule.pdf
签名参数：expires=1718000000&token=HMAC(secret, path + expires)
CDN校验：token合法且未过期才允许访问

    Nginx secure_link 示例：

    location /protected/ {
    secure_link $arg_token,$arg_expires;
    secure_link_md5 "$secure_link_expires$uri cdn-secret";

    if ($secure_link = "") { return 403; }
    if ($secure_link = "0") { return 410; }

    proxy_pass http://protected_origin;
}

    六、性能优化设计¶

    6.1.协议优化¶

    • 开启 HTTPS，全站强制 HTTPS，配置 HSTS。
    • 开启 HTTP/2；条件允许时开启 HTTP/3/QUIC，降低弱网和移动端握手开销。
    • 开启 TLS 1.3、会话复用、OCSP Stapling。
    • 静态资源开启 Brotli/Gzip，图片优先 WebP/AVIF。
    • 使用 preconnect、dns-prefetch、preload 优化关键资源加载。

    HTML 示例：

    <link rel="dns-prefetch" href="//static.example.com">
<link rel="preconnect" href="https://static.example.com" crossorigin>
<link rel="preload" href="https://static.example.com/assets/app.8f3a1c.js" as="script">

    6.2.图片与大文件优化¶

    场景 优化方式
    商品图 WebP/AVIF、自适应宽度、质量压缩
    用户头像 对象存储 + CDN，按尺寸生成缩略图
    视频 HLS/DASH 分片，边缘缓存切片
    下载文件 Range 请求、断点续传、下载限速、防盗链
    大促主图 提前预热，多地域检查命中

    图片 URL 示例：

    https://static.example.com/images/sku-1001.webp?x-oss-process=image/resize,w_600/quality,q_80

    6.3.边缘计算¶

    边缘函数适合处理轻量逻辑，不适合处理核心交易。

    适合放到边缘：

    • URL 规范化、去除无关查询参数。
    • A/B 实验分桶并回写 Cookie。
    • 地域跳转、移动端/PC 端路由。
    • 静态降级页返回。
    • 简单 Bot 挑战和请求头清洗。

    不适合放到边缘：

    • 库存扣减、创建订单、支付扣款。
    • 复杂用户权限判断。
    • 强一致事务。
    • 依赖大量内部服务的业务逻辑。

    Cloudflare Workers 自定义缓存 Key 示例：

    export default {
  async fetch(request) {
    const url = new URL(request.url);

    for (const key of [...url.searchParams.keys()]) {
      if (key.startsWith("utm_") || key === "from") {
        url.searchParams.delete(key);
      }
    }

    const cacheKey = new Request(url.toString(), request);
    const cache = caches.default;
    let response = await cache.match(cacheKey);

    if (!response) {
      response = await fetch(request);
      response = new Response(response.body, response);
      response.headers.set("Cache-Control", "public, max-age=30, s-maxage=60");
      await cache.put(cacheKey, response.clone());
    }

    return response;
  }
};

    七、落地实施步骤¶

    7.1.准备阶段¶

    1. 资源盘点：列出域名、路径、源站、静态资源目录、API 清单、是否登录态。
    2. 缓存分级：给每类路径定义 TTL、是否保留查询参数、是否缓存 4xx。
    3. 容量评估：估算峰值 QPS、带宽、对象大小、回源比例和源站最大承载。
    4. 安全基线：确认 WAF、DDoS、Bot、防盗链、源站 IP 限制、证书策略。
    5. 监控基线：定义命中率、回源 QPS、错误率、P95/P99、刷新成功率等指标。

    资源盘点表：

    域名 路径 类型 是否登录态 TTL 查询参数 源站 负责人
    static.example.com /assets/* 静态资源 否 30d 忽略营销参数 OSS 前端
    flash.example.com /activity/* 活动页 否 60s 保留 id/version SSR 活动服务
    flash.example.com /api/seckill/order 下单 是 no-store 全保留 网关 秒杀服务

    7.2.接入阶段¶

    1. 在 CDN 控制台创建域名并配置源站。
    2. 上传或申请 HTTPS 证书，开启 TLS 1.2/1.3、HTTP/2。
    3. 配置缓存规则：静态资源长缓存、HTML 短缓存、API 默认不缓存。
    4. 配置查询参数规则：忽略 utm_*、from，保留业务参数。
    5. 配置 WAF、限流、防盗链和源站 IP 白名单。
    6. 在测试域名验证命中、回源、刷新、预热、安全规则。
    7. 灰度切换 DNS：先小流量或低风险子域名，再全量切换。

    7.3.发布阶段¶

    T-7d  完成资源盘点、容量评估、压测计划
T-3d  CDN测试域名验证缓存、WAF、刷新、预热
T-1d  源站扩容、DNS TTL降到60s、准备回滚CNAME
T-1h  预热活动页、静态资源、配置JSON、商品图
T-10m 开启秒杀限流规则，检查命中率和回源QPS
T0    活动开始，监控边缘QPS、源站QPS、5xx、库存状态
T+10m 售罄页短缓存，降低放行QPS，开始订单对账
T+1h  恢复DNS TTL，复盘刷新、告警、回源峰值

    7.4.回滚方案¶

    故障 回滚动作
    CDN 节点异常 DNS/GSLB 切换到备用 CDN 或源站 SLB
    缓存规则误配 禁用规则并刷新受影响 URL
    WAF 误拦截 规则切观察模式，加入临时白名单
    静态资源 404 回滚前端发布版本或预热上一版本资源
    源站 5xx CDN 返回 stale 缓存或静态降级页，源站扩容排查
    证书异常 回滚证书版本，切换备用证书或备用域名

    八、监控与运维¶

    8.1.核心指标¶

    指标 建议阈值 说明
    CDN 请求 QPS 按业务容量 判断活动峰值和攻击流量
    CDN 命中率 静态资源 > 95%，活动页 > 80% 低命中说明缓存 Key 或 TTL 有问题
    回源 QPS 不超过源站压测容量 70% 超过阈值需要限流或扩容
    回源带宽 不超过链路容量 70% 防止带宽打满
    边缘 4xx 突增告警 可能是 WAF、鉴权、资源缺失
    边缘 5xx > 1% 告警 可能是源站异常或 CDN 回源失败
    TTFB / P95 / P99 按地域分桶 识别运营商或地域节点问题
    刷新成功率 > 99% 发布依赖刷新成功
    预热成功率 > 95% 秒杀前必须检查
    WAF 拦截数 异常突增告警 判断攻击或误杀

    8.2.日志字段¶

    边缘日志建议至少包含：

    request_id, timestamp, client_ip, country, province, isp,
host, path, query, method, status, cache_status,
edge_node, edge_time_ms, origin_status, origin_time_ms,
bytes_sent, referer, user_agent, bot_score, waf_action

    源站日志需要保留 CDN 透传字段：

    log_format cdn_main '$request_id $remote_addr $http_x_forwarded_for '
                    '$host $request_uri $status $body_bytes_sent '
                    '$http_user_agent $http_referer '
                    '$upstream_status $upstream_response_time';

    8.3.告警规则¶

    告警 触发条件 处理人
    命中率下降 5 分钟内下降超过 20% 运维 + 业务
    回源 QPS 过高 超过压测容量 70% 持续 3 分钟 运维
    5xx 升高 边缘或源站 5xx > 1% 持续 2 分钟 运维 + 后端
    WAF 误杀疑似 403/挑战数突增且业务转化下降 安全 + 业务
    刷新失败 发布刷新失败或超时 发布负责人
    证书过期 证书剩余有效期 < 15 天 运维
    秒杀售罄未生效 库存为 0 但下单仍大量进入 秒杀服务

    8.4.日常运维清单¶

    • 每周检查 CDN 命中率 Top 100 URL，优化低命中资源。
    • 每周同步 CDN 回源 IP 段到源站安全组和 Nginx set_real_ip_from。
    • 每月演练 CDN 主备切换和 DNS 回滚。
    • 每月检查证书有效期、TLS 配置和弱加密套件。
    • 大促前执行预热演练、刷新演练、WAF 观察模式验证。
    • 大促后复盘回源峰值、限流命中、误杀、缓存击穿和成本。

    九、故障排查手册¶

    9.1.缓存未命中率高¶

    1. 查看 CDN 日志 cache_status，确认是 MISS、BYPASS 还是 EXPIRED。
    2. 检查响应头是否存在 Cache-Control: no-store/no-cache。
    3. 检查 URL 是否被无关查询参数打散，如 utm_*、timestamp。
    4. 检查是否携带 Cookie 或 Authorization 导致 CDN 默认绕缓存。
    5. 检查缓存规则优先级，确认目标路径命中正确规则。
    6. 对热点 URL 执行预热，并观察命中率恢复。

    9.2.用户访问旧内容¶

    1. 确认发布是否使用文件 hash；若未使用 hash，需要刷新旧 URL。
    2. 检查浏览器 max-age 是否过长；浏览器本地缓存不一定受 CDN 刷新影响。
    3. 检查 CDN 是否存在多级缓存或区域节点尚未刷新完成。
    4. 检查 HTML 是否引用旧静态资源 URL。
    5. 通过 curl -I 查看 Age、Cache-Control、ETag、Last-Modified。
    curl -I "https://flash.example.com/activity/1001/index.html"

    9.3.源站被打满¶

    1. 判断是缓存失效、缓存刷新、攻击流量还是动态接口自然增长。
    2. 立即提高可缓存页面 TTL，开启 stale-if-error 或静态降级页。
    3. 对下单、登录、查询接口开启更严格边缘限流。
    4. 检查是否刚执行全量刷新，必要时暂停刷新任务。
    5. 扩容源站入口层 Nginx/API Gateway 和应用实例。
    6. 活动场景可临时关闭非核心接口，如推荐、排行榜、评论。

    9.4.WAF误拦截¶

    1. 从边缘日志定位 waf_rule_id、路径、请求样本。
    2. 对业务关键路径先切观察模式，不要直接关闭全局 WAF。
    3. 增加精确白名单：路径 + 方法 + 参数形态 + 可信来源。
    4. 回放样本验证规则不会放过明显攻击。
    5. 记录误杀原因并更新上线前规则验证用例。

    9.5.秒杀下单异常¶

    1. 确认 CDN 对 POST /api/seckill/order 没有缓存，响应头应为 no-store。
    2. 检查边缘限流是否过严导致正常用户被挑战或阻断。
    3. 检查源站是否收到真实 IP，避免所有请求被识别为 CDN 节点 IP。
    4. 检查 Redis 预扣库存 Lua、MQ 积压和订单服务消费速率。
    5. 售罄后确认 CDN 是否缓存售罄状态，避免继续放大回源。

    十、成本与容量规划¶

    10.1.容量估算¶

    CDN边缘QPS = 用户数 × 平均刷新频率
回源QPS = CDN边缘QPS × (1 - 命中率) + 动态接口QPS
回源带宽 = 回源QPS × 平均对象大小
源站安全容量 = 压测最大容量 × 0.7

    示例：

    100万用户同时访问活动页，平均每人10秒刷新1次：
边缘QPS = 1,000,000 / 10 = 100,000 QPS
活动页命中率 = 95%
活动页回源QPS = 100,000 × 5% = 5,000 QPS
若命中率下降到80%，回源QPS = 20,000 QPS，源站压力增加4倍。

    10.2.成本优化¶

    • 静态资源压缩和图片格式优化，减少下行流量费用。
    • 提高命中率，减少回源带宽和源站扩容成本。
    • 对大文件下载设置限速、防盗链和地域策略。
    • 对日志进行采样或冷热分层存储，避免日志费用失控。
    • 多 CDN 按地域和成本调度，高峰使用备用厂商兜底。

    十一、最佳实践清单¶

    11.1.上线前检查¶

    • [ ] 域名 CNAME 已指向 CDN，DNS TTL 已按计划调整。
    • [ ] HTTPS 证书有效，TLS 1.2/1.3、HTTP/2 已开启。
    • [ ] 静态资源文件名带 hash，响应头为长缓存。
    • [ ] HTML、配置 JSON、公共接口 TTL 已配置。
    • [ ] 登录态、订单、支付、下单接口明确 no-store。
    • [ ] 查询参数规则已去除 utm_*、from 等无关参数。
    • [ ] 源站安全组只允许 CDN 回源 IP。
    • [ ] WAF、Bot、防盗链、限流规则已在观察模式验证。
    • [ ] 刷新和预热脚本可执行，有审计记录。
    • [ ] 监控面板和告警已配置。

    11.2.秒杀前检查¶

    • [ ] 活动页、静态包、商品图、规则页已预热。
    • [ ] 活动配置接口短缓存生效，server_time 校准准确。
    • [ ] 下单接口绕过 CDN 缓存，边缘限流生效。
    • [ ] Redis 库存已加载，Lua 预扣脚本已压测。
    • [ ] MQ 消费速率与数据库容量匹配。
    • [ ] 售罄状态可快速写入并短缓存。
    • [ ] 源站扩容完成，入口层连接池和超时已检查。
    • [ ] 降级页、备用 CDN、DNS 回滚方案已演练。

    11.3.常见反模式¶

    反模式 风险 正确做法
    全站默认缓存 登录态数据泄漏 只缓存明确路径，敏感接口 no-store
    静态资源不带 hash 用户拿到旧版本 文件名 hash + 长 TTL
    大促前全量刷新 缓存雪崩、源站打满 发布新 URL + 分批刷新 + 预热
    完整查询参数进 Key 命中率极低 只保留业务参数
    下单接口开启重试 重复下单风险 POST 不自动重试，后端幂等
    源站公网裸露 绕过 CDN 攻击 安全组限制 CDN IP + 回源鉴权
    只看平均延迟 掩盖长尾问题 按地域/运营商看 P95/P99

    十二、参考配置总览¶

    12.1.Nginx静态资源响应头¶

    server {
    listen 443 ssl http2;
    server_name static-origin.example.com;

    location /assets/ {
        root /var/www/static;
        expires 365d;
        add_header Cache-Control "public, max-age=31536000, s-maxage=31536000, immutable" always;
        add_header Access-Control-Allow-Origin "*" always;
    }

    location /activity/ {
        root /var/www/activity;
        expires 1m;
        add_header Cache-Control "public, max-age=30, s-maxage=60, stale-while-revalidate=120, stale-if-error=600" always;
    }

    location /api/ {
        add_header Cache-Control "no-store, no-cache, must-revalidate" always;
        proxy_pass http://api_gateway;
    }
}

    12.2.CDN规则优先级¶

    优先级从高到低：
1. /api/seckill/order        不缓存 + 限流 + WAF
2. /api/user/*               不缓存 + 鉴权 + WAF
3. /api/seckill/config       1s - 5s 短缓存
4. /activity/*               30s - 60s 短缓存 + stale
5. /assets/*                 30d - 365d 长缓存
6. 默认规则                  不缓存或遵循源站

    12.3.curl验证命令¶

    # 查看缓存响应头

# 检查活动页是否命中 CDN

# 检查下单接口禁止缓存

# 查看不同查询参数是否被规范化

    重点关注响应头：

Age: 12

X-Origin-Cache: HIT

    十三、总结¶

    CDN 是系统入口层的核心能力，不应只理解为“静态资源加速”。在高并发和秒杀系统中，CDN 承担了流量调度、缓存拦截、协议优化、安全防护、源站保护和故障降级等职责。

    落地时要坚持三条原则：

    1. 能静态化就静态化，能边缘命中就不要回源：活动页、商品图、配置 JSON 都应提前预热。
    2. 交易链路绝不缓存，边缘只做保护：下单、支付、库存扣减必须回源，由 Redis/MQ/DB 保证一致性。
    3. 发布、监控、刷新、预热、回滚一体化：CDN 规则属于生产入口变更，必须纳入发布流程和故障演练。
